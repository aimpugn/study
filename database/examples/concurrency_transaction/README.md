# 동시 요청 시나리오 계약

같은 동시성 시나리오를 여러 언어로 구현할 때 모든 구현이 지켜야 할 계약입니다. 개념 설명은 [개념 문서](../../concurrent_payment_integrity.md)에 있습니다.

## 구현 목록

| 언어 | 디렉터리 | DB | 상태 |
| --- | --- | --- | --- |
| Go | [`go/`](go/README.md) | SQLite | 아래 시나리오 표의 "Go 확인 방법" 열 참고 |

## 시나리오

이 문서에서 **틈**은 한 요청이 값을 확인한 뒤 그 결과로 쓰기 전까지의 구간입니다. 시나리오마다 지켜야 할 규칙, 규칙을 깨는 구현, 규칙을 지키는 구현이 있습니다. 확인 방법은 두 가지입니다.

- **재현 테스트:** 깨지는 구현을 코드로 두고, 테스트가 버그를 재현합니다. 재현되지 않으면 테스트가 실패해야 합니다.
- **변이 확인:** 깨지는 구현을 따로 두지 않고, 지키는 구현을 일부러 망가뜨렸을 때 테스트가 실패하는지 확인합니다. 결과는 개념 문서의 [직접 확인하기](../../concurrent_payment_integrity.md#직접-확인하기) 표에 있습니다.

| ID | 지켜야 할 규칙 | 깨지는 구현 | 지키는 구현 | 테스트가 확인할 것 | Go 확인 방법 |
| --- | --- | --- | --- | --- | --- |
| B1 | 출금이 겹쳐도 잔액은 차례로 실행한 결과와 같다 | 읽고 계산해 덮어쓰기 | 조건부 `UPDATE` | 20,000원에서 5,000원 두 건: 깨지면 15,000원 | 재현 테스트 + 변이 확인 |
| B2 | 서버가 여러 대여도 B1이 성립한다 | 서버 안의 뮤텍스 | DB에서 지키는 방법(B1, B4, B5) | 같은 Server 값이면 두 번째 요청이 뮤텍스에 막혀 약속 지점에 오지 못하고, 서로 다른 Server 값이면 두 요청이 틈에서 만남 | 재현 테스트 (지키는 쪽은 서버 여러 대로 따로 테스트하지 않음) |
| B3 | 트랜잭션만 열어서는 틈이 막히지 않는다 | 일반 `BEGIN` 안에서 읽고 쓰기 | B4 | 두 요청이 틈에서 만남. 증상은 DB마다 다름 | 재현 테스트 |
| B4 | 락을 쥔 동안 다른 요청은 잔액을 읽고 판단하는 단계에 들어오지 못한다 | B3과 같음 | 비관적 락 | 락을 쥔 채 멈추면 상대가 약속 지점에 오지 못함, 그 밖의 오류 0건 | 변이 확인 |
| B5 | 충돌을 검출하고 재시도해 B1을 지킨다 | B1과 같음 | version 비교 낙관적 락 | 두 요청 중 하나가 한 번 더 시도, 잔액 10,000원 | 변이 확인 |
| L1 | 여러 행에 걸친 합계가 한도를 넘지 않는다 | 합계를 읽고 새 행 추가 | 한도 행에 사용액을 조건부로 누적 | 한도 10,000원에 6,000원 두 건: 깨지면 12,000원 | 재현 테스트 + 변이 확인 |
| P1 | 같은 멱등성 키로 여러 번 와도 PG 승인은 한 번 | 조회 후 PG 호출 후 기록 | `idempotency_key` UNIQUE로 PENDING 행을 먼저 INSERT(선점)한 뒤 PG 호출 | 깨지면 PG 호출 2회, 지키면 5회 요청에도 1회 | 재현 테스트 + 변이 확인 |
| P2 | 같은 키에 다른 내용이면 기존 결과를 돌려주지 않는다 | 키만 비교 | 계좌, 금액까지 비교 | 다른 금액, 다른 계좌: 키 재사용 오류 | 변이 확인 |
| P3 | 결과를 모르는 PG 응답은 실패로 기록하지 않는다 | 타임아웃을 `FAILED`로 기록 | `UNKNOWN` 기록 후 대사 | 승인 뒤 타임아웃: `UNKNOWN` -> 대사 -> `SUCCEEDED` | 변이 확인 |
| P4 | 늦게 도착한 결과 기록이 이미 확정된 상태를 조용히 덮지 않는다 | 상태 조건 없는 확정 | 이전 상태를 조건으로 거는 `UPDATE` | 대사가 `FAILED`로 확정한 뒤 늦은 승인 기록: 상태 충돌 오류 | 변이 확인 |

## 새 언어로 구현할 때 지킬 것

- **겹침을 강제합니다.** 스레드를 동시에 출발시키는 것만으로는 틈에서 만난다는 보장이 없습니다. 깨지는 구현의 틈에 멈출 자리를 두고, 테스트가 약속 지점으로 두 요청을 만나게 합니다. Go 구현의 `Pause`와 `Rendezvous`가 그 예입니다.
- **약속 지점에는 대기 시간 상한을 둡니다.** 락이 상대를 막으면 상대는 약속 지점에 오지 못합니다. 상한이 없으면 테스트가 멈추고, 상한이 있으면 "상대가 오지 못했다"는 사실 자체를 락이 동작한 증거로 쓸 수 있습니다.
- **결과를 세 가지로 셉니다.** 성공, 기대한 업무 오류(잔액 부족 등), 그 밖의 오류입니다. 그 밖의 오류가 0건인지 확인하지 않으면 락 없는 구현이 통과합니다. 잔액 30,000원에서 10,000원 출금 다섯 건을 보내면, 락을 잡는 구현은 성공 3, 잔액 부족 2, 락을 잡지 않는 구현은 성공 3, `database is locked` 2가 나와 성공 수와 최종 잔액이 똑같기 때문입니다.
- **틀린 결과가 정상과 구별되는 값을 고릅니다.** 잔액 10,000원에서 10,000원씩 두 번 빼는 예시는 갱신 손실이 나도 0원이라 정상처럼 보입니다.
- **지키는 구현을 일부러 망가뜨려 테스트가 실패하는지 확인합니다.** 컴파일이 실패해서 테스트가 멈춘 경우는 검출로 세지 않습니다.
