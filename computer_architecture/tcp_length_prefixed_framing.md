## 1. 시작 질문 — 보낸 만큼 받아지지 않는다

소켓 프로그래밍을 처음 하면 반드시 만나는 버그가 있습니다.

보내는 쪽은 이렇게 씁니다.

```java
out.write(message);   // 500바이트 한 건
out.flush();
```

받는 쪽은 이렇게 읽습니다.

```java
byte[] buf = new byte[500];
int n = in.read(buf);        // 500이 올 것이라 기대
process(buf);                // ← 여기서 터진다
```

**`n`이 500이 아닐 수 있습니다.** 200일 수도, 1,000일 수도 있습니다. 로컬에서 테스트하면 대개 500이 나와서 통과하고, 실제 네트워크에 올리면 깨집니다.

이 문서는 왜 그런지, 그리고 제대로 처리하는 방법과 **그 처리 과정에서 생기는 메모리 문제**까지 다룹니다.

## 2. 왜 경계가 사라지는가

TCP는 **바이트 스트림** 프로토콜입니다. 이름 그대로 "바이트가 흐르는 관"이고, 관 안에서 어디가 한 메시지의 끝인지 표시하지 않습니다.

이것이 UDP와 결정적으로 다른 점입니다.

| | TCP | UDP |
|---|---|---|
| 전송 단위 | 바이트 스트림 | 데이터그램(메시지) |
| 경계 보존 | **안 됨** | 됨 |
| `write()` 한 번 = `read()` 한 번 | 보장 없음 | 보장됨 |
| 순서·재전송 | 보장 | 없음 |

TCP에서 경계가 사라지는 이유는 여러 층에서 생깁니다.

| 원인 | 무슨 일이 일어나나 |
|---|---|
| **분할(fragmentation)** | 메시지가 MSS(최대 세그먼트 크기)보다 크면 여러 조각으로 나뉘어 전송 |
| **병합(coalescing)** | 작은 메시지 여러 개가 한 세그먼트에 묶여 전송 |
| **Nagle 알고리즘** | 작은 조각을 모아 한 번에 보내려고 지연시킨다 |
| **수신 버퍼 상태** | `read()`가 호출된 순간 버퍼에 있는 만큼만 준다 |
| **중간 장비** | 라우터·프록시가 재분할할 수 있다 |

그래서 500바이트 메시지 한 건이 이렇게 도착할 수 있습니다.

```
보낸 쪽:  write([500바이트])  한 번

받는 쪽에서 가능한 경우들:
  ① read() → 500바이트           한 번에 다 옴 (로컬 테스트에서 흔함)
  ② read() → 200, read() → 300   나뉘어 옴
  ③ read() → 17 × 29 + 7         조각조각 옴
  ④ read() → 1000               두 건이 붙어 옴
  ⑤ read() → 3, read() → 497     하필 앞 3바이트만 먼저 옴
```

⑤가 특히 고약합니다. 뒤에서 보겠지만 **길이 필드조차 다 못 받은 상태**를 처리해야 합니다.

> **핵심**: "어디까지가 한 건인가"를 애플리케이션이 판단해야 합니다.
> 이 판단을 **프레이밍(framing)** 이라 하고, 한 건의 단위를 **프레임(frame)** 이라 부릅니다.

## 3. 경계를 정하는 세 가지 방식

### ① 구분자 (delimiter)

메시지 끝에 특별한 바이트를 넣습니다.

```
"hello\n" "world\n" "bye\n"
          ↑ 개행이 경계
```

| 장점 | 단점 |
|---|---|
| 사람이 읽을 수 있다 | 본문에 구분자가 나오면 이스케이프해야 한다 |
| 길이를 미리 몰라도 된다 | 끝까지 읽어야 길이를 안다 → 버퍼 크기 예측 불가 |
| 구현이 단순 | 악의적 입력이 구분자를 안 보내면 무한 대기 |

HTTP 헤더(`\r\n\r\n`), Redis 프로토콜, 줄 단위 로그 전송이 이 방식입니다. **텍스트 프로토콜에 적합**합니다.

구분자 방식을 쓸 때는 반드시 **최대 길이 제한**을 둬야 합니다. 그러지 않으면 구분자를 안 보내는 클라이언트 하나가 서버 메모리를 고갈시킵니다.

### ② 고정 길이

모든 메시지가 같은 크기입니다.

```
[----- 500바이트 -----][----- 500바이트 -----]
```

| 장점 | 단점 |
|---|---|
| 가장 단순 | 크기가 다양한 메시지에 낭비 |
| 파싱 비용 없음 | 확장하려면 프로토콜을 바꿔야 한다 |

금융권 고정 길이 전문이 이 방식을 쓰는 경우가 있습니다. 다만 **메시지 종류마다 길이가 다르면** 종류를 먼저 읽어 길이를 결정해야 하고, 그러면 결국 길이 프리픽스에 가까워집니다.

### ③ 길이 프리픽스 (length prefix)

메시지 앞에 **뒤따라올 길이**를 붙입니다.

```
[길이=500][----- 본문 500바이트 -----][길이=320][--- 본문 320바이트 ---]
```

| 장점 | 단점 |
|---|---|
| 이진 데이터를 그대로 담을 수 있다 (이스케이프 불필요) | 길이 필드 자체가 분할될 수 있다 |
| 필요한 버퍼 크기를 미리 안다 | 길이가 잘못되면 이후 스트림 전체가 어긋난다 |
| 최대 길이 검증이 쉽다 | 사람이 읽기 어렵다 |

**가장 널리 쓰이는 방식**이고, 이 문서의 나머지는 이 방식을 다룹니다.

## 4. 길이 프리픽스 — 가장 흔한 선택

### 설계 결정 네 가지

길이 프리픽스를 쓰기로 하면 정해야 할 것이 네 개입니다.

| 결정 | 선택지 | 고려 사항 |
|---|---|---|
| **길이 필드 크기** | 2·4·8바이트, 또는 텍스트 N자리 | 최대 메시지 크기를 결정한다 |
| **인코딩** | 빅엔디언 이진 / 리틀엔디언 / ASCII 숫자 | 상호운용성. 네트워크 표준은 빅엔디언 |
| **길이가 포함하는 범위** | 본문만 / 길이 필드 포함 / 헤더 포함 | **가장 자주 어긋나는 지점** |
| **최대 길이 제한** | 예: 1MB | 없으면 메모리 고갈 공격에 노출 |

세 번째가 실무에서 가장 많은 버그를 만듭니다. 규격서에 "길이 6바이트"라고만 적혀 있으면, 그 길이가 **자기 자신을 포함하는지**를 양쪽이 다르게 해석할 수 있습니다.

```
해석 A: [길이=500][본문 500바이트]           길이는 본문만
해석 B: [길이=506][본문 500바이트]           길이는 자신(6) 포함
```

한쪽이 A로 보내고 다른 쪽이 B로 읽으면 6바이트씩 밀립니다. 그리고 **첫 건은 우연히 통과하고 두 번째 건부터 깨지는** 형태로 나타나서 원인 찾기가 어렵습니다.

**규격을 확정할 때 이 항목을 예시 바이트로 못 박아 두십시오.** "길이 필드에 500이 들어가면 그 뒤 500바이트가 본문이다" 처럼요.

### ASCII 숫자 길이 필드

이진 정수가 아니라 숫자 문자를 쓰는 규격도 흔합니다.

```
"000500" + [본문 500바이트]
 └ 6자리 ASCII, 앞을 0으로 채움
```

| 장점 | 단점 |
|---|---|
| 엔디언 문제가 없다 | 파싱에 문자 → 숫자 변환이 필요 |
| 사람이 덤프를 읽을 수 있다 | 6자리면 최대 999,999바이트로 제한 |
| 레거시 시스템과 호환 | 공백/0 채움 규칙을 맞춰야 한다 |

이 방식에서 주의할 점은 **채움 문자**입니다. `"   500"`(공백 채움)과 `"000500"`(0 채움)이 섞이면 파싱이 깨집니다. 그리고 정수 변환 시 오버플로를 확인해야 합니다 — 10자리 필드에 `"9999999999"`가 오면 32비트 정수로는 담기지 않습니다.

## 5. 길이 필드가 두 겹인 설계

실제 규격에서는 길이 필드가 **두 겹**인 경우를 자주 만납니다.

```
[바깥 길이=506][안쪽 길이=48][--- 헤더 48바이트 ---][--- 본문 ---]
      │              │
      │              └ 헤더가 어디서 끝나는지
      └ 이 프레임 전체가 어디서 끝나는지
```

왜 두 개가 필요한가.

| 필드 | 역할 | 없으면 |
|---|---|---|
| 바깥 길이 | **프레이밍** — 스트림에서 한 건을 자른다 | 어디서 자를지 모른다 |
| 안쪽 길이 | **구조 해석** — 자른 것 안에서 헤더/본문 경계를 찾는다 | 자르긴 했는데 안을 못 읽는다 |

두 관심사가 분리되어 있습니다. 바깥 길이는 **전송 계층의 문제**를 풀고, 안쪽 길이는 **표현 계층의 문제**를 풉니다.

이 분리의 실용적 이점은 **헤더 확장**입니다. 헤더에 필드를 추가하면 안쪽 길이만 늘어나고, 프레이밍 로직은 그대로 동작합니다. 바깥 길이 하나로 다 처리하려 하면 헤더 변경이 프레이밍 코드까지 흔듭니다.

## 6. 직접 구현해 보기 — 상태 기계

길이 프리픽스 파싱은 **상태 기계**로 생각하면 명확해집니다.

```
        ┌─────────────────┐
        │ 길이 필드 대기   │  누적 < 6바이트면 여기 머문다
        └────────┬────────┘
                 │ 6바이트 모임 → 길이 해석
                 ▼
        ┌─────────────────┐
        │ 본문 대기        │  누적 < 길이면 여기 머문다
        └────────┬────────┘
                 │ 길이만큼 모임
                 ▼
        ┌─────────────────┐
        │ 프레임 완성      │ → 처리하고 버퍼에서 제거
        └────────┬────────┘
                 │ 남은 바이트가 있으면
                 └──→ 다시 "길이 필드 대기" (여러 건이 붙어 왔을 수 있다)
```

이걸 코드로 옮기면 이렇습니다. 언어와 무관한 뼈대입니다.

```java
public class LengthPrefixedDecoder {
    private static final int LENGTH_FIELD_SIZE = 6;
    private static final int MAX_FRAME_SIZE = 1024 * 1024;   // 필수: 상한

    // 아직 완성되지 않은 바이트를 모아 두는 버퍼
    private final ByteArrayOutputStream pending = new ByteArrayOutputStream();

    /** 도착한 바이트를 넣고, 완성된 프레임 목록을 돌려준다. */
    public List<byte[]> feed(byte[] chunk, int len) {
        pending.write(chunk, 0, len);
        List<byte[]> frames = new ArrayList<>();

        while (true) {
            byte[] buf = pending.toByteArray();

            // ① 길이 필드조차 안 모였다 → 더 기다린다
            if (buf.length < LENGTH_FIELD_SIZE) {
                break;
            }

            int frameLength = parseLength(buf, 0, LENGTH_FIELD_SIZE);

            // ② 방어: 상한 검증. 이게 없으면 메모리 고갈에 노출된다
            if (frameLength <= 0 || frameLength > MAX_FRAME_SIZE) {
                throw new ProtocolException("비정상 길이: " + frameLength);
            }

            // ③ 본문이 아직 다 안 모였다 → 더 기다린다
            if (buf.length < LENGTH_FIELD_SIZE + frameLength) {
                break;
            }

            // ④ 한 건 완성
            frames.add(Arrays.copyOfRange(buf, LENGTH_FIELD_SIZE,
                                               LENGTH_FIELD_SIZE + frameLength));

            // ⑤ 소비한 만큼 버퍼에서 제거하고 루프를 계속한다
            //    (여러 건이 붙어 왔을 수 있으므로)
            byte[] rest = Arrays.copyOfRange(buf, LENGTH_FIELD_SIZE + frameLength,
                                                  buf.length);
            pending.reset();
            pending.write(rest, 0, rest.length);
        }
        return frames;
    }
}
```

### 이 코드에서 짚어야 할 다섯 가지

**① 길이 필드조차 못 받은 상태를 먼저 처리한다**

`buf.length < LENGTH_FIELD_SIZE` 검사가 없으면, 3바이트만 도착했을 때 길이를 읽으려다 예외가 납니다. 이 검사가 앞에 있어야 합니다.

**② 상한 검증은 선택이 아니다**

길이 필드에 `999999999`가 들어오면 그만큼 버퍼를 키우려 시도합니다. 악의적 클라이언트 한 대가 서버를 죽일 수 있습니다. **상한 검증은 보안 요구사항**입니다.

**③ 부분 수신은 정상 상황이다**

`break`로 나가서 다음 `feed()` 호출을 기다립니다. 조각을 버리면 안 됩니다. **한 건이 깨지면 그 뒤 스트림 전체가 어긋납니다.**

**④ 완성된 프레임은 복사해서 넘긴다**

누적 버퍼를 그대로 넘기면, 이후 `feed()`에서 버퍼가 변경될 때 이미 넘긴 프레임도 함께 바뀝니다.

**⑤ 루프를 돈다 — 한 번에 여러 건이 올 수 있다**

`while(true)`가 없으면 붙어서 도착한 두 번째 건이 처리되지 않고 버퍼에 남습니다. 다음 데이터가 올 때까지 지연되고, 마지막 건은 영원히 처리되지 않을 수 있습니다.

### 성능 개선 여지

위 코드는 이해를 위한 것이고, 실제로는 `toByteArray()`와 `copyOfRange()`가 매번 복사를 일으켜 비효율적입니다. 실전에서는

- 링 버퍼나 읽기/쓰기 인덱스를 가진 버퍼를 쓴다
- 복사 대신 슬라이스(뷰)를 넘긴다
- 프레임워크가 제공하는 디코더를 쓴다 (예: Netty의 `LengthFieldBasedFrameDecoder`)

프레임워크를 쓰는 것이 대개 맞습니다. **직접 구현할 가치는 "왜 이 처리가 필요한지"를 아는 데 있습니다.**

## 7. 두 가지 구현 모델 — 누적 디코더와 스트림 리더

프레이밍을 구현하는 방식이 크게 둘로 갈립니다. 이 차이가 뒤에서 다룰 메모리 문제와 직결됩니다.

### 모델 A — 누적 디코더 (이벤트 기반)

```
바이트 도착 → 디코더 호출 → 완성됐나?
                              ├ 예: 프레임 넘김
                              └ 아니오: 누적 버퍼에 보관하고 반환
```

이벤트 루프가 소켓을 감시하다가 데이터가 오면 디코더를 부릅니다. 디코더는 **미완성 상태를 자기 버퍼에 들고** 다음 호출을 기다립니다.

| 특징 | 함의 |
|---|---|
| 스레드를 점유하지 않는다 | 연결 수가 많아도 스레드가 적게 든다 |
| 상태를 디코더가 보관한다 | **누적 버퍼의 수명을 관리해야 한다** |
| 콜백 스타일 | 흐름이 코드에 드러나지 않아 읽기 어렵다 |

Netty가 이 모델입니다. 그리고 Netty의 버퍼는 참조 카운트 방식이라 **애플리케이션이 해제 시점을 관리**해야 합니다.

### 모델 B — 스트림 리더 (블로킹 스타일)

```
readFully(6)      → 길이 필드를 다 받을 때까지 블로킹
readFully(length) → 본문을 다 받을 때까지 블로킹
프레임 완성
```

코드가 순차적으로 읽습니다. "6바이트를 읽어라"고 하면 다 올 때까지 기다립니다.

| 특징 | 함의 |
|---|---|
| 흐름이 코드에 그대로 보인다 | 읽고 쓰기 쉽다 |
| 미완성 상태 관리가 필요 없다 | 프레임워크나 OS가 대신 기다린다 |
| 연결마다 스레드가 점유된다 | 연결 수가 많으면 스레드 부담 |

전통적으로 이 모델은 "연결 수 = 스레드 수"라서 확장성이 나빴습니다. 그런데 **가상 스레드(Java 21+)나 코루틴이 등장하면서 상황이 바뀌었습니다.** 블로킹 스타일 코드를 쓰면서도 OS 스레드는 적게 쓸 수 있게 됐습니다.

### 실측 비교 — 무엇이 달라지나

같은 프로토콜을 두 모델로 구현해 비교한 예시입니다. 생산 코드의 기계 집계입니다.

| 항목 | 모델 A (누적 디코더) | 모델 B (스트림 리더 + 가상 스레드) |
|---|---:|---:|
| 소스 파일 | 21개 | 16개 |
| 코드 줄 | 2,163 | 1,072 |
| 파이프라인·채널 관리 코드 | 83곳 | 0곳 |
| **참조 카운트 버퍼 관리 코드** | **21곳** | **0곳** |
| 이벤트 루프 수명 관리 코드 | 22곳 | 0곳 |
| 수동 정리·대기 코드 | 34곳 | 1곳 |

그리고 실행 중 자원 사용(같은 부하, 모델 A를 100으로 둔 지수)입니다.

| 지표 | 모델 A | 모델 B |
|---:|---:|---:|
| 최대 OS 스레드 | 100 | 52.7 |
| CPU 시간 | 100 | 51.2 |
| 최대 직접 버퍼 | 100 | **0.02** |

**직접 버퍼가 거의 0이 된 것이 프레이밍과 직결됩니다.** 모델 A는 네트워크 I/O용으로 미리 큰 덩어리(예시에서 48MB)를 잡아 재사용하고, 모델 B는 필요한 만큼만 쓰고 반납했습니다.

여기서 오해하지 말아야 할 것.

> 이 수치는 **두 프레임워크의 일반적 우열이 아닙니다.** 특정 구현 두 개를 같은 조건에서 비교한 결과이고, 구현 방식(요청마다 이벤트 루프를 만드는지 등)에 크게 좌우됩니다.

## 8. 미완성 프레임이 메모리를 먹는다

프레이밍에서 가장 조용한 버그가 여기 있습니다.

### 문제 상황

```
클라이언트가 [길이=1000000] 만 보내고 본문을 안 보낸다
  → 서버는 100만 바이트가 올 때까지 기다린다
  → 그 사이 누적 버퍼는 유지된다
  → 연결을 1,000개 만들어 같은 짓을 하면?
```

**연결마다 미완성 버퍼가 쌓입니다.** 이것은 두 가지 문제로 나타납니다.

| 문제 | 성격 |
|---|---|
| 메모리 고갈 | 악의적 공격 (Slowloris 계열) |
| 메모리 누수 | 연결이 끊겼는데 버퍼가 해제되지 않는 버그 |

### 방어 세 가지

**① 최대 프레임 길이 제한** (6장 ②)

길이 필드 값을 검증합니다. 이건 파싱 단계에서 즉시 막습니다.

**② 미완성 상태의 타임아웃**

길이 필드를 받고 본문을 기다리는 상태에 시간 제한을 둡니다. 초과하면 연결을 끊고 버퍼를 비웁니다.

**③ 연결 종료 시 버퍼 해제 보장**

이것이 누수와 직결됩니다. 연결이 정상 종료되든 예외로 끊기든 **반드시** 버퍼를 해제해야 합니다.

```java
// 모델 A(누적 디코더)에서 이 자리를 놓치면 누수가 된다
@Override
public void channelInactive(ChannelHandlerContext ctx) {
    pending.release();     // 참조 카운트 버퍼 해제
    super.channelInactive(ctx);
}

@Override
public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
    pending.release();     // 예외 경로도 놓치면 안 된다
    ctx.close();
}
```

앞 장의 집계에서 **"참조 카운트 버퍼 관리 코드 21곳"** 이 바로 이런 자리들입니다. 21곳 중 하나라도 빠지면 그 경로로 들어온 요청이 버퍼를 남깁니다.

### 어떻게 발견하나

이 누수는 조용합니다. 정상 트래픽에서는 프레임이 잘 완성되니 버퍼가 곧 비워지고, **비정상 종료·예외 경로에서만** 쌓입니다. 그래서 짧은 테스트로는 안 잡힙니다.

발견하려면

| 방법 | 무엇을 보나 |
|---|---|
| 장시간 부하 + 강제 회수 | 회수 후 남는 힙이 계단처럼 오르는지 |
| 클래스별 인스턴스 diff | 버퍼 관련 클래스가 계속 늘어나는지 |
| 네이티브 메모리 추적 | 직접 버퍼가 반납되는지 |
| 연결 강제 종료 시험 | 비정상 경로를 일부러 만든다 |

JVM에서 이 진단을 어떻게 하는지는 [JVM 메모리 누수 진단](../jvm/memory_leak_diagnosis.md)에 정리해 두었습니다.

## 9. 프레이밍 오류는 정확성 검증을 통과한다

프레이밍이 깨지면 특이한 방식으로 나타납니다. 이걸 알면 검증 설계가 달라집니다.

### 어긋남은 전파된다

```
정상:  [길이=500][본문A][길이=320][본문B]
                  ↑ 여기서 6바이트 밀려 읽으면

깨짐:  [길이=500][본문A의 6바이트 뒤부터...]
       → 다음 "길이"로 읽은 값이 본문A의 일부
       → 엉뚱한 크기만큼 잘라냄
       → 그 뒤 모든 프레임이 어긋남
```

**한 번 어긋나면 복구되지 않습니다.** 그런데 결과가 "오류"로 나타나지 않을 수 있습니다. 잘못 자른 조각이 **형식상 유효한 값처럼 보이면** 그대로 처리되어 저장됩니다.

### 그래서 건수 비교로는 못 잡는다

```
보낸 것:    1,000건
저장된 것:  1,000건        ← 건수는 맞다
그런데 내용이 다르다
```

건수만 확인하는 검증은 이걸 통과시킵니다. 그래서 **키 집합으로 대조**해야 합니다.

```
보낸 key 집합의 해시
  == 응답받은 key 집합의 해시
  == 저장된 key 집합의 해시
```

실제 시험에서 프레이밍·타임아웃 관련 실패가 났을 때 키 집합 일치가 `5/6`, `3/4` 같은 값으로 나왔습니다. **건수만 셌다면 통과했을 수 있는 실패들**입니다.

정확성 검증 설계는 [성능 비교 실험](../testing/performance_comparison_experiment.md)의 2장에 더 자세히 정리했습니다.

## 10. 어떻게 시험하나

프레이밍은 **일부러 고약하게 보내야** 검증됩니다. 정상 전송만으로는 앞서 본 경우들이 재현되지 않습니다.

### 시험 ① 조각 분할 전송

한 프레임을 작은 조각으로 쪼개 보냅니다.

```python
def send_fragmented(sock, frame, chunk_size):
    """프레임을 chunk_size 바이트씩 쪼개 보낸다."""
    for i in range(0, len(frame), chunk_size):
        sock.sendall(frame[i:i + chunk_size])
        time.sleep(0.001)      # 조각이 병합되지 않도록 살짝 지연
```

조각 크기를 바꿔 가며 확인합니다.

| 조각 크기 | 무엇을 겨냥하나 |
|---|---|
| 길이 필드보다 **작게** (예: 3바이트) | **길이 필드조차 못 받은 상태** 처리 |
| 길이 필드보다 조금 큰 값 (예: 17바이트) | 길이는 읽었지만 본문이 조각조각 오는 경우 |
| 프레임 크기의 절반 | 일반적인 부분 수신 |

**길이 필드보다 작게 쪼개는 시험을 반드시 포함하십시오.** 이 경우가 구현에서 가장 자주 빠집니다.

### 시험 ② 병합 전송

여러 프레임을 한 번에 보냅니다.

```python
sock.sendall(frame1 + frame2 + frame3)     # 한 번의 write
```

디코더가 루프를 돌지 않으면 두 번째·세 번째가 처리되지 않습니다.

### 시험 ③ 대형 프레임

기본 크기보다 훨씬 큰 프레임을 보냅니다. 예를 들어 기본이 500바이트인데 64KB를 보냅니다.

| 겨냥하는 것 | 왜 |
|---|---|
| 누적 버퍼 크기 | 미완성 상태로 들고 있는 양이 커진다 |
| 버퍼 확장 전략 | 재할당과 복사가 몇 번 일어나나 |
| 상한 검증 동작 | 제한을 넘으면 정상적으로 거부하나 |
| 대기열 메모리 | 11장에서 다룬다 |

### 시험 ④ 비정상 종료

프레임을 절반만 보내고 연결을 끊습니다.

```python
sock.sendall(frame[:len(frame)//2])
sock.close()                                # 본문 미완성 상태로 종료
```

이 시험을 반복해서 돌린 뒤 메모리를 확인하면, 8장의 누수를 잡을 수 있습니다.

### 시험 ⑤ 잘못된 길이

길이 필드에 이상한 값을 넣습니다.

| 값 | 기대 동작 |
|---|---|
| 0 | 거부 또는 빈 프레임 처리 |
| 음수 (또는 최상위 비트가 켜진 값) | 거부 |
| 상한 초과 (예: 100MB) | 거부. **버퍼를 키우지 않고** |
| 실제 본문보다 큰 값 | 타임아웃 후 연결 종료 |

### 클라이언트도 같은 규칙을 구현해야 한다

시험 도구가 응답을 검증하려면 **응답 프레임도 파싱**해야 합니다. 즉 프레이밍 구현이 서버와 클라이언트 양쪽에 필요합니다.

실제 실험에서 부하 도구를 준비하는 데 하루가 소모된 사례가 있습니다. 표준 배포본이 해당 프레이밍을 다루지 못해 수정본을 만들어야 했고, 그 도구가 정확해야 측정이 성립하기 때문입니다.

**시험 도구의 버전과 해시를 기록해 두십시오.** 도구가 바뀌면 측정 기준이 바뀝니다.

## 11. 대기열 상한은 전문 크기를 전제한다

마지막으로 프레이밍과 용량 설계가 만나는 지점입니다.

비동기 처리 구조에서는 보통 대기열 상한을 둡니다.

```
대기 건수가 10,000을 넘으면 새 요청을 거절한다
```

이 값은 어떻게 정했을까요. **암묵적으로 전문 크기를 전제하고 있습니다.**

```
전문 1KB × 대기 10,000건 = 약 10MB      ← 힙 512MB에서 문제없다
전문 64KB × 대기 10,000건 = 약 640MB    ← 힙 512MB를 넘는다
```

**같은 상한이 전문 크기에 따라 안전하거나 위험합니다.**

그래서 대형 전문 시험을 할 때는 건수를 함께 줄여야 합니다. 실제 시험에서 64KB 전문 실행이 400건으로 제한된 이유가 이것입니다.

### 상한을 바이트로 두는 대안

건수 대신 **총 바이트**로 상한을 두면 이 문제가 사라집니다.

```
대기 총량이 32MB를 넘으면 거절
  → 1KB 전문이면 약 32,000건
  → 64KB 전문이면 약 512건
```

전문 크기가 다양한 시스템이라면 바이트 기준이 안전합니다. 다만 구현이 조금 복잡해지고(각 항목의 크기를 알아야 한다) 모니터링 지표도 바뀌어야 합니다.

### 확인 방법

용량 설계를 검증하려면 이 계산을 명시적으로 해 봅니다.

```
최대 전문 크기 × 대기 상한 + 부대 객체 오버헤드  vs  힙 한도
```

그리고 실제로 상한까지 채우는 부하를 걸어 확인합니다. 계산만으로는 부대 객체(래퍼, 메타데이터, 추적 맵의 항목)를 놓치기 쉽습니다.

## 12. 체크리스트

### 프로토콜 설계

```
□ 경계 방식을 정했는가? (구분자 / 고정 길이 / 길이 프리픽스)
□ 길이 필드 크기와 인코딩을 정했는가?
□ 길이가 포함하는 범위를 예시 바이트로 못 박았는가?
□ 최대 프레임 크기 상한을 정했는가?
□ 두 겹 길이 필드가 필요한가? (프레이밍 / 구조 해석 분리)
```

### 구현

```
□ 길이 필드조차 못 받은 상태를 처리하는가?
□ 길이 값을 검증하는가? (0, 음수, 상한 초과)
□ 부분 수신 시 조각을 보관하고 기다리는가?
□ 여러 프레임이 붙어 왔을 때 루프를 도는가?
□ 완성된 프레임을 복사해서 넘기는가?
□ 미완성 상태에 타임아웃이 있는가?
□ 연결 종료·예외 경로에서 버퍼를 해제하는가? (모든 경로)
```

### 시험

```
□ 길이 필드보다 작게 쪼개 보냈는가?
□ 여러 프레임을 한 번에 보냈는가?
□ 기본보다 훨씬 큰 프레임을 보냈는가?
□ 프레임 절반만 보내고 끊었는가?
□ 잘못된 길이 값을 보냈는가?
□ 비정상 종료를 반복한 뒤 메모리를 확인했는가?
□ 정확성을 건수가 아니라 키 집합으로 대조했는가?
□ 시험 도구의 버전·해시를 기록했는가?
```

### 용량

```
□ 최대 전문 크기 × 대기 상한이 힙 한도 안에 들어오는가?
□ 상한을 건수로 둘지 바이트로 둘지 검토했는가?
□ 상한까지 채우는 부하로 확인했는가?
```
