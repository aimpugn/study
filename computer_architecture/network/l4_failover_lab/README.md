# L4 로드밸런서가 죽으면 이미 맺어진 TCP 연결은 어떻게 되는가

## 개요

`A 서비스 → L4 로드밸런서 → B 서비스 여러 대` 구조에서, A가 L4의 대표 주소(VIP)로 TCP 연결을 맺은 뒤 **L4가 죽으면 그 연결을 계속 쓸 수 있는지**를 실제로 재현해 답하는 실험입니다.

이 질문에는 흔히 두 가지 잘못된 답이 돌아옵니다. 하나는 "연결이 맺어진 뒤에는 L4가 필요 없으니 A와 B가 직접 통신한다"이고, 다른 하나는 "L4가 죽으면 무조건 연결도 끊긴다"입니다. 둘 다 틀렸습니다. 아래 실험은 **완전히 동일한 장애**(활성 L4의 데이터 경로 사망)를 내면서 설정만 바꿔, 기존 연결이 죽기도 하고 멀쩡히 살기도 한다는 것을 보여 줍니다.

여기서 실제로 결과를 가르는 것은 프록시냐 NAT냐 DSR이냐가 아니라 **"이 L4가 연결별 상태를 기억하는가, 매번 다시 계산하는가"** 입니다. 이 문서는 그 판정축을 실험으로 세웁니다.

## 먼저 알아야 할 것: VIP와 연결 상태

**VIP(virtual IP)** 는 로드밸런서가 대표로 들고 있는 가상의 IP 주소입니다. 실제 서버가 그 주소를 가진 것이 아니라, 로드밸런서가 "이 주소로 오는 것은 내가 받는다"고 선언한 주소입니다. 실무에서 이 주소는 장비 한 대에 고정된 것이 아니라, 활성 장비가 죽으면 대기 장비가 넘겨받도록 설계합니다. keepalived 같은 도구가 하는 일이 바로 이 주소의 이사입니다.

여기서 첫 번째 오해가 생깁니다. 클라이언트가 VIP로 접속하면 중간 어디선가 상대 주소가 실제 서버 IP로 바뀔 것 같지만, 그렇지 않습니다. TCP 연결은 `(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)` 네 값으로 식별되고, 이 값은 연결이 끝날 때까지 바뀌지 않습니다. 클라이언트 소켓이 기억하는 상대는 처음부터 끝까지 VIP입니다. 실험이 실제로 찍어 주는 값이 이렇습니다.

```
연결: local=10.0.1.10:32912  peer(소켓이 기억하는 상대)=10.0.1.100:8080
```

`10.0.1.100`은 VIP이고, 이 연결이 실제로 서비스되는 백엔드는 `10.0.2.13`입니다. 클라이언트는 그 사실을 모르고, 알 필요도 없습니다. 백엔드 주소를 아는 것은 오직 L4뿐입니다.

그래서 두 번째 질문이 따라옵니다. **L4는 그 대응 관계를 어디에 적어 두는가.** Linux의 IPVS는 연결 테이블에 적습니다. 실험 중에 이렇게 들여다볼 수 있습니다.

```
pro expire state       source             virtual            destination
TCP 14:56  ESTABLISHED 10.0.1.10:32912    10.0.1.100:8080    10.0.2.13:8080
```

왼쪽부터 "클라이언트가 누구인지", "어떤 VIP로 들어왔는지", "어느 백엔드로 보내기로 했는지"입니다. 이 한 줄이 이 문서 전체의 주인공입니다. 이 줄이 사라졌을 때 무슨 일이 벌어지는지, 그리고 이 줄 없이도 같은 결론에 도달할 수 있는지가 전부입니다.

## 실험대 구조

Linux network namespace로 서버 다섯 대짜리 망을 한 컨테이너 안에 만듭니다. namespace는 커널이 제공하는 격리 단위로, 각각이 자기만의 네트워크 인터페이스·라우팅 테이블·IPVS 상태를 갖습니다. 즉 진짜 서버 다섯 대와 같은 조건이면서 VM 다섯 개를 띄울 필요가 없습니다.

```
                     ┌─ lb1 (활성)  10.0.1.1 / 10.0.2.1
   cli ── br-front ──┤                                  ├── br-back ──┬── b1  10.0.2.11
   10.0.1.10         └─ lb2 (대기)  10.0.1.2 / 10.0.2.2 ┘             ├── b2  10.0.2.12
                                                                      └── b3  10.0.2.13

   앞단 VIP  10.0.1.100  : 클라이언트가 접속하는 주소       ← 장애 시 lb1에서 lb2로 이사
   뒷단 GW   10.0.2.254  : 백엔드의 기본 게이트웨이         ← 함께 이사
```

`br-front`와 `br-back`은 IP 없는 순수 L2 스위치입니다. 실제 랙에 스위치 두 대가 놓인 것과 같습니다.

앞단 VIP만이 아니라 **뒷단 게이트웨이 주소도 같이 이사해야** 한다는 점이 중요합니다. IPVS를 NAT 모드로 쓰면 백엔드의 응답은 반드시 L4를 거쳐 돌아와야 하는데, 백엔드의 기본 경로가 죽은 lb1을 가리키고 있으면 연결 테이블을 아무리 잘 넘겨받아도 돌아오는 길이 끊깁니다. 실제 이중화 구성이 양쪽에 VIP를 두는 이유가 이것입니다.

### 무엇이 무엇을 맡는가

일을 두 갈래로 나눴습니다. **망을 세우고 부수는 일은 셸이 맡습니다.** `ip`와 `ipvsadm`을 부르는 작업이라 다른 언어로 옮기면 오히려 읽기 나빠집니다. **서버 노릇을 하고 결과를 재는 일은 Rust 바이너리 하나가 맡습니다.** 소켓을 다루고 실패를 분류하는 일이라 타입과 `match`가 도움이 됩니다.

```
lab.sh              진입점. 아래 조각들을 순서대로 부릅니다.
net/                망을 세우고 부순다
  build.sh            토폴로지 (네임스페이스, 브리지, 주소)
  ipvs.sh             L4 설정 (스케줄러, 백엔드 목록)
  fail.sh             장애 주입 (takeover | vanish | backend | backend-proc | evict)
  up.sh               망 + IPVS + 백엔드 기동
scenario/           실험 절차
  failover.sh         L4 장애 전환 (실험 1~5)
  backend-death.sh    백엔드 사망 (실험 6)
  endpoints.sh        종단 관측 (실험 7)
observe/            관찰
  watch.sh            연결 테이블 실시간
  snapshot.sh         상태 전체를 라벨 붙여 기록
src/                측정 도구 (Rust)
  main.rs             명령줄 정의와 분배
  flow.rs             한 연결의 왕복과 실패 분류
  probe.rs            흐름 N개를 단계 K개에 걸쳐 측정
  serve.rs            백엔드
  proxy.rs            프록시 모드 시연
  talk.rs             손으로 두드리는 클라이언트
Dockerfile.builder  clippy 를 넣은 컴파일용 이미지
```

장애 주입이 [`net/fail.sh`](net/fail.sh) 한 곳에 어휘로 모여 있다는 점이 중요합니다. 실험마다 장애를 다르게 내는 대신, 실험은 `takeover`나 `backend` 같은 이름만 고릅니다. `takeover`는 lb1의 앞뒤 인터페이스를 모두 내려 데이터 경로를 완전히 죽이고, lb2가 두 VIP를 가져간 뒤 gratuitous ARP를 뿌려 "이제 이 주소의 MAC은 나다"라고 알립니다. 이 ARP 통보를 빠뜨리면 클라이언트가 계속 죽은 lb1의 MAC으로 패킷을 보내 **전혀 다른 이유로** 연결이 끊기므로, 실험이 재는 대상이 흐려집니다.

측정 도구가 장애를 내지 않는다는 점도 같은 이유입니다. [`src/probe.rs`](src/probe.rs)는 단계 사이에서 멈춰 셸이 신호를 줄 때까지 기다리기만 합니다. 그래서 "L4가 죽는다"와 "백엔드가 죽는다"처럼 성격이 다른 실험이 같은 측정 도구를 씁니다.

## 실행 방법

Linux 커널이 필요합니다. macOS에서는 Docker/OrbStack의 리눅스 VM 위에서 그대로 돕니다.

```bash
./lab.sh up && ./lab.sh all
```

`up`은 세 가지를 합니다. 측정 도구를 컴파일해 `bin/l4lab`을 만들고(문서 강제 lint를 먼저 통과해야 합니다), 호스트 커널에 `ip_vs` 모듈을 적재하고, 실험 컨테이너를 띄웁니다. 컨테이너에는 `/lib/modules`가 없으므로 모듈 적재는 PID 1의 마운트 네임스페이스로 들어가서 합니다.

개별 실험은 `./lab.sh 1` ~ `./lab.sh 7`, 코드를 고친 뒤 다시 컴파일하려면 `./lab.sh build`, 정리는 `./lab.sh down`입니다.

`ip_vs 적재 실패`가 나면 그 커널이 IPVS를 제공하지 않는 것이고, 이 실험은 그 환경에서 돌지 않습니다.

자동 실행은 결과를 확인하는 용도이고, 실제로 감을 잡으려면 손으로 만져 봐야 합니다. 연결을 직접 붙들고 장애를 원할 때 내면서 상태가 변하는 것을 지켜보는 방법은 [직접 다뤄 보기](#직접-다뤄-보기)에 있습니다.

## 실험 1: 상태를 못 넘겨받은 대기 장비

가장 흔한 구성입니다. lb1과 lb2는 같은 서비스 설정을 갖고 있지만 연결 상태는 공유하지 않습니다. 스케줄러는 라운드로빈(`rr`)이고, 상태 동기화는 꺼져 있습니다.

```bash
./lab.sh 1
```

장애 직전 두 장비의 연결 테이블을 나란히 보면 차이가 분명합니다.

```
[장애 전] lb1 연결 테이블:
    TCP 14:56  ESTABLISHED 10.0.1.10:57954  10.0.1.100:8080  10.0.2.13:8080
[장애 전] lb2 연결 테이블:
    (비어 있음)
```

lb1을 죽이고 lb2가 VIP를 인계한 뒤, 클라이언트가 **이미 맺어 둔 그 소켓으로** 데이터를 보냅니다.

```
1단계: OK [B3] (0.00s)
2단계: RST — 상대가 연결을 재설정했습니다 (0.00s)
```

연결이 끊깁니다. 그런데 흥미로운 것은 끊기는 **방식**입니다. 응답이 안 와서 타임아웃이 난 것이 아니라, 0.00초 만에 RST(연결 재설정)를 받았습니다. 누가 보낸 RST일까요?

패킷을 잡아 확인했습니다. 장애 전환 이후 lb2가 뒷단으로 내보낸 패킷은 **0개**이고, lb2에는 8080 포트를 듣는 프로세스도 없습니다. 즉 이 RST는 백엔드가 보낸 것이 아니라 **로드밸런서 자신의 TCP 스택**이 만든 것입니다.

메커니즘은 이렇습니다. IPVS는 커널 netfilter의 `LOCAL_IN` 지점에 걸려 있습니다. 클라이언트의 패킷이 lb2에 도착하면 IPVS가 먼저 연결 테이블을 뒤지는데, 넘겨받은 것이 없으니 찾지 못합니다. 그런데 이 패킷은 연결을 새로 여는 SYN이 아니라 이미 진행 중인 연결의 데이터입니다. IPVS는 기본 설정에서 SYN이 아닌 패킷에 대해서는 백엔드를 새로 고르지 않고 그냥 통과시킵니다. 통과한 패킷은 lb2의 로컬 TCP 스택으로 올라가고, lb2는 `10.0.1.100:8080`을 실제로 갖고 있으므로 "내 주소인데 그 포트를 듣는 소켓이 없다"고 판단해 RST를 돌려보냅니다.

이것이 이 실험의 첫 결론입니다. **연결별 상태를 기억하는 L4에서 그 상태가 사라지면 기존 연결은 끊깁니다.**

## 실험 2: 상태 동기화를 켜면

같은 장애를 내되, 이번에는 lb1이 연결 정보를 lb2로 복제하게 합니다. IPVS는 이 목적의 sync daemon을 내장하고 있습니다. lb1은 master, lb2는 backup으로 띄우면 멀티캐스트로 연결 항목이 흘러갑니다.

```bash
./lab.sh 2
```

장애 직전, 이번에는 lb2도 같은 줄을 갖고 있습니다.

```
[장애 전] lb1 연결 테이블:
    TCP 14:56  ESTABLISHED 10.0.1.10:51466  10.0.1.100:8080  10.0.2.13:8080
[장애 전] lb2 연결 테이블:
    TCP 14:58  ESTABLISHED 10.0.1.10:51466  10.0.1.100:8080  10.0.2.13:8080
```

결과가 뒤집힙니다.

```
1단계: OK [B3] (0.00s)
2단계: OK [B3] (0.04s)
```

기존 연결이 살아남았을 뿐 아니라 **원래 백엔드 B3로 그대로** 이어집니다. 활성 장비가 죽었는데도 애플리케이션은 아무 일도 없었던 것처럼 계속 대화합니다. 2단계의 0.04초는 VIP가 이사한 뒤 ARP를 다시 푸는 시간입니다.

여기에 정직하게 붙여야 할 단서가 있습니다. 이 실험을 처음 돌렸을 때는 lb2의 테이블이 비어 있어 연결이 끊겼습니다. 원인은 **동기화가 비동기라는 것**입니다. 연결이 생기고 상태가 lb2에 도착하기까지 시간이 걸리고, 그 사이에 장애가 나면 그 연결은 못 살립니다. 그래서 시나리오에 명시적인 전파 대기(`SETTLE`)가 들어 있습니다.

이 관측은 실무 결론으로 이어집니다. 상태 동기화를 켰다고 해서 "모든 연결이 반드시 살아남는다"고 말할 수 없습니다. 정확한 표현은 **"대부분의 기존 연결을 이어가도록 설계할 수 있다"** 이고, 갓 맺어진 연결과 동기화 주기 안에 있던 연결은 여전히 희생됩니다.

## 실험 3: 애초에 넘겨받을 상태가 없는 설계

여기가 이 실험의 핵심입니다. 상태 동기화를 **다시 끕니다**. lb2는 여전히 빈 테이블로 인계받습니다. 대신 두 가지를 바꿉니다.

첫째, 스케줄러를 라운드로빈에서 **Maglev 해시(`mh`)** 로 바꿉니다. 라운드로빈은 "지난번에 어디까지 줬는지"를 기억해야 다음 대상을 정할 수 있는, 상태에 의존하는 방식입니다. 해시는 다릅니다. 흐름의 5-tuple을 해시 함수에 넣어 백엔드를 **계산**합니다. 기억할 것이 없으니 잃을 것도 없습니다. `mh-port` 플래그를 함께 주어 출발지 포트까지 해시에 넣으면, 클라이언트가 한 대여도 흐름마다 다른 백엔드로 흩어집니다.

둘째, `sloppy_tcp`를 켭니다. 실험 1에서 봤듯 IPVS는 SYN이 아닌 패킷에 대해서는 백엔드를 고르지 않고 그냥 통과시킵니다. `sloppy_tcp=1`은 그 제한을 풀어, 연결 중간의 패킷이 들어와도 스케줄러를 돌려 항목을 만들게 합니다.

```bash
./lab.sh 3
```

```
[장애 후] lb2 연결 테이블:
    (비어 있음)
---
1단계: OK [B3] (0.00s)
2단계: OK [B3] (0.05s)
```

**연결 테이블은 끝까지 비어 있었는데 기존 연결이 살았습니다.** 그리고 원래 백엔드로 갔습니다. lb2는 lb1이 무엇을 골랐는지 전혀 모르지만, 같은 5-tuple을 같은 해시 함수에 넣으면 같은 답이 나오기 때문에 **알 필요 없이 같은 결론에 도달**합니다.

이것이 "L4가 죽으면 기존 연결도 죽는다"의 두 번째 반례입니다. 첫 번째 반례는 실험 2의 *상태를 넘겨받는 경우*였고, 이번 것은 *애초에 넘겨받을 상태가 없는 설계*입니다. Google Maglev, Meta Katran, Cloudflare Unimog 같은 대규모 L4가 이 계열이며, `ip_vs_mh`는 Maglev 논문의 해시를 리눅스 커널에 옮긴 구현입니다.

두 조건이 각각 필요하다는 것도 확인했습니다. 해시 스케줄러를 쓰되 `sloppy_tcp`를 끄면 다시 RST가 납니다. 백엔드를 결정론적으로 고를 수 있어도, 애초에 중간 패킷에 대해 고르는 절차를 밟지 않으면 소용이 없기 때문입니다.

| 스케줄러 | sloppy_tcp | 상태 인계 | 기존 연결 |
|---|---|---|---|
| `rr` | 0 | 없음 | RST (끊김) |
| `rr` | 0 | sync daemon | 유지 |
| `mh` | 0 | 없음 | RST (끊김) |
| `mh` | 1 | 없음 | **유지** |

## 실험 4: 아무도 VIP를 인계하지 않으면

지금까지는 대기 장비가 VIP를 가져갔습니다. 이번에는 lb1만 죽이고 아무도 인계하지 않습니다. 현실에서는 이중화가 없거나, 대기 장비까지 함께 나갔거나, 전환이 늦어지는 상황입니다.

```bash
./lab.sh 4
```

```
2단계: 타임아웃 — 응답이 없습니다 (15.03s)
```

같은 장애인데 **증상이 완전히 다릅니다.** 실험 1은 0.00초 만의 RST였고, 여기서는 15초 동안 아무 응답이 없습니다. 차이의 원인은 VIP를 가진 장비의 유무입니다. 실험 1에서는 lb2가 VIP를 갖고 있었기에 "그 포트에 소켓이 없다"고 즉시 대답할 수 있었지만, 여기서는 VIP를 가진 장비가 아예 없으므로 패킷이 허공으로 사라지고 아무도 대답하지 않습니다.

장애 4초 뒤 클라이언트 소켓 상태를 보면 이 상황의 본질이 드러납니다.

```
State  Recv-Q Send-Q  Local Address:Port   Peer Address:Port
ESTAB  0      3       10.0.1.10:32912      10.0.1.100:8080
   rto:3216 backoff:4 cwnd:1 bytes_sent:18 bytes_retrans:12
   retrans:1/4 lost:1 lastack:7108
```

- `ESTAB` — 운영체제는 이 연결이 **여전히 정상이라고 믿고 있습니다.**
- `Send-Q 3` — 애플리케이션이 보낸 3바이트가 송신 큐에 갇혀 상대에게 전달되지 못했습니다.
- `retrans:1/4`, `bytes_retrans:12` / `bytes_sent:18` — 네 번 재전송했고, 보낸 바이트의 대부분이 재전송분입니다.
- `backoff:4`, `rto:3216` — 재전송 간격이 지수적으로 늘어 3.2초까지 벌어졌습니다.
- `cwnd:1` — 혼잡 윈도우가 1로 주저앉았습니다.
- `lastack:7108` — 마지막 ACK를 받은 지 7초가 지났습니다.

여기서 "소켓이 유효하다"는 말이 두 가지 뜻으로 갈린다는 것이 보입니다. 하나는 **로컬 파일 디스크립터와 TCP 상태가 아직 존재한다**는 뜻이고, 다른 하나는 **상대까지 데이터를 전달하고 응답을 받을 수 있다**는 뜻입니다. 위 상태는 앞은 참이고 뒤는 거짓입니다. 첫 `write()`는 로컬 송신 버퍼에 데이터를 넣고 성공을 반환하기까지 합니다.

이 구분은 장애 대응에서 실제로 중요합니다. 애플리케이션이 붙어 있는 연결 수만 세거나 소켓 상태가 `ESTABLISHED`인지만 보는 헬스체크는 이 상황을 정상으로 오판합니다. 재전송 카운터와 마지막 ACK 시각을 함께 봐야 실제 상태가 보입니다. 그리고 즉시 RST와 조용한 타임아웃은 원인이 같아도 애플리케이션이 느끼는 지연이 완전히 다르므로, 장애를 읽을 때 이 둘을 구분해야 합니다.

## 실험 5: 흐름 여러 개로 재는 진짜 차이

실험 1~3은 연결 하나만 봤습니다. 연결이 하나면 우연이 끼어들 여지가 큽니다. 갓 켜진 lb2의 라운드로빈 포인터는 항상 같은 자리에서 시작하므로, 운 좋게 원래 백엔드를 다시 고를 수 있기 때문입니다.

그래서 흐름 16~18개를 동시에 열고, **장애 후 각 흐름이 원래 백엔드를 유지하는 비율**을 셉니다. 요청 순서도 섞습니다. 실제 트래픽은 연결이 만들어진 순서대로 도착하지 않기 때문입니다. 이 셔플이 없으면 라운드로빈이 생성 순서 그대로 다시 배분하면서 16/16을 맞춰 버립니다.

```bash
./lab.sh 5
```

**5a. 라운드로빈 + `sloppy_tcp`, 백엔드 3대**

```
1단계 배분: B3 B2 B1 B3 B2 B1 B3 B2 B1 B3 B2 B1 B3 B2 B1 B3
2단계: 기존 백엔드 유지 7/16
```

살아남지 못한 아홉 개는 전부 RST를 받았습니다. lb2가 백엔드를 다시 고르기는 했지만 **원래와 다른 서버**로 보냈고, 그 서버는 자기가 모르는 연결의 패킷을 받았으니 RST로 거절한 것입니다.

이 비율은 우연이 아니라 기대값과 맞습니다. 백엔드가 3대면 다시 고를 때 원래와 같은 서버를 뽑을 확률이 약 1/3입니다. 셔플 시드를 바꿔 가며 다섯 번 돌린 결과는 7, 3, 6, 5, 5 / 16이었습니다. 라운드로빈이 살려 내는 연결은 실력이 아니라 운입니다.

**5b. Maglev 해시 + `sloppy_tcp`, 백엔드 3대**

```
1단계 배분: B2 B1 B3 B3 B3 B3 B2 B3 B3 B1 B2 B2 B2 B1 B1 B3
2단계: 기존 백엔드 유지 16/16
```

전부 유지입니다. 같은 조건에서 셔플 시드만 바꿔 다섯 번 돌린 결과도 전부 16/16이었습니다. 바로 위 라운드로빈의 7, 3, 6, 5, 5와 나란히 놓으면 차이가 운의 문제가 아님이 분명합니다. 장애 전 배분이 세 백엔드에 고르게 흩어져 있다는 점도 확인해 두어야 합니다. 만약 모든 흐름이 한 백엔드에 몰려 있었다면 "유지됐다"는 결과가 의미 없었을 것입니다.

**5c. Maglev 해시인데 장애와 동시에 백엔드 B3가 빠짐**

무상태 해시 방식에도 약점이 있습니다. 백엔드 집합이 바뀌면 계산 결과가 흔들립니다. 장애 전환과 동시에 백엔드 한 대가 스케일 인되거나 헬스체크에서 탈락한 상황을 재현했습니다. 유지 개수 자체는 실행마다 달라집니다. 출발지 포트가 매번 새로 배정되므로 B3에 해시되는 흐름 수가 바뀌기 때문입니다. 달라지지 않는 것은 대응 관계입니다.

```
seed=1  B3에 붙었던 흐름=5  끊긴 흐름=5  그중 B3였던 것=5   → 13/18 유지
seed=2  B3에 붙었던 흐름=9  끊긴 흐름=9  그중 B3였던 것=9   →  9/18 유지
seed=3  B3에 붙었던 흐름=4  끊긴 흐름=4  그중 B3였던 것=4   → 14/18 유지
```

**끊긴 흐름 수 = 사라진 백엔드에 붙어 있던 흐름 수**이고, 무관한 흐름의 피해는 매번 0입니다.

이것이 Maglev 해시가 단순한 해시와 다른 지점입니다. `hash(5-tuple) % 백엔드수` 같은 소박한 방식이었다면 백엔드 하나가 빠질 때 나머지 값도 전부 밀려 거의 모든 흐름이 재배치됐을 것입니다. 일관 해싱은 **사라진 백엔드에 붙어 있던 흐름만** 옮기고 나머지는 제자리에 둡니다. Maglev 논문이 균등 분산과 최소 재배치를 함께 목표로 삼은 이유가 이것이며, 논문의 실제 구현은 여기에 더해 노드마다 로컬 연결 추적 테이블을 두어 백엔드 변경 중에도 기존 흐름을 고정합니다. 다만 그 테이블은 노드 간에 공유되지 않는 최적화이고, 정확성의 근거는 어디까지나 해시 쪽입니다.

## 종단은 누구인가 — 모드가 답을 바꾼다

"연결이 맺어지고 나면 A와 B의 일이고 중간 장비는 상관없다"는 생각이 자연스럽게 떠오릅니다. 이 문장은 절반만 맞습니다. 그리고 어느 절반이 맞는지가 모드에 따라 달라집니다.

```bash
./lab.sh 7
```

같은 백엔드에 두 경로로 접속해, 양쪽 끝에서 `getpeername()`을 물어본 결과입니다.

```
주소 배치:  클라이언트=10.0.1.10   VIP=10.0.1.100   LB 뒷단=10.0.2.1   백엔드=10.0.2.11

── 패킷 모드 (IPVS NAT) ──
   클라이언트가 본 상대: 10.0.1.100:9090      ← VIP
   백엔드가 본 상대:     10.0.1.10:34356      ← 클라이언트의 실제 주소

── 프록시 모드 ──
   클라이언트가 본 상대: 10.0.1.100:9091      ← VIP (구분 불가)
   백엔드가 본 상대:     10.0.2.1:43688       ← 로드밸런서의 주소
```

**클라이언트 쪽만 보면 두 모드가 똑같아 보입니다.** 어느 쪽이든 상대는 VIP입니다. 차이는 백엔드 쪽에서 드러납니다.

패킷 모드에서 로드밸런서는 목적지 주소만 고쳐 쓰고 지나가므로 TCP 연결의 종단이 아닙니다. 백엔드는 클라이언트와 직접 마주 봅니다. 이 경우 "연결의 주인은 A와 B"라는 말이 맞습니다.

프록시 모드에서는 전혀 다릅니다. TCP 연결이 두 개 존재하고, 로드밸런서가 양쪽 모두의 종단입니다. 클라이언트의 상대는 문자 그대로 로드밸런서이고, **백엔드는 클라이언트와 아무 연결도 맺고 있지 않습니다.** 이 모드에서는 "A와 B의 일"이라는 전제 자체가 성립하지 않습니다. HAProxy, Nginx stream, 그리고 대부분의 상용 ADC 기본 설정이 이쪽입니다.

그래서 실무에서 가장 먼저 할 일은 **백엔드의 접속 로그에 찍히는 출발지 IP를 확인하는 것**입니다. 클라이언트의 IP가 보이면 패킷 모드, 로드밸런서의 IP가 보이면 프록시 모드입니다. 이 한 줄로 이후의 모든 판단이 갈립니다.

한 가지 덧붙일 것이 있습니다. 패킷 모드에서 종단이 A와 B라는 사실은 **경로에 대해 아무것도 보장하지 않습니다.** TCP 연결은 회선을 예약하는 것이 아니라 양쪽이 서로에 대한 상태(시퀀스 번호, 윈도우, 재전송 버퍼)를 만들어 기억하는 것뿐입니다. 매 패킷은 매번 새로 경로를 찾아갑니다. 그래서 종단이 둘 다 멀쩡해도 중간이 끊기면 통신이 안 됩니다. [실험 4](#실험-4-아무도-vip를-인계하지-않으면)의 `ESTAB`인데 재전송만 쌓이는 소켓이 정확히 그 상태입니다.

경로상의 평범한 라우터라면 이 걱정을 할 필요가 없습니다. 라우터는 목적지 IP만 보고 전달하므로 어느 라우터든 대신할 수 있고, 한 대가 죽으면 라우팅이 우회합니다. **상태를 가진 L4가 다른 이유는 목적지를 고쳐 쓰기 때문입니다.** 어느 백엔드로 고쳐 쓸지는 그 흐름을 처음 받았을 때의 결정에 달려 있고, 그 결정이 사라지면 다른 장비가 대신할 수 없습니다. 이 문서 전체가 그 한 가지를 다룹니다.

## 백엔드가 죽는 것과 L4가 죽는 것은 다른 문제다

여기까지 읽으면 자연스럽게 이런 사례가 떠오릅니다. 액티브-액티브 DB 두 대 앞에 VIP를 두고, 애플리케이션은 커넥션 풀로 연결을 유지합니다. 이때 붙어 있던 DB가 죽으면 풀에 남은 그 연결은 못 씁니다. 로드밸런서가 살아 있어도 소용없습니다.

이 관찰은 **맞습니다.** 다만 이것을 "그러니까 중간 장비는 원래 상관없다"로 일반화하면 틀립니다. 두 장애는 지점이 다르고 결론도 다릅니다.

```bash
./lab.sh 6
```

연결을 하나 맺어 둔 상태에서 그 연결이 붙은 백엔드를 죽입니다.

```
  (이 연결이 붙은 백엔드: B3 = 10.0.2.13)
  (장애: B3 서버를 통째로 끊는다 — 정전·네트워크 단절)
  (헬스체크가 죽은 백엔드를 풀에서 빼는 것과 동등한 조작)
  (같은 시점에 새 연결을 맺어 본다)
1단계: OK [B3] (0.00s)
2단계: 타임아웃 — 응답이 없습니다 (6.18s)
3단계: 타임아웃 — 응답이 없습니다 (6.04s)
4단계 (새 연결): OK [B2] (0.00s)
```

3단계가 핵심입니다. **헬스체크가 죽은 백엔드를 걷어내도 기존 연결은 여전히 못 씁니다.** 헬스체크가 고치는 것은 새 연결뿐이고, 그 증거가 4단계입니다. 같은 순간에 새로 맺은 연결은 살아 있는 B2로 멀쩡히 갑니다.

로드밸런서가 살아 있는 연결을 다른 백엔드로 옮기지 못하는 이유는 분명합니다. TCP 연결에는 양쪽이 임의의 초기값에서 시작해 관리해 온 시퀀스 번호와 재전송 버퍼가 있고, 그 위에 DB라면 인증 상태, 트랜잭션 컨텍스트, prepared statement, 임시 테이블 같은 것이 얹혀 있습니다. 새 백엔드는 그중 무엇도 모릅니다. 억지로 패킷을 돌려도 받는 쪽은 자기가 모르는 연결의 조각을 받은 것이므로 RST로 거절합니다. [실험 5a](#실험-5-흐름-여러-개로-재는-진짜-차이)에서 라운드로빈이 흐름을 원래와 다른 백엔드로 보냈을 때 무더기로 RST가 났던 것이 바로 이 장면입니다.

장애가 어떻게 끝나는지도 갈립니다.

- **프로세스만 죽은 경우** — 운영체제가 그 프로세스의 소켓을 닫으면서 FIN을 보냅니다. 같은 실험의 사례 A가 `2단계: FIN — 상대가 연결을 닫았습니다 (0.00s)`로 끝나는 것이 그것입니다. 애플리케이션이 즉시 EOF를 보므로 오히려 다루기 쉽습니다.
- **서버가 통째로 사라진 경우** — FIN을 보낼 주체가 없으므로 아무 신호도 오지 않습니다. 위 출력의 `타임아웃 (6.18s)`이 그것이고, 타임아웃을 걸지 않았다면 훨씬 오래 매달립니다. 커넥션 풀에서 문제가 되는 쪽은 거의 항상 이쪽입니다.

그래서 이 상황의 방어선은 로드밸런서가 아니라 **연결을 빌려주기 전에 살아 있는지 확인하는 것**과 **연결을 너무 오래 재사용하지 않는 것**입니다. HikariCP라면 `isValid()` 기반 검증, `maxLifetime`으로 주기적 폐기, `keepaliveTime`으로 유휴 연결 점검이 그 역할입니다. OS의 TCP keepalive는 기본값이 2시간이라 이 용도로는 너무 느립니다.

정리하면 이렇습니다.

| 무엇이 죽었나 | 기존 연결 | 누가 결정하나 |
|---|---|---|
| 백엔드 한 대 | **무조건 끊긴다** | 로드밸런서 설계와 무관 |
| L4 로드밸런서 | 설계에 따라 갈린다 | 상태 유지형인가 무상태형인가, 동기화가 있는가 |

## 정리: 판정 질문

| 실험 | 상태 인계 | 백엔드 선택 방식 | 기존 연결 |
|---|---|---|---|
| 1 | 없음 | 라운드로빈 | 즉시 RST |
| 2 | sync daemon | 라운드로빈 | 유지 |
| 3 | 없음 | Maglev 해시 | 유지 |
| 4 | 인계 자체가 없음 | — | 조용한 타임아웃 |
| 5a | 없음 | 라운드로빈 | 3~7 / 16만 유지 (시드 5회) |
| 6 | — (백엔드가 죽음) | 무관 | 무조건 끊김 |
| 5b | 없음 | Maglev 해시 | 16/16 유지 (시드 5회 전부) |
| 5c | 없음 | Maglev 해시, 백엔드 집합 변경 | 사라진 백엔드 몫만 손실, 나머지 전부 유지 |

그래서 "L4가 죽으면 기존 연결은 어떻게 되나요"에 한 문장으로 답할 수 없습니다. 답을 정하려면 아래 네 가지를 먼저 확인해야 합니다.

0. **정말 L4가 죽은 것인가, 백엔드가 죽은 것인가.**

    백엔드가 죽었다면 로드밸런서가 무엇이든 기존 연결은 끊깁니다. 이건 설계로 어떻게 해 볼 여지가 없는 문제이고, 방어선은 애플리케이션의 연결 검증과 재연결입니다. 아래 세 질문은 L4 자신이 죽은 경우에만 의미가 있습니다.

1. **이 L4는 연결별 상태를 저장하는가, 매번 계산하는가.**

    저장한다면 그 상태를 잃는 순간 기존 연결이 끊깁니다. 계산한다면 잃을 것이 없으므로 다른 노드가 같은 답에 도달합니다. TCP 프록시(HAProxy, Nginx stream 등)는 아예 연결의 종단점이라 상태를 잃는 정도가 아니라 소켓 자체가 닫히므로 가장 확실하게 끊깁니다.

2. **상태를 저장한다면 그것을 동기화하는가, 동기화 지연은 얼마인가.**

    동기화가 있어도 비동기이므로 갓 맺어진 연결은 희생됩니다. "전부 살아남는다"가 아니라 "대부분 살아남게 설계할 수 있다"가 정확합니다.

3. **"죽었다"가 정확히 무슨 뜻인가.**

    새 연결만 안 받고 기존 전달은 계속하는 상태, 관리 평면만 죽고 데이터 평면은 도는 상태, 데이터 평면이 완전히 죽은 상태, 상태를 동기화한 대기 장비가 인계한 상태는 전부 다른 결과를 냅니다.

여기에 관측 측면의 부산물이 하나 붙습니다. **VIP를 가진 장비가 있으면 즉시 RST, 없으면 조용한 타임아웃**입니다. 장애 로그에서 `Connection reset by peer`가 쏟아지면 인계는 됐는데 상태나 백엔드 선택이 어긋난 것이고, 아무 소리 없이 지연만 치솟으면 VIP를 아무도 들고 있지 않은 것입니다.

## 직접 다뤄 보기

### 읽는 순서

각 파일이 답하는 질문을 따라가는 편이 빠릅니다.

1. [`net/build.sh`](net/build.sh) — **"무엇이 무엇에 연결되어 있는가"**

    네임스페이스 여섯 개와 브리지 두 개, 두 VIP가 어디에 붙어 있는지가 전부 여기 있습니다. 위 [실험대 구조](#실험대-구조)의 그림과 나란히 놓고 읽으면 한 줄씩 대응됩니다.

2. [`net/ipvs.sh`](net/ipvs.sh) — **"L4를 어떻게 설정하는가"**

    `-A`로 가상 서비스를, `-a`로 백엔드를 등록합니다. `-m`이 NAT(masquerading) 모드 지정이고, `-s`가 스케줄러입니다. IPVS 설정의 최소 형태를 보기 좋습니다.

3. [`net/fail.sh`](net/fail.sh) — **"장애란 정확히 무엇인가"**

    이 실험에서 "죽었다"가 어떤 조작인지 여기서 확정됩니다. 다섯 종류가 한 곳에 모여 있어 서로 비교하며 읽을 수 있습니다. `takeover` 갈래의 세 줄이 keepalived가 하는 일의 최소 형태입니다.

4. [`scenario/failover.sh`](scenario/failover.sh) — **"측정을 어떤 순서로 하는가"**

    연결을 맺고 → 상태를 찍고 → 장애를 내고 → 다시 상태를 찍고 → 같은 소켓으로 보내 봅니다. 실험의 뼈대입니다.

5. [`src/`](src) — **"무엇을 성공으로 세는가"**

    측정 도구입니다. 읽는 순서는 [Rust 코드 읽기](#rust-코드-읽기)에 따로 적었습니다.

### 손으로 만져 보기

자동 실행은 결과만 보여 줍니다. 연결을 직접 붙들고 장애를 원하는 순간에 내 보면 감이 다릅니다. 터미널 세 개를 씁니다.

```bash
./lab.sh up
./lab.sh manual rr - 0 0     # 스케줄러 rr, 플래그 없음, sync 끔, sloppy_tcp 끔
```

| 터미널 | 명령 | 하는 일 |
|---|---|---|
| A | `./lab.sh talk` | 연결을 맺고 직접 타이핑합니다 |
| B | `./lab.sh watch` | 두 L4의 연결 테이블을 1초마다 갱신해 보여 줍니다 |
| C | `./lab.sh snap 장애전` → `./lab.sh fail` → `./lab.sh snap 장애후` | 상태를 찍고, 장애를 내고, 다시 찍습니다 |

터미널 A에서 아무 글자나 치면 백엔드가 자기 이름을 붙여 답합니다.

```
연결됨.  내 주소=10.0.1.10:40600   소켓이 기억하는 상대=10.0.1.100:8080
> hello
  OK [B3] (0.00s)
```

이때 터미널 B를 보면 lb1에만 항목이 하나 생겨 있고 lb2는 비어 있습니다. 여기서 터미널 C의 `fail`을 실행하면 B의 화면에서 `◆ VIP 보유` 표시가 lb1에서 lb2로 넘어가는 것이 보입니다. 그 상태로 터미널 A에 다시 타이핑하면 이렇게 답합니다.

```
> hello
  RST — 상대가 연결을 재설정했습니다 (0.00s)
     VIP를 가진 장비는 살아 있는데 이 연결을 모릅니다.
```

같은 절차를 조건만 바꿔 반복하면 실험 1~4를 전부 손으로 재현할 수 있습니다.

```bash
./lab.sh manual rr - 1 0        # 실험2: sync 켬        → 살아남습니다
./lab.sh manual mh mh-port 0 1  # 실험3: 해시 + sloppy  → 살아남습니다
./lab.sh manual mh mh-port 0 0  # 대조군: sloppy 끔     → 다시 RST
```

장애 종류도 골라 낼 수 있습니다. `./lab.sh fail vanish`면 아무도 인계하지 않아 RST 대신 조용한 타임아웃이 나고, `./lab.sh fail backend 3`이면 백엔드 B3가 통째로 사라집니다. 타임아웃이 나는 동안 `./lab.sh snap 타임아웃중`을 찍으면 소켓이 `ESTAB`인 채로 재전송만 쌓이는 상태가 그대로 남습니다.

네임스페이스를 직접 뒤지고 싶으면 `./lab.sh shell`로 들어가 `ip netns exec lb1 <명령>` 형태로 아무 명령이나 실행할 수 있습니다.

### 로그 남기기

두 경로가 있고 목적이 다릅니다.

- **자동 실행** — `./lab.sh 1` 같은 명령은 화면에 보여 주면서 동시에 `logs/20260822-173124_exp1.log`처럼 시각과 실험 이름이 붙은 파일로 남깁니다. 실행할 때마다 새 파일이 생기므로 조건을 바꿔 가며 돌린 결과가 쌓입니다.
- **수동 스냅샷** — `./lab.sh snap <라벨>`은 그 순간의 상태 전체를 라벨과 함께 찍어 `logs/session.log`에 **이어 붙입니다**. 장애 전과 후가 한 파일 안에 나란히 남아 비교하기 좋습니다.

남은 것을 보려면 `./lab.sh logs`입니다. `./lab.sh down`은 컨테이너만 지우고 `logs/`와 `bin/`은 남기므로, 실험대를 부수고 다시 세워도 기록은 유지됩니다.

### 로그 읽기

스냅샷 하나에 네 종류의 표가 들어 있습니다. 각각 답하는 질문이 다릅니다.

**서비스 테이블 (`ipvsadm -Ln`) — "이 L4는 무엇을 어디로 보내기로 되어 있는가"**

```
TCP  10.0.1.100:8080 rr
  -> 10.0.2.11:8080               Masq    1      0          1
```

`rr`이 스케줄러입니다. `Masq`는 전달 방식이 NAT라는 뜻이고, DR 모드면 `Route`, 터널 모드면 `Tunnel`로 찍힙니다. 이어지는 세 숫자는 가중치, `ActiveConn`(ESTABLISHED인 연결 수), `InActConn`(그 밖의 상태에 있는 연결 수)입니다. 설정만 나타내므로 **장애 전후에 거의 변하지 않습니다.** lb1과 lb2가 이 표는 똑같이 갖고 있다는 점이 중요합니다. 두 장비의 차이는 여기가 아니라 다음 표에서 납니다.

**연결 테이블 (`ipvsadm -Lnc`) — "지금 어떤 연결을 어디로 보내고 있는가"**

```
pro expire state       source             virtual            destination
TCP 14:56  ESTABLISHED 10.0.1.10:45564    10.0.1.100:8080    10.0.2.13:8080
```

이 문서의 주인공입니다. `expire`는 이 항목이 저절로 사라지기까지 남은 시간이며, ESTABLISHED의 기본 수명은 15분이라 `14:5x`부터 줄어듭니다. `state`는 IPVS가 지나가는 패킷을 보고 **추정한** TCP 상태이지 종단이 실제로 갖고 있는 상태가 아닙니다. 그래서 클라이언트가 이미 끊긴 줄 아는데 여기에는 한동안 남아 있을 수 있습니다.

읽을 때 볼 것은 딱 하나입니다. **장애 후 새 활성 장비에 이 줄이 있는가.** 있으면 상태를 넘겨받은 것이고(실험 2), 없는데도 연결이 살아 있으면 해시로 다시 계산한 것입니다(실험 3).

**누적 통계 (`ipvsadm -Ln --stats`) — "실제로 트래픽이 흘렀는가"**

```
TCP  10.0.1.100:8080                     7       39       25     2126     1433
  -> 10.0.2.13:8080                      3       17       11      926      629
```

연결 수와 패킷·바이트 누적치입니다. 설정은 맞는데 트래픽이 안 흐르는 상황을 잡을 때 씁니다. 장애 후 새 활성 장비의 이 숫자가 0에서 올라가기 시작하면 실제로 전달을 넘겨받은 것입니다.

여기에 함정이 하나 있습니다. IPVS는 per-CPU 카운터를 추정 타이머가 돌 때 집계하므로, `net.ipv4.vs.run_estimation`이 0이면 **트래픽이 흘러도 이 표가 영원히 0으로 보입니다.** 이 환경의 기본값이 0이어서 [`net/build.sh`](net/build.sh)가 1로 켜 둡니다. 다른 곳에서 IPVS 통계가 0으로만 나온다면 이 값을 먼저 확인하세요.

**클라이언트 소켓 (`ss -tin`) — "클라이언트 입장에서 이 연결은 살아 있는가"**

```
State  Recv-Q Send-Q  Local Address:Port   Peer Address:Port
ESTAB  0      8       10.0.1.10:39280      10.0.1.100:8080
   rto:3216 backoff:4 cwnd:1 bytes_sent:56 bytes_retrans:40 retrans:1/5 lost:1 lastack:7054
```

`State`만 보면 안 된다는 것이 실험 4의 교훈입니다. 함께 봐야 할 값은 이렇습니다.

- `Send-Q` — 보냈지만 아직 확인받지 못해 큐에 갇힌 바이트 수. 0이 아니면서 줄지 않으면 전달이 안 되고 있는 것입니다.
- `retrans:X/Y` — X는 지금 미확인 상태인 재전송 수, Y는 이 연결의 누적 재전송 수입니다.
- `bytes_retrans` 대 `bytes_sent` — 보낸 것의 대부분이 재전송이면 상대에게 닿지 않고 있습니다.
- `backoff`, `rto` — 재전송 간격이 지수적으로 늘어난 횟수와 현재 재전송 대기 시간(ms). `backoff`가 계속 올라가면 죽어 가는 연결입니다.
- `lastack` — 마지막 ACK를 받은 지 지난 시간(ms). 이 값이 크면 `ESTAB` 표시는 허상입니다.
- `cwnd` — 혼잡 윈도우. 1까지 떨어졌다면 TCP가 경로를 거의 포기한 상태입니다.

**클라이언트 판정 줄** — `2단계: ...` 또는 `2단계: 기존 백엔드 유지 N/M`이 실험의 최종 답입니다. 위 표들은 그 답이 왜 그렇게 나왔는지를 설명하는 근거입니다.

### 조건 바꿔 재실행하기

수동 모드는 인자 네 개로 조건을 바꿉니다. `./lab.sh manual <스케줄러> <플래그> <sync> <sloppy_tcp>` 형식이고, 플래그가 없으면 `-`를 씁니다. 스케줄러는 `rr`(라운드로빈), `sh`(출발지 해시), `mh`(Maglev 해시), `wrr`(가중 라운드로빈)을 쓸 수 있습니다.

시나리오는 환경변수로 조건을 바꿉니다.

| 변수 | 뜻 | 예 |
|---|---|---|
| `FLOWS` | 동시에 여는 흐름 수 | `FLOWS=32` |
| `SEED` | 요청 순서를 섞는 난수 시드 | `SEED=7` |
| `REALS2` | lb2가 가진 백엔드 목록 | `REALS2="11 12"` |
| `TIMEOUT` | 클라이언트 응답 대기 시간(초) | `TIMEOUT=15` |
| `SETTLE` | 장애 전 상태 전파 대기(초) | `SETTLE=0` |

예를 들어 상태 동기화의 지연을 직접 보려면 전파 대기를 0으로 두고 실험 2를 돌립니다. 동기화를 켰는데도 연결이 끊기는 것을 볼 수 있습니다.

```bash
docker exec -e SETTLE=0 l4lab sh /work/scenario/failover.sh "sync 지연" rr - 1 0 takeover
```

흐름 수를 늘려 라운드로빈의 생존율이 실제로 백엔드 수의 역수에 수렴하는지 보려면 이렇게 합니다.

```bash
for s in 1 2 3 4 5; do
  docker exec -e FLOWS=64 -e SEED=$s l4lab \
    sh /work/scenario/failover.sh "rr seed$s" rr - 0 1 takeover | grep '^2단계:'
done
```

같은 조건을 반복해도 출발지 포트가 매번 달라지므로 결과가 조금씩 흔들립니다. **한 번 돌린 숫자를 결론으로 삼지 말고 시드를 바꿔 여러 번 돌린 뒤 경향을 보세요.** 위 실험 5의 수치가 전부 그렇게 얻은 것입니다.

두 로그를 비교할 때는 판정 줄만 뽑아 보는 것이 빠릅니다.

```bash
# 자동 실행 로그: 판정 줄만 뽑아 비교
grep -h '^2단계:' logs/*_exp5a.log logs/*_exp5b.log

# 세션 로그: 어느 스냅샷에서 어느 장비가 그 연결을 알고 있었는지
awk '/^####/{L=$2} /^===== /{N=$2} /ESTABLISHED/{print L"  "N"  "$0}' logs/session.log
```

두 번째 명령의 출력이 이 실험의 핵심을 한눈에 보여 줍니다.

```
장애전  lb1  TCP 14:57  ESTABLISHED 10.0.1.10:39526  10.0.1.100:8080  10.0.2.12:8080
장애후  lb1  TCP 14:53  ESTABLISHED 10.0.1.10:39526  10.0.1.100:8080  10.0.2.12:8080
```

두 줄 다 `lb1`입니다. 죽은 lb1은 아직 그 연결을 기억하고 있지만 인터페이스가 내려가 아무 소용이 없고, 실제로 트래픽을 받는 lb2에는 그 줄이 아예 없습니다.

상태 동기화를 켜고(`./lab.sh manual rr - 1 0`) 같은 절차를 반복하면 출력이 이렇게 바뀝니다.

```
장애전  lb1  TCP 14:55  ESTABLISHED 10.0.1.10:40842  10.0.1.100:8080  10.0.2.13:8080
장애전  lb2  TCP 14:58  ESTABLISHED 10.0.1.10:40842  10.0.1.100:8080  10.0.2.13:8080
장애후  lb1  TCP 14:51  ESTABLISHED 10.0.1.10:40842  10.0.1.100:8080  10.0.2.13:8080
장애후  lb2  TCP 14:54  ESTABLISHED 10.0.1.10:40842  10.0.1.100:8080  10.0.2.13:8080
```

`장애전 lb2` 줄이 늘어난 것이 동기화가 실제로 일어난 증거이고, `장애후 lb2` 줄이 남아 있는 것이 연결이 살아남는 이유입니다. **lb2에 그 한 줄이 있는가 없는가가 연결의 생사입니다.**

`(대기 또는 사망)` 표시에 대해서도 한 가지 알아 둘 것이 있습니다. 인터페이스를 내려도 그 인터페이스의 IP 주소는 그대로 남습니다. 그래서 주소 목록만 보면 장애 후에도 lb1이 VIP를 들고 있는 것처럼 보입니다. 이 실험대는 `ip addr show up`으로 **살아 있는 인터페이스만** 보고 판정하므로 실제 보유자가 정확히 나옵니다.

조건을 바꿔도 결과가 안 바뀐다면 실험대가 리셋되지 않았을 수 있습니다. `./lab.sh manual ...`은 매번 토폴로지를 처음부터 다시 세우므로, 이상하면 `./lab.sh down && ./lab.sh up`으로 완전히 새로 시작하세요.


## Rust 코드 읽기

서브커맨드 네 개가 한 바이너리에 들어 있습니다.

```bash
bin/l4lab serve --name B1 --port 8080
bin/l4lab proxy --listen 10.0.1.100:9091 --to 10.0.2.11:9099
bin/l4lab probe --to 10.0.1.100:8080 --flows 16 --stages 2 --seed 1
bin/l4lab talk  --to 10.0.1.100:8080
```

### 문서를 컴파일러가 강제한다

`./lab.sh build`는 컴파일 전에 이 lint를 돌립니다.

```
cargo clippy -- -D missing_docs -D clippy::missing_docs_in_private_items
```

**문서 주석이 없는 함수가 하나라도 있으면 빌드가 실패합니다.** 비공개 헬퍼까지 포함합니다. 주석을 쓰는 일을 사람의 규율에 맡기지 않으려는 것입니다.

문서 형식은 rustdoc 관례를 따릅니다. 한 줄 요약, 필요하면 단계 설명, 그리고 `# Arguments` / `# Returns` / `# Errors`. 명령줄 인자는 `clap`의 derive를 쓰는데, **필드에 붙인 문서 주석이 그대로 `--help` 출력이 됩니다.** 그래서 문서와 실제 동작이 갈라질 수 없습니다.

```
$ bin/l4lab probe --help
측정. 흐름을 열고 단계마다 왕복시키며, 단계 사이에서 셸의 신호를 기다린다

Options:
      --to <TO>          접속할 주소. `10.0.1.100:8080` 형식
      --flows <FLOWS>    동시에 열 흐름 수 [default: 1]
      --seed <SEED>      요청 순서를 섞는 난수 씨앗. 같은 값이면 같은 순서가 나온다 [default: 1]
```

### 인자 파싱은 왜 라이브러리를 쓰는가

처음에는 인자 파서를 42줄로 직접 짰습니다. 외부 crate 없이 표준 API에만 집중하자는 이유였는데, 목적에 비춰 보면 틀린 판단이었습니다. 인자 파싱은 이 실험대의 주제가 아니고, 직접 짠 파서에는 이런 결함이 있었습니다.

| 입력 | 손으로 짠 파서 | `clap` |
|---|---|---|
| `--flow 16` (오타) | 흐름 1개로 조용히 실행 | `unexpected argument '--flow'` + `--flows` 제안 |
| `--flows abc` | 흐름 1개로 조용히 실행 | `invalid digit found in string` |
| `--flows` (값 누락) | 흐름 1개로 조용히 실행 | `a value is required` |
| `--help` | 없음 | 문서 주석에서 생성 |

측정 도구가 **틀린 조건으로 조용히 돌아 그럴듯한 숫자를 내는 것**이 여기서 가장 나쁜 실패입니다. 시드 스윕을 오타로 돌린 사람은 잘못된 수치를 얻고도 모릅니다. 관심사가 아닌 문제는 그 문제를 더 잘 다루는 라이브러리에 맡기는 편이 낫습니다.

### 읽는 순서와 배울 것

1. [`src/flow.rs`](src/flow.rs) — **한 연결의 왕복과 실패 분류**

    가장 먼저 읽을 파일입니다. `Conn`이 TCP 연결 하나를 감싸고, `Outcome`이 왕복 결과를 다섯 갈래로 나눕니다. 여기서 볼 것이 셋입니다.

    첫째는 `try_clone()`입니다. 같은 소켓을 읽기용과 쓰기용으로 나눠 쓰려고 핸들을 하나 더 만드는데, **새 연결을 만드는 것이 아닙니다.** 내부적으로 `dup()`이라 같은 파일 디스크립션을 가리키고, 그래서 `set_read_timeout`을 한쪽에 걸면 양쪽에 적용됩니다.

    둘째는 `BufReader`와 `read_line`입니다. TCP는 바이트 스트림이라 메시지 경계를 지켜 주지 않습니다. 보내는 쪽이 한 번에 쓴 `[B3] hello\n`이 받는 쪽에서 `[`와 `B3] hello\n`으로 쪼개져 도착할 수 있습니다. 이 실험대를 만들 때 실제로 그 일이 벌어졌습니다. `read`를 한 번만 부르는 코드였는데 백엔드 이름이 절반쯤 `?`로 나왔고, 원인은 백엔드 쪽 `writeln!`이 포맷 조각마다 `write`를 불러 `[`만 먼저 도착한 것이었습니다. 연결마다 `BufReader`를 하나씩 붙여 개행이 나올 때까지 읽도록 고쳤습니다. **스트림에는 경계가 없다**는 말이 실무에서 어떻게 물리는지 보여 주는 사례입니다.

    셋째는 `ErrorKind`로 실패를 가르는 부분입니다. RST는 `ConnectionReset`이고, 읽기 타임아웃은 리눅스에서 `EAGAIN`으로 오기 때문에 `WouldBlock`으로 보입니다. 이 둘을 구분하는 것이 실험 1과 실험 4를 가르는 관측이었습니다. `enum`과 `match`가 "이 실패가 무엇을 뜻하는지"를 타입에 적어 두게 해 줍니다.

2. [`src/serve.rs`](src/serve.rs) — **백엔드**

    30줄 남짓입니다. `TcpListener::bind` → `incoming()` 반복 → 연결마다 `thread::spawn`. `move` 클로저가 소켓의 소유권을 스레드로 넘기는데, 넘기지 않으면 반복문이 다음 연결로 넘어갈 때 소켓이 사라집니다. 소유권이 왜 필요한지 가장 짧게 보여 주는 예입니다.

3. [`src/proxy.rs`](src/proxy.rs) — **프록시 모드**

    실험 7의 절반을 담당하는 코드입니다. 소켓 두 개를 각각 맺고 `io::copy`로 바이트를 나릅니다. 방향마다 스레드가 하나씩 필요한데, `io::copy`가 상대가 끊을 때까지 막히기 때문입니다. 한 스레드로 양방향을 처리하면 한쪽이 조용할 때 반대쪽이 굶습니다.

    `pump` 끝의 `shutdown(Shutdown::Write)`이 중요합니다. 한쪽 방향이 끝났다는 사실을 반대쪽에 알리는 것인데, 빠뜨리면 상대가 EOF를 못 받아 보낼 것이 없는데도 계속 기다립니다. TCP의 **반쪽 닫기(half-close)** 를 다루는 자리입니다.

4. [`src/probe.rs`](src/probe.rs) — **측정**

    흐름을 N개 열고 단계마다 한 번씩 왕복시킵니다. 장애를 언제 어떻게 낼지는 이 코드가 정하지 않고, 단계 사이에서 파일 하나를 기다리기만 합니다. 그래서 장애 종류가 늘어도 이 코드는 그대로입니다.

    `shuffled`가 자체 xorshift 난수기를 씁니다. 외부 crate를 안 쓰기 위한 것이기도 하지만, **같은 시드면 같은 순서**가 나와야 결과를 재현할 수 있기 때문입니다.

### 고쳐 보기

읽기만 하는 것보다 고쳐 보는 편이 빠릅니다. 몇 가지 제안입니다.

- `flow.rs`의 `Outcome`에 갈래를 하나 더 추가해 보세요. `match`가 빠진 갈래를 컴파일 단계에서 잡아 줍니다. 문서를 안 붙이면 lint도 함께 막습니다.
- `proxy.rs`에서 `shutdown` 호출을 지우고 `./lab.sh 7`을 돌려 보세요. 무엇이 멈추는지 관찰한 뒤 되돌리면 반쪽 닫기가 왜 필요한지 몸으로 알게 됩니다.
- `serve.rs`의 `thread::spawn`을 지우고 한 연결씩 순차 처리하도록 바꾼 뒤 `FLOWS=16`으로 실험 5를 돌려 보세요.
- `probe.rs`에서 `shuffled`가 항상 `0..len`을 그대로 돌려주게 바꾸면 라운드로빈이 갑자기 16/16을 맞춥니다. 순서 상관이 실험을 어떻게 망치는지 직접 보게 됩니다.

고친 뒤에는 `./lab.sh build`로 다시 컴파일합니다.

## 이 실험이 증명하지 않는 것

- **DSR(Direct Server Return)은 재현하지 않았습니다.** 이 실험은 IPVS의 NAT(masquerading) 모드만 씁니다. DSR에서는 응답이 L4를 우회하지만 클라이언트가 보내는 패킷은 계속 L4를 거치므로 위 판정축이 그대로 적용될 것으로 **추론**하나, 여기서 실행해 확인하지는 않았습니다.
- **특정 상용 제품의 동작을 증명하지 않습니다.** AWS NLB, F5 BIG-IP 등의 결과는 각 제품이 상태 유지형인지 무상태형인지, 고가용성을 어떻게 구성했는지에 따라 달라집니다. 제품명만으로는 판정할 수 없습니다.
- **kube-proxy의 iptables 모드는 다루지 않았습니다.** IPVS 모드는 이 실험과 같은 계열이지만, iptables 모드는 netfilter conntrack에 상태를 두므로 별도 확인이 필요합니다.
- **성능이나 처리량은 재지 않았습니다.** 이 실험이 재는 것은 오직 "기존 연결의 생존 여부"입니다.
