## 방향 전환 두 가지

1. **Spring 화면 시안 선택을 지도 설계에 합친다(원문 6의 b).** 시안 넷은 버리지 않고 지도의 보기 방식이 된다.
   - ② 구조도 → 중간 줌의 지도(장소와 연결)
   - ④ 단계 레일 → 경로 안내의 단계 목록
   - ③ 트랙 → 시간축 보기(구간 드래그에 맞음)
   - ① 시퀀스 → 경로를 생명선 위에 펼친 보기
   - v2의 호출 기록 표 → 전문가용 목록 보기
2. **공통 틀을 떼어 내는 시점을 “둘째 주제 때”에서 지금으로 옮긴다.** 트랜잭션 관측 WORK 「범용화 경계」는 둘째 주제의 기록에 맞춰 떼어 내기로 했다. 원문 3이 그 비용을 문제로 보고 플랫폼을 먼저 요구했다. 그래서 지금 있는 여러 주제의 기록(요청의 여정, 커널 보기, 트랜잭션 실험 1~4, Spring 전파)을 첫 시험 입력으로 쓴다. 둘째 주제는 그 형식이 새 층을 담는지 보는 둘째 시험이 된다.

## 설계

### 1. 지도 모델

지도는 네 가지로 이뤄진다.

1. **장소(place).** 기록 안의 “누가·어디서”, 곧 실행 위치와 그 식별자다. 포함 관계는 실제 소속을 따른다: 시스템 → 호스트·컨테이너 → 프로세스 → 구성 요소(층) → 함수, 그리고 호스트 → 커널 → 커널 함수. 사용자 함수에서 커널 함수로 넘어가는 실행(시스템 콜)과 장소 사이의 호출·전송은 포함이 아니라 연결(4)로 기록한다. 시스템 디자인이면 맨 위가 서비스·저장소·큐다. (2026-10-17 고침: 앞 글은 함수 → 커널 함수를 포함으로 적었지만 시스템 콜은 장소를 건너는 연결이다. 작업 지도 항목 검증 f5.)
2. **층(zoom level).** 장소 포함 관계의 깊이. 줌 인은 한 장소를 그 안의 장소들로 펼치는 일이다. 기록이 없는 깊이는 “안 봄”이다.
3. **사건(event).** 시각이 있는 일. 들어감·나감이 짝인 구간(함수 호출, 기다림)과 한 점(메시지 보냄, 시스템 콜, 관찰)이 있다. 사건마다 장소, 시각, 값, 출처(JFR·함수 기록·연결 위 메시지·관찰·추론·AI 해설)를 가진다.
4. **연결(link).** 장소 사이를 건너는 사건의 짝: 보낸 메시지와 받은 메시지, 사용자 공간의 시스템 콜과 커널 함수, 한 연결 위 요청과 응답. 경로가 장소를 건너는 자리다.

**경로**는 한 실행 기록 안에서 출발 사건부터 도착 사건까지, 호출의 부모·자식 관계와 출처가 있는 연결을 따라 이어지는 사건들이다. 장소를 끝점으로 고르면 그 실행에서 그 장소를 지난 사건 후보를 보여 고르게 하고, 같은 장소를 여러 번 지난 사건을 구별한다. 기본 경로는 요청 하나의 입구(예: 백엔드가 `Q`를 받음)에서 출구(`Z`를 보냄)까지이고, 사용자가 장소나 사건 둘을 출발·도착으로 고르면 그 사이의 부분 경로가 된다. 같은 장소들을 지난 기록이 여럿이면 그것들이 서로 다른 경로 후보다. 같은 시간에 경로 밖에서 일어난 일(배경 프로세스)은 접어서 보인다.

주제마다 다른 것과 공통인 것:

| 공통(플랫폼) | 주제마다(플러그인) |
| --- | --- |
| 장소·층·사건·연결·경로의 형식과 저장 | 수집기(JFR, uprobe, strace, ftrace, eBPF, pcap, 로그) |
| 지도·줌·경로·재생·선택 화면 | 해석기(수집 기록 → 공통 사건) |
| 출처 표지, “안 봄” 표시 | 구성도(장소의 배치와 이름) |
| 설명 층(고정 설명 틀, AI 해설, 버전·피드백) | 주요 지점의 고정 설명 |
| 렌즈(기록에서 셈한 기준으로 보이는 줄 고르기)의 틀 | 렌즈 규칙(무엇이 핵심 동작인가) |
| 장면 고르기 | 장면 목록(장면 질문, 실행 a·b…) |

알고리즘은 이 모델에 맞는지 아직 모른다. 알고리즘의 장소는 프로세스가 아니라 상태(배열, 메모 표, 재귀 나무)이고 경로는 실행 단계다. 시간축과 줌은 맞을 것으로 보지만, 알고리즘 하나로 시험하기 전에는 범용이라고 주장하지 않는다(범위 밖, 다시 열 조건 참고).

### 2. 공통 사건 형식(후보)

T1에서 확정한다. 지금의 후보는 아래 다섯 표다. 필드 이름은 T0의 선례 확인 뒤 바꿀 수 있다.

| 표 | 한 줄이 뜻하는 것 | 핵심 칸 |
| --- | --- | --- |
| `place` | 장소 하나 | id, parent, kind(system·host·process·layer·function·kernel), name, 소스 위치 |
| `run` | 기록 한 벌 | 주제, 장면, 실행 이름(a, b…), 기록 도구와 도구 버전, 소스 사본의 해시 |
| `event` | 사건 하나 | run, place, 시작·끝 시각(점이면 같음), 부모 사건, 출처, 값(주제별 확장 칸) |
| `link` | 장소를 건너는 짝 | 보낸 사건, 받은 사건, 종류(메시지, 시스템 콜, 패킷) |
| `note` | 설명 | 범위(아래 6), 종류(고정·AI), 버전, 공급자·모델, 피드백 |

주제별 값은 확장 칸 하나에 둔다. 공통 칸에 주제 칸을 더해야 기존 기록을 옮길 수 있다면 형식이 틀린 것이다(T1의 실패 조건).

### 3. 주제 플러그인 계약

주제 하나는 디렉터리 하나다. 들어갈 것: 수집기 실행 방법, 해석기(Go), 구성도 정의, 주요 지점 설명, 렌즈 규칙, 장면 목록. 플랫폼은 이 디렉터리를 읽기만 한다. “공통 코드 변경 없이”는 둘째 주제를 붙이는 커밋이 플랫폼 디렉터리를 건드리지 않는지로 판정한다(T6).

### 4. 저장

원문 5의 질문(같은 부분은 재사용할 수 없나)에 대한 설계다.

1. **지도와 경로를 나눈다.** 장소(함수, 소스 줄, 호출 관계)는 소스 버전마다 한 번 저장하고, 사건은 장소 번호만 가진다.
2. **경로 안의 반복을 접는다.** 행마다·페이지마다 같은 모양으로 도는 부분은 모양을 한 번, 반복마다 다른 값과 시각을 N줄로 둔다. 이렇게 하면 접어도 손실이 없다. 화면의 「× N」 접기는 이와 별개로 보기만 바꾼다(화면은 이미 반복되는 배경 일을 접는다. 예: `CREATE INDEX` 329단계 → 31단계, 카탈로그 조회 접기).
3. **경로 사이의 같은 가지를 공유한다.** 호출 나무의 가지마다 모양(장소 순서와 포함 관계)으로 해시를 만들고, 같은 해시는 한 번만 둔다. 실행마다 다른 값과 시각은 가지 모양과 따로 둔다. 이 모양 해시는 설명 층도 쓴다(6).
4. **기록 범위를 좁힌다.** 그 세션의 백엔드와 관련 프로세스만, 요청 구간만 기록한다. 기록 훅은 사건마다 `write()`를 부르는 대신 모아서 쓴다.
5. **압축한다.** 효과는 재지 않았다.

공유할 수 없는 것: 값(행 내용, 트랜잭션 번호, LSN)과 시각. 모든 함수 호출의 나노초 시각을 남길지, 깊은 층은 순서만 남기고 시각은 시스템 콜·기다림·메시지 층에만 둘지는 T2의 측정으로 정한다. 후자의 대가는 깊은 층의 시간 비교를 잃는 것이고, 그 비교가 필요하면 그 구간을 다시 기록한다.

**DB인가 파일인가.** 판단 기준은 질의다. 여러 기록을 가로지르는 질의가 화면과 설명 층에 필요하면 DB가 낫고, 저장소에 커밋하는 재생본과 학습 자산은 파일이 낫다(오프라인, 이식성). T2에서 같은 기록으로 세 후보를 잰다.

- **PostgreSQL(따로 띄운 인스턴스).** 사용자가 허락했다(원문 6). 실험 대상과 다른 인스턴스여야 한다(X3). 서버가 하나 더 돌고, 디스크가 꽉 찼던 이 맥에서는 운영 부담이 있다.
- **내장 DB 파일(SQLite 또는 DuckDB).** 질의와 파일 하나의 이식성을 함께 준다. Go에서는 SQLite를 순수 Go 드라이버로 쓸 수 있다고 알고 있지만 확인하지 않았다(T2에서 확인). DuckDB의 Go 드라이버가 cgo를 요구하는지도 확인 대상이다.
- **파일(내용 주소 저장 + 색인).** 가장 단순하다. 질의는 Go 코드로 한다.

T2가 재는 질의는 셋이다. Q1 함수 X를 지난 실행 목록, Q2 두 실행의 경로가 처음 갈리는 자리, Q3 한 범위의 해설 버전·피드백 이력. 결정 규칙은 단계 계획 T2 칸에 적었다.

### 6. 설명 층

앞 대화(원문 1, 2)에서 정한 설계를 그대로 쓴다.

- **고정 설명.** 주제가 주요 지점마다 정한 문장 틀에 기록 값을 채운다(지금 `TOPIC.effect`·`effectDetail`의 방식). 사실 표지.
- **AI 해설.** 고른 범위의 사실 묶음(장면 질문, 그 줄 앞뒤 코드, 단계, 그 순간의 호출 사슬과 깊이, 그 범위의 기록 값과 출처, 고정 설명, 쌓인 피드백)을 공급자에게 넘긴다. 지시: 3문장 이내, 넘긴 사실만, 해석에는 [추론]. 표지는 「AI 해설 · 모델 이름」.
- **공급자.** 표준 입력으로 지시문을 받아 해설을 출력하는 명령. 설정은 사용자 맥의 `~/.config/txlab/explain.json`(위치는 환경 변수로 바꿈), 기본 공급자는 환경 변수, 작성 화면에서 고를 수도 있다. API 키는 설정에 두지 않는다. 이 맥에서 Claude CLI는 동작을 확인했고(E-10), Codex CLI는 페르소나 시험에서 화면 없이 돌린 기록이 있고, Gemini는 `agy`로 돌린 기록이 있다(E-11). Gemini CLI 실행 파일은 PATH에 없고 ollama에는 모델이 없다.
- **대체 순서.** 채택한 해설 → 없으면 고정 설명 → 작성 화면에 공급자가 있을 때만 「받기」·「다시 설명」 → 오류면 고정 설명을 두고 오류만 작게. 정적 재생본은 공급자를 부르지 않는다.
- **숫자 검사.** 해설의 숫자와 식별자가 모두 묶음 안에 있는지 Go가 확인하고, 없으면 표시하거나 받지 않는다.
- **범위에 붙이기(원문 3의 “쌓이는 문제”).** 드래그한 범위를 지금 줌의 단계 경계에 맞춰 정규화한다. 같은 범위는 같은 설명 자리다. 범위마다 버전을 쌓고 채택한 버전 하나를 보인다. 저장된 해설은 경로 위에 표시로 보인다. 큰 범위를 물으면 그 안의 작은 해설을 맥락으로 넘기고, 묶음에는 크기 한도를 둔다(넓은 드래그가 지시문을 무한히 키우지 않게). “스택”은 설명 더미가 아니라 줌 이동 기록(되돌아가기)이다. 이 부분은 AI 제안이므로 T3 그림으로 합의한다(규칙은 아래 「범위 해설의 규칙」).
- **다시 쓰는 단위(원문 1의 “매번 재설명하게 하지 말고”).** 해설의 열쇠는 한 실행의 사건 번호가 아니라 **정규화한 선택 범위 + 장소(소스 버전마다 다름) + 가지 모양 해시(4의 3) + 줌 + 장면 질문 + 지시문 버전 + 해설이 의존하는 사실의 정규화 해시 + 피드백 버전**이다. 사실 정규화 규칙은 재사용 시험 전에 정하고, 제외한 값이 해설의 사실·인과에 영향을 주지 않는지는 독립 검토로 확인한다. 그래서 같은 쿼리를 새로 기록해도 열쇠가 같으면 저장한 해설을 그대로 보인다. 이를 위해 기본 해설은 실행마다 다른 값(시각, 트랜잭션 번호)을 쓰지 않고, 코드에 적힌 값(예: `lock_timeout = '3s'`)만 쓴다. 특정 실행의 값으로 설명하는 “실행 해설”은 따로 고를 수 있고, 그 열쇠에는 실행이 들어간다. 열쇠의 어느 하나라도 다르면 저장한 해설을 현재 해설로 보이지 않는다(2026-10-17 더함: 구조가 같다는 것만으로 다시 쓰면 코드·장면·지시문이 달라진 기록에 예전 해설이 붙는다. 작업 지도 항목 검증 1차 f6, 2차 f3에서 범위·사실·피드백 버전을 더함).
- **피드백 두 종류.** 그 범위만(그 범위를 다시 받음)과 전체 문체(지시문 버전을 올리고 모두 다시 받음).
- **기록.** 해설의 버전·피드백·채택은 저장 방식(4)을 따른다. 열쇠와 묶음 해시가 같으면 다시 부르지 않는다.

#### 범위 해설의 규칙(T3, 시안과 함께 합의)

드래그한 범위에 해설이 붙고 쌓이는 방식이다(원문 3의 “쌓이는 문제”). 시안은 이 규칙을 그림으로 보이고, 규칙 자체는 시안마다 같다. 모두 AI 기본값이며, 사용자가 시안을 보고 고칠 수 있다. 결과가 크게 갈리는 두 곳(8의 자동 채택, 3의 줌이 다른 같은 범위)은 시안과 함께 따로 묻는다.

1. **범위의 단위(정규화).** 범위는 경로 하나 위에서, 지금 줌에서 보이는 단계의 연속 구간 [첫 단계, 끝 단계]다. 줌마다 단계가 다르다: L1(시스템)은 장소 사이의 이동, L2(프로세스 안)는 사건 줄, L3(함수·커널)은 함수 호출 구간. 드래그가 단계의 일부만 덮으면 그 단계 전체를 넣는다(바깥쪽으로 맞춤). 클릭 한 번은 단계 하나다. 접힌 반복(「× N」)을 덮으면 반복 전체가 들어간다. 흐리게 보이는 경로 밖 사건(배경 프로세스)은 들어가지 않는다.
2. **범위의 정체.** 정규화한 범위는 줌과 첫·끝 단계의 자리로 적는다. 이 자리는 한 실행의 사건 번호가 아니라 가지 모양(설계 4의 3) 안의 위치라서, 같은 모양의 새 기록에서도 같은 자리를 가리킨다. 두 범위를 견줄 때는 둘 다 가장 깊은 기록 층의 사건 집합(잎 집합)으로 펼쳐서 본다. 이 범위가 설계 6 「다시 쓰는 단위」 열쇠의 첫 항목이다.
3. **같은 범위.** 줌이 같고 잎 집합이 같으면 같은 해설 자리다. 같은 범위를 다시 고르면 새 자리를 만들지 않고 그 자리의 버전 목록을 연다. 잎 집합이 같아도 줌이 다르면 다른 자리로 둔다. 같은 일을 줌마다 다른 깊이로 설명하기 때문이다. 목록에서는 한 묶음으로 나란히 보인다. (사용자 결정 후보: 줌과 관계없이 한 자리로 합칠지)
4. **포함.** 한 범위의 잎 집합이 다른 범위 안에 들어가면 안쪽 해설이다. 바깥 범위의 해설을 받을 때 안쪽 해설의 채택본을 맥락으로 넘긴다. 넘기는 양에는 한도를 두고(값은 T5에서 정함), 바깥 범위에 가까운 것(큰 것)부터 넣고 넘치는 것은 개수만 적는다. 화면에서는 안쪽 표시가 바깥 표시 안에 들어간다.
5. **겹침.** 일부만 겹치면 둘은 서로 다른 자리다. 새 범위를 물으려 할 때 겹치거나 포함하는 해설이 이미 있으면 그 목록을 먼저 보여, 다시 묻지 않고 읽을 수 있게 한다. 겹치기만 하는 해설은 맥락으로 넘기지 않는다(묶음이 넓은 드래그를 따라 끝없이 커지지 않게).
6. **경로 위 표시.** 해설 자리마다 표시 하나. 채택본이 있으면 진하게, 버전만 있고 채택본이 없으면 옅게. 겹치는 표시는 줄을 나눠 쌓는다(시작 순서로, 비어 있는 가장 위 줄에). 보이는 줄 수를 넘으면 「+k」로 접는다. 다른 줌의 해설은 지금 줌의 단계 위에 작은 점으로만 보인다. 해설을 받은 적이 없거나 받기가 모두 실패한 범위는 자리를 만들지 않고 표시하지 않는다(2026-10-17 더함, 「T3 지도 화면 시안」).
7. **목록.** 지금 경로의 해설 목록은 시작 위치 순서, 시작이 같으면 긴 범위가 위다(바깥이 위, 안쪽은 들여 씀). 줄마다 범위(첫 단계 → 끝 단계), 줌, 채택 버전, 버전 수, 상태(현재 / 이전 기록 기준 / 숫자 검사 경고)를 보인다.
8. **버전과 채택.** 처음 받은 버전은 숫자 검사를 통과하면 바로 채택한다(아무 해설도 없는 것보다 낫다는 판단). 그 뒤 피드백과 함께 「다시 설명」으로 받은 버전은 후보로 쌓이고, 사용자가 「채택」을 눌러야 바뀐다. 숫자 검사를 통과하지 못한 버전은 채택할 수 없다. 채택을 내리면 그 자리는 고정 설명으로 돌아간다. 버전은 지우지 않는다(피드백 이력). (사용자 결정 후보: 첫 버전도 사용자가 채택해야 보일지)
9. **열쇠가 달라진 기록.** 새 기록에서 설계 6의 열쇠 가운데 하나라도 다르면 저장한 해설을 현재 해설로 보이지 않는다. 「이전 기록 기준 해설 n개」로 접어 두고, 펼치면 무엇이 달라졌는지(소스 버전, 장면 질문, 사실 등)를 보인다.
10. **공급자가 없을 때와 오류일 때.** 보이는 순서는 채택 해설 → 없으면 고정 설명이다. 공급자가 설정되어 있고 작성 화면일 때만 「받기」·「다시 설명」이 있다. 공급자 설정이 없으면 그 자리에 「공급자 설정 없음」을 흐리게 보이고, 범위 고르기와 저장된 해설 읽기는 그대로 된다. 오류면 고정 설명을 그대로 두고 오류 종류(시간 초과, 명령 실패, 숫자 검사 탈락)만 작게 보이며 「다시 시도」를 둔다. 정적 재생본은 공급자를 부르지 않는다.
11. **“스택”의 뜻.** 원문 3의 “스택처럼 설명을 쌓을지”에 대한 답은 해설 더미가 아니다. 해설은 범위에 붙고, 쌓이는 것은 줌 이동 기록(뒤로 가기로 돌아갈 자리)이다.

### 7. 실시간 입구

지금 흐름은 기록 → 해석 → 재생이다. 실시간 입구는 작업대 서버(E-01)의 실시간 실행을 확장해, 실제 클라이언트가 보낸 요청 하나의 구간만 기록하고 바로 해석해 지도에 올린다. 여러 프로세스·호스트에 걸친 요청(MSA)은 요청을 하나로 엮을 식별자 전달과 시계 맞추기가 필요해 가장 어렵다. T7은 한 호스트에서 브라우저가 보낸 요청까지 다룬다(psql은 덧붙임).

## 설계 비판과 보강

1. **공통 형식이 너무 이르다.** 둘째 주제 없이 형식을 정하면 첫 주제에 맞춘 형식이 된다.
   - 보강: 첫 시험 입력을 한 주제가 아니라 이미 있는 네 종류(요청의 여정, 커널 보기, 트랜잭션 실험, Spring 전파)로 잡는다. 이들은 수집 도구(gdb, 함수 기록, strace, ftrace, JFR, 연결 위 메시지, 관찰)와 층(앱, 풀, 프로토콜, DB 엔진, 커널)이 서로 다르다. 그래도 T6(소켓·커널)에서 형식이 깨지면 T1로 돌아간다.
2. **OpenTelemetry를 그대로 쓰면 된다는 반론.** 구간과 문맥 전달은 MSA에 맞다.
   - 판단: 선례로 확인하되 그대로 쓰는지는 T0에서 정한다. 이 플랫폼은 함수 호출 수만 개, 커널 함수, 한 점 사건(메시지 바이트, 관찰)이 많다. 서비스 사이 요청을 주로 다루는 형식에 그것이 맞는지는 확인하지 않았다.
3. **같은 가지 공유가 시각을 잃게 하고, 그만한 이득이 없을 수도 있다.** 함수 호출 기록은 반복이 많아 일반 압축만으로 충분히 줄어들 수 있다.
   - 보강: 결정을 T2 측정 뒤로 미루고, 기준선으로 “원본 + 일반 압축”을 함께 재며, 복원 시험(바이트 단위 일치)을 판정에 넣었다. 가지 공유는 기준선보다 확실히 작을 때만 쓴다. 다만 가지 모양 해시는 저장과 별개로 설명 층의 열쇠로 쓰인다(설계 6).
4. **AI 해설이 사실처럼 읽힌다.** E-10에서 묶음에 없는 사실 때문에 틀린 표현이 나왔다.
   - 보강: 표지 분리(X2), 숫자 검사, 묶음에 그 범위의 해석기 값을 모두 넣는 규칙. 숫자가 아닌 틀린 해석(“교착 상태”)은 숫자 검사가 못 잡는다. 그래서 T5 판정에 사람 또는 다른 모델의 검토를 넣는다.
5. **실시간과 MSA를 같은 일정에 넣으면 계획이 끝나지 않는다.**
   - 보강: T7은 한 호스트까지. MSA·k8s는 다시 열 조건이 있는 범위 밖으로 둔다.
6. **화면을 먼저 그리면 형식과 어긋난다.** 그림 합의(T3)를 형식(T1) 뒤에 두면 늦고, 앞에 두면 형식이 그림을 못 받칠 수 있다.
   - 보강: T3은 T1과 나란히 시작한다. 그림은 지도 모델(1)에만 기대므로 형식 세부와 독립이다. 그림에서 형식에 없는 것이 나오면 T1에 더한다.
7. **둘째 주제가 같은 프로그램이라 범용성 시험이 약하다.** psql 요청의 커널 경로는 새 층과 새 수집 내용이지만 프로그램은 같다.
   - 보강: C5가 증명하는 범위를 “같은 프로그램의 더 깊은 층”으로 적고, 다른 프로그램 주제 하나를 C8·T8에서 따로 시험한다. 그리고 T6의 실패를 “고치고 다시”로 흡수하지 않고, 플랫폼 변경 건수를 결과로 남긴다.

**T1에 적용할 결정.** 아래는 확인한 원문과 우리 기록의 사정을 함께 놓고 정한 것이다. 원문이 말한 것과 우리 판단은 근거 파일 8절의 D1~D13에 나눠 적혀 있다.

1. **시각(D1).** 정수 나노초, run 시작 기준 상대값으로 둔다. run에는 시작 시각(epoch 나노초)과 시계 종류를 둔다. 지금 기록의 소수 마이크로초(예: `t0` 95.172)는 나노초로 손실 없이 옮겨진다. epoch 나노초를 그대로 쓰면 브라우저 JavaScript가 정수를 정확히 담는 한도(2^53 = 9,007,199,254,740,992)를 넘는다.
2. **구간 한 행(D2·D4).** 들어감·나감 짝은 적재할 때 한 행(`start_ns`, `end_ns`)으로 합친다. 끝을 못 본 구간은 `end_ns`를 비운다. 점 사건은 `kind`로 구분한다(`span`, `instant`, `sample`). 설계 2의 「점이면 시작·끝이 같음」은 이 규칙으로 바꾼다(끝을 못 본 구간과 점이 섞이지 않게).
3. **부모와 깊이(D3).** `parent_event_id`가 정본이고 `depth`는 적재기가 셈해 넣는 사본이다(줌의 깊이 거르기를 한 번의 범위 조회로 하려고). 깊이를 바꾸는 것은 적재기뿐이다. 중첩은 같은 실행 맥락(스레드에 해당하는 장소) 안에서만 뜻이 있다.
4. **연결(D5).** `link(run, src_event, dst_event, kind, basis, attrs)`. 우리 연결은 대부분 ID 전파가 아니라 기록 뒤에 짝지은 것이라, 어떻게 짝지었는지를 `basis`(예: 같은 바이트, 순서, 직접 진입)로 남긴다. 이것이 연결의 출처 표지가 되고 X1(기록하지 않은 경로를 실제처럼 그리지 않음)을 연결에도 적용하는 자리다.
5. **확장 칸(D6).** 구조 칸은 최소(`id`, `run`, `place`, `kind`, `name`, `start_ns`, `end_ns`, `parent_event_id`, `depth`, `source`)로 두고 주제별 값은 `attrs` 한 칸에 둔다. 설계 2의 「주제별 값은 확장 칸 하나」와 같은 결정이다.
6. **장소(D7).** 대리키와 자기 참조(`parent_place_id`) 하나로 시스템부터 함수, 호스트 → 커널 → 커널 함수까지 둔다. pid·tid·컨테이너 id는 `attrs`에 두고 키로 쓰지 않는다.
7. **열린 질문(T1이 실제 기록으로 정함).** 함수·커널 함수 같은 정적 장소를 기록 사이에 공유할지(D8), 관찰(`pg_stat_activity` 등)을 `kind = sample` 사건으로 둘지 별도 표로 둘지(D10).
8. **해설(D11).** 이 조사의 어느 원문에도 정규화한 범위에 붙는 해설의 선례가 없었다. 설계 6과 「범위 해설의 규칙」을 그대로 쓰고, 열쇠를 내용에서 만드는 원리만 git에서 빌린다.
9. **파생 보기와 검사(D12·D13).** 집계 보기(접힌 스택, flame graph)는 질의나 내보내기로만 만든다. T1의 적재 결과를 Chrome JSON으로 내보내 Perfetto UI에서 열면 짝이 틀린 구간이 넘침(overflow) 트랙으로 드러난다. 이 검사는 T1에서 시험한다.

**다시 볼 조건.** 원문을 요약 없이 직접 대조했을 때 위 결정의 근거와 다르면 T1 형식을 대조해 고친다. 지금 알려진 충돌은 Chrome 점 사건의 글자 하나다(Perfetto 문서 요약은 대문자 `I`, Google 문서 요약은 소문자 `i`이고 대문자는 Deprecated). 나머지 조건(Perfetto 시계 동기화, PostgreSQL 와이어 프로토콜에 추적 문맥 자리가 있는지, `longjmp` 경로에서 나감 기록이 빠지는지, 해시 함수 전환)은 근거 파일 9절에 있다.

| 스스로 적은 약점 | 지도 위 거리가 시간이 아님, 호출 깊이가 목록에만 보임 | 같은 층 안의 이동과 공유 메모리가 「더 깊음」으로 읽힘 | 짧은 사건(`pwrite64` 49.5 µs)이 1 px보다 좁음, 장소 사이 관계가 흐려짐 |

외부 모델 비평(디자인 번호를 가리고 받은 순위): 30초 안에 경로와 시간 파악은 B > A > C, 세련됨·밀도 부담·조작 알아보기는 A > B > C. 제안은 “A를 전체 시스템의 첫 화면으로, B를 상세 추적 화면으로”였다. 이 비평은 사람의 판정이 아니며, 선택은 사용자가 한다.

**사용자 의견(원문 10)과 다음 판.** 원문: A가 직관적(넓고 깊은 과정에서 지금 어디에 있는지 보임), 시간과 깊이는 C보다 B, 그러나 B는 선이 너무 많아 구별이 안 됨. 구체화(AI 해석, 다음 그림으로 확인받음): 틀과 시스템 줌은 A, 프로세스 안과 함수·커널 줌은 B의 단면을 선을 줄여 A의 틀 안에 넣는다. B에서 선이 많아진 원인은 셋이다. 사건 하나마다 경로가 목적지 층까지 내려갔다 오는 U자(프로세스 안 화면에 15개 안팎), 고르지 않은 2차 경로의 평행선, 화면 높이를 가르는 출발·도착 세로선과 범위 상자의 테두리. 그래서 다음 판은 고른 경로 한 줄만 그리고(다른 후보는 갈리는 자리의 표지와 비교 단추로), 같은 층으로 갔다 바로 돌아오는 짧은 왕복은 출발 층 위의 작은 표지로 접고, 경로가 지면(시스템 콜 경계)을 건너는 깊은 하강만 선으로 그린다. 관계선은 고른 때만 그린다(리서치의 Perfetto: 흐름 화살표는 사건을 골랐을 때 보임). 초점 단계는 펼치고 먼 단계는 요약한다(Furnas의 관심도). 판정은 그림으로 받는다.

**규칙 보강(시안에서 드러남, AI 기본값).** 「범위 해설의 규칙」 6에 버전이 하나도 없는 범위를 어떻게 보일지가 없었다(B 시안은 회색 점선 괄호로 그렸다). 해설을 받은 적이 없거나 받기가 모두 실패한 범위는 해설 자리를 만들지 않고 경로 위에 표시도 하지 않는다. 오류는 그 순간 해설 패널에만 보인다.

**1. 형식 v0.** 한 run을 JSON 파일 하나로 쓴다. 저장 방식은 T2가 정하므로 이것은 그 전까지의 교환 형식이다. id는 run 안의 정수다.

| `place` | `id`, `parent`, `kind`, `name`, `key`, `loc`(소스 경로, 줄), `source`, `attrs` | 장소 하나 |

형식 규칙은 아래와 같다.

1. 같은 출처의 사건은 기록 순서대로 id가 늘어난다(시각이 없는 gdb 기록의 순서를 지킴).
2. `parent`는 부모와 자식의 출처가 같을 때만 쓴다(그 출처가 정한 포함). 출처가 다른 사건 사이의 묶음(해석기가 정한 요청 창과 기록기가 남긴 서버 사건)은 `link`(kind `contains`, 근거는 해석기 출처)로 둔다. 그래서 관찰 사건의 구조 칸에는 해석기가 셈한 관계가 들어가지 않는다.
3. 부르는 모양의 정본은 한 출처 안의 `parent` 나무다. `contains`는 출처를 건너는 묶음이고, `stack`은 사건 한 순간의 호출 사슬이다. T2의 가지 모양 해시는 `parent` 나무 위에서 장소 `key`의 차례로 만든다. 해시 방식과 예는 T2가 정한다.
4. `place`는 그 일이 실행된 자리다(코드 위치 → 함수 → 프로세스, 연결 위 메시지면 연결). `target`은 사건이 향하거나 다루는 실행 위치이고(이동의 도착 칸, 빌린 연결), `from`은 무엇을 옮기는 사건의 출발 장소다(이동의 출발 칸). 경로 선이 장소를 건너는 자리이고, 짝이 되는 사건이 기록에 없을 때 쓴다. 양쪽 사건이 모두 기록에 있으면 `link`로 잇는다. `from`은 구현 중 더했다(2026-10-18, 형식의 첫 번째 고침): 이동 하나가 실행한 프로세스·코드 자리와 출발·도착 칸을 함께 가져, `place`를 출발 칸으로 쓰면 `place`가 입력마다 다른 뜻(gdb는 코드 위치, 여정은 칸)이 되기 때문이다(5의 2).
5. `group`은 따로 떼어 낼 수 없는 여러 번의 일을 묶은 사건이다(concept-3·4의 합친 이동). `count`가 2 이상이고, 시작과 끝은 처음과 마지막 일의 시각이다. 다른 사건의 `parent`가 될 수 없고, 재생과 호출 차례 계산은 이것을 한 번의 구간으로 쓰지 않는다. 다른 사건의 `count`는 1이다.
6. 시각은 정수 나노초이고 출처가 쓰는 시계의 좌표다(아래 3). 원본의 소수 마이크로초 `x`는 `round(x × 1000)`으로 옮기고, `ns / 1000`이 원본 `x`와 같은지 적재 때 확인한다.

**2. T0 결정에서 더하거나 바꾼 것.**

1. **`attrs`를 출처마다 나눈다:** `attrs = {출처 id: {…}}`. 한 사건에 기록기 값과 해석기 값이 함께 붙어도 값마다 출처가 드러나고, 해석기를 고쳐 다시 적재해도 관찰 값의 비교는 그대로다(재고 조사 5절 함정 5). T0 결정 5는 확장 칸을 하나로 정했고 그 안의 모양은 정하지 않았다.
2. **`stack`을 구조 칸에 더한다.** 장소 id의 목록이고, 있으면 0번은 사건의 장소 자신(가장 안쪽 칸)이고 그 뒤가 바깥쪽으로 부른 쪽이다(형식 검사가 0번 = `place`를 본다). 원본이 바깥 함수부터 적으면(concept-3·4) 적재기가 뒤집고 내보내기가 되돌린다. 0번 규칙은 바깥 검토(셋째)의 지적으로 입력마다 같게 정했다(2026-10-18). gdb BT, uprobe 사용자 스택, JFR 스택, 함수 기록의 스택, concept-3·4의 이동 스택이 모두 이 모양이다. `attrs`에 두면 끝 기준의 '호출 사슬'을 주제를 알아야만 읽는다. Perfetto의 callsite 표(프레임과 부모 callsite)와 같은 생각이다.
3. **프레임 장소를 둔다.** 함수 장소 아래에 '함수 + 소스 경로 + 줄' 장소를 둔다. 스택 칸마다 부른 줄(`at`)이 있어, 함수만 장소로 두면 줄이 사라진다.
4. **`dur_ns`를 더한다.** 시작과 끝을 모르고 길이만 아는 사건(concept-4 커널 마디의 `us`, strace의 시스템 콜 시간 `sysUs`)에만 쓴다. 시작과 끝이 있으면 비워서 같은 사실을 두 칸이 갖지 않게 한다.
5. **`target`, `from`, `group`, `count`를 더한다.** 위 형식 규칙 4·5.
6. **run에 `clocks[]`를 두고 출처가 시계를 가리킨다.** 아래 3.
7. **run에 `coverage[]`를 더한다.** 아래 4.
8. **출처는 run의 `sources[]`에 둔다.** 칸은 `id`, 도구, 판, 시계, 성격(`observed`·`derived`·`inferred`·`human`), 설명이다. 사건과 장소의 `source`, 연결의 `basis`가 이 id를 가리킨다.
9. **장소에도 `source`를 둔다.** 장소가 있다는 주장과 그 이름을 누가 했는지다(기록기가 본 pid, 해석기가 붙인 칸, ps 없이 추정한 역할). 장소의 분류 가운데 층(커널 마디의 `layer` 등)은 그 분류를 붙인 출처의 `attrs`에 둔다. 프로세스의 역할은 여정 적재기를 짜며 역할 장소(kind `role`, 프로세스의 부모, 그 분류를 붙인 출처)로 두었고 트랜잭션 실험도 같게 둔다(2026-10-18 고침). 지도에서 '역할 → 프로세스'가 줌 한 단계라 장소 나무가 맞고, 출처는 장소의 `source`로 남는다. `key`는 정적 장소에만 붙이고 `H(kind, name, loc.path, 부모의 key, 소스 판)`이다. 소스 판은 `workbench.json`의 `sourceRoot`(`/src/postgresql-18.6`)처럼 기록이나 설정에 남은 것만 쓰고, 없으면 `unrecorded`에 적는다.

**3. 시계.** 시계마다 `id`, 정밀도, 다른 시계와의 관계(차이의 범위와 그 근거 출처, 또는 '모름')를 둔다. 관계가 '모름'이거나 범위보다 촘촘한 차이를 두 시계 사이에서 견주면 플랫폼의 비교 함수는 순서를 내지 않고 '견줄 수 없음'을 낸다. Chrome JSON 내보내기는 시계마다 다른 프로세스 묶음으로 나눈다. 아래 투영은 모두 해석기가 이미 한 것이고 원래의 시계 좌표는 기록에 남아 있지 않다.

**4. 빈 값과 관찰 범위.**

- 구조 칸이 비면 뜻은 하나다. `start_ns`가 비면 그 출처가 시각을 기록하지 않는다는 뜻이고 `unrecorded`에 출처와 칸을 적는다. `span`의 `end_ns`가 비면 끝을 보지 못했다는 뜻이다(Spring 트리의 `passed` 54마디). `dur_ns`는 형식 규칙대로 시작·끝이 없을 때만 있다.
- `attrs`의 값은 원본 그대로 둔다(`null`, `""`, 0, 빈 목록). 원본이 뜻을 가르지 못하는 꼴을 적재기가 골라 채우면 없는 사실을 만드는 것이라 고르지 않는다. 대신 알려진 모호함마다 run의 note(kind `ambiguity`)에 경로, 값, 가능한 뜻, 그 꼴을 정한 코드 줄을 적는다. 지금 아는 것: Spring 시각 0(기준 순간과 값 없음, `decode/spring.go` 408~411행), 스냅숏 `xip = null`(0개와 기록 안 됨, `decode/scenario.go` 825~827행), 빌림 `conn = ""`(연결 없이 끝난 timeout 빌림 4건), concept-4 `stack = null` 5건.
- `coverage`는 출처마다 {무엇을(함수 진입, 시스템 콜, 연결 위 메시지, 관찰 등), 어느 장소나 이름을, 어느 구간에서(run 전체 또는 구간), 완전성(`complete`·`partial`·`sampled`), 그 목록의 근거(파일, 추정)}다. 지켜본 함수에 사건이 없으면 '봤고 0번'이고, 목록에 없는 함수는 '안 봄'이다. 재추출에서 해당 기록에 없는 사실(gdb 기록의 연결 위 메시지)은 '해당 없음'으로 낸다.

**5. 입력별 적재 규칙.** 순서는 작은 것부터다(gdb 기록으로 검사 장치 전체를 먼저 돌려 본다). 키마다의 결정은 [`t1-structural-roles.tsv`](evidence/learning-map-20261017/t1-structural-roles.tsv)에 있다(아래 6).

1. **gdb 기록(E-05, 8벌).** 장소는 백엔드 프로세스, 함수, 프레임(함수와 줄). STOP 하나가 `instant` 사건이고 장소는 멈춘 프레임이며 시각은 비운다. BT 줄은 그 사건의 `stack`이다. STOP 순번과 값 글은 기록기 출처의 `attrs`다. 값 글은 원문 그대로 둔다(trace.py 86행이 `식=값`을 공백으로 이어 붙여, 값에 공백이 있으면 감시 목록의 식 없이는 나눌 수 없음. 값 글이 있는 run에 `ambiguity` note). END의 항목 하나는 그 함수 장소의 `sample` 사건이고 횟수만 `attrs`(`hits`)에 둔다. END 한 줄은 trace.py가 끝에 횟수를 한 번 읽은 관찰이고(130행), 항목의 함수는 대응표가 장소로 정했으므로(`$.counts[].function` → `place/target`) run `attrs`에 목록으로 두면 장소가 `attrs`에 숨는다(구현 중 고침, 2026-10-18). 재추출은 이 사건의 횟수를 STOP 사건 수와 견준다. 감시 목록은 파일이나 `#` 줄로 남은 둘만 `coverage`(근거: 파일)에 넣고, 나머지 여섯은 나온 함수로 짐작한 목록을 근거 '추정'으로 넣는다. `#` 설명 줄과 psql 출력은 run의 note다. 기존 파서(`internal/trace`)는 `#` 줄을 건너뛰므로 되돌림 비교는 원문 줄 단위로 한다.
2. **요청의 여정과 커널(concept-4의 11개, concept-3의 2개).** 사건의 `place`는 gdb 기록과 같은 뜻(실행된 자리)이다. 구현을 시작하며 이동 하나가 장소 값을 여섯 가진다는 것(실행한 `pid`와 역할 `proc`, 코드 자리 `site`, 출발·도착 칸 `from`·`to`, 다룬 파일 `files`)을 확인했고, 첫 판의 '출발 칸이 `place`'로는 나머지가 갈 칸이 없어 형식에 `from`을 더하고 이 항목을 다시 썼다(2026-10-18, 형식 규칙 4). 수는 재고 조사 3.4·3.5절과 같은 추출본에서 셌다.
   - 장소: 구성도의 칸(kind `lane`, 해석기 출처), 파일(kind `file`, 그 칸 아래, 기록기 출처), 프로세스(kind `process`, 이름은 pid, 기록기 출처), 역할(kind `role`, `procs`의 열쇠, ps 출처이고 `procsGuess`면 추정 출처)과 그 아래 프로세스, 함수와 프레임(프로세스 아래), 코드 자리(kind `site`, 함수 이름 없이 경로와 줄, 프로세스 아래). 정적 장소(함수·프레임·코드 자리)의 key에서 정적이 아닌 부모(프로세스)는 빈 칸이라, 같은 함수는 어느 프로세스 아래에 있어도 key가 같다(`builder.go`의 `Place`).
   - 질의 하나는 백엔드 프로세스의 `span`(0부터 `endUs`, 해석기 출처)이다. 이 사건의 장소가 그 질의의 백엔드라서 이동의 `proc`는 저장하지 않고, 내보내기가 '이동의 프로세스가 질의의 백엔드면 `backend`, 아니면 `other`'로 다시 셈한다(1,194행 모두 이 규칙과 맞음).
   - 이동 하나는 기록기 출처의 사건이다. `place`는 코드 자리(`site`가 빈 5행은 프로세스), `from`·`target`은 출발·도착 칸, 이름은 `kind`, 시각은 `t0`·`t1`, 스택은 원본 `stack`을 뒤집은 것이다(원본은 바깥 함수부터 적음, 1,189행 모두 `BackendMain`이나 `IoWorkerMain`으로 시작, `null` 5행은 스택 없음과 `ambiguity` note). 합친 이동은 `group`이다. 스택이 있으면 0번은 코드 자리이고 그 뒤가 원본 스택을 뒤집은 프레임이다. 파일이 있으면(198행, 모두 하나) 파일 장소(그 칸 아래)를 출발 칸이 파일 칸(`data_files`·`wal_files`)일 때 `from`에, 아닐 때 `target`에 둔다. 내보내기는 파일 장소의 부모 칸으로 `from`·`to`를 되살리고 파일 이름으로 `files`를 되살린다(출발이 파일 칸 183행, 도착만 15행, 파일 칸인데 파일이 없는 이동 0행). `n`·`stage`·`catalog`는 해석기 출처, `bytes`는 기록기 출처의 `attrs`다.
   - 메시지는 기록기 출처의 사건이고 따로 시각이 없다(`unrecorded`). 이동과 메시지는 `contains` 연결로 잇는다. 첫 판의 '자식 사건'은 합친 이동 둘(select의 `count` 3)이 메시지를 가져 `group`이 부모가 될 수 없어 바꿨다. 송신·수신 이동의 메시지는 그 이동의 바이트를 나눈 것이라 근거가 기록기다. 응답 버퍼에 쓰기 이동의 메시지는 해석기가 뒤따른 송신의 메시지(앞 송신에서 이어진 나머지 뺌)와 수가 맞을 때만 차례로 짝지어 붙인 사본이라(`decode/journey.go` 676~693행, 수가 다르면 붙이지 않음) `contains`와, 송신 메시지에서 사본으로 가는 `copy` 연결의 근거가 추정이다. `cont`(앞 송신에서 시작한 메시지의 나머지)는 앞 송신의 잘린 메시지에서 오는 `continues` 연결이다. `cut`(이 송신에서 메시지가 끝나지 않음: 보이는 바이트 밖으로 이어지거나 선언 길이가 4보다 작음)은 나가는 `continues` 연결이 있거나 그런 메시지의 사본이라는 뜻이라 내보내기가 다시 셈한다. 이어지는 메시지가 없는 `cut`(선언 길이가 틀린 경우 등)은 이 규칙으로 되살릴 수 없어 적재기가 멈춘다(지금 기록에는 없음). 둘은 짝이 아니다(같은 파일 190·213~219·346행).
   - 단계는 해석기 출처의 `instant`이고 장소는 단계 함수(`fn`), 스택은 [단계 함수, 부른 쪽 프레임(`caller`와 부른 줄 `at`)]이다. concept-3에는 `caller`가 없어 스택 1번이 코드 자리(`at`)다. `fn`이 없는 단계(받기, 오류 처리)는 백엔드 프로세스의 사건이다.
   - `sysUs`가 있는 이동(71)은 strace 출처의 시스템 콜 사건(`dur_ns`, 이름과 시각은 미기록)과 `syscall` 연결로 잇는다. 커널 마디는 ftrace 출처의 `span`(`dur_ns`)이고, 장소는 커널 프로세스(`kernelPid`) 아래의 커널 함수와 프레임(`at`이 없는 마디는 함수)이며, 서로의 포함은 `parent`, 시스템 콜 사건과의 짝은 `kernel` 연결이다. `syscall`·`kernel` 연결의 근거는 해석기가 순서와 인자로 맞춘 것이라 추정이다. 커널 층·`guess`·`hidden`·`calls`·`callsOf`는 해석기 출처의 `attrs`다.
   - run의 `attrs`(경로 무리 `$`): 주제가 붙인 `key`·`label`·`typed`·`x`(사람 출처), 질의 글 `data.query`(기록기 출처), 소스 발췌 `data.src`·`data.ksrc`(발췌 출처). 열쇠에 원본의 아래 경로를 적는 것은 run의 경로 무리가 `$` 하나이기 때문이다. `procsGuess`는 역할 장소의 출처 성격으로 나타나 따로 두지 않는다.
   - concept-3의 두 질의는 concept-4의 두 run에 두 번째 해석기 출처(`rec-c3`, `journey-c3`, 사본 짝 `pair-c3`)로 들어간다. 장소는 concept-4가 만든 것을 같이 쓰고(종류·이름·위치·부모가 같은 장소를 찾고, 없을 때만 concept-3 출처로 만듦), 사건을 셀 때는 출처 하나를 고른다. 판정 기준은 두 표시 파일을 합친 것이다(경로가 `$.hops`와 `$.data.hops`로 겹치지 않음). 질의 글은 같지만 pid·끝 시각·이동이 다른 기록(`insert` 셋, `create_index` 둘)은 다른 run이다(재고 조사 3.6절).
3. **트랜잭션 실험(44벌).** 적재기를 짜기 전에 원본을 다시 세어 첫 판(장소는 세션 C1·C2, kill과 멈춤은 `instant`)을 고쳤다(2026-10-18). 세션 이름은 `S1`·`S2`이고, 멈춤은 원본에 `t`·`t1`이 있고 kill은 `t`·`tReady`가 있어 구간이다. 수는 concept-5~8의 44벌에서 셌다.
   - 장소: txlab 장소(kind `client`, txlab 출처)와 그 아래 세션(kind `session`). 서버 쪽은 역할(kind `role`, main 함수로 붙인 분류라 해석기 출처) 아래 프로세스(이름은 pid), 그 아래 함수·프레임·코드 자리. 세션과 백엔드의 짝은 따로 두지 않는다. '단계(세션 장소) `contains` 요청(백엔드 장소)'의 두 장소가 그 짝이고, `sessions[].pid`, `server.procs[].session`, `kills[].session`은 내보내기가 이 짝으로 다시 센다(세션마다 백엔드 하나, 88행 모두 맞음. 하나가 아니면 적재기가 멈춤).
   - 단계는 세션의 `span`(txlab 출처, 보내고 받은 시각)이고 `n`은 X1, 자기 점검 `check`는 해석기 출처의 `attrs`다. 요청은 기록기가 본 `exec_simple_query` 호출 하나다(입구와 반환, `scenario.go` 494~511행). 그래서 첫 판의 '해석기 출처'를 고쳐 기록기 출처의 `span`으로 두고, 장소는 백엔드 프로세스, 이름은 `exec_simple_query`다(구현 중 고침, 2026-10-18). 요청은 세션과 백엔드의 짝을 나르는 단위라(단계 → 요청 연결의 두 장소가 곧 세션과 백엔드) 백엔드 자신에 두고, 아래 서버 함수 구간은 고른 함수에 머문 구간이라 그 함수의 프레임에 둔다. 둘 다 관찰한 입구·반환 짝이지만 무엇의 구간인지가 다르다. 여정의 질의 구간(`query`)도 프로세스 장소에 있어 같은 자리이고, 프로세스 줌에서 백엔드가 요청을 처리한 구간이 보인다. 오류로 끝난 요청 12건은 반환 사건이 없어(longjmp) 해석기가 끝을 단계의 끝으로 채웠으므로 `end_ns`를 비우고, 내보내기가 `t1`을 단계 끝으로, `aborted`를 '끝이 빔'으로 다시 센다(12건 모두 단계 끝과 같고, 끝난 요청 280건은 하나도 같지 않음). 단계와 요청은 `contains`(근거 해석기: 입구가 단계 구간 안인 호출을 고름)로 잇는다.
   - 받은 메시지 `in[]`은 백엔드의 `instant`이고 `from`이 세션, 보낸 메시지 `out[]`은 백엔드의 `instant`이고 `target`이 세션이다. strace 출처(recvfrom·sendto의 데이터를 푼 것, `scenario.go` 524~545행)이고 시각은 미기록이다. 요청과는 `contains`(근거 해석기: 요청 입구 직전의 recvfrom, 창 끝 + 5 ms 안의 sendto)로 잇는다. `out`이 `null`(65행)이면 보낸 메시지가 없다는 뜻이다(빈 목록은 원본에 없음).
   - 요청 안의 사건·스냅숏은 관찰이고 출처는 종류로 갈린다. `kill`·`io`·`sleep_syscall`은 strace(`scenario.go` 529~535행), 나머지는 기록기다. 장소는 가장 안쪽 프레임(원본 스택은 바깥부터라 뒤집음. 828개 모두 `exec_simple_query`나 `BackendMain`으로 시작), 스택이 없는 사건은 백엔드 프로세스다. 줄을 모르는 스택 칸(`at`이 `?`. 요청 안 사건 4개와 서버 사건 144개로, 모두 스택 칸이다)은 위치 없는 프레임이고, 그 부모 함수의 경로는 같은 프로세스의 스택 칸과 서버 함수 구간에서 그 이름이 나온 경로로 찾는다(경로가 둘 이상이면 적재기가 멈춤). 같은 함수가 위치 있는 장소와 없는 장소로 갈리지 않게 하려는 것이고, 줄 판정 안의 부른 함수도 같은 규칙이다. 공통 장부의 `Frame`은 `?`를 받지 않아 이 규칙을 건너뛸 수 없다(구현 중 고침, 2026-10-18). 이름은 `kind`이고 요청과 `contains`(근거 해석기, 창으로 나눔)로 잇는다.
   - 줄 판정은 기록기 출처의 `instant`(이름 `check`)이고 장소는 가장 안쪽 프레임이다. 그 안의 줄 `lines[]`, 판정 경로 `path[]`, 경로 안의 호출 `inner[]`은 같은 출처라 `parent`로 잇는 자식 `instant`(이름 `line`·`path`·`inner`, 시각 미기록)다. `fn`은 부른 함수이고 `at`은 부른 줄이라(예: heapam_visibility.c:977의 `HeapTupleHeaderXminCommitted`) 여정 concept-3의 단계와 같은 꼴로 장소는 부른 함수, 스택은 [그 함수, 부른 줄의 코드 자리]다. `visible`은 해석기 출처의 `attrs`이고, `path = null`(4행)은 경로 사건이 없다는 뜻이다.
   - 서버 사건은 모두 관찰이다. 출처는 종류대로 기록기(redo·clog·bg_flush·wal_flush·async_lsn·hint_fpi), strace(wal_io·signal·exit), server.log(log)이고, 기록기 사건 가운데 함수 기록에 짝이 없어 ftrace 시각을 옮겨 쓴 것(`f.clock = ftrace`, 541행, `scenario_server.go` 449~505행)은 같은 uprobe 관찰을 `ftrace-shifted` 시계로 적은 출처다. 옮긴 것은 시각의 좌표이지 사건이 아니다. `f.clock`은 사건 출처의 시계로 다시 센다. 서버 함수 구간은 기록기 출처의 `span`이고 장소는 함수 입구 프레임(위치는 함수가 정의된 줄, `scenario_server.go` 293행)이다. 프로세스 수명(`t0`·`t1`)은 처음과 마지막으로 본 기록(함수 기록, 관찰용 접속은 strace)과 strace의 끝 줄이라 관찰 `span`이고, 역할만 해석기 출처의 역할 장소다.
   - 관찰은 txlab 장소의 `sample`이고 읽기 구간은 자식 `span`(이름은 부분)이다. 마지막 관찰의 마지막 부분은 해석기가 끝을 몰라 끝을 시작과 같게 둔 것이라(`scenario.go` 560행) `end_ns`를 비우고, 내보내기가 시작으로 되돌린다. `afterStep`은 관찰 → 단계의 `after` 연결(0은 첫 단계 앞이라 연결 없음), `afterKill`은 관찰 → kill의 `after` 연결이다(근거 txlab).
   - kill은 txlab 장소의 `span`(`t`부터 `tReady`)이고 `target`은 죽인 백엔드, `beforeStep`은 kill → 단계의 `before` 연결이다. `walWrittenT`는 kill 전에 끝난 pg_wal 쓰기 가운데 쓴 범위의 끝(LSN)이 가장 먼 것의 끝 시각이다(`scenario_server.go` 591행 `walExtentBefore`: WAL은 앞에서부터 차례로 쓰므로 가장 먼 끝이 쓴 끝. 시각으로 마지막인 쓰기와 다를 수 있다). 그 쓰기 사건과 잇는 `wal` 연결(근거 해석기)로 두고 그 사건의 끝으로 다시 센다. 그 사건은 서버 사건 `wal_io`(4행)나 요청 안 사건 `io`(2행) 가운데 해석기처럼 `pg_wal/` 아래 파일에 쓴 `pwrite64`·`pwritev`이고 끝이 `walWrittenT`와 정확히 같은 것 하나이며, 그 쓰기가 닿은 위치 `lsn1`이 `walWritten`과 같아야 한다(6행 모두 맞음). 없거나 둘 이상이거나 위치가 다르면 적재기가 멈춘다. 위치까지 보아 끝 시각만 우연히 같은 다른 쓰기에 연결이 붙지 않는다(검토 의견으로 더함, 2026-10-18). 멈춤은 txlab 장소의 `span`이고 `before` 연결을 가진다.
   - 힌트 변화는 추정 출처의 `instant`다(`via`가 주소나 값으로 맞춘 설명이고 `by`가 추정, 재고 조사 3.3.6절 1). 장소는 코드 자리(`at`, SetHintBits를 부른 줄)이고 그 부모가 `by` 세션의 백엔드다. 같은 종류·위치·부모의 장소가 이미 있으면(판정 경로의 SetHintBits가 만든 코드 자리) 출처와 상관없이 그것을 쓰고, 없을 때만 힌트 출처로 만든다(여정 concept-3과 같은 규칙). 힌트는 관찰 다음에 적재해 추정 장소가 관찰 장소를 먼저 차지하지 않는다. `step`은 단계 → 힌트의 `contains` 연결이다(18행은 `by`와 그 단계의 세션이 달라 `by`로 다시 셀 수 없음).
   - 관찰 대상이 아닌 백엔드의 요약 `bystanders[]`는 해석기 출처의 `sample`(시각 미기록)이고 장소는 그 프로세스다. 표 정의 `tables`, 행 주소 `tupleAddrs`, 시계 맞춤 `clock`·`joins`, 자리 고침 `siteRepair`, 소스 발췌 `src`는 run `attrs`다.
   - 출처는 열둘이다. 관찰: `txlab`, `recorder`(함수 기록기·uprobe), `recorder-span`(입구·출구 짝의 서버 함수 구간), `uprobe-ftrace`(`ftrace-shifted` 시계), `strace`, `serverlog`(`serverlog` 시계), `server`(프로세스 수명), `src`(소스 발췌). 도출: `tx`(해석기의 규칙과 판정). 추정: `tx-hint`. 사람: `topic`(장소 이름), `pgsql-topic`(스냅숏 `xip`의 `null`이 진행 중 0개인지 기록하지 못한 것인지 원본이 가르지 않는다는 ambiguity note, `decode/scenario.go` 824~827행).
   - 미정 경로 30개는 대응표에 정했다(같은 날 커밋).
4. **Spring(E-03, 14벌).** 장소는 연결(C1, C2), 앱 스레드, 백엔드 프로세스, 자바 메서드, PostgreSQL 함수와 프레임. 연결 위 메시지 하나는 `mac` 시계의 사건(`t`)과 `container` 시계의 사건(`tc`) 둘과 그 사이의 `message` 연결이다(두 흐름을 맞춘 것은 해석기라 근거는 해석기). 멈춤 자리도 시계마다(`t`, `tGo`, `tCapture`) 사건 하나씩이고 `same` 연결로 잇는다. 요청 묶음과 서버 창은 해석기 출처의 `span`이고, 서버 사건·스냅숏·줄 판정은 기록기 출처의 백엔드 사건으로 서버 창과 `contains`로 잇는다. 트랜잭션은 해석기 출처의 `span`이고 처음·마지막 요청과 `contains`, 뒤따른 메시지와 `next`, 서버 사건 사본(`xids`, `clog`)은 원래 사건과 `copy` 연결이다. JFR 구간은 관찰 `span`이고 `parent`를 두지 않는다. 호출 트리 `view.tree`는 해석기 출처의 `span`으로 따로 두고 그 안의 포함을 `parent`로 둔다(트리에는 스택에만 나온 메서드의 마디가 섞여 JFR 구간과 하나씩 맞지 않고 원본에 마디와 구간의 대응이 없다, `decode/spring_tree.go`의 `buildCallTree`). 효과는 트리 마디의 자식 `instant`, 빌림은 앱 스레드의 사건이고 빌린 연결이 `target`이다. 관찰 도중 지나간 메시지(`overlap`)는 메시지 사건과 `overlap` 연결이다. 미정 경로 44개는 이 적재기를 짜기 전에 정해 커밋한다.

**7. 출처 성격과 추정 목록.** 표시 파일의 출처 칸은 관찰·도출·이름 셋뿐이라 `derived`와 `inferred`를 가르지 않는다. 여기서 `derived`는 기록 사실에서 정해진 규칙으로 셈한 값(합친 수, 요청 창, 트리 만들기)이고, `inferred`는 틀릴 수 있는 짝짓기와 짐작이다. 구현 전에 정한 `inferred` 목록: 빌림(100 ms 창으로 JFR 구간에 연결을 붙임), 기다림 고리의 `heldBy`·`cycle`, 값으로 맞춘 힌트 설명(`via = value`), 커널 마디의 `calls`·`callsOf`·`guess`, `procsGuess`인 역할표, 파일로 남지 않은 감시 목록 여섯, 순서나 인자로 맞춘 메시지·시스템 콜·커널 짝, 갈림에서 길을 정한 것의 판단(화면이 '추론'으로 적는 자리, 재고 조사 2.5절 831행). 검사 4는 이 목록에 든 사건·장소·연결·관찰 범위의 출처가 `inferred`인지도 본다(감시 목록은 사건이 아니라 `coverage`라, 관찰 범위도 검사에 넣음. 구현 중 고침, 2026-10-18). 해석기가 정한 규칙으로 만든 연결 가운데 표시 파일에 맞는 경로가 없는 것(단계 → 요청, 요청 → 사건·메시지의 창 묶음, kill → 마지막 WAL 쓰기)은 경로 무리를 `rule:`로 시작하는 이름으로 두고, 검사 4는 그 무리의 근거가 `derived`인지 본다. 추정 짝이 `topic:` 무리와 추정 목록으로 검사받는 것과 같은 자리다(트랜잭션 실험 적재기 앞에 더함, 2026-10-18).

**8. 화면만 들고 있는 사실의 자리.** 데이터 literal 밖에서 화면이 들고 있는 상수(재고 조사 5절 함정 9)는 주제 디렉터리의 자료 파일로 옮긴다. 구성도(`REL`, `LANES`, `LANE_OF`, `NODES`, `ZONES`, `FORK`, `STAGES`·`SHORT`, `KLAYER`, `SYSKINDS`)는 `layout.json`, 장면 목록(`TOPIC.scenes`, `LABEL`, `TITLE`)은 `scenes.json`, 소스와 프로토콜에 대한 주장과 범례·용어 글(`LOGKO`, `MASK`, `MODE`, `MXST`, `HINT`, `OPER`, `ROLE`, `SPANKO`, `PART`, `MSG`의 이름, `KLAYER_ROLE`, `KWAIT`, `KSRC_NOTE`, `KTIME_NOTE`, `END`, `LENSES`, `TOPIC`의 범례와 용어 풀이, app.js 216·322행과 index.html의 안내 글)은 고정 설명 `fixed.json`이다. 옮긴 값은 화면 파일의 선언을 JavaScript로 평가한 값과 같은지 견준다(검사 6). 이 대조만 node로 한다. JavaScript literal을 가장 정확히 읽는 것은 JavaScript 엔진이고, Go에는 새 의존성 없이 쓸 엔진이 없다(작업대 도구는 Go라는 원칙의 예외, 검증 전용). 색 값과 기호(`MSGCOLOR`, `WHYCOLOR`, `WHYGLYPH`, `MSG`의 색, 칸 색)는 기록이나 소스에 대한 사실이 아니라 표시 방식이라 옮기지 않는다. 구성도의 좌표는 주제의 배치라 옮긴다. 화면이 다른 상수로 셈하는 값(`X`, `W`, `SCS`, `PROC`, Spring의 `LANES`)은 셈 규칙이라 옮기지 않는다. 그 밖의 빈 목록·`null`·0회는 모두 값이므로 옮긴다. 구현하며 정한 것(2026-10-18): 자료 파일의 모양은 `{화면 파일: {상수 이름: 값}}`이라 값마다 어느 화면의 어느 선언에서 왔는지가 남는다(두 화면의 `REL`·`LANES`는 합치지 않음. 합칠지는 T4가 소비하며 정함). 목록에 없던 둘을 더했다. concept-4의 `BAR`는 처리 단계 막대의 좌표라 구성도이고(단계 마디 `st0~7`은 `BAR`·`STAGES`·`SHORT`로 셈해 옮기지 않음), Spring의 `TOPIC.lanes`는 칸 목록이라 구성도다(색만 뺌). `TOPIC.title`은 장면 무리의 제목이라 `scenes.json`이다. 옮기지 않은 상수는 까닭과 함께 검사 스크립트의 `EXCLUDED` 한 곳에 있다: 기록 데이터(`RUNS`, `QUERIES`, concept-3의 `DATA`), 다른 상수로 셈하는 값(`SCS`, concept-4의 `DATA`, Spring의 `LANES`·`PROC`), 표시 방식(색·기호, 줄 높이와 칸 폭 `ROW`·`LANE`·`SEQ`, 시간 막대 크기 `SCRUB`, 브라우저 저장 열쇠), `TOPIC`의 함수 11개. app.js의 두 글과 index.html의 안내 글 다섯은 선언이 아니라 `text` 목록으로 두고, 화면 파일에 글자 그대로 있는지 본다.

**9. 검사.** 아래가 모두 통과해야 T1 체크를 낸다.

1. **되돌림 비교.** 기록마다 `내보내기(적재(원본))`가 원본과 같음(gdb 기록은 원문 줄이 같음). 차이 목록은 비어야 한다. 원본이나 원본 조각을 `attrs`에 통째로 두는 길은 검사 3이 막는다.
2. **형식 검사.** 참조가 모두 풀림, 장소 사슬과 부모 사슬에 고리 없음, `depth`가 부모 사슬로 셈한 값과 같음, 같은 출처일 때만 `parent`, `group`은 부모가 아님, `attrs`의 키가 모두 출처 id, 시각이 있으면 시작 ≤ 끝, 시작·끝과 `dur_ns`가 함께 있지 않음, 시계가 다른 사건의 비교는 관계 범위 안에서만. 적재 결과를 Chrome JSON으로 내보내 같은 장소의 구간이 서로 어긋나 겹치지 않는지(Perfetto의 넘침 트랙이 드러내는 것) Go 시험으로 보고, 가능하면 Perfetto UI에서도 연다. 이 검사가 볼 것이 있는 입력은 트랜잭션 실험뿐이다. gdb 기록은 시각이 없고, 여정은 장소마다 시각 있는 구간이 하나다(질의 구간. concept-3의 두 번째 해석은 같은 구간). 그래서 시험은 트랜잭션 실험 44벌에서 어긋남 0과, 포개진 구간 하나를 밀어 어긋나게 한 사본에서 그 구간을 찾는지를 보고, 실행 명령도 어긋남이 있으면 쓰지 않는다(구현 중 정함, 2026-10-18).
3. **구조 숨김.** 각 기록의 `attrs` 맨 윗단 키가 허용 목록 안에 있음. 허용 목록은 표시 파일에서 그 기록 무리의 그 키가 구조 아닌 역할(값·출처·발췌·이름·모음)인 키와, 6의 대응표에서 예외 부류(X1~X7)를 받은 키다. 구조 칸 결정을 받은 키, 표시 파일에 없는 키는 실패다. 구조 아닌 역할이어도 그 아래 경로(표시 파일에서 그 키 경로 뒤에 `.`이나 `[`가 이어지는 경로)에 예외 부류가 아닌 구조 역할이 있으면 실패다. 모음(`$.steps`, `$.counts`)을 통째로 두면 그 안의 장소·사건이 숨기 때문이다(구현 중 고침, 2026-10-18). 변이 시험: `t`를 남긴 적재와 원본 객체 조각을 통째로 넣은 적재가 각각 실패.
4. **출처 성격.** 6의 대응표의 출처 칸과 7의 추정 목록이 사건·장소·연결·관찰 범위의 출처 성격과 맞음. 변이 시험: 연결 근거 하나를 `observed`로 바꾼 적재가 실패.
5. **주제를 모르는 재추출.** 플랫폼 패키지(주제 패키지를 가져오지 않음)가 주제 디렉터리의 선택 규칙만 받아, 기록마다 화면이 보이는 단계 수(gdb STOP과 END, 이동 줄과 단계, txlab 단계, Spring 요청과 트리 마디), 연결 위 메시지(종류·길이·방향·순서), 기다림(ProcSleep 입구·출구, `view.waits`, 막힘 관찰, JFR 잠듦, 커널 잠듦 함수), 결과 값(psql 출력, 잔액 시작·끝, 관찰한 행 버전)을 출처 성격과 함께 뽑는다. 원본 JSON에 같은 화면 함수의 규칙을 적용해 셈한 값과 같아야 한다.
6. **화면 상수 대조.** 8의 주제 자료 파일이 화면 파일의 선언 값과 같음(색 값 제외). 반대 방향으로, 화면 파일의 대문자 상수(속성마다 옮기는 `TOPIC`은 속성)가 모두 자료 파일에 있거나 `EXCLUDED`에 까닭과 함께 있음. 명령은 `node topics/pgsql/check-screens.mjs`이고, 다르면 차이를 쓰고 종료 코드 1이다. 변이 일곱(값·좌표·글 바꿈, 상수·장면 뺌, 색 넣음, 화면에 새 상수)이 모두 실패한다(2026-10-18).

그 뒤 만든 쪽이 아닌 검토자가 코드와 결과를 읽고(구조가 `attrs`에 숨지 않았는지, 출처 표시, 내보내기가 적재 결과 밖의 것을 읽지 않는지), 답 전문과 지적마다 처분을 남기고 X1~X6을 확인한다.

**10. 디렉터리.** 플랫폼은 `workbench/internal/atlas/`(형식과 형식 검사, 시계 비교, 구조 숨김·출처 성격 검사, 주제를 모르는 재추출, Chrome JSON 내보내기)이고 주제는 `workbench/topics/pgsql/`(입력별 적재기와 내보내기, 실행 명령, `layout.json`·`scenes.json`·`fixed.json`, 재추출 선택 규칙, 원래 화면 규칙의 계산과 시험)이다. 실행 명령도 주제 쪽에 두어 주제를 더할 때 플랫폼을 고치지 않는다(T6의 판정 방법). Spring 장면은 v0에서 pgsql 주제 안의 장면 무리로 둔다. 다시 열 조건: T6에서 둘째 주제를 붙일 때 Spring이 따로 서야 경계가 맞으면 나눈다. 적재 결과(약 20 MB, 다시 만들 수 있음)는 저장소에 넣지 않고 `database/postgresql/scripts/.lab-tmp/atlas/`에 쓴다.

**11. 하지 않는 것.** 저장 방식과 가지 공유(T2), 지도 화면(T4), 원시 `.bin`이 지워진 기록의 재해석(재고 조사 5절 함정 11: '빠진 사실 0'의 기준은 해석 결과 JSON과 `.trace` 원문이다). 트리 마디와 JFR 구간을 짝짓는 연결은 원본에 없어 만들지 않는다.

**12. 예상과 다시 짠 계획.** 처음 예상 480분은 입력 규모를 모르고 잡았다. 남은 일의 어림은 설계 고침과 재검토 60분, 적재기와 내보내기 600분(내보내기가 구현을 40%쯤 늘림), 비교 180분, 검토와 처분 120분이고, 이미 들어간 약 400분(T3과 나란히)과 합쳐 약 1,350분이다. 장치는 예상을 넘기 전의 초과 기록을 받지 않아, 480분을 넘을 때 이 계획으로 기록한다. 10-18 04:40에 484분이 되어 초과를 기록했고, 새 예상은 이 어림이 아니라 실제로 정했다(780분). 장치의 분은 T0·T3과 나란히 흐른 벽시계이고, 적재기 셋은 03:13~04:39 커밋 사이에 끝나 위 600분 어림보다 훨씬 빨랐다. 남은 일은 Spring 적재기 120분, 주제 자료 파일과 검사 6 45분, 코드 검토와 처분 45분, 검토 뒤 고침 여유 60분, 체크 제출 10분이다.

#### 검증과 등록

## 부록: 설명 공급자 첫 시험(E-10)

2026-10-17, 이 세션의 작업 폴더에서 실행했다. 명령은 `claude -p --model sonnet --setting-sources local --strict-mcp-config --no-session-persistence --output-format json`이고, 지시문(system prompt)은 다음이다.

> 당신은 백엔드 학습 도구의 해설자입니다. 주어진 사실만 쓰고, 사실에 없는 숫자나 이름을 만들지 않습니다. 해석은 문장 끝에 [추론]을 붙입니다. 한국어 합니다체로 3문장 이내, 처음 배우는 백엔드 개발자가 이 단계가 장면 질문에서 왜 중요한지 알게 씁니다.

넘긴 사실 묶음(Spring 「REQUIRES_NEW · 같은 행」 장면 실행 a, +1,026 ms 단계):

```text
[장면 질문] REQUIRES_NEW 안쪽이 바깥이 이미 고친 같은 행을 고치면 어떻게 되나?
[코드] lab/Inner.java 39: jdbc.update("UPDATE acct SET balance = balance + 10 WHERE id = 1");
[단계] +1,026 ms · C2 백엔드(pid 4688)가 트랜잭션 번호 754를 받음 → 1번 행은 753이 고치는 중(TM_BeingModified) → 753이 끝나기를 기다림(XactLockTableWait) [함수]
[그 순간 상태] main은 C1(753)을 떼어 둔 채 쥐고 C2의 응답을 기다림 [JFR]. C1 백엔드 4679는 idle in transaction [관찰]. 안쪽 코드가 SET LOCAL lock_timeout = '3s'.
[호출 깊이] 0 TransactionInterceptor.invoke → 2 Outer.requiresNewSameRow → 5 Inner.requiresNewSameRow → 6 JdbcTemplate.update → 8 QueryExecutorImpl.execute
[지금 고정 문장] C2 백엔드가 753이 끝나기를 기다림
```

받은 해설(모델 `claude-sonnet-5-5`, 한 번, 모델 시간 7.2초, 명령 전체 11초 중 3초는 표준 입력 대기, CLI가 보고한 비용 $0.118):

> C2 백엔드(4688)가 번호 754를 받았지만, 같은 1번 행을 753(바깥 C1)이 아직 고치는 중이라 753이 끝나기를 기다립니다. 바깥 트랜잭션은 커밋 전이고 main이 C2의 응답을 기다리며 C1을 쥐고 있어서(C1 백엔드 4679는 idle in transaction), 서로 풀어 줄 수 없는 교착 상태가 됩니다 [추론]. 안쪽의 lock_timeout 3s가 이 대기를 끊어 줄 유일한 출구이므로, 이 장면 질문의 답은 "무한정 막히지 않고 3초 뒤 잠금 오류로 끝난다"가 됩니다 [추론].

판정: 숫자와 식별자(4688, 754, 753, 4679, 1번 행, 3초)는 모두 묶음 안에 있다. 그러나 “교착 상태”는 기록과 어긋난다. 같은 기록에서 PostgreSQL의 교착 검사는 +2,033 ms에 NoDeadlock으로 판정했다(고리의 절반이 서버 밖, 앱 안에 있기 때문). 묶음에 그 사실을 넣지 않아 생긴 오류이고, 숫자 검사로는 잡히지 않는다. 그래서 T5는 묶음에 그 범위의 해석기 값을 모두 넣는 규칙과 사람·다른 모델의 검토를 함께 둔다.
