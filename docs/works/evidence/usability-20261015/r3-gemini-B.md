### C1. 'REQUIRES_NEW · 같은 행' 장면에서 안쪽(REQUIRES_NEW) UPDATE는 어느 연결로 갔나요? 그 순간 바깥 트랜잭션의 연결은 어디에, 어떤 상태로 있었나요?

- **안쪽 UPDATE의 연결**: **C2 연결**로 갔습니다. [화면에서 확인: 장면 'REQUIRES_NEW · 같은 행', 위쪽 그림판 `Spring 트랜잭션` 칸의 `스레드에 묶인 연결 C2`, `pgjdbc` 칸의 `PgConnection C2` 아래 `8 execute(...)`, 그리고 `PostgreSQL 18.6` 칸의 `C2 · pid 4688` (xid 754)]
- **그 순간 바깥 트랜잭션의 연결 위치와 상태**:
  - **위치**: Spring 트랜잭션 매니저에서 스레드로부터 잠시 내려둔 상태이며, HikariCP 풀 입장에서는 여전히 대여(빌려준) 중으로 잡혀 있습니다. [화면에서 확인: 위쪽 그림판 `Spring 트랜잭션` 칸 `떼어 둔 연결 C1 [추론]`, `HikariCP` 칸 `C1 빌려줌 [추론]`]
  - **상태**: DB(PostgreSQL) 엔진 관점에서는 1번 행(kim)을 수정한 트랜잭션을 열어둔 채 클라이언트(앱)의 다음 명령을 기다리는 **`idle in transaction` (대기 상태 `Client/ClientRead`, 트랜잭션 번호 `xid 753`)**으로 머물러 있었습니다. [화면에서 확인: 위쪽 그림판 `PostgreSQL 18.6` 칸의 `C1 · pid 4679`, 줄 시각 `+2,653 ms`, "idle in transaction · Client/ClientRead · xid 753", 그리고 '기다림의 고리' 상자 ③ 설명]

### C2. 같은 장면에서 안쪽 UPDATE는 왜 진행되지 않았고, 어떻게 끝났나요? DB는 왜 이것을 교착(deadlock)으로 보지 않았나요?

- **안쪽 UPDATE가 진행되지 않은 이유**: 바깥 트랜잭션(C1, xid 753)이 이미 1번 행을 수정하여 행 배타 락을 쥐고 있는 상태에서, 안쪽 트랜잭션(C2, xid 754)이 같은 1번 행을 수정하려 했기 때문에 DB 엔진에서 C1의 트랜잭션이 끝나기만을 기다리는 **`Lock/transactionid` (753 대기)** 상태로 멈췄습니다. [화면에서 확인: 위쪽 그림판 `PostgreSQL 18.6` 칸 `C2 · pid 4688` "지금 753 끝나기를 기다리는 중 · active · Lock/transactionid · xid 754", 우측 패널 '막힌 동안 찍은 관찰' "C2 → transactionid 753 ShareLock"]
  - 그런데 xid 753을 끝내줄(커밋/롤백할) 유일한 주체인 `main` 스레드는 지금 C2의 UPDATE 실행 응답(`QueryExecutorImpl.execute`)을 기다리느라 블로킹되어 있었습니다. [화면에서 확인: '기다림의 고리' 상자 ① 설명]
- **어떻게 끝났는가**: 안쪽 코드에 설정된 `SET LOCAL lock_timeout = '3s'`에 의해 3초 동안 락을 얻지 못하고 타임아웃되어, DB 서버로부터 `55P03 (canceling statement due to lock timeout)` 오류를 받고 끝났습니다. [화면에서 확인: '기다림의 고리' 상자 "끊은 것: C2의 lock_timeout 3s -> 오류 55P03", 타임라인 줄 시각 `+4,033 ms` 연결 위 메시지 `C2 · E 55P03 · Z(E)`]
  - 이후 `+4,037 ms PSQLException`과 `+4,045 ms UncategorizedSQLException`이 터지며 C2 롤백, C1 롤백 순으로 종료되었습니다. [화면에서 확인: 상단 주요 순간 칩 `+4,037 ✕ PSQLException`, `+4,046 C2 ROLLBACK`, `+4,053 C1 ROLLBACK`]
- **DB가 이것을 교착(Deadlock)으로 보지 않은 이유**: PostgreSQL의 교착 검사기는 서버 내부의 락 대기 관계만 검사하는데, DB 서버 관점에서 C2는 C1(753)을 기다리고 있지만, C1은 DB 안에서 다른 락을 기다리는 것이 아니라 단순히 클라이언트의 다음 소켓 패킷을 기다리는 상태(`idle in transaction`, `Client/ClientRead`)였기 때문입니다. [화면에서 확인: '기다림의 고리' 상자 "서버의 교착 검사는 서버 안의 락 기다림(②)만 보고 ①·③은 앱 안의 일이라 보지 못함 [추론] · 교착 검사 결과 NoDeadlock [함수 기록]", 타임라인 `+2,033 ms` "교착 검사 -> NoDeadlock"]
  - 즉, 대기 고리가 DB 안에서 닫히지 않고 자바 애플리케이션 스레드(main)에서 닫혔기 때문에 DB 데드락 감지기가 작동하지 않았습니다. [화면에서 확인: '기다림의 고리' 상자 "고리가 main에서 닫힘"]

### C3. 'REQUIRES_NEW · 풀 1칸' 장면에서 풀이 한 칸이면 무슨 일이 일어나나요? 그동안 DB 서버로 무엇이 갔나요?

- **풀이 한 칸일 때 일어나는 일**: 바깥 트랜잭션이 풀의 유일한 커넥션(C1)을 빌려서 쥐고 있는 상태에서, 안쪽 REQUIRES_NEW가 새 트랜잭션을 열기 위해 `HikariPool.getConnection()` -> `ConcurrentBag.borrow`를 호출하여 풀의 빈자리를 기다리며 무한 대기(잠듦)에 빠집니다. [화면에서 확인: 장면 'REQUIRES_NEW · 풀 1칸', 타임라인 줄 시각 `+587 ms ~ +2,590 ms`, '기다림의 고리(풀)' 상자 ① `ConcurrentBag.borrow에서 잠듦`]
  - C1을 풀에 돌려주어야 할 유일한 주체인 `main` 스레드 자신이 풀 대기에 갇혀 버렸으므로 앱 내부에서 "자기 자신과의 교착(데드락)"이 발생합니다. [화면에서 확인: '기다림의 고리(풀)' 상자 "고리가 main에서 닫힘: 빈 칸이 나오려면 C1가 풀로 돌아와야 하는데, 돌려줄 스레드가 바로 이 기다림 안에 있음 [추론]"]
  - 결국 2,000ms 동안 대기하다가 HikariCP 풀 타임아웃(`connectionTimeout 2,000 ms`)이 발생하여 `SQLTransientConnectionException`이 던져지고, 스프링이 C1을 다시 묶은(`doResume`) 뒤 C1 트랜잭션을 롤백하고 `CannotCreateTransactionException`을 뱉으며 종료됩니다. [화면에서 확인: 타임라인 줄 시각 `+2,592 ms`, 우측 패널 "SQLTransientConnectionException: Connection is not available, request timed out after 2004ms"]
- **그동안 DB 서버로 무엇이 갔는가**: **아무것도 가지 않았습니다 (0개, 연결 위 메시지 없음).** [화면에서 확인: '기다림의 고리(풀)' 상자 "이 기다림은 앱 안(풀)의 일이라 DB 서버는 모름(그동안 연결 위 메시지 없음) [추론]", 타임라인 `+587 ms ~ +2,592 ms` 구간의 `연결 위 메시지` 열이 완전히 비어 있음, 위쪽 그림판 `C1 · pid 4899` 칸 "idle in transaction · Client/ClientRead", `C2 없음` 칸 "풀이 1칸이라 열리지 않음"]

### C4. 'REQUIRED · 안쪽이 실패' 장면에서 안쪽이 실패했는데, 왜 바깥은 UnexpectedRollbackException으로 끝나나요?

- **이유**:
  1. 안쪽 메서드(`Inner.requiredFails`)에서 `IllegalStateException`이 발생했을 때, 안쪽은 새 트랜잭션을 만든 것이 아니라 바깥 트랜잭션에 참여한 상태(`isNewTransaction() == false`)이므로 직접 DB에 ROLLBACK을 보내지 않고, 스프링 트랜잭션 매니저가 트랜잭션 상태 객체에 **`롤백 전용 표시(doSetRollbackOnly)`**만 남깁니다. [화면에서 확인: 장면 'REQUIRED · 안쪽이 실패', 타임라인 줄 시각 `+822 ms`, 우측 패널 `DataSourceTransactionManager.doSetRollbackOnly`, "한 일: 롤백 전용 표시(연결 위로는 보내지 않음)"]
  2. 바깥 메서드(`Outer.required`)는 안쪽의 예외를 `try-catch`로 정상 포획(`outer-caught`)했기 때문에 정상 종료되어 스프링 인터셉터가 커밋(`AbstractPlatformTransactionManager.commit`)을 시도합니다. [화면에서 확인: 타임라인 줄 시각 `+822 ms 앱: outer-caught`, `+1,235 ms AbstractPlatformTransactionManager.commit`]
  3. 하지만 스프링은 커밋을 진행하기 직전에 트랜잭션이 이미 `rollback-only`로 표시되어 있음을 감지하고, 커밋 대신 강제로 롤백(`processRollback` -> `doRollback` -> DB로 `C1 ROLLBACK` 전송)을 수행합니다. [화면에서 확인: 타임라인 줄 시각 `+1,236 ms QueryExecutorImpl.execute` "C1 · P B E S · ROLLBACK (S_1)"]
  4. 롤백을 마친 후, 호출자는 정상 처리를 기대했으나 내부적으로 강제 롤백되었음을 명시적으로 알리기 위해 스프링이 **`UnexpectedRollbackException: Transaction rolled back because it has been marked as rollback-only`**를 생성하여 바깥 호출자에게 던지기 때문입니다. [화면에서 확인: 타임라인 줄 시각 `+1,241 ms`, 우측 패널 `AbstractPlatformTransactionManager.processRollback`의 "한 일" 설명]

### C5. '0.5초 안에 다시 빌림' 장면에서 HikariCP는 연결을 빌려줄 때마다 연결이 살아 있는지 검사하나요?

- **답변**: **아닙니다. 매번 검사하지 않습니다.** [화면에서 확인: 장면 '0.5초 안에 다시 빌림', 상단 주요 순간 칩 및 타임라인]
- **상세 근거**:
  - 첫 번째 빌릴 때(줄 시각 `+8.85 ms`): 풀에서 C1을 빌린 뒤 `+8.93 ms`에 생존 검사(`PoolBase.isConnectionDead` -> `isValid` -> DB로 빈 질의 `Q ""` 전송)를 수행했습니다. 이때 타임라인 설명에 **`풀에서 C1 빌림 · 쉰 지 1,225 ms > 창 500 ms -> 생존 검사`**라고 명시되어 있습니다. [화면에서 확인: 타임라인 줄 시각 `+8.85 ms` `ConcurrentBag.borrow`]
  - 두 번째 빌릴 때(줄 시각 `+132 ms`): 첫 번째 트랜잭션이 끝나고 커넥션을 반납한 지 불과 몇 밀리초 만에 다시 빌렸는데, 이때는 생존 검사 호출 없이 곧바로 `setAutoCommit false`로 넘어갔습니다. 이때 설명에 **`풀에서 C1 빌림 · 쉰 지 6 ms < 창 500 ms -> 검사 건너뜀`**이라고 명시되어 있습니다. [화면에서 확인: 타임라인 줄 시각 `+132 ms` `ConcurrentBag.borrow`, 우측 패널 상세 설명]
  - 즉, HikariCP는 연결이 풀에서 쉰 시간(유휴 시간)이 500ms(창 500ms) 미만이면 생존 검사를 생략하는 최적화를 수행합니다. [화면에서 확인]

## 표지 질문 (M1 ~ M5)

### M1. 호출 줄 맨 앞의 숫자
- **이해한 뜻**: 메서드의 **호출 깊이(스택 depth)**를 나타냅니다. 가장 바깥 호출(뿌리)이 0이고, 하위 호출로 들어갈 때마다 1씩 증가합니다. 추적하지 않은 프록시나 리플렉션 계층은 `⋯n칸`으로 접혀 있습니다.
- **확인 여부**: **화면에서 뜻을 직접 확인했습니다.** [화면에서 확인: 아래쪽 범례·풀이 본문 `숫자는 호출 깊이: 뿌리가 0이고, 추적한 호출과 스택에만 보인 호출을 한 단씩 셈. 추적하지 않은 칸(프록시·반사 등)은 사슬에서 ⋯n칸으로 접음.`]

### M2. 줄 끝의 [갈림]
- **이해한 뜻**: 여러 시나리오나 반복 실행된 기록들(전체 14벌의 기록)을 함께 비교했을 때, **해당 메서드가 호출한 자식 메서드의 순서나 분기 경로(길)가 다른 지점**을 의미합니다.
- **확인 여부**: **화면에서 뜻을 직접 확인했습니다.** [화면에서 확인: 상단 설명 줄 `[갈림]은 모든 장면의 기록 14벌을 함께 견줘 셉니다.`, 아래쪽 범례·풀이 본문 `[갈림] 함께 견준 기록에서 이 메서드가 자식을 부른 차례(길)가 둘 이상`]

### M3. 점선 막대와 기울인 글씨의 줄
- **이해한 뜻**: **스택에만 보이고 정상 종료 시각이 없는 호출**을 의미합니다. 아래쪽 자식 호출에서 발생한 예외가 상위로 던져지면서(pass-through) 끝나버려 메서드 자체의 정상 리턴 기록이 없고, 다른 기록의 호출 스택 덤프에만 칸으로 남아 있는 경우입니다.
- **확인 여부**: **화면에서 뜻을 직접 확인했습니다.** [화면에서 확인: 아래쪽 범례·풀이 본문 `스택에만 보인 호출(끝 시각 없음, 기울인 글씨): 아래에서 올라온 예외가 지나가며 끝나 자기 끝 기록이 없고, 다른 기록의 스택에만 칸으로 남은 호출`]

### M4. 줄 끝의 ＋2, ＋5 같은 표시
- **이해한 뜻**: 현재 화면의 필터(보이는 줄 조건) 때문에 **화면에서 접혀 있는 하위 자식 호출의 개수**를 나타내며, 클릭하면 접힌 자식 호출들이 펼쳐집니다.
- **확인 여부**: **화면에서 뜻을 직접 확인했습니다.** [화면에서 확인: 상단 설명 줄 `호출 82개 가운데 33개를 줄로 보임 · 나머지는 줄 끝의 ＋n으로 접혀 있음`, 아래쪽 범례·풀이 본문 `＋n은 접힌 자식 수(누르면 펼침)`]

### M5. '관찰 +…', 'JFR 기록', '추론' 같은 작은 표지
- **이해한 뜻**: 해당 데이터나 상태 값이 수집된 **원천(출처, Data Source)**을 구분해 주는 출처 표지입니다.
  - `관찰 +t`: 실험 도구가 PostgreSQL의 시스템 상태 뷰(`pg_stat_activity`, `pg_locks`, 커밋 로그)를 직접 읽어온 값 (+t는 캡처 시각).
  - `JFR 기록`: JVM 내부의 JDK Flight Recorder가 수집한 실제 메서드 시작/종료/스택 기록.
  - `추론`: 로그에 직접 찍히지 않아 분석기가 전후 호출 순서나 소스 코드를 바탕으로 계산해 낸 값.
- **확인 여부**: **화면에서 뜻을 직접 확인했습니다.** [화면에서 확인: 아래쪽 범례·풀이 본문 '출처 표지' 섹션]

- **C2**: **(나)** 위쪽 그림판(기다림의 고리 상자, PostgreSQL 상자 C2 pid 4688), **(다)** 시간 순 줄 그림 (`lock_timeout` 오류 및 `NoDeadlock` 라인), **(라)** 오른쪽 자세한 내용 ('막힌 동안 찍은 관찰' 세션 상태)
- **C3**: **(가)** 맨 위 장면 설명 줄·주요 순간 칩, **(나)** 위쪽 그림판('기다림의 고리(풀)' 상자, `C2 없음` 칸), **(다)** 시간 순 줄 그림 (`연결 위 메시지` 열이 비어 있는 대기 구간)
- **C4**: **(가)** 맨 위 장면 설명 줄·주요 순간 칩 (`+822 롤백 전용 표시`, `+1,236 C1 ROLLBACK`), **(다)** 시간 순 줄 그림, **(라)** 오른쪽 자세한 내용 (`DataSourceTransactionManager.doSetRollbackOnly` 및 `AbstractPlatformTransactionManager.processRollback`)
- **C5**: **(가)** 맨 위 장면 설명 줄·주요 순간 칩, **(다)** 시간 순 줄 그림 (`ConcurrentBag.borrow` 줄 텍스트), **(라)** 오른쪽 자세한 내용 (6ms < 500ms 검사 건너뜀 상세)

## 마지막 세 가지

### 1. 이 화면에 더 있었으면 하는 것
- **격리 수준(Isolation Level) 및 전파 옵션 조합 실험**: 현재 6개 시나리오도 훌륭하지만, 실무에서 자주 문제가 되는 `READ_COMMITTED` vs `REPEATABLE_READ` 격리 수준 차이로 인한 Phantom Read/Non-repeatable Read 현상이나, `SUPPORTS`, `MANDATORY` 같은 다른 전파 옵션 시나리오도 추가되면 좋겠습니다. [추측]
- **컴포넌트 박스 인터랙션**: 중앙 상단의 `HikariCP`나 `PostgreSQL` 박스를 클릭했을 때 타임라인에서 해당 컴포넌트의 로그/패킷만 모아보는 필터가 켜지거나, HikariCP의 대기 큐(`poolEntry`, `handOffQueue`) 상태를 별도 팝업으로 볼 수 있으면 더 직관적일 것 같습니다. [추측]

### 2. 실제 업무에서 다시 쓸지와 그 이유
- **다시 쓸 것인가**: **네, 반드시 다시 쓸 것입니다 (팀 스터디 및 장애 분석 시 강력 추천).** [원래 알던 것/추측]
- **이유**: 실무에서 트랜잭션 롤백 이슈(`UnexpectedRollbackException`)나 커넥션 풀 고갈 장애가 발생했을 때, 보통 애플리케이션 로그의 스택 트레이스 한 줄만 보고 원인을 역추적하느라 며칠씩 삽질을 하곤 합니다. 하지만 이 화면은 **JVM 스레드 스택 - 커넥션 풀 상태 - DB 내부 트랜잭션 xid 및 락 대기**를 하나의 타임라인으로 완벽하게 동기화해서 보여주기 때문에, 복잡한 트랜잭션 전파와 커넥션 반납 실패 원인을 한눈에 규명할 수 있는 최상의 시각화 도구이기 때문입니다. [화면에서 확인/추측]

### 3. 이 화면으로 이해했다는 자신감 (1~5)과 그 이유
- **점수**: **5점 (매우 자신 있음)**
- **이유**: 이전에는 "REQUIRED는 참여하고, REQUIRES_NEW는 새로 연다"는 식으로 텍스트로만 암기하고 있어서 내부 동작이 머릿속에 안 그려졌습니다. 하지만 이번에 화면을 조작하면서:
  1. 참여한 트랜잭션이 실패할 때 메모리에 플래그(`doSetRollbackOnly`)만 남기고 바깥 커밋 시점에 최종 롤백된다는 점,
  2. REQUIRES_NEW가 기존 커넥션을 `suspend`하고 풀에서 새 커넥션을 꺼내 쓰기 때문에 풀이 1칸이면 자기 자신과 데드락에 빠진다는 점,
  3. 같은 행을 수정할 때 DB 데드락 감지기가 왜 무력화되는지(`idle in transaction` 대기 고리),
  4. HikariCP의 500ms 유휴 검사 생략 최적화까지
  
  프레임워크와 DB 엔진의 실제 동작 메커니즘을 소스 코드 라인과 네트워크 패킷 단위로 명확하게 확인했기 때문입니다. [화면에서 확인]
