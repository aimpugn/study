## 1. 내용 질문 (C1 ~ C5)

### C1. 'REQUIRES_NEW · 같은 행' 장면에서 안쪽(REQUIRES_NEW) UPDATE는 어느 연결로 갔나요? 그 순간 바깥 트랜잭션의 연결은 어디에, 어떤 상태로 있었나요?

- **안쪽 UPDATE가 간 연결**:
  - 안쪽 UPDATE는 새로 빌린 **연결 `C2`**로 갔습니다 [화면에서 확인: 위쪽 그림판 Spring 트랜잭션 칸의 `스레드에 묶인 연결 C2`, pgjdbc 칸의 `C2`, PostgreSQL 칸의 `C2 · pid 4688 active Lock/transactionid xid 754`, 타임라인 +530 ms 부근의 메시지 `-> C2 마지막 <- S +924`].
- **그 순간 바깥 트랜잭션 연결 `C1`의 위치와 상태**:
  - **애플리케이션(스프링)**: main 스레드에서 잠시 내려놓은 채(`doSuspend`) HikariCP 풀에 반납하지 않고 앱이 들고 있었습니다 [화면에서 확인: 위쪽 그림판 Spring 트랜잭션 칸 `떼어 둔 연결 C1 [추론]`].
  - **DB 서버(PostgreSQL)**: 백엔드 프로세스 `C1 · pid 4679`에서 트랜잭션 753을 열어둔 채 락을 기다리지 않고, 클라이언트의 다음 명령을 기다리는 **`idle in transaction`** 및 **`Client/ClientRead`** 상태(`xid 753`)로 대기하고 있었습니다 [화면에서 확인: 위쪽 그림판 PostgreSQL 칸 `C1 · pid 4679 idle in transaction Client/ClientRead xid 753`, 우측 패널 세션 표 `C1 4679 idle in transaction Client/ClientRead xid 753`].

### C2. 같은 장면에서 안쪽 UPDATE는 왜 진행되지 않았고, 어떻게 끝났나요? DB는 왜 이것을 교착(deadlock)으로 보지 않았나요?

- **진행되지 않은 이유**:
  - 바깥 트랜잭션(753)이 이미 1번 행의 잔액을 수정한 뒤 커밋하지 않고 행 락을 쥐고 있었기 때문에, 안쪽 트랜잭션(754)의 UPDATE가 1번 행의 락을 얻지 못하고 대기에 빠졌기 때문입니다 [화면에서 확인: 위쪽 그림판 "기다림의 고리" 2번 "C2 백엔드 -> 트랜잭션 753이 끝나기를 기다림(락 기다림) [함수 기록]", 우측 패널 "받지 못한 락 C2 -> transactionid 753 ShareLock"].
- **어떻게 끝났는가**:
  - 안쪽 자바 코드에 설정된 `SET LOCAL lock_timeout = '3s'`에 의해 3초 동안 락을 기다리다 타임아웃이 발생했습니다. PostgreSQL이 `lock_timeout` 오류(SQLSTATE 55P03, "canceling statement due to lock timeout")를 반환했고, C2 트랜잭션(754)이 롤백된 후 연쇄적으로 C1(753)도 롤백되면서 최종적으로 바깥에 `UncategorizedSQLException`을 던지며 끝났습니다 [화면에서 확인: 위쪽 그림판 "끊은 것: C2의 lock_timeout 3s -> 오류 55P03 +4,033 ms", 타임라인 +4,033 ms `<- C2 · E 55P03 · Z(E)`, 결과 요약 "C1, C2 ROLLBACK", "outer-threw UncategorizedSQLException"].
- **DB가 교착(deadlock)으로 보지 않은 이유**:
  - PostgreSQL의 교착 검사기는 DB 서버 내부의 락 대기 관계만 확인합니다. DB 입장에서 C2는 753번 트랜잭션을 기다리고 있지만, C1은 DB 내부의 어떤 락도 기다리지 않고 정상적으로 클라이언트의 다음 쿼리를 대기(`Client/ClientRead`)하는 중이었습니다 [화면에서 확인: 위쪽 그림판 "기다림의 고리" 3번 "서버에서 C1는 락을 기다리지 않고 다음 명령을 기다림(Client/ClientRead)"].
  - 실제 대기 고리는 "C1을 끝낼(커밋/롤백) main 스레드가 앱 JVM 안에서 C2의 응답을 기다리며 블로킹되어 있는" 애플리케이션 내부의 일인데, DB 서버는 이를 볼 수 없으므로 순환 고리가 없다고 판단하여 교착 검사 결과 **`NoDeadlock`**을 내렸습니다 [화면에서 확인: 위쪽 그림판 "고리가 main에서 닫힘... 서버의 교착 검사는 서버 안의 락 기다림만 보고 앱 안의 일이라 보지 못함 [추론] · 교착 검사 결과 NoDeadlock [함수 기록]"].

### C3. 'REQUIRES_NEW · 풀 1칸' 장면에서 풀이 한 칸이면 무슨 일이 일어나나요? 그동안 DB 서버로 무엇이 갔나요?

- **풀이 한 칸이면 일어나는 일**:
  - 바깥 트랜잭션이 풀의 유일한 커넥션 C1을 빌려 사용 중인 상태에서, 안쪽 `REQUIRES_NEW`가 새 트랜잭션을 열기 위해 C1을 잠시 내려놓고(`doSuspend`) HikariCP 풀에 새 커넥션을 요청(`ConcurrentBag.borrow`)합니다 [화면에서 확인: 위쪽 그림판 "기다림의 고리(풀)" 1, 2번].
  - 풀의 최대 크기가 1칸(`최대 1칸 [실험 설정]`)이므로 빈 커넥션이 없어 main 스레드가 `ConcurrentBag.borrow` 안에서 대기하며 잠듭니다 [화면에서 확인: 우측 패널 "한 일: 풀에서 받지 못함(시간 초과) · 잠듦 2,003 ms [JFR 기록]"].
  - 빈 커넥션이 나오려면 C1을 풀에 반납해야 하는데, C1을 들고 있는 주체이자 반납해 줄 유일한 스레드(main)가 바로 이 대기에 갇혀 있으므로 "고리가 main에서 닫히는" 애플리케이션 레벨의 셀프 데드락이 발생합니다 [화면에서 확인: 위쪽 그림판 "고리가 main에서 닫힘: 빈 칸이 나오려면 C1이 풀로 돌아와야 하는데, 돌려줄 스레드가 바로 이 기다림 안에 있음 [추론]"].
  - 결국 HikariCP의 대기 제한 시간인 2초가 지나 `connectionTimeout 2,000 ms` 만료로 `SQLTransientConnectionException`이 발생하고, 스프링이 `CannotCreateTransactionException`으로 감싸 던지며 트랜잭션이 롤백됩니다 [화면에서 확인: "끊은 것: connectionTimeout 2,000 ms -> SQLTransientConnectionException", 결과 요약 "outer-threw CannotCreateTransactionException"].
- **그동안 DB 서버로 간 것**:
  - **아무것도 가지 않았습니다 (0개).** [화면에서 확인: 위쪽 그림판 "이 기다림은 앱 안(풀)의 일이라 DB 서버는 모름(그동안 연결 위 메시지 없음) [추론]", 타임라인 +587 ms ~ +2,592 ms 구간의 '연결 위 메시지' 칸에 전송된 쿼리 패킷이 전혀 없음].

### C4. 'REQUIRED · 안쪽이 실패' 장면에서 안쪽이 실패했는데, 왜 바깥은 UnexpectedRollbackException으로 끝나나요?

- **이유**:
  - 안쪽 메서드(`REQUIRED`)에서 예외(`IllegalStateException`)가 발생했을 때, 스프링 트랜잭션 매니저는 물리 커넥션 C1에 롤백을 바로 보내지 않고, 트랜잭션 상태에 **`DataSourceTransactionManager.doSetRollbackOnly`**를 호출하여 "롤백 전용 표시"를 남겨둡니다 [화면에서 확인: 타임라인 +822 ms `DataSourceTransactionManager.doSetRollbackOnly · 롤백 전용 표시(연결 위로는 보내지 않음)`].
  - 바깥 메서드가 catch 블록으로 이 예외를 삼키고 정상 종료하자, 스프링의 AOP 프록시(`TransactionAspectSupport`)는 메서드가 정상 반환되었으므로 커밋을 시도하기 위해 `AbstractPlatformTransactionManager.commit`을 호출합니다 [화면에서 확인: 타임라인 +1,235 ms `AbstractPlatformTransactionManager.commit`].
  - 트랜잭션 매니저는 커밋을 실행하려다 이미 트랜잭션에 "롤백 전용" 마킹이 되어 있는 것을 확인하고, 커밋 대신 강제로 `processRollback`을 실행하여 PostgreSQL(C1)에 물리적 `ROLLBACK (S_1)`을 전송합니다 [화면에서 확인: 타임라인 +1,235 ms `processRollback +2 · x UnexpectedRollbackException`, +1,236 ms `-> C1 · P B E S · ROLLBACK (S_1)`].
  - 그리고 "바깥은 정상 종료되어 커밋을 기대했으나 트랜잭션은 롤백되었다"는 사실을 호출자에게 알리기 위해 스프링 자체 예외인 **`UnexpectedRollbackException`**을 던지며 종료됩니다 [화면에서 확인: 타임라인 +1,244 ms `앱: outer-threw · UnexpectedRollbackException`, 하단 범례 "Spring · HikariCP - 롤백 전용 표시"].

### C5. '0.5초 안에 다시 빌림' 장면에서 HikariCP는 연결을 빌려줄 때마다 연결이 살아 있는지 검사하나요?

- **답**: **아니요, 빌려줄 때마다 항상 검사하지 않습니다.** [화면에서 확인: '0.5초 안에 다시 빌림' 타임라인 +8.85 ms 및 +132 ms 줄].
- **근거 및 메커니즘**:
  - **첫 번째 빌릴 때 (+8.85 ms)**: 커넥션이 풀에서 쉰 지 1,225 ms가 지나 기준치(500 ms)를 초과했기 때문에 생존 검사를 수행하여 `PoolBase.isConnectionDead`와 `isValid` 쿼리(`-> C1 · Q ""` / `<- C1 · I · Z(I)`)가 실제로 실행되었습니다 [화면에서 확인: 타임라인 +8.85 ms `ConcurrentBag.borrow · 풀에서 C1 빌림 · 쉰 지 1,225 ms > 창 500 ms -> 생존 검사`, +8.93 ms `PoolBase.isConnectionDead`, 주요 순간 `+8.93 생존 검사`].
  - **두 번째 빌릴 때 (+132 ms)**: 첫 번째 트랜잭션이 끝나 커넥션이 풀에 반납(+127 ms)된 지 불과 6 ms밖에 지나지 않았기 때문에, 생존 검사를 완전히 건너뛰고 커넥션을 즉시 빌려주었습니다 [화면에서 확인: 타임라인 +132 ms `ConcurrentBag.borrow · 풀에서 C1 빌림 · 쉰 지 6 ms < 창 500 ms -> 검사 건너뜀`, 주요 순간 칩에서도 생존 검사 없이 `+132 C1 빌림` 바로 다음 `+145 C1 COMMIT`으로 연결됨].
  - 즉, HikariCP는 커넥션이 반납된 뒤 경과한 유휴 시간이 **500 ms(생존 검사 창)**를 넘었을 때만 살아 있는지 검사하고, 500 ms 이내에 다시 빌려지는 경우에는 검사를 생략합니다 [화면에서 확인].

### M3. 점선 막대와 기울인 글씨의 줄
- **이해한 뜻**: **스택에만 보인 호출**입니다. 하위 호출에서 예외가 발생하여 위로 뚫고 올라가는 바람에 자기 자신의 정상적인 종료 시각이 기록되지 못하고, 다른 기록의 호출 스택에 프레임 칸으로만 남아 있는 미완료 호출을 나타냅니다 [화면에서 확인].
- **출처**: [화면에서 확인: 최하단 범례 둘째 줄 "[점선 네모] 스택에만 보인 호출(끝 시각 없음, 기울인 글씨): 아래에서 올라온 예외가 지나가며 끝나 자기 끝 기록이 없고, 다른 기록의 스택에만 칸으로 남은 호출"].

### M4. 줄 끝의 ＋2, ＋5 같은 표시
- **이해한 뜻**: 해당 메서드 호출 아래에 숨겨져 있는 **접힌 자식 호출의 개수**입니다. 이 줄을 클릭하면 접혀 있던 하위 호출들이 펼쳐집니다 [화면에서 확인].
- **출처**: [화면에서 확인: 최하단 범례 넷째 줄 "줄을 누르면 그 호출까지의 사슬이 펼쳐지고 오른쪽에 자세한 내용 · +n은 접힌 자식 수(누르면 펼침)"].

### M5. '관찰 +…', 'JFR 기록', '추론' 같은 작은 표지
- **이해한 뜻**: 해당 데이터나 상태를 수집·기록한 **정보의 출처 표지**입니다 [화면에서 확인].
  - `관찰 +t`: 실험 도구가 PostgreSQL의 내부 상태 뷰(`pg_stat_activity`, `pg_locks`, 커밋 로그)를 직접 실측하여 읽어온 값 (+t는 측정한 시각) [화면에서 확인].
  - `JFR 기록`: JVM 내부의 JDK Flight Recorder가 남긴 실제 자바 메서드 호출 시작·끝·스택 기록 [화면에서 확인].
  - `추론`: 로그에 직접 찍히지 않아 해석기가 다른 정황 기록(호출 순서, 소스 코드 등)을 종합하여 논리적으로 계산·도출한 값 [화면에서 확인].
  - `함수 기록`: PostgreSQL 백엔드 내부 C 함수 호출을 외부에서 후킹하여 남긴 DB 엔진 측 기록 [화면에서 확인].
- **출처**: [화면에서 확인: 최하단 범례 "출처 표지" 섹션].

### 1) 이 화면에 더 있었으면 하는 것
- **주요 순간 칩과 타임라인 줄의 클릭 점프 연동**: 상단에 배치된 주요 순간 칩(예: `+822 롤백 전용 표시`, `+1,241 UnexpectedRollbackException`)을 클릭했을 때, 해당 타임라인 행으로 즉시 스크롤되고 우측 패널이 열리도록 인터랙션이 연결되면 탐색 피로도가 훨씬 줄어들 것 같습니다.
- **트랜잭션 격리 수준(Isolation Level) 시나리오 추가**: 현재 전파 옵션과 풀 크기 위주로 구성되어 있는데, `READ COMMITTED`와 `REPEATABLE READ` 환경에서 일어나는 Phantom Read, Non-repeatable Read, 그리고 PostgreSQL MVCC의 스냅샷 생성 시점 차이를 보여주는 장면이 추가된다면 DB 동시성 제어 학습에 완벽한 도구가 될 것입니다.
- **파라미터 변경 시뮬레이션(Playground) 모드**: HikariCP의 커넥션 풀 크기(`maximumPoolSize`), `connectionTimeout`, 또는 `lock_timeout` 값을 사용자가 슬라이더나 입력창으로 직접 바꿔보고 그에 따른 타임라인 변화를 확인해볼 수 있는 기능이 있다면 실험적 이해에 큰 도움이 될 것입니다.

### 2) 실제 업무에서 다시 쓸지와 그 이유
- **반드시 다시 씁니다.**
- **이유**: 실무에서 비즈니스 로직 분리를 위해 `@Transactional(propagation = Propagation.REQUIRES_NEW)`를 도입했다가 배포 후 커넥션 풀 고갈이나 원인 모를 락 타임아웃 장애를 겪는 경우가 적지 않습니다. 이때 사내 동료나 주니어 개발자에게 "REQUIRES_NEW는 커넥션을 하나 더 잡으니 풀 크기를 넉넉히 해야 한다"거나 "DB 행 락 때문에 셀프 데드락이 난다"고 구두나 글로만 설명하면 체감하기 어렵습니다. 이 화면은 스프링 프록시의 스레드 바인딩 해제(`doSuspend`), HikariCP 대기, DB 백엔드의 `idle in transaction` 상태를 단 하나의 통합 타임라인으로 증명해 주므로, 팀 내 장애 부검(Post-mortem) 회고나 신규 입사자 교육용 시각 자료로서 실무적 효용이 압도적입니다.

### 3) 이 화면으로 이해했다는 자신감 (1~5)과 그 이유
- **5점 (매우 높음)**
- **이유**: 기존에는 서비스 계층의 어노테이션과 DB 쿼리가 각각 어떻게 맞물려 도는지 머릿속에서 추상적인 개념으로만 흩어져 있었습니다. 하지만 이 도구를 통해 스프링 트랜잭션 인터셉터가 어느 라인에서 롤백 플래그를 세팅하고, HikariCP가 몇 ms 단위로 생존 검사를 스킵하며, PostgreSQL 백엔드가 왜 분산 교착 상태를 `NoDeadlock`으로 판정하는지까지 실제 JVM 실행 기록(JFR)과 DB 엔진 상태(pg_locks)를 일대일로 대조하며 확인했습니다. 이제는 실무에서 전파 옵션 관련 코드를 작성하거나 예외 로그를 볼 때 내부에서 일어나는 물리적 동작 흐름을 완벽하게 머릿속에 시각화하여 디버깅할 수 있다는 확신이 듭니다.
