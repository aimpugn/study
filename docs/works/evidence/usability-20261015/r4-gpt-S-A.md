## 1. 열기 전 질문

1. 글을 읽는 자료일까, 상태를 바꿔 가며 보는 도구일까?
2. REQUIRED, REQUIRES_NEW, NESTED가 실제 호출에서 어떻게 달라지는지 볼 수 있을까?
3. 커넥션 풀과 행 락 대기가 실행 결과와 어떻게 연결될까?

## 2. 첫인상(60초)과 첫 세 번의 조작

첫 화면은 `Spring 전파`라는 제목 아래 시나리오 버튼, 시간선, JVM과 DB 연결 그림, 코드, 호출 기록이 빽빽하게 배치돼 있었습니다. 처음엔 무엇부터 읽을지 막막했지만, 위쪽 시나리오 버튼부터 눌러 보면 되겠다고 생각했습니다. **1)** `REQUIRES_NEW`를 눌렀습니다. 새 트랜잭션의 연결을 보고 싶었고, 화면에 C1과 C2가 각각 커밋된 결과가 나왔습니다. **2)** `REQUIRES_NEW · 같은 행`을 눌렀습니다. 안쪽이 바깥이 고친 행을 건드리면 어떻게 되는지 궁금했고, 락 대기 관찰과 양쪽 롤백이 보였습니다. **3)** `REQUIRES_NEW · 풀 1칸`을 눌렀습니다. 커넥션 부족을 예상했고, 연결을 빌리지 못해 시간 초과되는 장면을 확인했습니다.

## 4. 다 써 본 뒤 이해한 화면

[화면에서 확인] 이 화면은 Spring 전파 옵션별로 기록된 호출, 연결, DB 메시지와 결과를 시간순으로 대조하는 관측 화면입니다.  
[화면에서 확인] 상단 버튼으로 장면과 실행 기록을 고르고, 호출이나 시간선을 선택해 코드와 상세 기록을 따라갑니다.  
[추측] 실행 a/b와 “기록 때 컴파일한 사본”이라는 표기를 보아, 설정을 직접 바꾸는 샌드박스보다는 미리 기록한 실행을 탐색하는 화면으로 이해했습니다.

## 5. 질문별로 배운 것

**질문 1 — 어떤 화면인가?**  
[화면에서 확인] 시나리오 버튼과 실행 a/b, 시간선, 호출 기록을 오가며 쓰는 기록 탐색 화면이었습니다.

**질문 2 — 전파 옵션은 어떻게 다른가?**  
[화면에서 확인] REQUIRED 장면의 상단 결과는 C1 롤백과 두 잔액 원상복구를 보여 줬고, 안쪽 호출 상세에는 `IllegalStateException`이 표시됐습니다.  
[화면에서 확인] 도움말의 “롤백 전용 표시” 설명은 참여한 안쪽의 실패가 공유 트랜잭션을 롤백 전용으로 만들고, 바깥 커밋 시 `UnexpectedRollbackException`을 낸다고 적었습니다.  
[화면에서 확인] NESTED 장면의 시간선에는 `SAVEPOINT`, `ROLLBACK TO SAVEPOINT`가 보였고 결과는 C1 커밋, kim 100→90, lee 200→200이었습니다.  
[화면에서 확인] REQUIRES_NEW 장면의 구성도에는 바깥 C1 연결이 떼어진 동안 C2가 작업하고, 두 연결의 트랜잭션이 각각 커밋되는 모습이 나왔습니다.

**질문 3 — 풀과 락은 결과와 어떻게 연결되나?**  
[화면에서 확인] 풀 1칸 장면의 호출 상세는 `connectionTimeout 2,000 ms`와 `ConcurrentBag.borrow`의 약 2초 대기 후 `CannotCreateTransactionException`을 보여 줬습니다.  
[화면에서 확인] 같은 행 장면의 관찰 칸에는 C1 `idle in transaction`, C2 `Lock/transactionid`, “C2 → transactionid 753 ShareLock”가 표시됐고, 코드에는 해당 트랜잭션에만 적용하는 3초 `lock_timeout`이 보였습니다.  
[원래 알던 것] HikariCP가 커넥션 풀이라는 것은 알고 있었지만, 풀에서 새 연결을 못 빌리는 시간과 DB에서 락을 기다리는 시간이 별개로 나타나는 것은 몰랐습니다.

**그 밖에 배운 것.**  
[화면에서 확인] 도움말은 Spring이 스레드의 트랜잭션에 연결을 묶고, REQUIRES_NEW 때 잠시 떼어 두며, `JdbcTemplate`은 같은 스레드의 연결을 쓴다고 설명했습니다.  
[화면에서 확인] 도움말은 풀에서 빌린 연결을 `close`해도 연결 자체를 닫는 게 아니라 풀에 돌려준다고 설명했습니다.  
[화면에서 확인] 도움말의 출처 표지는 앱 호출을 JFR, PostgreSQL 내부 사건을 함수 기록, DB 상태를 관찰, 직접 찍히지 않은 해석을 추론으로 구분했습니다.  
[화면에서 확인] 생존 검사 장면의 상세에는 쉰 시간 5.7ms와 500ms 창이 함께 표시됐고, HikariCP 코드 줄에는 `aliveBypassWindowMs` 기본값 500이 보였습니다.

## 6. 막힌 곳과 바로잡은 점

[화면에서 확인] 처음에는 실행 a/b가 서로 비교하는 동시 실행처럼 느껴졌지만, 도움말에서 같은 장면을 다시 돌린 기록이라고 확인했습니다.  
[화면에서 확인] 처음에는 `idle in transaction`을 DB 안에서 뭔가 기다리는 상태로 읽었지만, 도움말은 클라이언트의 다음 명령을 기다리는 상태이며 서버 안에서는 아무것도 기다리지 않는다고 설명했습니다.  
[화면에서 확인] 도움말에는 MVCC 설명이 없어 이 화면만으로 MVCC 동작은 배우지 못했습니다.
