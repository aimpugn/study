### [내용 질문] C1 ~ C5

#### C1. 'REQUIRES_NEW · 같은 행' 장면에서 안쪽(REQUIRES_NEW) UPDATE는 어느 연결로 갔나요? 그 순간 바깥 트랜잭션의 연결은 어디에, 어떤 상태로 있었나요?
- **안쪽 UPDATE가 간 연결**: **C2** 연결로 갔습니다 [화면에서 확인: 위쪽 구성도에서 `main` 스레드가 굵은 분홍색 화살표로 `C2` 박스를 거쳐 PostgreSQL의 `C2 · 4688`로 `P B D E S · UPDATE acct SET b...` 요청을 보내고 있음 / 하단 트레이스 `+924 ms`의 `8 QueryExecutorImpl.execute -> C2 P B E S · UPDATE acct SET balance = ...`].
- **그 순간 바깥 트랜잭션의 연결(C1)의 위치와 상태**: 바깥 트랜잭션의 연결인 **C1**은 HikariCP 풀 안에 스레드로부터 **"떼어 둔 상태(`---||` 떼어 둔 연결)"**로 놓여 있었고, PostgreSQL 서버 백엔드에서는 **`C1 · 4679`** 세션이 **`idle in tx` (xid `753`)** 상태로 멈춰 있었습니다 [화면에서 확인: 위쪽 구성도의 `HikariCP` 박스 안 `C1`과 `main` 스레드 사이 점선 `---||`, PostgreSQL 박스 안 `C1 · 4679`의 `idle in tx` 뱃지, 우측 인스펙터 관찰 기록 `C1 4679 idle in transaction Client/ClientRead xid 753`].

#### C2. 같은 장면에서 안쪽 UPDATE는 왜 진행되지 않았고, 어떻게 끝났나요? DB는 왜 이것을 교착(deadlock)으로 보지 않았나요?
- **진행되지 않은 이유**: 바깥 트랜잭션(C1, xid 753)이 이미 수정한 행에 대해 안쪽 트랜잭션(C2, xid 754)이 다시 수정을 시도하면서, PostgreSQL 데이터베이스 차원에서 C1 트랜잭션이 끝나기를 기다리는 행 락 대기(`Lock/transactionid`, `ShareLock`)에 걸렸기 때문입니다 [화면에서 확인: 위쪽 구성도의 `C2 · 4688 🔒 락 기다림`, 754에서 753으로 이어지는 분홍색 화살표 `기다림의 고리 ⏱3s`, 우측 인스펙터의 `받지 못한 락: C2 -> transactionid 753 ShareLock`].
- **어떻게 끝났는가**: `main` 스레드는 안쪽 메서드가 끝나기를 기다리고 있고, 안쪽 트랜잭션(C2)은 바깥 트랜잭션(C1)이 끝나기를 기다리는 상태가 되어 꼼짝 못 하다가, 안쪽 코드에 설정된 3초 락 타임아웃(`SET LOCAL lock_timeout = '3s'`)이 만료되면서 PostgreSQL이 오류(`E 55P03`)를 던졌습니다. 이로 인해 Spring에서 `UncategorizedSQLException`이 발생했고, C2가 `ROLLBACK`된 후 바깥의 C1도 연쇄적으로 롤백(`( C1 753 ↶ ROLLBACK | C2 754 ↶ ROLLBACK )`)되며 끝났습니다 [화면에서 확인: 하단 트레이스 `+4,033 ms`의 `<- C2 · E 55P03`, `QueryExecutorImpl.execute -> C2 P B E S · ROLLBACK (S_1)`, 맨 위 요약의 `× UncategorizedSQLException`].
- **DB가 이것을 교착(deadlock)으로 보지 않은 이유**: PostgreSQL 서버 입장에서 C1과 C2는 그저 서로 다른 두 개의 독립된 클라이언트 세션(4679, 4688)일 뿐입니다. C2는 C1의 락 해제를 기다리고 있지만(`Lock/transactionid`), C1은 DB 차원에서 어떤 락도 기다리지 않고 단지 클라이언트 앱의 다음 명령을 기다리는 대기 상태(`Client/ClientRead`, `idle in transaction`)였습니다. 즉, DB 엔진 내부 락 그래프 상에 순환(cycle) 고리가 형성되지 않았기 때문에 DB의 교착 검사기는 교착이 아니라고 판단했습니다 [화면에서 확인: 위쪽 구성도 `C2 · 4688` 아래 표기된 `교착 검사 -> NoDeadlock`, 하단 트레이스 `+2,033 ms`의 `교착 검사 -> NoDeadlock`, 우측 인스펙터의 세션 상태 비교 `C1 4679 Client/ClientRead` vs `C2 4688 Lock/transactionid`].

#### C3. 'REQUIRES_NEW · 풀 1칸' 장면에서 풀이 한 칸이면 무슨 일이 일어나나요? 그동안 DB 서버로 무엇이 갔나요?
- **무슨 일이 일어나는가**: 바깥 트랜잭션이 풀의 유일한 연결(C1)을 쥔 상태에서 REQUIRES_NEW 안쪽 트랜잭션을 시작하려고 C1을 스레드에서 떼어두고(`doSuspend`) 풀에 새 연결을 요구합니다. 그러나 풀 최대 크기가 1칸뿐이어서 남은 연결이 없으므로, `main` 스레드는 HikariCP의 `ConcurrentBag.borrow` 호출 안에서 연결이 반납되기를 기다리며 2초(정확히 2,003 ms) 동안 완전히 잠들어 멈춥니다(블로킹) [화면에서 확인: 위쪽 구성도의 `⏳ <= 2,000 ms`, 하단 트레이스 `+587 ms`의 `13 ConcurrentBag.borrow • 빈 칸 없음 ⏳2,003 ms`, 우측 인스펙터의 `한 일: 풀에서 받지 못함(시간 초과) · 잠듦 2,003 ms`]. 결국 2초 타임아웃으로 `SQLTransientConnectionException`이 터지며 Spring의 `CannotCreateTransactionException`으로 실패하고, 떼어두었던 C1을 다시 이어받아(`doResume`) C1마저 롤백됩니다 [화면에서 확인: 하단 트레이스 `+2,592 ms ~ +2,593 ms`].
- **그동안 DB 서버로 무엇이 갔는가**: 2초 동안 `main` 스레드가 HikariCP 대기에 묶여 잠들어 있는 동안, **DB 서버로는 단 하나의 패킷/쿼리도 가지 않았습니다 (0개)** [화면에서 확인: 위쪽 구성도의 C1 연결선 위에 전송 메시지가 없음, 하단 트레이스 `+587 ms`부터 `+2,592 ms` 사이의 메시지 공백 구간, 우측 인스펙터 관찰 기록 `도중 연결 위 메시지 0개`]. 타임아웃으로 실패한 직후인 `+2,593 ms`에 바깥 트랜잭션을 정리하기 위한 `ROLLBACK (S_1)` 쿼리만 1회 전송되었습니다 [화면에서 확인: 하단 트레이스 `+2,593 ms`].

#### C4. 'REQUIRED · 안쪽이 실패' 장면에서 안쪽이 실패했는데, 왜 바깥은 UnexpectedRollbackException으로 끝나나요?
- **이유**:
  1. 안쪽 메서드(`Inner.requiredFails`)는 `REQUIRED` 속성이므로 새 물리 트랜잭션을 열지 않고 바깥 트랜잭션에 그대로 참여했습니다 [화면에서 확인: `Inner.java` 16행 주석 `/** 바깥 트랜잭션에 참여해(REQUIRED) ... */`].
  2. 안쪽에서 `IllegalStateException`이 터졌을 때, 안쪽 Spring 프록시는 단독으로 DB 롤백을 할 수 없으므로 `DataSourceTransactionManager.doSetRollbackOnly`를 호출하여 현재 트랜잭션 동기화 저장소에 **"롤백 전용(🚩 롤백 전용)"** 마킹만 남깁니다 [화면에서 확인: 하단 트레이스 `+822 ms`의 `8 DataSourceTransactionManager.doSetRollbackOnly • 🚩롤백 전용`].
  3. 바깥 메서드(`Outer.required`)는 안쪽의 예외를 `catch (RuntimeException e)`로 잡아서 삼켜버렸기 때문에 정상 반환되었고, 바깥 Spring 프록시는 커밋을 시도합니다(`AbstractPlatformTransactionManager.commit`) [화면에서 확인: `Outer.java` 32-33행 catch 블록, 하단 트레이스 `+1,235 ms`의 `commit`].
  4. 그러나 Spring 트랜잭션 매니저는 커밋을 처리하려다 트랜잭션에 이미 찍혀 있는 "롤백 전용" 마킹을 발견합니다. 바깥 코드는 비즈니스 로직이 성공했다고 믿고 커밋을 요청했으나 실제로는 데이터 정합성을 위해 롤백을 해야만 하는 상황(기대와 실행의 모순)이므로, Spring은 강제로 DB에 `ROLLBACK` 쿼리를 보내 롤백시킨 뒤, 바깥 호출자에게 **"커밋을 기대했으나 뜻밖에 롤백되었다"**고 경고하기 위해 **`UnexpectedRollbackException`**을 던집니다 [화면에서 확인: 하단 트레이스 `+1,235 ms`의 `processRollback • +2 × UnexpectedRollbackException`, `+1,244 ms: outer-threw · UnexpectedRollbackException`].

#### C5. '0.5초 안에 다시 빌림' 장면에서 HikariCP는 연결을 빌려줄 때마다 연결이 살아 있는지 검사하나요?
- **검사하지 않습니다** [화면에서 확인: 우측 인스펙터 `한 일: 풀에서 C1 빌림 · 쉰 지 6 ms < 창 500 ms -> 검사 건너뜀`].
- HikariCP는 풀에서 커넥션을 빌려줄 때 직전 반납 이후 경과한 시간(쉰 시간)을 확인하여, 그 시간이 설정된 생존 검사 유예 창(500 ms = 0.5초) 미만일 경우 연결이 여전히 유효하다고 판단하고 DB 핑/검사 쿼리(`isValid`)를 생략합니다 [화면에서 확인: 위쪽 구성도의 `|--- 6 ms ---|` 생존 검사 창 표시, 하단 트레이스 `+132 ms`의 `9 ConcurrentBag.borrow • <- C1 6 ms 쉼 검사 없음`].

  - **확인/짐작 여부**: [화면에서 확인] - 화면 맨 아래쪽 기호 설명 줄에 **`↳ 갈림`**이라고 적혀 있고, 우측 인스펙터 상단 태그에도 `갈림`이라는 배지가 붙어 있습니다.

  - **확인/짐작 여부**: [화면에서 확인] - 화면 맨 아래쪽 기호 설명 줄에 **`| 스택에만 보인 호출(기울임)`**이라고 명시되어 있습니다.
- **M4. 줄 끝의 ＋2, ＋5 같은 표시**

  - **확인/짐작 여부**: [화면에서 확인] - 화면 맨 아래쪽 기호 설명 줄에 **`+n 접힌 자식`**이라고 명시되어 있습니다.
- **M5. '◉', '≈' 같은 작은 표지와, 자세한 내용의 'JFR 기록', '추론' 같은 표지**
  - **이해한 뜻**:
    - **`◉`**: 실험 도구가 실행 중인 애플리케이션의 특정 시점에 상태(세션, 락, 풀 상태 등)를 찍어낸 **'관찰(Observation)'** 지점입니다 [화면에서 확인: 맨 아래 기호 줄 `◉ 관찰`].
    - **`≈`**: 직접 계측된 데이터가 아니라 전후 이벤트를 바탕으로 복원해 낸 **'추론(Inference)'** 상태입니다 [화면에서 확인: 위쪽 구성도 범례 좌하단 `≈ 추론`].
    - **'JFR 기록' / '추론'**: 화면에 표시된 데이터의 수집 출처이자 신뢰도 수준입니다. Java Flight Recorder(JFR) 이벤트로 직접 로깅된 팩트인지, 아니면 전후 맥락을 통해 도구가 추론해 낸 정보인지를 명확히 구분해 주는 표지입니다 [화면에서 확인 및 추측].

### [마지막 세 가지]

#### 1. 이 화면에 더 있었으면 하는 것
- **`@Transactional` 내부 호출(Self-invocation) 누락 시나리오**: 실무에서 주니어들이 가장 흔하게 겪는 버그인 "같은 빈 내부에서 `@Transactional` 메서드를 호출할 때 프록시를 안 타서 트랜잭션이 아예 안 걸리는 현상"을 비교해 주는 장면이 있으면 좋겠습니다.
- **`readOnly = true` 최적화 관측**: 트랜잭션에 읽기 전용 옵션을 주었을 때 JDBC 드라이버(`setAutoCommit`, `readOnly`)와 DB 엔진에서 실제로 쓰기 락이나 스냅샷 처리가 어떻게 달라지는지 보여주는 탭이 추가되면 좋겠습니다.
- **상단 탭 UI 그룹화**: 시나리오 선택 탭과 실행(run a, b, c, d) 버튼이 시각적으로 분리되지 않아 조작 실수가 잦았으므로, 둘 사이에 명확한 구분선이나 그룹 라벨이 제공되면 조작성이 훨씬 개선될 것 같습니다.

#### 2. 실제 업무에서 다시 쓸지와 그 이유
- **반드시 다시 쓴다 (적극 활용)**.
- **이유**: "REQUIRES_NEW는 풀 고갈 데드락을 유발할 수 있다", "REQUIRED는 안쪽 예외를 catch해도 바깥이 롤백된다"는 교과서적 지식을 말로만 들었을 때는 막연했는데, 이 도구를 통해 JVM 스레드가 커넥션을 떼어두고(suspend) 대기하는 모습과 DB의 락 타임아웃, 커넥션 풀 대기 2초 블로킹을 눈으로 직접 확인하니 원리가 완벽히 체득되었습니다. 실무에서 트랜잭션 관련 타임아웃 장애를 디버깅하거나, 동료 코드 리뷰 및 신규 입사자 온보딩 교육 시 시각 교재로 매우 강력할 것입니다.

#### 3. 이 화면으로 이해했다는 자신감 (1~5)과 그 이유
- **점수: 5점 (매우 높음)**
