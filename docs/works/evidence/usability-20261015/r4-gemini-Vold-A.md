## 1. 열기 전 질문 (2~3개)

동료에게서 "이거 한번 써 봐, 배울 게 있을 거야"라는 말과 함께 링크만 받았을 때, URL의 `spring`이라는 단어를 보고 평소 실무를 하며 속 시원히 알지 못했던 아래 의문들이 떠올랐습니다.

1. **질문 1**: 서비스 메서드에 `@Transactional`을 걸고 그 안에서 다른 `@Transactional` 메서드를 호출할 때, 기본인 `REQUIRED`와 `REQUIRES_NEW`는 커넥션 풀(HikariCP)과 DB 세션을 실제로 어떻게 다르게 쓰는가?
2. **질문 2**: 실무에서 "안쪽 트랜잭션에서 예외가 났는데 바깥에서 try-catch로 잡아도 결국 전체가 롤백되고 `UnexpectedRollbackException`이 터진다"고 하던데, 대체 "롤백 전용(Rollback-only)"이라는 표시는 어디에 어떻게 남는 것인가?
3. **질문 3**: 시니어 개발자들이 "REQUIRES_NEW를 남발하면 커넥션 풀 고갈이나 데드락이 발생할 수 있다"고 경고하곤 했는데, 커넥션 풀 크기가 작거나 같은 행을 수정할 때 내부에서 실제로 어떤 대기와 락이 일어나는가?

## 2. 첫인상(60초)과 첫 세 번의 조작

### 첫인상 (처음 60초)
- **눈에 들어온 것**: 상단에 늘어선 시나리오 탭(`REQUIRED · 안쪽이 실패`, `REQUIRES_NEW`, `REQUIRES_NEW · 같은 행`, `REQUIRES_NEW · 풀 1칸`, `NESTED · 안쪽이 실패`, `0.5초 안에 다시 빌림`)과, 그 아래 `앱 코드 → Spring 트랜잭션 → JdbcTemplate → HikariCP → pgjdbc → 연결(TCP/소켓) → PostgreSQL`로 이어지는 박스 구조도가 강렬하게 들어왔습니다. 화면 하단에는 밀도 높은 시간대별(+452 ms 등) 타임라인/시퀀스 차트가 빼곡했고, 우측에는 실제 자바 코드(`lab/Inner.java`, `lab/Outer.java`)와 호출 상세 패널이 배치되어 있었습니다.
- **무엇을 하는 화면이라고 생각했는가**: 스프링의 `@Transactional` 전파 옵션이 작동할 때, 자바 코드 프록시 호출부터 트랜잭션 매니저, HikariCP 커넥션 대여/반납, JDBC 패킷 전송, PostgreSQL DB 엔진 내부 상태(트랜잭션 ID `xid`, 행 락, 커밋 로그)까지 전 과정을 타임라인 단위로 일치시켜 보여주는 심층 인터랙티브 옵저버빌리티/학습 도구라고 생각했습니다.
- **어디부터 보려 했는가**: 첫 화면에 선택되어 있던 `REQUIRED · 안쪽이 실패`의 시나리오 설명("안쪽이 실패하고 바깥이 그 예외를 삼키면, 바깥은 커밋되나?")과 결과 요약("C1 트랜잭션 753 -> ROLLBACK", "UnexpectedRollbackException")에 즉시 눈이 갔고, 왜 바깥이 예외를 잡았는데도 롤백되는지 확인하고자 하단 타임라인의 예외 발생 구간(+822 ms)을 먼저 보려 했습니다.

### 첫 세 번의 조작
1. **조작 1 (상단 배지 클릭 시도)**
   - **무엇을 왜 눌렀나**: 상단 "주요 순간"에 있는 `+822 롤백 전용 표시` 알약(pill) 버튼을 눌러 해당 시점으로 바로 이동하고자 했습니다.

2. **조작 2 (하단 타임라인 선택)**
   - **무엇을 왜 눌렀나**: 배지가 안 눌려 하단 타임라인에서 롤백이 일어나는 `8 DataSourceTransactionManager.doSetRollbackOnly` 부근(X=240, Y=820)을 직접 클릭했습니다.

3. **조작 3 (`REQUIRES_NEW` 탭 클릭)**
   - **무엇을 왜 눌렀나**: 내가 가진 지식("REQUIRES_NEW는 새 트랜잭션을 연다")이 커넥션 풀과 DB 관점에서 실제로 어떻게 동작하는지 비교하기 위해 상단 탭의 `REQUIRES_NEW`(X=280, Y=25)를 눌렀습니다.
   - **무슨 일이 일어났나**: URL이 `sc=5-requires-new`로 바뀌며, 커넥션 2개(C1, C2)와 트랜잭션 2개(753, 754)가 등장하는 완전히 새로운 시나리오 화면으로 전체가 갱신되었습니다.

## 4. 이 화면이 무엇을 보여 주는 화면인가?

이 화면은 Spring Framework의 `@Transactional` 전파 옵션(`REQUIRED`, `REQUIRES_NEW`, `NESTED`)과 HikariCP 커넥션 풀, 그리고 PostgreSQL 데이터베이스 엔진이 실제 런타임에서 상호작용하는 구체적인 내부 메커니즘을 시간축 기반으로 동기화하여 보여주는 심층 관측 도구입니다 [화면에서 확인]. 기존에는 서비스 코드 레벨에서 `@Transactional` 어노테이션만 붙여두면 스프링이 마법처럼 트랜잭션을 관리해준다고 막연하게 생각했었습니다 [원래 알던 것]. 하지만 이 화면을 통해 스프링의 `TransactionInterceptor`와 `DataSourceTransactionManager`가 스레드 로컬에 커넥션을 바인딩하고 해제(`doSuspend`/`doResume`)하는 과정, 안쪽 트랜잭션 실패 시 `doSetRollbackOnly`로 마킹하는 과정, 그리고 HikariCP가 커넥션의 유휴 시간(500ms)에 따라 `isValid` 검사를 생략하거나 풀이 고갈되었을 때 스레드가 락에 갇히는 과정이 타임라인과 다이어그램으로 완벽히 증명됩니다 [화면에서 확인]. 또한 애플리케이션의 스레드 상태(JFR)와 DB 백엔드의 내부 상태(`pg_stat_activity`, `pg_locks`, `xid`, `idle in transaction`)를 한 화면에 엮어 보여줌으로써, 분산 환경에서 발생하는 앱 레벨의 셀프 데드락과 락 타임아웃의 근본 원인을 직관적으로 규명할 수 있도록 돕는 학습용 플랫폼으로 이해됩니다 [추측].

## 5. 질문에 대한 답과 화면에서 배운 것

### 1) 열기 전 질문에 대한 답

- **질문 1 (REQUIRED vs REQUIRES_NEW의 커넥션과 세션 차이)**
  - `REQUIRED`는 바깥 메서드가 빌린 커넥션 `C1`을 안쪽 메서드가 그대로 공유하여 같은 트랜잭션 번호(xid 753) 안에서 쿼리를 실행합니다 [화면에서 확인: `REQUIRED · 안쪽이 실패` 중앙 다이어그램 "스레드에 묶인 연결 C1", 하단 타임라인 +453 ms `handleExistingTransaction`].
  - 반면 `REQUIRES_NEW`는 바깥의 `C1`을 스레드에서 잠시 내려놓고(`doSuspend`), HikariCP 풀에서 새 커넥션 `C2`를 새로 빌린 뒤(`ConcurrentBag.borrow`), DB에 새로운 `BEGIN`을 날려 새 트랜잭션(xid 754)을 엽니다 [화면에서 확인: `REQUIRES_NEW` 타임라인 +454 ms `DataSourceTransactionManager.doSuspend · C1을 스레드에서 떼어 둠`, 중앙 다이어그램 "떼어 둔 연결 C1", "C1 빌려줌 C2 빌려줌"].
  - 안쪽 트랜잭션이 끝나 커밋되면 `C2`를 풀에 돌려준 뒤, 떼어 두었던 `C1`을 다시 스레드에 묶어(`doResume`) 바깥 트랜잭션을 재개합니다 [화면에서 확인: `REQUIRES_NEW` 주요 순간 `+946 C1 다시 묶음`, 하단 타임라인 +946 ms].

- **질문 2 (안쪽 예외 catch 시 롤백 전용 마킹과 UnexpectedRollbackException의 실체)**
  - `REQUIRED` 환경에서 안쪽 메서드가 예외(`IllegalStateException`)를 던지면, 안쪽 프록시의 `AbstractPlatformTransactionManager.processRollback`이 실행되지만 물리 커넥션 `C1`에 ROLLBACK SQL을 바로 보내지는 않습니다 [화면에서 확인: `REQUIRED · 안쪽이 실패` 타임라인 +822 ms `DataSourceTransactionManager.doSetRollbackOnly · 롤백 전용 표시(연결 위로는 보내지 않음)`].
  - 대신 트랜잭션 상태 객체에 "롤백 전용(Rollback-only)" 플래그만 세팅해 둡니다 [화면에서 확인: 최하단 범례 "Spring · HikariCP - 롤백 전용 표시"].
  - 바깥 메서드가 try-catch로 예외를 삼키고 정상 종료하여 프록시가 `AbstractPlatformTransactionManager.commit`을 호출할 때, 트랜잭션 매니저가 이 롤백 전용 마킹을 발견하고는 커밋 대신 물리적 `ROLLBACK (S_1)`을 DB에 전송한 뒤, 호출자에게 `UnexpectedRollbackException`을 던집니다 [화면에서 확인: `REQUIRED · 안쪽이 실패` 타임라인 +1,235 ms `AbstractPlatformTransactionManager.processRollback +2 · x UnexpectedRollbackException`].

- **질문 3 (REQUIRES_NEW의 풀 고갈 및 같은 행 수정 데드락 메커니즘)**
  - **풀 크기 1칸일 때**: 바깥 트랜잭션이 커넥션 `C1`을 쥔 채 안쪽 `REQUIRES_NEW`로 들어가서 새 커넥션을 요청하는데, 풀에 남은 커넥션이 없으므로 main 스레드가 `ConcurrentBag.borrow`에서 대기 상태에 빠집니다 [화면에서 확인: `REQUIRES_NEW · 풀 1칸` 중앙 빨간 상자 "기다림의 고리(풀) +587 ~ +2,590 ms"]. `C1`이 반납되어야 빈 칸이 생기는데, 반납할 주체인 main 스레드가 대기에 갇혀 있으므로 자기 자신을 기다리는 교착이 발생하고, 결국 HikariCP 설정값인 `connectionTimeout 2,000 ms`가 지나 `SQLTransientConnectionException`이 터지며 전체가 롤백됩니다 [화면에서 확인: `REQUIRES_NEW · 풀 1칸` 우측 패널 `ConcurrentBag.borrow 한 일: 잠듦 2,003 ms`, 결과 요약].
  - **같은 행을 수정할 때**: 바깥 `C1`이 1번 행을 수정한 상태(`idle in transaction, xid 753`)에서 안쪽 `C2`가 같은 1번 행에 UPDATE를 시도하면, PostgreSQL 엔진 수준에서 `C2`가 `C1`의 트랜잭션 753의 행 락(`ShareLock`)을 기다리며 멈춥니다 [화면에서 확인: `REQUIRES_NEW · 같은 행` 중앙 빨간 상자 "기다림의 고리", 우측 패널 "받지 못한 락 C2 -> transactionid 753 ShareLock"]. 이때 DB 엔진은 `C1`이 그냥 멍때리고 있는 상태(`ClientRead`)로만 보이고 앱 안의 스레드 대기 관계를 알 수 없기 때문에 데드락이 아니라고 판단(`NoDeadlock`)합니다 [화면에서 확인: 중앙 빨간 상자 3번 "교착 검사 결과 NoDeadlock"]. 결국 안쪽에 설정해 둔 `lock_timeout = '3s'`가 만료되어 `canceling statement due to lock timeout (55P03)` 오류로 강제 중단됩니다 [화면에서 확인: 타임라인 +4,033 ms `E 55P03`].

### 2) 그 밖에 이 화면에서 새롭게 배운 것
- **NESTED의 실체 (SAVEPOINT 활용)**:
  - `NESTED` 전파 옵션은 새 커넥션을 빌리는 것이 아니라, 기존 커넥션 `C1` 안에서 DB의 `SAVEPOINT "SAVEPOINT_1"`을 생성합니다 [화면에서 확인: `NESTED · 안쪽이 실패` 타임라인 +472 ms `JdbcTransactionObjectSupport.createSavepoint` 및 연결 메시지 `SAVEPOINT "SAVEPOINT_1"`].
  - 안쪽에서 실패하면 `ROLLBACK TO SAVEPOINT`를 날려 안쪽 변경분만 되돌리고, 바깥은 정상적으로 최종 커밋(`COMMIT`)할 수 있습니다 [화면에서 확인: `NESTED · 안쪽이 실패` 결과 요약 "잔액 kim 100 -> 90, lee 200 -> 200", 주요 순간 `+890 C1 ROLLBACK TO SAVEPOINT`].
- **HikariCP의 커넥션 생존 검사 최적화 (500ms 룰)**:
  - 커넥션을 풀에서 빌릴 때 매번 DB에 검사 쿼리(`isValid`)를 날리는 것이 아니라, 풀에 반납된 지 500ms가 넘었을 때만 생존 검사를 수행합니다 [화면에서 확인: `0.5초 안에 다시 빌림` 타임라인 +8.85 ms `쉰 지 1,225 ms > 창 500 ms -> 생존 검사` vs +132 ms `쉰 지 6 ms < 창 500 ms -> 검사 건너뜀`]. 잦은 커넥션 대여 시 네트워크 핑 오버헤드를 줄이는 HikariCP의 구체적인 내부 정책을 처음 알게 되었습니다 [원래 알던 것과 비교하여 화면에서 확인].
- **PostgreSQL 프로토콜과 상태 코드**:
  - 클라이언트-서버 간 메시지에서 `Q`는 단순 질의, `P B D E S`는 확장 질의(Parse, Bind, Describe, Execute, Sync)이며, 트랜잭션 상태를 알리는 `Z(T)`(트랜잭션 안), `Z(I)`(트랜잭션 밖), `Z(E)`(실패한 트랜잭션 안)의 차이를 배웠습니다 [화면에서 확인: 최하단 범례 "연결 위 메시지 (PostgreSQL 프로토콜)"].

   - 화면 최하단에 있는 범례(JFR 기록, 관찰, 추론, PostgreSQL 프로토콜 등)는 이 화면을 이해하는 데 핵심적인 가이드라인입니다. 스크롤을 맨 밑까지 내려야만 볼 수 있는 지금 형태보다는, 상단의 `[표지·약어 풀이]` 버튼을 눌렀을 때 모달이나 사이드 드로어로 바로 열려 언제든 참고할 수 있다면 초심자에게 훨씬 친절할 것입니다.
