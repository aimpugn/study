## 1. 열기 전 질문 2~3개

동료에게 `http://127.0.0.1:8765/concept-9-spring.html` 링크 하나만 전달받았을 때, 3년 차 백엔드 개발자로서 떠올린 질문은 다음과 같았습니다.

1. URL에 `concept-9-spring`이라고 되어 있는데, 내가 실무에서 늘 쓰던 `@Transactional`이나 스프링의 어떤 핵심 개념을 시각적으로 다루는 화면일까?
2. 서비스 메서드에 `@Transactional`을 붙였을 때 스프링 내부(트랜잭션 매니저)와 HikariCP 커넥션 풀, 실제 DB(PostgreSQL) 사이에서 커넥션을 획득하고 트랜잭션을 시작/종료하는 실제 순서를 눈으로 확인할 수 있을까?

## 2. 첫인상(60초)과 첫 세 번의 조작

### 첫인상 (처음 60초)
페이지가 열리자마자 상단 좌측의 **'Spring 전파'** 타이틀과 함께 상단 탭의 여러 시나리오 버튼들(`REQUIRED · 안쪽이 실패`, `REQUIRES_NEW`, `NESTED · 안쪽이 실패` 등)이 눈에 들어왔습니다. 바로 아래에는 **"안쪽이 실패하고 바깥이 그 예외를 삼키면, 바깥은 커밋되나?"**라는 구체적인 질문과 결과 요약(`{ C1 753 ↶ ROLLBACK | C2 - } ... UnexpectedRollbackException`)이 적혀 있어, "아, 스프링 트랜잭션 전파 속성의 실제 동작을 단계별로 검증해 주는 시뮬레이션/트레이스 도구구나"라고 즉시 파악했습니다.

화면은 크게 4개 영역으로 나뉘어 있었습니다:
- **중앙 상단 타임라인 바**: 시간축(0 ms ~ 1.00 s)에 따른 `main` 스레드와 `C1`, `C2` 커넥션의 상태
- **중앙 좌측 다이어그램**: JVM(main 스레드, HikariCP 풀)과 PostgreSQL DB 세션의 물리적 연결 관계
- **중앙 우측 코드 뷰어**: 실제 작성된 Java 코드(`lab/Inner.java`, `lab/Outer.java`)
- **하단 트레이스 목록 및 상세 패널**: 시간순으로 실행된 스프링 내부 클래스(`AbstractPlatformTransactionManager` 등), HikariCP, JDBC 패킷 로그와 우측 상세 정보

정보량이 굉장히 방대하고 전문적이어서 처음에는 어디부터 봐야 할지 살짝 압도당했습니다. 가장 눈길이 간 곳은 상단 질문의 결과인 `UnexpectedRollbackException`이었고, "바깥에서 예외를 잡았는데 왜 롤백 예외가 터졌을까?"를 확인하기 위해 하단 트레이스 영역의 롤백 관련 로그로 시선이 이동했습니다.

### 첫 세 번의 조작
1. **조작 1 (click_at x: 250, y: 825)**:
   - **한 일**: 하단 트레이스 목록에서 안쪽 예외 발생 후 롤백이 진행되는 구간을 확인하고자 클릭했습니다.

## 4. 다 써 본 뒤 화면에 대한 총괄 이해

이 화면은 Spring 프레임워크의 `@Transactional` 전파 옵션(REQUIRED, REQUIRES_NEW, NESTED)과 HikariCP 커넥션 풀, 그리고 PostgreSQL 데이터베이스의 물리적 세션이 런타임에 어떻게 상호작용하는지를 마이크로초 단위의 단일 타임라인 상에서 통합 시각화해 주는 관측/분석 도구입니다 [화면에서 확인]. 

기존에는 서비스 계층에 `@Transactional`을 붙이면 스프링 AOP가 트랜잭션을 알아서 열고 닫는다는 정도로만 추상적으로 알고 있었는데 [원래 알던 것], 화면을 통해 `TransactionInterceptor`부터 `DataSourceTransactionManager`, `HikariPool`, `ConcurrentBag`, JDBC 드라이버(`pgjdbc`)의 쿼리 패킷 송수신(P, B, D, E, S), 그리고 실제 DB 세션의 트랜잭션 ID(xid 753, 754)와 락 대기 상태까지 단계별로 어떻게 묶이고 풀리는지 명확히 확인할 수 있었습니다 [화면에서 확인]. 

이 화면에 표시된 데이터는 단순한 정적 도표가 아니라, `txlab`이라는 계측 도구가 실제 Spring Boot 애플리케이션과 PostgreSQL 인스턴스를 구동하여 중단점(멈춤 자리)을 걸고 각 컴포넌트의 런타임 상태를 직접 캡처하여 재구성한 실제 실험 결과물로 보입니다 [추측].

## 5. 배운 점 (질문별 & 추가 학습)

### [질문 1] 스프링의 어떤 개념을 다루는 화면인가?
- **[화면에서 확인]**: 상단 헤더의 'Spring 전파' 문구와 시나리오 버튼들(`REQUIRED · 안쪽이 실패`, `REQUIRES_NEW`, `REQUIRES_NEW · 같은 행`, `REQUIRES_NEW · 풀 1칸`, `NESTED · 안쪽이 실패`, `0.5초 안에 다시 빌림`)에서 확인했습니다.
- 실무에서 자주 마주치지만 내부를 보기 힘든 `@Transactional` 전파 속성에 따른 트랜잭션 경계 설정, 예외 전파, 커넥션 풀링 고갈, DB 행 락 대기 현상을 집중적으로 다루고 있었습니다.

### [질문 2] `@Transactional` 동작 시 커넥션과 트랜잭션의 실제 라이프사이클 순서는?
- **[화면에서 확인]**: `REQUIRED · 안쪽이 실패` 시나리오의 하단 트레이스 목록과 우측 하단 상세 패널에서 확인했습니다.
  - 안쪽 메서드(`Inner.requiredFails`)에서 예외가 터지면 (+453 ms, 깊이 5), 스프링 트랜잭션 매니저는 트랜잭션을 즉시 롤백하지 않고 `DataSourceTransactionManager.doSetRollbackOnly`를 호출하여 트랜잭션 상태에 `⚑ 롤백 전용` 플래그를 마킹합니다 (+822 ms, 트레이스 8번 줄).
  - 바깥쪽 코드(`Outer.required`)의 `try-catch` 블록에서 `IllegalStateException`을 정상적으로 삼켰기 때문에, 바깥 메서드 종료 시점에는 정상 완료로 판단하여 `commitTransactionAfterReturning` -> `AbstractPlatformTransactionManager.commit`을 호출합니다 (+1,235 ms, 트레이스 3번 줄).
  - 하지만 트랜잭션 매니저는 커밋 내부에서 "이미 rollback-only로 마킹되어 있음"을 확인하고 커밋 대신 `processRollback`을 호출하며, 최종적으로 `UnexpectedRollbackException`을 던집니다 (+1,235 ms 우측 하단 패널: *"Transaction rolled back because it has been marked as rollback-only"*).

### [질문 3] 전파 옵션(REQUIRES_NEW, NESTED)과 HikariCP의 상호작용은 어떻게 일어나는가?
- **[화면에서 확인]**: 각 시나리오 탭에서 다음 사실들을 명확히 배웠습니다.
  1. **REQUIRES_NEW의 동작 (`REQUIRES_NEW` 탭)**:
     - 바깥 트랜잭션이 쓰던 커넥션 C1을 일시 중단하고 떼어 둡니다 (`DataSourceTransactionManager.doSuspend • +1 𝄁𝄁C1`, 다이어그램의 `---II 떼어 둔 연결` 표시, +454 ms).
     - HikariCP에서 새 커넥션 C2를 빌려와(`ConcurrentBag.borrow • +C2`) PostgreSQL 세션 4467에 새 트랜잭션 `번호 754`를 시작합니다 (+455 ms).
  2. **REQUIRES_NEW와 DB 행 락 충돌 (`REQUIRES_NEW · 같은 행` 탭)**:
     - 바깥 트랜잭션(C1, xid 753)이 UPDATE한 동일 행을 안쪽 트랜잭션(C2, xid 754)이 수정하려고 하자, DB 세션 C2가 `Lock/transactionid` 상태로 락을 기다립니다 (+2,653 ms 우측 하단: *"받지 못한 락: C2 -> transactionid 753 ShareLock"*, 다이어그램의 `↻ 기다림의 고리` 및 `🔒 락 기다림`).
     - 결국 3초 타임아웃(`SET LOCAL lock_timeout = '3s'`)이 만료되면서 `UncategorizedSQLException`이 발생하고 두 트랜잭션 모두 롤백됩니다.
  3. **커넥션 풀 고갈 데드락 (`REQUIRES_NEW · 풀 1칸` 탭)**:
     - 커넥션 풀 크기가 1개(`HikariCP · 최대 1칸`)일 때 바깥 트랜잭션이 C1을 쥔 채 떼어 두고 새 커넥션을 요청하자, 풀에 가용한 커넥션이 없어 `ConcurrentBag.borrow`에서 2,003 ms 동안 잠들며 멈춰 섭니다 (타임라인의 붉은 빗금 구간, +587 ms ~ +2,590 ms).
     - 타임아웃 후 `SQLTransientConnectionException` -> `CannotCreateTransactionException`이 발생하며 전체 작업이 롤백됩니다.
  4. **NESTED의 세이브포인트 동작 (`NESTED · 안쪽이 실패` 탭)**:
     - 새 커넥션을 빌리지 않고 기존 C1 커넥션을 그대로 공유합니다 (C2는 idle 유지, 다이어그램 및 트레이스 +474 ms).
     - 대신 DB에 `SAVEPOINT "SAVEPOINT_1"` 쿼리를 전송합니다 (+472 ms). 안쪽에서 예외가 발생하면 전체 트랜잭션을 롤백하거나 rollback-only로 마킹하는 대신, `ROLLBACK TO SAVEPOINT "SAVEPOINT_1"` 쿼리를 날려 안쪽 변경사항만 되돌리고 세이브포인트를 해제합니다 (+890 ms).
     - 바깥 트랜잭션은 안쪽 예외를 삼킨 뒤 정상 커밋되어 최종 데이터가 `kim 100->90`(바깥 수정 반영), `lee 200->200`(안쪽 수정 취소)으로 남습니다 (상단 결과 바).
  5. **HikariCP의 생존 검사 최적화 (`0.5초 안에 다시 빌림` 탭)**:
     - 커넥션을 반납한 후 아주 짧은 시간 안에 다시 빌릴 때는 생존 검사(validation query)를 생략합니다 (+132 ms 우측 하단 패널: *"한 일: 풀에서 C1 빌림 · 쉰 지 6 ms < 창 500 ms -> 검사 건너뜀"*).
     - 반면 REQUIRES_NEW에서 새 커넥션을 빌릴 때는 `PoolBase.isConnectionDead`로 생존 검사 쿼리(`QueryExecutorImpl.execute ... -> C2 Q ""` )를 실제로 날리는 것을 확인했습니다.

### [화면에서는 알 수 없었던 것]
- PostgreSQL 엔진 내부에서 행 락(Row Exclusive Lock)이 디스크 페이지 내 튜플 헤더(`xmax` 등)에 물리적으로 어떻게 기록되는지, MVCC 스냅샷 격리 수준이 언두 로그나 가비지 컬렉션(VACUUM)과 어떻게 연결되는지는 화면에 표시되지 않아 알 수 없었습니다.

## 6. 막힌 곳, 헷갈린 곳, 바로잡은 곳

1. **상단 시나리오 탭 클릭 위치 혼선**:
   - 처음에는 상단 시나리오 버튼들의 너비와 배치가 화면 전체에 넓게 퍼져 있을 것으로 생각하고 x: 740, 710 부근을 클릭했으나 버튼이 반응하지 않았습니다.
   - 스크린샷을 자세히 관찰한 결과, 각 시나리오 탭마다 우측에 붙는 실행 버튼(`실행 a ⚠️`, `실행 b ⚠️`, `실행 c` 등)의 유무에 따라 버튼들의 가로 폭과 시작 위치가 유동적으로 변하며 좌측 영역에 모여 있다는 것을 파악했습니다. 스크롤을 `Home` 키로 최상단에 맞춘 후 정밀한 픽셀 좌표를 계산하여 클릭함으로써 원하는 시나리오를 정상적으로 탐색할 수 있었습니다.
2. **트레이스 목록 행 선택의 정밀도**:
   - 하단 트레이스 목록의 행 높이가 매우 촘촘하여, 마우스 좌표 클릭만으로는 원하는 특정 스프링 내부 메서드(예: `commit`, `processRollback`)를 짚기 어려웠습니다.
   - 키보드 방향키(`ArrowDown`, `ArrowUp`)를 입력했을 때 트레이스 선택이 한 행씩 순차적으로 부드럽게 이동하는 것을 발견하고, 키보드 조작을 통해 정확하게 원하는 메서드 호출 시점의 상세 패널을 열어볼 수 있었습니다.
3. **다이어그램 기호의 의미 파악**:
   - JVM 다이어그램에서 `main` 스레드와 `C1` 커넥션 사이의 `---II` 표시를 보고 처음에는 "연결이 끊어졌거나 에러가 났나?" 하고 헷갈렸습니다.
   - 다이어그램 하단 범례의 `---II 떼어 둔 연결`이라는 설명을 읽고 나서야 스프링의 `TransactionSynchronizationManager`가 기존 커넥션을 ThreadLocal에서 잠시 `suspend`하여 보관해 둔 상태를 의미한다는 것을 바로잡아 이해했습니다.

## 7. 이 화면에 바라는 것

1. **상단 결과 바 클릭 시 핵심 원인 줄 점프 기능**:
   - 상단에 "UnexpectedRollbackException"이나 "CannotCreateTransactionException"처럼 결과가 명시되어 있는데, 이 텍스트 뱃지를 클릭하면 하단 트레이스 목록에서 그 원인이 된 핵심 줄(`doSetRollbackOnly` 또는 `ConcurrentBag.borrow` 타임아웃 줄)로 포커스가 즉시 이동하고 하이라이트되면 학습자가 인과관계를 훨씬 빠르게 짚을 수 있을 것 같습니다.
2. **약어 및 프로토콜 풀이 팝업 상시화**:
   - 트레이스에 `P B D E S`, `Z(T)`, `AC=false` 같은 드라이버/DB 수준의 약어가 매우 유익하게 제공되지만, 화면 하단으로 스크롤을 내리면 약어 범례가 시야에서 벗어납니다. 상단이나 마우스 호버 툴팁으로 해당 약어(예: Parse, Bind, Describe, Execute, Sync)의 풀이를 바로 볼 수 있다면 백엔드 주니어 개발자들에게 훨씬 친절할 것입니다.
3. **타임라인 바의 직접 클릭 및 스크러빙(Scrubbing) 지원**:
   - 타임라인 바의 특정 시간대(예: 800 ms 지점)를 마우스로 클릭하거나 드래그했을 때 해당 시간의 다이어그램 상태와 트레이스 줄로 동기화되어 이동한다면, 시간의 흐름에 따른 상태 변화를 훨씬 직관적으로 체감할 수 있을 것입니다.
