### C1. 'REQUIRES_NEW · 같은 행' 장면에서 안쪽(REQUIRES_NEW) UPDATE는 어느 연결로 갔나요? 그 순간 바깥 트랜잭션의 연결은 어디에, 어떤 상태로 있었나요?
- **안쪽 UPDATE가 간 연결**: **`C2` 연결**로 갔습니다. [화면에서 확인]

- **그 순간 바깥 트랜잭션 연결의 위치와 상태**: 
  - **위치**: JVM 내부에서는 `main` 스레드와 분리되어 **`HikariCP` 풀 안에 보관**되어 있었고, DB 쪽에서는 **PostgreSQL `C1 · 4679` 세션**에 물려 있었습니다. [화면에서 확인]
  - **상태**: 
    - JVM 스레드 관점에서는 **`---II 떼어 둔 연결`(suspend)** 상태였습니다 (다이어그램 범례 및 main-C1 사이의 점선 기호). [화면에서 확인]
    - DB 관점에서는 트랜잭션을 끝내지 않고 열어둔 채 클라이언트의 다음 요청을 기다리는 **`idle in tx` (`idle in transaction`)** 상태였습니다. 우측 하단 관찰창의 표에서도 `C1 4679 | idle in transaction | Client/ClientRead | xid 753`으로 표시되어 있었습니다 (+2,653 ~ +3,102 ms 관찰창). [화면에서 확인]

### C2. 같은 장면에서 안쪽 UPDATE는 왜 진행되지 않았고, 어떻게 끝났나요? DB는 왜 이것을 교착(deadlock)으로 보지 않았나요?
- **진행되지 않은 이유**: 바깥 트랜잭션(C1, xid 753)이 이미 1번 계좌 행을 UPDATE한 뒤 아직 커밋/롤백을 하지 않아 해당 행의 배타적 락을 쥐고 있었는데, 안쪽 트랜잭션(C2, xid 754)이 같은 1번 행을 UPDATE하려고 시도하여 **C1의 트랜잭션 락 해제를 대기**해야 했기 때문입니다. [화면에서 확인]
  - *확인 위치*: 우측 하단 '막힌 동안 찍은 관찰' 칸의 *"받지 못한 락: C2 -> transactionid 753 ShareLock"*, 그리고 구성도에서 C2(754)로부터 C1(753)으로 연결된 붉은색 `↻ ⏱️3s` 곡선 화살표와 `🔒 락 기다림` 뱃지에서 확인했습니다.
- **끝난 방식**: 안쪽 코드에서 사전에 `SET LOCAL lock_timeout = '3s'`로 설정해 두었기 때문에, 3초 동안 락을 얻지 못하고 대기하다가 **락 타임아웃 오류(`오류 · postgres.c:3437`, SQLSTATE `55P03`)가 발생하며 안쪽 트랜잭션 754가 중단/롤백**되었습니다 (+4,030 ms 트레이스). 이 예외가 바깥으로 던져져(`x UncategorizedSQLException`) 결국 바깥 트랜잭션 753도 함께 롤백(`C1 753 ↶ ROLLBACK`)되며 끝났습니다. [화면에서 확인]
  - *확인 위치*: 맨 위 결과 칩 `{ C1 753 ↶ ROLLBACK | C2 754 ↶ ROLLBACK } ... x UncategorizedSQLException`, 우측 상단 코드 `lab/Inner.java:37`, 하단 트레이스 +4,030 ms 줄.
- **DB가 교착(deadlock)으로 보지 않은 이유**: 
  - 구성도의 C2 블록 아래에 초록색 글씨로 **`교착 검사 -> NoDeadlock`**이라고 명시되어 있습니다. [화면에서 확인]
  - 화면의 관찰 표를 보면 C2는 C1(xid 753)을 기다리고 있지만, C1은 DB 내부의 어떤 락도 기다리지 않고 단순히 앱의 다음 입력을 기다리는 유휴 상태(`idle in transaction`, `Client/ClientRead`)입니다. [화면에서 확인]
  - DB의 교착 감지기(Deadlock Detector) 관점에서는 `C2 -> C1`이라는 **단방향 대기만 존재하고 순환 대기 고리(Cycle)가 없기 때문에 교착이 아니라고 판단**한 것입니다. [화면에서 확인 및 추측] (실제로는 클라이언트 JVM의 main 스레드가 C2의 응답을 기다리며 블로킹되어 있어 C1으로 요청을 보낼 수 없는 '앱과 DB 사이의 분산 교착' 상태이지만, DB 엔진 자체의 세션 락 그래프에는 순환이 없으므로 DB는 교착으로 감지하지 못합니다.) [추측]

### C3. 'REQUIRES_NEW · 풀 1칸' 장면에서 풀이 한 칸이면 무슨 일이 일어나나요? 그동안 DB 서버로 무엇이 갔나요?
- **풀이 한 칸일 때 일어난 일**: 
  - 바깥 트랜잭션이 풀의 유일한 커넥션인 C1을 점유한 상태에서 안쪽 REQUIRES_NEW로 진입하여 C1을 잠시 떼어 두고(`doSuspend`), 새 커넥션을 HikariCP에 요청했습니다 (`ConcurrentBag.borrow`, +587 ms). [화면에서 확인]
  - 하지만 풀의 최대 크기가 1칸(`HikariCP · 최대 1칸`)뿐이어서 빌려줄 수 있는 빈 커넥션이 없었습니다 (`• 빈 칸 없음`). [화면에서 확인]
  - `main` 스레드는 커넥션을 얻기 위해 풀 대기 제한 시간인 **약 2초(2,003 ms) 동안 완전히 멈춰 서서 잠들었습니다** (구성도의 `⌛ <= 2,000 ms`, `↻ 기다림의 고리`, 타임라인 바의 붉은 빗금 블로킹 구간, +587 ms ~ +2,590 ms). [화면에서 확인]
  - 결국 타임아웃이 만료되어 `SQLTransientConnectionException` -> `CannotCreateTransactionException`이 발생했고, 떼어 두었던 C1을 다시 깨워(`doResume`) 바깥 트랜잭션 753마저 롤백되었습니다. [화면에서 확인]
  - *확인 위치*: 우측 하단 상세 패널 *"한 일: 풀에서 받지 못함(시간 초과) · 잠듦 2,003 ms"*, 맨 위 질문 줄 `{ C1 753 ↶ ROLLBACK } ... x CannotCreateTransactionException`.
- **그동안 DB 서버로 무엇이 갔나요?**:
  - **아무것도 가지 않았습니다 (0개의 요청/패킷)**. [화면에서 확인]
  - *확인 위치*: 하단 시간 순 줄 그림의 +587 ms부터 +2,592 ms 구간을 보면 `연결 위 메시지`, `백엔드 C1`, `백엔드 C2` 칸에 화살표나 메시지가 일체 없습니다. 구성도에서도 `C1 · 4899`는 그저 `◉ idle in tx` 상태로 멈춰 있을 뿐이며, 2초가 지나 클라이언트에서 타임아웃 예외가 터진 후인 +2,593 ms에 이르러서야 바깥 트랜잭션을 정리하기 위한 `ROLLBACK (S_1)` 패킷이 C1으로 처음 전송됩니다.

### C4. 'REQUIRED · 안쪽이 실패' 장면에서 안쪽이 실패했는데, 왜 바깥은 UnexpectedRollbackException으로 끝나나요?
- **이유**:
  - 안쪽 메서드(`Inner.requiredFails`)는 REQUIRED 속성이므로 바깥 트랜잭션(753)에 그대로 참여합니다. [화면에서 확인]
  - 안쪽에서 `IllegalStateException` 예외가 발생하자, 스프링의 트랜잭션 인터셉터가 이를 감지하고 `DataSourceTransactionManager.doSetRollbackOnly`를 호출하여 현재 트랜잭션 상태에 **`⚑ 롤백 전용` 플래그를 마킹**했습니다 (+822 ms, 트레이스 8번 줄). [화면에서 확인]
  - 바깥 메서드(`Outer.required`)는 `try-catch`로 안쪽의 예외를 삼켰기 때문에(우측 상단 코드 `Lab.note("outer-caught", e)`), 바깥 메서드는 정상 리턴된 것으로 간주되어 스프링의 정상 커밋 절차(`TransactionAspectSupport.commitTransactionAfterReturning` -> `AbstractPlatformTransactionManager.commit`)를 시도했습니다 (+1,235 ms, 트레이스 3번 줄). [화면에서 확인]
  - 하지만 트랜잭션 매니저는 커밋을 실행하려던 도중 트랜잭션이 이미 **"rollback-only로 마킹되어 있음"을 발견**하고, 커밋 대신 `processRollback`을 호출하면서 **`UnexpectedRollbackException`을 발생**시켰습니다 (+1,235 ms 우측 하단 상세 패널: *"한 일: × UnexpectedRollbackException: Transaction rolled back because it has been marked as rollback-only"*). [화면에서 확인]
  - 즉, 개발자 코드는 커밋을 요청했으나 트랜잭션은 안쪽의 실패로 인해 이미 되돌려질 운명이었기에, "커밋될 줄 알았는데 예기치 않게 롤백되었다"는 불일치를 스프링이 예외로 알린 것입니다. [화면에서 확인 및 추측]

### C5. '0.5초 안에 다시 빌림' 장면에서 HikariCP는 연결을 빌려줄 때마다 연결이 살아 있는지 검사하나요?
- **답**: **빌려줄 때마다 매번 검사하지 않습니다.** [화면에서 확인]
- **근거 및 동작 원리**:
  - *확인 위치*: 구성도의 HikariCP 풀 안 `C1` 박스에 표시된 `■ 6 ms` 표기와 하단 범례의 `■ 쉬 시간 · 생존 검사 창`, 그리고 우측 하단 상세 패널 (+132 ms).
  - 트레이스 +132 ms의 `ConcurrentBag.borrow` 줄을 보면 `• +C1 6 ms 쉼 검사 없음`이라고 적혀 있고, 우측 하단 패널에는 다음과 같이 명시되어 있습니다:
    > **한 일: 풀에서 C1 빌림 · 쉰 지 6 ms < 창 500 ms -> 검사 건너뜀**
  - 커넥션이 풀에 반납된 뒤 지난 유휴 시간(6 ms)이 생존 검사 유효 창인 500 ms(0.5초) 이내이면, DB로 ping/검증 쿼리를 날리지 않고 검사를 즉시 건너뛰고 커넥션을 대여해 줍니다. [화면에서 확인]
  - 반면 커넥션을 처음 빌리거나 오랜 시간(500 ms 이상) 쉬었을 때는 `PoolBase.isConnectionDead`를 호출하여 실제로 DB로 검사 쿼리(`QueryExecutorImpl.execute ... -> C2 Q ""`)를 전송하는 것을 'REQUIRES_NEW' 시나리오(+454 ms)에서 확인할 수 있었습니다. [화면에서 확인]

## 표지 질문: 화면의 표기 이해

### M1. 호출 줄 맨 앞의 숫자
- **이해한 뜻**: **호출 깊이 (Call Depth)**입니다. [화면에서 확인]
- **확인 근거**: 하단 범례 줄에 `0 1 2 호출 깊이`라고 명시되어 있습니다. 우측 상세 패널에서도 `깊이 5`, `깊이 13` 등으로 동일한 숫자가 표시됩니다.

### M2. 줄 끝의 ⑂ 기호 (또는 ↳ 기호)
- **이해한 뜻**: **갈림 (분기, Fork / Branch)**입니다. [화면에서 확인]
- **확인 근거**: 상단 필터 뱃지의 `↳ 갈림` 버튼 및 하단 범례의 `↳ 갈림` 표기에서 확인했습니다. 예외 발생으로 정상 흐름을 벗어나거나 별도의 롤백/분기 경로로 갈라져 나간 호출 지점에 붙습니다.

### M3. 점선 막대와 기울인 글씨의 줄
- **이해한 뜻**: **스택에만 보인 호출 (시작/끝 시각을 온전히 측정하지 못하고 호출 스택 샘플링에서만 포착된 메서드)**입니다. [화면에서 확인]
- **확인 근거**: 하단 범례의 `| 스택에만 보인 호출(기울임)` 항목과 우측 상세 패널의 *"스택에만 보임: 아래에서 올라온 예외가 지나가며 끝남(끝 시각 없음)"* 설명에서 직접 확인했습니다.

### M4. 줄 끝의 ＋2, ＋5 같은 표시
- **이해한 뜻**: **접힌 자식 (하위 호출 메서드 중 현재 화면에서 접혀 숨겨진 개수)**입니다. [화면에서 확인]
- **확인 근거**: 하단 범례의 `+n 접힌 자식` 표기에서 직접 확인했습니다. 화면 공간 절약을 위해 하위 호출들을 요약해 두고 펼칠 수 있도록 숫자로 표시한 것입니다.

### M5. '◉', '≈' 같은 작은 표지와, 자세한 내용의 'JFR 기록', '추론' 같은 표지
- **이해한 뜻**: 
  - `◉`: **관찰 (Observation)** 표지입니다. 도구(txlab)가 멈춤 자리나 런타임에서 시스템 상태(세션, 락, 풀 상태 등)를 직접 실측/스냅샷한 데이터 지점을 나타냅니다. [화면에서 확인] (다이어그램 범례: `◉ 관찰`)
  - `≈`: **추론 (Inference)** 표지입니다. 프록시, 리플렉션 호출처럼 직접 측정되지 않았으나 전후 인과관계상 논리적으로 연결된 관계를 나타냅니다. [화면에서 확인] (다이어그램 범례: `≈ 추론`)
  - 'JFR 기록', '추론': 데이터 수집 출처를 나타내는 표지입니다. Java Flight Recorder(JFR)의 실제 이벤트 로그에 기반한 것인지, 아니면 전후 스택을 바탕으로 추론한 것인지 정보의 근거 수준을 보여줍니다. [화면에서 확인 및 추측]

### 1. 이 화면에 더 있었으면 하는 것
- **타임라인 스크러버(시간 막대 직접 클릭/드래그)**: 현재는 타임라인 바의 특정 시간대를 직접 클릭해도 해당 시점으로 즉시 이동하지 않습니다. 시간 막대를 마우스로 훑으면 구성도와 트레이스가 해당 시점의 스냅샷으로 애니메이션처럼 연동되면 흐름을 이해하기 훨씬 쉬울 것입니다.
- **약어 및 프로토콜 모달/툴팁 고정**: `P B D E S`, `Z(T)`, `AC=false` 같은 JDBC/PostgreSQL 프로토콜 약어들이 트레이스에 빈번히 나오는데, 하단의 접힌 풀이를 스크롤해서 찾아보지 않더라도 마우스를 올렸을 때(hover) 툴팁으로 바로 풀이(Parse, Bind, Describe, Execute, Sync 등)가 뜨면 좋겠습니다.
- **예외 발생 지점 원클릭 역추적**: 상단 결과 칩의 예외 이름(`UnexpectedRollbackException` 등)을 누르면, 트레이스에서 그 원인이 된 마킹 지점(`doSetRollbackOnly`)으로 바로 스크롤되고 하이라이트되는 기능이 있으면 디버깅 학습에 큰 도움이 될 것입니다.

### 2. 실제 업무에서 다시 쓸지와 그 이유
- **반드시 다시 쓸 것입니다.**
- **이유**: 실무에서 멀티스레드 환경이나 서비스 간 호출 시 간헐적으로 발생하는 `UnexpectedRollbackException`, 커넥션 풀 고갈 데드락, 그리고 외래키나 공통 레코드를 갱신할 때 발생하는 원인 모를 락 타임아웃은 로그 파일의 스택 트레이스만 보고는 원인을 직관적으로 파악하기가 매우 어렵습니다. 이 화면처럼 **Java 코드 - Spring 트랜잭션 AOP - HikariCP 커넥션 풀 - DB 세션 및 락 상태**를 하나의 화면에서 입체적으로 보여주는 도구가 있다면, 팀 내 장애 부검(Post-mortem) 회의나 신규 입사자 교육, 복잡한 전파 옵션 설계 리뷰 시 강력한 시각적 근거 자료로 활용할 수 있기 때문입니다.

### 3. 이 화면으로 이해했다는 자신감 (1~5)과 그 이유
- **점수: 5점 (매우 높음)**
- **이유**: 3년 차 백엔드 개발자로서 평소 책이나 블로그 글로만 접해 추상적으로만 짐작하고 있던 개념들(REQUIRED의 rollback-only 전파 메커니즘, REQUIRES_NEW가 실제로 커넥션을 분리하여 suspend하는 과정, 풀 크기 1칸일 때 발생하는 셀프 데드락, NESTED가 DB SAVEPOINT를 활용해 부분 롤백을 수행하는 원리, HikariCP의 0.5초 커넥션 유효성 검사 생략 최적화)을 실제 메서드 호출 스택과 물리적 DB 세션의 패킷/락 레벨에서 완벽하게 눈으로 확인하고 검증할 수 있었기 때문입니다. 화면의 시각적 일치성과 구체성이 매우 뛰어나 의문점이 남지 않았습니다.
