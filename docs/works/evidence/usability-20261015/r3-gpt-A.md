## 1. 열기 전 질문

1. 전파 옵션마다 어떤 상황을 보여 주고, 결과가 어떻게 달라질까?
2. 커넥션과 DB 상태가 바뀌는 과정도 볼 수 있을까?
3. 장면을 직접 바꿔 보거나 실행 기록을 비교할 수 있을까?

## 2. 첫인상(60초)과 첫 세 번의 조작

첫 화면은 코드, 시간축, 커넥션 풀과 DB 상태가 한꺼번에 보여 복잡했습니다. 상단의 전파 옵션과 실행 버튼이 먼저 눈에 들어왔고, 화면 전체를 누르며 흐름을 알아보는 도구일 것 같았습니다. 아래쪽은 호출 시간순 기록, 오른쪽은 선택한 줄의 상세 내용으로 보였습니다.

1. `REQUIRES_NEW`를 눌렀습니다. 결과와 타임라인이 함께 바뀌어 옵션별 장면을 비교하는 화면이라고 이해했습니다.
2. `+454 C1 떼어 둠`을 눌렀습니다. C1은 스레드에서 분리됐지만 DB 관찰에는 `idle in transaction`, xid 753이 남아 있었습니다.
3. `+454 C2 빌림`을 눌렀습니다. 풀에서 C2를 빌리는 호출과 함께, C1은 여전히 DB에서 트랜잭션을 열고 있는 상태로 표시됐습니다.

## 4. 다 써 본 뒤, 이 화면이 보여 주는 것

[화면에서 확인] 이 화면은 Spring 전파 장면을 앱 호출, Spring 내부 호출, 커넥션 풀, PostgreSQL 상태와 메시지를 시간순으로 함께 보여 줍니다.  
[화면에서 확인] 상단 장면을 바꾸면 결과 요약과 코드, 시간축이 바뀌고, 시간 칩이나 타임라인 줄을 누르면 해당 순간의 상세가 열립니다.  
[화면에서 확인] 상세에는 출처 표지가 있으며, 화면은 JFR 기록, PostgreSQL 관찰, 함수 기록, 추론을 구분합니다.  
[화면에서 확인] 화면에 적힌 환경은 Java 25.0.4, PostgreSQL 18.6이며, 코드 패널은 기록 당시 컴파일한 사본이라고 설명합니다.  
[추측] 따라서 이 화면은 모든 Spring 설정에서의 보편적 실행 보장이라기보다, 표시된 실험 장면과 그 기록을 학습하기 위한 관측 화면으로 읽었습니다.

## 5. 질문에 대한 답과 새로 배운 점

**전파 옵션마다 어떤 상황을 보여 주나?**

[화면에서 확인] REQUIRED 장면의 설명과 `Inner.requiredFails` 코드 줄(18~21행)은 안쪽이 바깥 트랜잭션에 참여해 실패하는 상황을 보여 줍니다.  
[화면에서 확인] NESTED 장면의 상단 요약에는 C1의 하위 754와 COMMIT이 표시되고, 시간축에는 `SAVEPOINT`와 `ROLLBACK TO SAVEPOINT`가 나옵니다.  
[화면에서 확인] REQUIRES_NEW 같은 행 장면의 요약과 막힌 동안의 관찰에는 C2가 C1의 transactionid를 기다린 뒤 시간 초과되는 흐름이 나옵니다.

**커넥션과 DB 상태도 볼 수 있나?**

[화면에서 확인] REQUIRES_NEW의 C1 분리 시점에는 앱 쪽 `떼어 둔 연결 C1`과 DB 쪽 `idle in transaction`, xid 753이 함께 보였습니다.  
[화면에서 확인] 풀 1칸 장면의 `ConcurrentBag.borrow` 상세에는 연결을 받지 못하고 2,003 ms 잠든 뒤 시간 초과된 기록이 있습니다.  
[화면에서 확인] 같은 행 장면의 관찰 칸은 C2 → transactionid 753 대기와 `lock_timeout`으로 인한 55P03을 보여 줍니다.

**실행 기록을 비교하거나 직접 바꿀 수 있나?**

[화면에서 확인] 실행 a와 b 버튼으로 같은 장면의 기록을 바꿔 볼 수 있었습니다. REQUIRES_NEW의 반복 실행은 두 트랜잭션 모두 커밋됐고, REQUIRED 반복 실행은 둘 다 롤백됐습니다.  
[화면에서 확인] 보이는 줄 필터를 바꾸자 호출 111개 중 표시 수가 24개, 33개, 41개, 111개 등으로 달라졌습니다.

**그 밖에 배운 점**

[화면에서 확인] REQUIRED 장면의 `+822 롤백 전용 표시` 상세에는 연결로 메시지를 보내지 않는다고 적혀 있고, 뒤의 예외 상세에는 rollback-only로 표시돼 롤백됐다는 이유가 나옵니다.  
[화면에서 확인] 0.5초 재대여 장면에서 두 번째 연결 빌림은 4~6 ms 쉰 연결에 대해 500 ms 기준 안이라 생존 검사를 건너뛰었습니다.  
[원래 알던 것] 저는 `@Transactional`을 사용해 봤고 REQUIRED가 기본이며, REQUIRES_NEW는 새 트랜잭션이라는 이름 정도만 알고 있었습니다.  
[원래 알던 것] HikariCP가 커넥션 풀이라는 점과 DB가 인덱스로 위치를 찾아 페이지를 읽는다는 정도도 알고 있었습니다.  
[화면에서 확인] 이 화면에서는 풀에서 연결을 빌리고 돌려주는 흐름과 DB의 트랜잭션 상태는 봤지만, SELECT의 인덱스 탐색이나 디스크 페이지 읽기는 확인하지 못했습니다.

## 6. 막힌 곳과 바로잡은 점

처음에는 C1을 “떼어 둔다”는 말이 연결이나 트랜잭션을 끝낸다는 뜻인 줄 알 뻔했습니다. 선택한 순간의 DB 관찰에서 xid 753이 `idle in transaction`으로 남아 있어 바깥 트랜잭션은 계속 열려 있다고 이해를 고쳤습니다. 같은 행 장면도 교착으로 끝날 것이라 예상했지만 화면은 `NoDeadlock`을 표시하고 C2의 `lock_timeout`으로 중단했습니다. 화면 설명상 관찰은 선택 순간보다 앞서 찍혔을 수 있어 시각을 정확한 동시 상태로 단정하기 어렵습니다.

## 7. 이 화면에 바라는 것

처음 보는 사람을 위해 “장면 → 결과 → 시간축 → 상세” 순서의 짧은 시작 안내가 있으면 좋겠습니다. 필터의 현재 상태와 `전부`가 바꾸는 범위를 더 쉽게 구분하고, “풀 대기”와 “DB 락 대기”도 화면 위에서 한 문장으로 비교해 주면 좋겠습니다.
