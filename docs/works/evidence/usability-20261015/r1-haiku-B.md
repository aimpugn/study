**먼저 정정할 것.** A단계 보고에서 REQUIRED 장면의 "바깥이 왜 롤백되는지는 화면에서 알 수 없었다"고 적었는데 틀렸습니다. A단계에서는 글 읽기를 4,000자로 잘라서 상세 패널 끝을 놓쳤고, 찾기도 그때 렌더링되지 않은 상세 글을 찾지 못했습니다. 이번에 전체를 읽으니 답이 화면에 있었습니다(C4에 적었습니다).

**C1. 같은 행 장면에서 안쪽 UPDATE는 어느 연결로 갔나? 그 순간 바깥 연결은?**
- 안쪽 UPDATE는 C2로 갔습니다. 안쪽 BEGIN은 +530에 C2로, UPDATE는 멈춤이 풀린 뒤 +924에 C2로 보내졌습니다. [화면에서 확인: 타임라인 "→ C2 Q BEGIN … SET LOCAL lock_timeout", "→ C2 P B D E S · UPDATE acct SET balance"]
- 그 순간 바깥 연결 C1은 스레드에서 떨어진 상태였습니다. 위쪽 Spring 카드에는 "떼어 둔 연결 C1 추론"이라고 적혀 있습니다. [화면에서 확인: 위쪽 Spring 트랜잭션 카드, +528 "C1을 스레드에서 떼어 둠"]
- DB 쪽 C1은 "idle in transaction", xid 753 상태였습니다. [화면에서 확인: "멈춘 채로 찍은 관찰 +2,653" 카드의 세션 칸] 바깥은 열린 트랜잭션으로 행 (0,1)을 이미 고쳐 둔 상태였고, 화면에도 "행 (0,1)은 753이 고치는 중"이라고 나옵니다. [화면에서 확인: +1,026]
- "idle in transaction"은 트랜잭션은 열려 있지만 지금 쿼리를 실행하고 있지 않다는 뜻으로 짐작했습니다. [추측]

**C2. 안쪽 UPDATE는 왜 진행되지 않았고, 어떻게 끝났나? DB는 왜 교착으로 보지 않았나?**
- 진행되지 않은 이유: 행 (0,1)을 753이 쥐고 있어서 안쪽이 753의 커밋을 기다렸습니다. [화면에서 확인: +1,026 "753 끝나기를 기다림", 받지 못한 락 "C2 → transactionid 753 ShareLock"]
- 바깥은 안쪽이 돌아오기를 기다리는 중입니다. 화면 주석이 이 상호 기다림을 적고 있습니다. [화면에서 확인: Outer.java 47행 "안쪽은 바깥의 커밋을, 바깥은 안쪽의 반환을 기다립니다", Inner.java 31~34행 "락 기다림을 3초로 묶어 둡니다. 묶지 않으면 … 끝없이 기다립니다"]
- 끝난 과정: 3초 뒤 오류(+4,030, 코드 E 55P03), 안쪽 ROLLBACK(+4,046), C2 반납(+4,053), C1 다시 묶음, 바깥 ROLLBACK, "outer-threw · UncategorizedSQLException"(+4,060). [화면에서 확인] 55P03이 락 대기 초과라는 뜻은 화면에서 찾지 못했고, 3초 설정과 시간 차로 짐작했습니다. [추측]
- 교착 아님: 화면에 "교착 검사 → NoDeadlock"(+2,033)이 찍혀 있습니다. [화면에서 확인] DB는 C2가 753을 기다리는 것만 보았고, 753 쪽 C1은 락을 기다리는 중이 아니라 앱이 다음 명령을 보내기를 기다리는 상태("Client/ClientRead")였습니다. 교착이 되려면 바깥이 DB에 무언가를 기다려야 하는데, 바깥이 기다리는 것은 자바 스레드의 반환이라 DB에 보이지 않습니다. [추측] 이 추론은 화면 문장을 짜맞춘 것이라 원래 알던 DB 교착 검사 방식으로 확인하지는 못했습니다.

**C3. 풀이 한 칸이면 무슨 일이 생기나? 그동안 DB에 무엇이 갔나?**
- 바깥이 C1을 빌린 뒤 행을 고치고(+186 COMMIT 전 UPDATE), 안쪽 REQUIRES_NEW가 C1을 떼어 두고(+587 "C1을 스레드에서 떼어 둠") 풀에서 받으려 했습니다. 받지 못해 "시간 초과, 잠듦 2,003 ms"로 기다렸습니다. [화면에서 확인: +587 ConcurrentBag.borrow]
- 그 뒤 doBegin이 CannotCreateTransactionException을, getConnection이 SQLTransientConnectionException을 던졌습니다(+587). 바깥은 +2,592에 C1을 다시 묶고 C1 ROLLBACK(+2,594)을 보낸 뒤 "outer-threw · CannotCreateTransactionException"으로 끝났습니다(+2,613). [화면에서 확인]
- 대기 동안 DB에 간 것은 없었습니다. 대기 구간(+587~+2,592)에는 DB 연결 줄이 하나도 없습니다. 보이는 줄 필터의 "효과"가 켜져 있어 연결로 보낸 일은 보였을 것입니다. [화면에서 확인: 보이는 줄 필터, 타임라인] 안쪽은 연결을 못 얻어서 BEGIN도 보내지 못했습니다. [추측]
- 주의할 점: 위쪽 관찰 카드가 "관찰 +2,354"인데 "753 중단"이라고 적고 있습니다. 롤백은 타임라인에서 +2,594 이후에 일어났으므로, 카드 내용은 그 뒤 상태로 보입니다. [화면에서 확인: 카드와 타임라인 비교] 이 불일치의 원인은 짐작하지 못했습니다.

**C4. 안쪽이 실패했는데 바깥이 UnexpectedRollbackException으로 끝나는 이유는?**
- 안쪽은 새 트랜잭션이 아니라 바깥 트랜잭션에 참여했습니다(handleExistingTransaction, +453). [화면에서 확인]
- 바깥 commit 줄(+1,235)의 상세 패널에 답이 있었습니다. 예외 메시지는 "Transaction rolled back because it has been marked as rollback-only"이고, 만든 곳은 processRollback:938입니다. [화면에서 확인]
- 754행 코드는 "전역 롤백 전용 표시가 있으면 커밋하지 않고 롤백한다"는 분기입니다. [화면에서 확인: 상세 패널의 코드 조각] 바깥은 예외를 삼켰어도 커밋 시점에 이 표시를 보고 롤백하고 예외를 던집니다.
- 표시를 세우는 줄은 902~906행입니다. 참여한 트랜잭션이 실패하면 "marking existing transaction as rollback-only"라고 디버그 메시지를 찍고 doSetRollbackOnly를 부릅니다. [화면에서 확인: 갈린 줄 902 조각] 다만 이 장면의 안쪽 호출이 그 분기를 탔다는 연결은 상세 라벨에서 분명하지 않았습니다. [추측]
- 그래서 REQUIRED 장면에서 안쪽 실패 시점(+822)에는 DB ROLLBACK이 없고, 바깥 commit 시점(+1,236)에 한 번만 나갑니다. [화면에서 확인]
