## 2. 첫인상(60초)과 첫 세 번의 조작

첫인상은 스크린샷만 보고 적었습니다. 위에 시나리오 버튼 6개와 칩이 있고, 중간에는 앱 코드·Spring·HikariCP·pgjdbc·PostgreSQL을 가로로 나눈 구조도가 있습니다. 아래에는 시간순 타임라인이 있고 오른쪽에 상세 패널이 있습니다. "한 번 돌린 기록을 층별로 펼친 화면"이라고 짐작했지만 글씨가 작고 용어가 많아 어디부터 볼지 막막했습니다. 눈에 들어온 곳은 HikariCP 칸의 `C1 빌려줌 / C2 빈 칸`과 PostgreSQL 칸의 C1·C2였습니다.

## 4. 질문별로 알게 된 것

**질문 1 (REQUIRED)**
- [화면에서 확인] REQUIRED 장면의 결과 줄은 트랜잭션 번호가 753 하나뿐입니다(`C1 트랜잭션 753 → ROLLBACK`).
- [화면에서 확인] 안쪽 `Inner.requiredFails` 순간(+453)에 구조도는 `스레드에 묶인 연결 C1`을 보여 주고, C1은 `idle in transaction xid 753`, C2는 `idle xid -`입니다.
- [화면에서 확인] 타임라인의 안쪽 구간에는 `handleExistingTransaction` 다음 `→ C1 · P B D E S · UPDATE …`가 이어집니다. 필터가 켜진 상태라 `borrow` 줄은 안 보였지만, 같은 C1로 두 번째 UPDATE가 갑니다.
- [추측] `handleExistingTransaction`은 이름으로 보아 "이미 있는 트랜잭션에 참여"하는 단계일 것입니다.
- [화면에서 확인] 바깥이 예외를 잡았는데도 `+1,236 → C1 ROLLBACK`이 나가고 앱은 `UnexpectedRollbackException`을 받습니다. 잔액은 `kim 100 → 100, lee 200 → 200`이라 양쪽 변경이 모두 사라졌습니다.
- [화면에서 확인] 이유는 `+822 DataSourceTransactionManager.doSetRollbackOnly`의 "롤백 전용 표시(연결 위로는 보내지 않음)"와 맨 아래 용어집의 "롤백 전용 표시" 설명입니다.
- [화면에서 확인] 트랜잭션이 시작되는 모양도 보였습니다. `setAutoCommit false · 보낸 것 0개`에서는 DB로 아무것도 안 갔고, 이후 첫 UPDATE와 함께 `Q BEGIN + P B D E S · UPDATE`가 나갔으며 그 뒤 `번호 753 받음`이 나왔습니다.

**질문 2 (REQUIRES_NEW와 풀)**
- [화면에서 확인] 주요 순간 칩 순서는 `+454 C1 떼어 둠 → +454 C2 빌림 → +932 C2 COMMIT → +946 C1 다시 묶음 → +1,343 C1 COMMIT`입니다.
- [화면에서 확인] `+454` 순간에 Spring 칸은 "떼어 둔 연결 C1"이고 PostgreSQL 칸은 `C1 idle in transaction xid 753`입니다. 용어집은 이를 "바깥 트랜잭션은 서버에서 열린 채 남음"이라고 설명합니다.
- [화면에서 확인] 풀 1칸 장면의 결과 줄은 `C1 트랜잭션 753 → ROLLBACK`이고 예외는 `CannotCreateTransactionException`, 잔액은 변화가 없습니다.
- [화면에서 확인] 풀 1칸 타임라인에는 `ConcurrentBag.borrow · 풀에서 받지 못함(시간 초과) · 잠듦 2,003 ms`와 `+2,592 SQLTransientConnectionException`이 있습니다.
- [추측] 바깥이 C1을 쥔 채 안쪽이 두 번째 연결을 기다리다 시간 초과가 난 것으로 읽었습니다. 화면은 이 순서를 보여 주지만 "자기가 쥔 연결을 자기가 기다린다"는 문장은 제 해석입니다.
- [화면에서 확인] 2,003 ms가 어떤 설정값에서 왔는지는 화면에 없었습니다.

**질문 3 (NESTED)**
- [화면에서 확인] 결과 줄은 `C1 트랜잭션 753·하위 754 → COMMIT · 잔액 kim 100 → 90, lee 200 → 200 · outer-caught IllegalStateException`입니다. 안쪽(lee +10)만 사라지고 바깥(kim −10)은 커밋됐습니다.
- [화면에서 확인] 안쪽 실행 중(+474) C2는 `idle xid -`라서 같은 연결 C1을 쓴 것으로 보입니다. `Inner.java`의 주석도 "바깥 트랜잭션 안에 저장점을 만들고(NESTED)"라고 적고 있습니다.
- [추측] 어떻게 lee만 되돌렸는지는 SAVEPOINT 용어집 설명으로 짐작했을 뿐, 타임라인에서 `ROLLBACK TO SAVEPOINT` 줄은 직접 못 봤습니다. 주요 순간 칩에도 저장점 칩은 없었습니다.
- [화면에서 확인] `하위 754`가 무엇인지는 화면에 따로 설명이 없었습니다.

원래 알던 것: `REQUIRES_NEW`는 새 트랜잭션을 연다는 정도와 "풀"이라는 이름 자체는 [원래 알던 것]입니다. 이 보고서에서는 그 이상을 끌어다 쓰지 않았습니다.

## 5. 막힌 곳과 바로잡은 곳

- **오독 바로잡음**: REQUIRED 결과 줄의 "풀이 연 연결 C1, C2"를 처음엔 "이 장면이 연결 2개를 썼다"로 읽었습니다. 구조도에서 C2가 `idle xid -`이고 트랜잭션 번호가 753 하나뿐인 것을 보고, "풀이 열어 둔 연결"과 "쓴 연결"이 다르다고 바로잡았습니다. 같은 문구가 REQUIRES_NEW 결과 줄에도 있어서, 이 문구만으로는 둘을 구분할 수 없습니다.
- **DB 상태 시각**: 선택한 순간보다 347 ms 앞선 시각의 DB 상태가 그 순간의 구조도에 표시됩니다. "도구가 앱을 멈추고 찍은 것"이라는 설명이 아래쪽에 있었지만 읽기 전까지는 DB 칸이 실시간 값인 줄 알았습니다.
- **용어 설명 위치**: `[갈림]`, `[효과]`, `[시간]`, `＋n`, `추론` 같은 표지의 뜻과 용어집이 페이지 맨 아래에 있었고, 저는 글 읽기 도구를 한 번 쓴 뒤에야 알았습니다.
- **창 크기**: 제가 쓴 창에서는 오른쪽 코드·상세 패널이 잘려 보였습니다.
- **다루지 못한 것**: `REQUIRES_NEW · 같은 행`, 실행 b, `전부` 필터, `0.5초 안에 다시 빌림`의 결론은 열어 보지 못했습니다. 행 락 대기와 MVCC는 이 화면에서 확인하지 못했습니다.

## 6. 이 화면에 바라는 것

- 장면마다 맨 위에 "트랜잭션 몇 개 / 실제로 쓴 연결 몇 개 / 최종 커밋·롤백" 한 줄 요약.
- 칩과 줄을 눌렀을 때 선택 표시와 타임라인 이동이 즉시 일어나는 것.

- 구조도에 "바깥/안쪽 트랜잭션 ↔ 연결" 연결선.
- 구조도에서 DB 값이 몇 ms 전에 찍힌 것인지 더 눈에 띄게 표시.
- NESTED의 저장점 단계를 주요 순간 칩에 넣는 것.
