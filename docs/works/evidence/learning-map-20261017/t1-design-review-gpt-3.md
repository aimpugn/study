## 답 전문

수정 후 승인

1. **낮음 — `from`을 추가한 판단과 `place`의 뜻은 타당합니다.** 이동 기록에는 실행한 프로세스·코드 자리와 출발·도착 칸이 함께 있으므로, 이동을 두 사건으로 쪼개기보다 `place`·`from`·`target`으로 나누는 편이 원본 한 항목을 보존합니다. 두 사건으로 나누면 원본에 없던 사건 경계와 연결을 만들어야 합니다. `place`를 실행된 자리로 통일한 것도 트랜잭션 실험의 세션·백엔드 장소, Spring의 연결·스레드·백엔드 장소와 충돌하지 않습니다. 트랜잭션·Spring 규칙은 이동의 양 끝을 나타내지 않아 `from`을 쓰지 않는 경우입니다.  
   **근거:** 설계 메모 §1 규칙 4, §5의 2~4(특히 409~419행); 대응표 [t1-structural-roles.tsv](docs/works/evidence/learning-map-20261017/t1-structural-roles.tsv) 20~23·33~35·44~47·57~59행.  
   **고칠 방법:** 필수 수정은 없습니다. 다만 파일이 어느 쪽 끝인지 결정한다는 표현은, 원본에 `from`과 `to`가 이미 보존된다는 점을 감안해 “파일 장소와 양 끝 칸의 대응을 확인한다”로 다듬으면 규칙이 더 명확합니다.

2. **중간 — 단계 사건의 `stack[0]` 규칙이 공통 스택 규칙과 어긋납니다.** 메모 §2는 `stack[0]`을 멈춘 자리, 즉 가장 안쪽 프레임으로 정의하지만, 수정된 §5.2는 단계 사건의 `place`를 단계 함수로 두고 `stack[0]`을 그 부른 쪽 프레임으로 둡니다. 호출자를 보존하려는 선택은 이해되지만, 이 경우 스택이 사건 장소를 포함하는지 여부가 입력에 따라 달라집니다. 같은 `stack`을 공통 구조로 소비할 때 혼동이 생길 수 있습니다.  
   **근거:** [WORK_20261017_LEARNING_MAP_PLATFORM.md](docs/works/WORK_20261017_LEARNING_MAP_PLATFORM.md:382) 382행과 414행; [journey.go](open_source_internals/workbench/design/feasibility/fulltrace/decode/journey.go:581) 581~597행은 `Fn`, 호출자, 호출 줄을 따로 얻습니다.  
   **고칠 방법:** 단계 사건도 현재 함수 프레임을 `stack[0]`에 넣고 호출자를 다음 칸에 두거나, `stack`은 이벤트 장소를 제외한 호출자 문맥이라는 규칙을 명시하고 모든 입력에 같은 계약을 적용하세요. `at`의 호출 줄을 어느 프레임 위치에 보존하는지도 함께 정하면 됩니다.

3. **낮음 — 여정의 이식 규칙과 출처 분류는 대체로 맞습니다.** `proc`는 현재 기록에서 `backend`/`other` 두 값이고, pid를 질의의 백엔드 pid와 대조하면 1,194개 이동 모두 복원할 수 있다는 대응표의 규칙과 일치합니다. `from`·`to`는 원본에 별도로 있어 각각 `from`·`target`으로 보존되며, `files` 경로는 파일 장소와 어느 끝이 맞는지 확인하는 데 쓰입니다. 따라서 현 자료에서는 되돌릴 수 있습니다. 스택 원본은 바깥쪽부터 쌓이고 `stackSampler`도 같은 순서로 반환하므로 뒤집는 규칙이 맞습니다. `at`을 호출 줄로 읽는 해석도 `r.Site - 4`를 줄 위치로 바꾸는 코드와 일치합니다.  
   **근거:** 대응표 21~23·33~35·45~47·57~59행; [journey.go](open_source_internals/workbench/design/feasibility/fulltrace/decode/journey.go:908) 908~954행.  
   응답 버퍼의 메시지는 송신 메시지 수와 대기 중인 쓰기 수가 같을 때 차례로 붙인 사본이며, 이 짝짓기 자체는 추정으로 표시한 것이 적절합니다. 단, 코드는 수가 다르면 쓰기 쪽 메시지를 붙이지 않습니다. `cont`는 앞 송신에서 넘어온 바이트 조각이고, `cut`은 현재 보이는 바이트만으로 메시지가 끝나지 않는 경우를 뜻하므로 두 표시를 일대일 짝으로 취급하지 않는 것도 맞습니다.  
   **근거:** [journey.go](open_source_internals/workbench/design/feasibility/fulltrace/decode/journey.go:189) 189~219행, 338~368행, 670~693행; 설계 메모 413행.  
   **고칠 방법:** “응답 버퍼에 쓴 메시지는 뒤따른 송신과 수가 맞을 때만 순서대로 짝짓는다”고 조건을 적으세요. 또 `splitMessages`가 선언 길이 `n < 4`도 `Cut`으로 표시하므로, `cut`의 정의는 “보이는 바이트 밖으로 이어짐”보다 “불완전하거나 유효하지 않은 길이로 끝남”을 포괄하도록 조정하는 편이 코드와 맞습니다. 이 예외가 현재 자료에 실제로 나타나는지는 확인하지 못했습니다.

4. **낮음 — 표시된 출처 성격에서 뚜렷한 역전은 찾지 못했습니다.** `proc`, 시간 끝, 단계 이름처럼 해석기 규칙으로 다시 계산하는 값은 도출로 두었고, 버퍼 메시지 짝짓기·`procsGuess` 역할표 같은 추정은 추정 목록에 들어 있습니다. `procsGuess`는 대응표에서 도출로 표시돼 있지만, 설계 메모가 해당 조건의 장소 출처를 `inferred`로 덮어쓰도록 명시해 모순은 아닙니다. `roles.py`는 표시 파일의 출처 표기를 옮기고 예외 경로를 수동 대응하므로, 출처 자체가 옳은지까지 생성기로 검증하지는 않습니다.  
   **근거:** [roles.py](docs/works/evidence/learning-map-20261017/t1-inventory/roles.py:35) 35~48행, 대응표 42행·66~80행; 설계 메모 410~417·433행.  
   **고칠 방법:** 출처 분류를 바꿀 필요는 확인하지 못했습니다. `procsGuess` 조건부 override와 파일 경로 대응이 실제 적재기에서도 유지되는지는 해당 여정 적재기가 구현될 때 검증하세요.

5. **낮음 — END 및 검사 3·4 수정은 트랜잭션·Spring 규칙과 충돌하지 않습니다.** END를 함수 장소의 `sample` 사건으로 두면 함수 이름이 `attrs`에 숨지 않으며, 트랜잭션 실험의 관찰 `sample`과도 같은 사건 종류를 씁니다. 출처별 선택 규칙으로 gdb END만 다시 셀 수 있습니다. 검사 3의 하위 경로 확인은 모음 안의 구조 칸을 숨기는 경우를 더 잡고, 검사 4의 `coverage` 확인은 추정한 감시 목록을 검사 범위에 포함합니다. 트랜잭션·Spring의 기존 사건·장소 규칙을 바꾸지는 않습니다.  
   **근거:** 설계 메모 356·408·418~419·442행; [gdbtrace.go](open_source_internals/workbench/open_source_internals/workbench/topics/pgsql/gdbtrace/gdbtrace.go:212) 212~240행; [checks.go](open_source_internals/workbench/internal/atlas/checks.go:35) 35~80행, 106~162행.  
   **고칠 방법:** 수정 불필요. 기존 T3/T4 적재기가 `coverage`를 만들 때도 각 항목의 `origins`를 제공해야 새 검사 4를 통과합니다. 해당 적재기는 이번 검토 범위에서 확인하지 못했습니다.
