## 2. 할 일(차례대로)

0. **T1 보강: 앞선 적재기 셋의 독립 코드 검토(T4보다 먼저, 2026-10-18 22:30 KST에 더함).** 작업 지도의 판정자가 T1 체크를 반려했습니다. 반려 까닭 가운데 남은 빈틈은 하나입니다. gdb·요청 여정·트랜잭션 실험 적재기(`topics/pgsql/{gdbtrace,journey,txlab,load}`, 63벌)는 설계 메모 검토와 고친 곳 검토만 받았고, 코드와 적재 결과를 읽은 독립 검토의 답 전문이 없습니다(Spring 쪽은 `t1-e03-code-review.md`가 있음).
   - 이 대화의 맥락을 받지 않은 독립 하위 에이전트(읽기와 실행만)에게 Spring 코드 검토와 같은 기준으로 맡깁니다. 기준: 구조가 `attrs`에 숨지 않았는가, 출처 표시(관찰·도출·추정), 내보내기가 적재 결과 밖을 읽지 않는가, X1~X7, 되돌림·재추출·변이 시험의 판별력, 정확성, 코드 꼴. 실제로 적재 결과(`pgsql-atlas -out <임시 폴더>`)를 몇 벌 열어 원본과 견주게 합니다.
   - 요청과 답 전문은 `docs/works/evidence/learning-map-20261017/t1-e04e05-code-review.md`에, 지적마다의 처분 표(지적, 처분, 고친 곳, 확인)는 WORK 「T1」 아래 새 절 「앞선 적재기 코드 검토와 처분」에 남깁니다.
   - 고친 코드는 4절의 게이트를 통과하고, 고친 곳은 다른 하위 에이전트가 고친 곳과 회귀만 재검토합니다. 끝나면 올리고 1번으로 넘어갑니다.
   - 로컬 세션이 이 결과로 T1 체크를 다시 냅니다. 그때 쓰도록 마지막 보고에 검토 판정, 지적 수, 처분 절의 WORK 줄 번호를 적어 주세요.
1. **전제 확인.** 시안이 그린 사실이 공통 형식 출력에 있는지 먼저 봅니다. `go run ./topics/pgsql/cmd/pgsql-atlas -out <임시 폴더>`로 77벌을 쓰고(`.lab-tmp/`는 git이 무시하지 않으므로 쓰지도 커밋하지도 않음), `t3-merged/notes.md` 5절 「사실표와 대조한 숫자」의 값을 공통 형식에서 프로그램으로 뽑아 견줍니다. 적어도 다음이 들어갑니다.
   - INSERT 1차 376.8 ms·2차 148.5 ms, 단계 머문 시간(0.6 · 1.9 · 276.6 · 15.3 · 19.3 · 56.3 · 6.8 ms), 카탈로그 조회 ×25.
   - `pwrite64`, `fdatasync` 51,845.8 µs와 그 안의 `mutex_lock` 40,815.3 µs·`schedule`, 1차와 2차가 갈리는 `btrfs_sync_log`.
   - T4 행이 요구하는 다른 경로 후보(같은 SELECT의 첫 조회와 다시 조회)가 어느 실행인지.
   빠진 사실이 있으면 T1의 빈틈입니다. 화면 코드에서 메우지 말고 멈춰 WORK 문서에 기록하고, T1 행의 실패 칸(형식을 고치고 다시)을 따릅니다. 견준 스크립트나 시험은 커밋해 다시 돌릴 수 있게 합니다.
2. **설계 메모(구현 전).** WORK 문서 「단계 결과」에 「T4 지도 화면 v1」 절을 새로 만들어 적고, 코드보다 먼저 커밋합니다.
   - 시안의 요소마다 v1에서 만드는지, 뒤 단계(T5 해설 생성·저장, T7 실시간 등)로 미루는지 대응표.
   - 줌 세 단계(시스템, 프로세스 안, 함수·커널)를 공통 형식의 무엇(장소 계층, 깊이, 출처)으로 정하는지. 주제(pgsql, Spring)의 지식은 주제 쪽 자료에만 두고 화면 코드는 플랫폼 쪽에 둡니다. T6의 통과 칸이 "주제 디렉터리에 화면 코드가 없음, 플랫폼 변경 0건"이므로 지금 경계를 바르게 잡습니다.
   - Spring 기록이 끝나는 층의 빗금. '기록하지 않은 층'과 '기록했지만 그 구간에 사건이 없음'을 다른 모양으로 구별합니다.
   - 경로(출발·도착 사이의 사건 순서), 경로 후보(같은 요청의 다른 실행), 재생, 범위 선택. 범위 선택은 「범위 해설의 규칙」의 정규화와 같은 범위·겹침·포함 판정까지 하고, 해설 자리 표시는 하되 공급자 호출은 0번입니다(해설 생성·저장·채택은 T5).
   - 관측과 추정의 구별. 추정 출처(메모 7의 목록, 예: Spring 트리 마디의 `self`, autocommit `sent`)는 화면에서도 추정으로 보입니다(지금 화면은 ≈).
   - 저장은 T2에서 정하므로, 화면은 공통 형식 출력을 좁은 인터페이스 하나로 읽고 T2의 결정이 들어올 자리를 남깁니다.
   - 기존 서버에 붙일지 정적 파일을 만들지 고르고 이유를 적습니다.

## 5. 일하는 원칙(사용자의 실행·개발 기준을 줄인 것)

- 최상위 기준은 자원 효율입니다. 다만 데이터 무결성, 정확성, 요구한 정밀도는 시간을 아끼려고 낮추지 않습니다.
- 사실, 추론, 모르는 것을 섞지 않고, 핵심 주장마다 확인 경로를 둡니다.
- 중요한 결정은 구현 전에 설계하고, 새 사실이 설계를 깨면 설계부터 고칩니다.
- 중요한 결과는 만든 쪽이 스스로 인증하지 않고 분리된 검토를 받습니다. 재검토는 앞선 지적의 수정과 회귀만 봅니다.
- 시험은 결과와 상태를 보고, 틀린 규칙도 통과할 우려가 있으면 변이나 반례로 판별력을 확인합니다.
- 작고 응집된 커밋. 돌리지 않은 검사를 돌린 것처럼 쓰지 않습니다.
- 요청한 결과가 있고, 중요한 성질을 확인했고, 요구를 낮추지 않았고, 남은 잔여물이 없고, 확인하지 못한 범위를 밝혔을 때만 완료라고 합니다.
