# T4 지도 화면 v1 설계 메모의 분리 검토: 요청과 답 전문

2026-10-18, 클라우드 세션(T4 지시서 2절 3번). 설계를 쓴 쪽이 아닌 하위 에이전트(같은 모델의 새 문맥, 이 대화의 맥락 없이, 읽기와 실행만, 저장소 파일과 git 상태를 바꾸지 말라고 지시)에게 맡긴 검토입니다. 처분은 WORK 문서 「T4 지도 화면 v1」의 「설계 검토와 처분」에 있습니다. 검토자가 만든 재현 파일은 세션의 임시 폴더(`scratchpad/review-t4design/`)에 있어 커밋하지 않았습니다.

## 요청(요지)

검토 대상은 WORK 문서 「T4 지도 화면 v1」의 「전제 확인」과 「설계 메모(2026-10-18, 구현 전)」 1~10(커밋 66c77ba, f639f72)입니다. 기준으로 같은 문서의 T4 행(통과·실패 칸이 바닥선)과 T5·T6·T2 행, 설계 1·4·5·6과 「범위 해설의 규칙」, T3 확정 문단, 금지 X1~X6, T1 설계 메모 2·3·6·7·9, 시안 메모와 그림, 지시서 2절 2·3번과 3절, 형식 코드와 전제 시험, 주제 자료 파일을 주었고, 필요하면 77벌을 임시 폴더에 써서 열어 보라고 했습니다. 볼 것은 아홉입니다: T4 통과 칸을 모두 만족하는가(바닥선을 낮추지 않았는가), 플랫폼/주제 경계와 T6, 줌·칸·잎 집합·범위 판정이 「범위 해설의 규칙」과 맞는가, 빗금 판정이 X1과 관찰 범위의 뜻에 맞는가, 시계 규칙과 시각 없는 사건의 차례, 추정 표시가 T1 메모 7의 추정 목록을 덮는가, 후보와 주된 갈림의 정의, 정적 파일과 범위 규칙의 이중 구현, 시험의 판별력. 답은 판정, 지적(번호, 심각도, 위치, 문제, 근거, 제안), 확인한 것, 확인하지 못한 것으로 쓰고, 취향 문제를 높이지 말고 사실과 추론을 나누라고 했습니다.

## 답 전문

## 판정

**수정 후 승인.** 이 판정은 코드를 쓰기 전에 아래 높음 둘과 중간 항목을 설계 메모에서 고친다는 조건을 붙인 것입니다.

틀은 맞습니다. 플랫폼 `mapview`와 명령은 플랫폼 쪽에, 주제는 `map.json`만 두는 경계, `Store` 인터페이스 하나, 정적 파일, 관찰 범위(coverage)로 빗금을 가르는 방식, 시계를 섞지 않는다는 원칙은 T1 형식과 T6 판정 방식에 맞습니다. 다시 설계할 필요는 없습니다.

그러나 규칙 수준에 구멍이 있습니다. 첫째, 메모가 "같은 화면 코드로 보인다"고 한 대상 셋 가운데 Spring의 경로 규칙이 비어 있습니다. 메모가 정한 한 시계 규칙을 그대로 두면 Spring 앱 층(JFR)을 경로에 넣을 수 없습니다. 둘째, 「추정 표시를 출처 성격으로 자동 전파한다」는 주장이 실제 77벌의 데이터에서 성립하지 않는 곳이 있습니다(T1의 빈틈). 셋째, ×N 접기, 처리 단계 열, 하강 판정, L3 칸 집합이 시안이나 데이터와 어긋납니다. 모두 메모의 규칙을 다시 쓰면 닫히는 것들이라 「수정 후 승인」으로 둡니다.

## 지적

**1. [높음] Spring 경로 규칙이 비어 있고, 메모 3의 한 시계 규칙 아래에서는 Spring 장면(앱 층)이 경로에 들어갈 길이 없음**
- 위치: 설계 메모 2(경로 규칙), 3-1(「단계들은 한 시계여야」), 3-3(Spring: `server`·`contains`), 5(후보).
- 사실(spring/5-required/a를 직접 열어 봄):
  - 요청 `request`의 출처는 `spring-mac`(mac 시계)입니다.
  - 서버 창 `server`의 출처는 `spring-cont`(container 시계)이고, 백엔드 함수 기록은 `recorder`(container)입니다.
  - 앱 메서드 나무는 `jfr`·`spring-jfr`(jfr 시계)입니다.
  - jfr과 mac의 관계는 `relation: null`(모름)입니다. container와 mac은 `known: true, lo −131113 ns ~ hi 81400 ns`입니다.
  - JFR 마디와 요청을 잇는 연결은 `wire`(근거 `spring-guess`, inferred) 5개뿐이고, 요청은 11개입니다.
- 추론:
  - L2를 요청(mac)으로 잡으면 Spring 장면의 핵심인 전파 나무(JFR)가 경로 밖으로 빠집니다.
  - JFR로 잡으면 연결 위 메시지와 백엔드에는 추정 연결 5개로만 닿습니다.
  - 메모 3-1은 「시계가 다른 사건이 섞이면 보기 모형을 만들지 않는다」입니다. 이것은 T1 메모 3보다 엄격합니다. T1 메모 3은 관계가 알려진 범위 밖의 차이라면 비교를 허용합니다. 그래서 mac 요청과 container 서버 창을 한 줄에 두는 것도 막힙니다.
  - T3 시안은 pgsql INSERT만 그렸으므로 Spring 화면의 꼴은 합의된 것이 없습니다.
- 제안: Spring 장면 무리의 경로 뿌리, L2 칸, L3 펼침, 띠, 구역을 메모에 구체적으로 적습니다. 그다음 아래 둘 가운데 하나를 정합니다.
  - (a) L2는 요청(mac)으로 두고, JFR 나무는 추정 연결 `wire`로 매단 별도 띠(≈, 시계 다름 표시)로 둡니다.
  - (b) 시계마다 따로 줄을 그리고 서로의 순서는 그리지 않습니다.

  또 한 시계 규칙을 T1 메모 3의 비교 함수(「견줄 수 없음」)에 맞춰 다시 씁니다. 차례를 정할 수 없는 짝이 있을 때만 거부하는 식입니다.

**2. [높음] 추정 표시가 T1 메모 7의 추정 목록을 덮지 못함: 커널 마디 `calls`·`callsOf`·`guess`, 그리고 관찰 범위**
- 위치: 설계 메모 6(「보기 모형의 칸·값마다 출처 성격이 따라가서 화면이 따로 판단하지 않는다」).
- 사실:
  - T1 메모 7은 「커널 마디의 `calls`·`callsOf`·`guess`」를 `inferred`로 정했습니다. 그런데 journey/kernel_insert에서 이 값들은 attrs 열쇠 `journey` 아래에 있고, 그 출처의 성격은 `derived`입니다. `guess` 9마디, `calls` 107마디가 그렇습니다(`journey.go` 586~589행이 `l.B.EventAttrs(id, "journey", k, v)`로 넣음).
  - Spring에는 추정 attrs 경로 목록이 `spring.InferredGroups()`로 있지만, 여정에는 같은 것이 없습니다.
  - 재고 조사 1656행에 따르면 `guess`는 「층(layer)을 부모에게서 물려받았다는 표시」입니다. 메모 2는 커널 띠를 바로 이 `layer`로 배정합니다.
  - 관찰 범위도 같은 문제가 있습니다. gdb의 `watch-guess` 관찰 범위는 출처가 inferred이고, `watch` 관찰 범위는 출처가 human입니다(basis: 「기록한 순간의 판과 같은지는 기록에 없음」). 메모 4·6은 관찰 범위의 출처 성격을 보지 않습니다.
- 추론: 이대로 구현하면 9마디가 짐작한 층의 띠에 「규칙으로 셈」 표지를 달고 그려지고, 호출 사슬 발췌도 같은 표지로 보입니다. T1 행의 「추정한 연결을 관측 사실로 표시하지 않음」과 T1 검사 4가 이 경로를 잡지 못한 것으로 보입니다(검사 4의 코드는 확인하지 않음).
- 제안: 「새 근거가 앞선 가정을 깨면 가장 이른 단계로」에 따라 T1에 되돌립니다. 여정 적재기가 이 셋을 inferred 출처 열쇠로 옮기게 하거나, 여정의 추정 attrs 경로 무리를 검사 4에 넣습니다. 메모 6에는 「관찰 범위의 출처가 inferred·human이면 '봤고 0번'을 ≈로 표시하거나 빗금으로 둔다」를 더합니다. 전제 확인의 「빠진 사실은 없어 T1로 돌아가지 않는다」도 이 건만큼 고칩니다.

**3. [중간] ×N 접기 규칙이 데이터와 모순되고, 접힌 칸 안의 하강이 정의되지 않음**
- 위치: 메모 1 표(「×24」), 메모 3-1(「접기 조건에 맞는 잇단 칸은 한 칸 「×N」」).
- 사실(kernel_insert의 이동 42줄):
  - `journey.catalog=true`는 n 3~12와 n 14~27입니다. n 13 「락 잡기」가 그 사이를 끊습니다.
  - 그래서 「잇단 칸」 규칙을 따르면 ×24 하나가 아니라 ×10과 ×14 두 칸이 됩니다.
  - N이 줄 수인지 원래 횟수(`count` 합: 24와 47, 합 71)인지도 정해져 있지 않습니다.
  - 카탈로그 줄 가운데 n 6·8·10·16·20은 파일에서 온 페이지 읽기이고, 각각 시스템 콜 연결이 있습니다. 시안은 이 다섯을 접힌 칸 안에서 지면을 건너는 하강 「×5」로 그렸습니다.
  - 시안 L2 아래 번호는 「3–27」이라, n 13까지 포함해 의미 분석 단계로 접었습니다.
- 제안:
  - 접기 무리의 정의를 하나로 정합니다(잇단 칸만인지, 끼어든 비해당 칸을 허용하는지, 처리 단계 경계 안인지).
  - N의 뜻(줄 수 또는 횟수)을 정합니다.
  - 접힌 칸 안에 지면을 건넌 사건이 있으면 그 하강을 「×k」 선으로 남긴다는 규칙을 적습니다.
  - 이 셋을 변이 시험에 넣습니다.

**4. [중간] 시안 L2의 처리 단계 열(받기~응답 일곱, 머문 시간, 초점 단계 넓힘)에 대응하는 규칙이 없음**
- 위치: 메모 1(「초점 단계 넓게·먼 단계 좁게」, 「단계 띠」), 메모 3.
- 사실: 시안 L2는 처리 단계 알약 7개가 열 머리를 이루고, 그 아래에 이동 n이 들어 있습니다(커밋 열 316 px). 메모에서 「단계」는 L2 칸(이동 하나)을 가리킵니다. 처리 단계는 해석기 instant 일곱과 이동의 attrs `journey.stage`로 따로 있습니다.
- 제안: 자료 파일에 「열 묶음」 규칙(묶는 attrs 열쇠나 사건 Selector, 머문 시간 셈)을 더합니다. 「단계」라는 낱말도 칸과 처리 단계로 나눠 씁니다. 범위 규칙 1의 「단계」는 칸입니다.

**5. [중간] 하강 판정(띠 = `target`, 없으면 장소)이 페이지 읽기를 지면 위로 분류함**
- 위치: 메모 3-1.
- 사실: n 33과 n 6·8·10·16·20은 `from = file`, `target = lane:shared_buffer`이고, 각각 `syscall` 연결이 있습니다. 시안과 notes 1절은 이것들을 「지면을 건너는 하강」(점선과 빗금 칸)으로 그렸습니다.
- 추론: 칸의 띠를 `target`으로만 정하면 이 여섯은 공유 메모리 띠의 점이 되고, 하강선과 빗금 칸이 사라집니다.
- 제안: 하강 여부는 따로 판정합니다. 예: `from`·`target`·펼친 사건 가운데 지면 아래 띠가 있거나 지면 연결(`syscall` 등, 자료 파일이 댐)이 있으면 하강. 이 판정을 변이 대상에 넣습니다.

**6. [중간] L3 칸 집합이 시안과 다름: 나무 전체를 먼저 부른 차례로 펼치면 158칸**
- 위치: 메모 3-3.
- 사실: kernel_insert의 `fdatasync` 나무는 158마디이고 `pwrite64` 나무는 18마디입니다. 시안 L3는 줄기 약 14마디(계단, `+3`·`+2` 렌즈)만 그렸습니다. 설계 1의 표는 「렌즈 규칙(무엇이 핵심 동작인가)」을 주제의 몫으로 둡니다. 메모의 렌즈는 「자식 하나, 같은 띠 사슬」 접기뿐입니다.
- 추론: 이대로면 L3 화면이 시안의 「고른 경로 한 줄」이 아니게 됩니다. 또 범위 정규화와 잎 집합이 렌즈의 켜고 끔에 따라 흔들릴 수 있습니다.
- 제안: L3에서 보이는 칸을 고르는 규칙을 자료 파일에 둡니다. 예: 뜨거운 마디 문턱, 잠드는 함수, 기존 `KWAIT` 같은 것입니다. 숨긴 칸이 범위에 어떻게 들어가는지도 정합니다. 숨긴 칸은 통째로 넣고, 정체는 렌즈와 무관하게 하는 식입니다.

**7. [중간] 「시각 없는 사건은 같은 출처에서 앞선 사건 바로 뒤」는 출처를 건너는 순서를 지어냄**
- 위치: 메모 3-1.
- 사실:
  - 형식 규칙 1이 정하는 것은 같은 출처 안의 기록 차례뿐입니다.
  - 여정의 `strace` 사건은 `start_ns`가 없고(unrecorded) 시계도 없습니다(clock null). `ftrace`도 마찬가지입니다.
  - Spring 트리에서 스택에만 보인 54마디는 시작이 없습니다. 그 출처는 해석기(`spring-jfr`)라서 id 차례는 적재기가 만든 차례입니다.
- 추론:
  - 시각 있는 앞 사건 바로 뒤에 놓으면, 실제로는 그 사이에 있었던 다른 출처의 사건보다 앞선다는 순서가 화면에 생깁니다.
  - 출처의 첫 사건에 시각이 없으면 놓을 자리가 정의되지 않습니다.
  - 「시계 없음(null)」을 「다른 시계」로 볼지도 정해져 있지 않습니다.
- 제안: 시각 없는 사건은 L2 칸으로 만들지 않습니다. 대신 그 사건을 가리키는 시각 있는 사건(연결로 이어진 것)의 펼침(L3)이나 부속으로만 둡니다. 출처 전체가 시각이 없는 경우(gdb)에만 id 차례로 칸을 만들고 「순서만 기록」 표지를 붙입니다. clock null인 출처의 처리를 적습니다.

**8. [중간] 잎 집합의 정의가 「범위 해설의 규칙」 2·3과 다름**
- 위치: 메모 3-4, 5(범위).
- 사실: 규칙 2는 잎 집합을 「가장 깊은 기록 층의 사건 집합」으로 정합니다. 메모는 「그 칸의 사건과 펼쳐서 닿는 모든 사건의 id 집합」(중간 마디 포함)입니다.
- 반례: L2 칸 n 37 하나와, L3에서 그 펼침 칸 전부를 덮은 범위를 견줍니다. 규칙 2로 보면 잎 집합이 같아서 「줌만 다른 같은 범위」이고, 규칙 3에 따라 목록에서 한 묶음으로 보여야 합니다. 메모의 정의로 보면 L2 쪽에 rec 이동과 strace 사건이 더 있어서 「포함」으로 판정되고, 한 묶음이 되지 않습니다.
- 그 밖의 사실:
  - 메모는 같은 잎 집합이면서 줌이 다른 경우를 따로 가르지 않습니다. 이 경우 서로 포함하는 꼴이 됩니다.
  - 규칙 2는 범위의 정체를 「가지 모양 안의 위치」로 적습니다(새 기록에서도 같은 자리). 메모의 정체는 run 안의 사건 id입니다.
- 제안:
  - 잎 집합을 규칙 2대로 정의합니다.
  - 판정 결과에 「줌만 다름(같은 잎)」을 따로 둡니다.
  - T4의 정체는 「세션 안 임시 정체」이고, T5가 가지 모양 위치(T2 해시)로 바꾼다고 메모 7·10에 적습니다. 보기 모형의 칸마다 장소 `key` 사슬을 실어 두면 T5가 그대로 이어 쓸 수 있습니다.

**9. [중간] 「봤고 0번」을 경로 사건만 보고 판정함: 경로 밖 사건이 있으면 거짓 진술**
- 위치: 메모 4.
- 사실: 「사건 있음」은 「그 띠에 경로의 사건이 있음」으로 정의됩니다. 관찰 범위에는 `window`(구간)가 있을 수 있는데, 메모는 이것을 다루지 않습니다.
- 추론:
  - 관찰 범위가 complete인 띠에 같은 시간대의 경로 밖 사건(다른 요청의 메시지)이 있으면 화면은 「봤고 0번」이라고 말하게 됩니다. 예: requires-new에서 C1과 C2 연결이 엇갈리는 경우. 이 장면에서 실제로 그런 일이 있는지는 확인하지 않았습니다.
  - X1의 반대 방향 오류지만 기록과 다른 진술이라는 점은 같습니다.
- 제안: 판정을 세 갈래로 둡니다. 경로 사건 있음, 경로 밖 사건만 있음(흐림), 관찰 범위가 그 칸의 시간을 덮고 complete이며 run 전체에 그 띠의 사건이 0개일 때만 「봤고 0번」. 관찰 범위 창과 칸 시각의 겹침도 판정에 넣습니다.

**10. [중간] 후보의 정체: Spring 「장면 이름이 같은 run」을 구조 칸으로 낼 수 없음**
- 위치: 메모 5(후보), 메모 2(「후보의 정체: run attrs나 뿌리 attrs의 열쇠와 장소」).
- 사실: Spring 14벌은 모두 `scene = "spring"`이고, 장면은 `name`의 앞부분(`5-required/a`)에만 있습니다. run attrs에 장면 열쇠는 없습니다(`jsrc`·`spring`·`spring-compare`·`src`·`txlab`). 트랜잭션 실험도 `name = "1-rc-read/a"`이고 b가 따로 있는데, 메모는 실험 a·b를 서로의 후보로 보는지 말하지 않습니다.
- 추론: `run.scene`으로 묶으면 14벌이 모두 서로의 후보가 되어 X1의 뜻(같은 장소를 지난 같은 요청의 다른 기록)을 벗어납니다.
- 제안: 자료 파일에 「run 이름에서 마지막 `/` 앞」 같은 정체 규칙을 둘 수 있게 하거나, 적재기가 장면 열쇠를 run attrs에 넣게 합니다(T1 쪽 변경이므로 그 경로를 적음). 여정 후보 열쇠는 출처가 human인 `topic.typed`가 아니라 관찰 출처의 `rec.data.query`를 쓰는 편이 낫습니다. 두 값은 select에서 `;` 하나가 다릅니다.

**11. [중간] 「주된 갈림」의 일반화가 정해지지 않음**
- 위치: 전제 확인 표의 갈림 행, 메모 5(「두 후보의 L3 나무가 있으면」).
- 사실(premise_test.go): 걷기는 `*DurNS`를 씁니다. 커널 마디만 길이를 갖고, recorder 나무는 시작과 끝을 갖습니다. 견줄 나무 짝은 `r1[1]`, `r2[1]`(두 번째 kernel 연결)로 손으로 골랐습니다. 자식 차례가 끝까지 같고 머문 시간만 다르면 걷기가 잎에서 멈추고, 그 잎을 「갈림」이라고 냅니다.
- 제안:
  - 나무 짝을 고르는 규칙을 정합니다(같은 L2 칸 자리, 같은 시스템 콜 장소 key 등).
  - 길이는 `dur_ns` 또는 `end − start`로 셉니다.
  - 구조 차이 없이 끝나면 「구조 같음, 시간 차 최대 마디」라는 다른 표지를 냅니다.
  - 갈림 표지는 해석(derived)이고, 추정 목록의 「갈림에서 길을 정한 것의 판단」과는 다르다는 점을 표지에 반영합니다.

**12. [중간] Go와 브라우저 대조표 「한 경로의 모든 범위와 그 짝」은 실행할 수 없는 규모이고, 드래그 → 칸 맞춤은 덮지 못함**
- 위치: 메모 8.
- 사실(셈): L2 42칸은 연속 범위 903개, 짝 약 41만입니다. `fdatasync` 158마디는 범위 12,561개, 짝 약 7,900만입니다. 줌을 건너는 짝은 더 많습니다. 정규화의 앞 절반(픽셀 구간 → 칸)은 브라우저에만 있습니다.
- 제안: 브라우저가 하는 일을 집합 연산으로 줄입니다. 칸마다 잎 집합은 Go가 셈해 보기 모형에 넣습니다. 대조표는 경계 사례 목록(×N 경계, 렌즈 접힘, 흐린 칸, 줌 간 같은 잎)과 무작위 표본으로 둡니다. 또는 판정 함수를 Go로 쓰고 WASM으로 같은 코드를 쓰는 대안을 검토해 기록합니다. X5는 브라우저 밖 도구에 대한 것이라 WASM과 충돌하지 않습니다.

**13. [중간] 참가자 시험 사전 등록의 참조가 비어 있고, 「조작 기록」을 얻을 수단이 설계에 없음**
