   - **메모 7:** 메모 7(460행)과 `format.go` 70행이 `derived`의 예로 "요청 창"을 직접 듭니다.
   - **"트랜잭션 실험의 요청과 같은 자리"는 사실이 아님:** 트랜잭션 실험의 요청은 `exec_simple_query` 호출 하나의 입구와 반환입니다(`scenario.go` 499~511행). Spring의 창은 서로 다른 ReadyForQuery 호출 둘의 입구 사이 `[rfq[k-1], rfq[k]]`입니다(`spring.go` 518~523행). 이 창은 "두 입구 사이가 요청 하나"라는 해석기 규칙(372~373행)으로 만든 것입니다.
   - **직접 센 것:** 창 142개 가운데 122개가 그 요청의 첫 F 메시지가 컨테이너 쪽 중계기에 닿기 전에 시작합니다(중앙값 11.0 ms, 최대 4.50 s). 백엔드가 클라이언트를 기다린 시간이 창에 들어 있다는 뜻입니다. 관찰한 "처리 구간"으로 읽으면 틀린 그림이 됩니다.
   - **검사 4가 못 잡음:** `CheckNature`(`checks.go` 112~151행)는 적재기가 고른 경로 무리의 표시로 기대 성격을 정합니다. 그래서 `…server`(모음, 관찰)를 고르면 관찰이 통과하고, `…server.t0`(도출)를 고르면 도출이 통과합니다.
   - **제안:** 창을 `spring-cont`(도출, 컨테이너 시계)의 span으로 두고, 경로 무리를 `$.conns[].requests[].server.t0`로 둡니다. `catalogSnapshots`는 `recorder` attrs에 그대로 둘 수 있습니다.

   **2. 중간: 관찰 `sample`의 끝을 `span[1]`로 둔 결정** (메모 435행, 근거 2.2의 52행). 1과 같은 꼴입니다.
   - `span`은 도출입니다(E25, marks 59~60행). `captureSpans`(`spring.go` 772~803행)가 관찰용 접속의 strace에서 규칙으로 고른 값이고, 근거 보고서 2.2도 `observe`를 "해석기가 정한 … 관찰 span"이라고 적습니다. 그런데 `observe`의 성격이 관찰이라, 도출 값이 관찰 사건의 구조 칸에 들어갑니다.
   - 구간으로 따로 두면 어긋남이 생깁니다. 직접 세어 보니 읽기 구간 370개 가운데 60개가 span 끝보다 늦게 끝납니다.
   - **제안:** sample의 `end_ns`는 비우고, `span[1]`은 `spring-cont`의 instant(경로 무리 `$.captures[].span`)로 두어 관찰에서 잇습니다. 1과 같은 규칙으로 정해야 합니다.
