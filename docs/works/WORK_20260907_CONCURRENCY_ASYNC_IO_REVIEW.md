# 동시성·비동기·I/O 면접 문서 검토

## 목적과 범위

`interviews/concurrency-async-io.md` 전체 38개 원문 묶음을 검토하고, 짧은 답변과 꼬리 질문을 복습할 수 있도록 오류를 수정한다. 대상 문서는 시작 시 수정 사항이 없었다. 기존의 다른 문서·코드 변경은 보존한다. 완료 단위는 이 문서 전체 검토이며, 저장소 전체 동시성 문서 감사는 아니다.

전역·저장소·interviews 지침, PROJECT_INTENT, USECASE와 WORK 템플릿을 확인했다. 상세 양식의 중복 항목은 이 기록에 합쳤다. 검증 후 현재 main에 이 작업 파일만 커밋한다.

## 판단과 설명 설계

원문의 문장만 고치는 방법과, 중복을 통합하고 질문별 출처·링크를 유지하는 방법을 비교했다. 같은 monitor 설명이 반복되고 잘못된 코드까지 중복되어 있어 후자를 선택했다. 원문은 source/에 남기고, 복습 본문은 검토한 설명으로 교체한다. 원문 해시는 출처 식별값이며 수정 본문의 무결성 해시가 아님을 명시한다.

Primary exemplar는 `jvm/java/java_synchronized.md`다. 작은 객체·같은 모니터·반례·불변식으로 연결하는 설명을 참고한다. Secondary는 `computer_architecture/threads/threads.md`로 런타임/OS/하드웨어 계층의 구분을 참고한다. 방대한 분류와 과거 구현 세부를 그대로 복제하지 않는다.

독자는 Java/Kotlin 코드를 읽지만 대기·재개·가시성을 혼동할 수 있는 면접 준비자다. API 반환, 실행 자원, I/O 준비/완료, 공유 상태 순으로 판단을 복원하게 한다. 동시 작업 수와 처리량을 혼동하거나, 짧은 코드가 안전성을 증명한다고 오해하지 않도록 반례와 관측점을 둔다.

## 근거와 수정 판단

- API가 비동기라는 사실은 하위 스레드가 블로킹되지 않는다는 증거가 아니다. Future, OkHttp, WebFlux 공식 계약으로 구분한다.
- epoll은 준비 알림이다. read/recv 결과와 HTTP 메시지 완료를 별도로 처리해야 한다. Linux man-pages로 확인한다.
- wait의 복귀 원인은 notify 외에도 interrupt, timeout, spurious wakeup이 있다. Object API와 JLS 17의 조건 재검사·모니터 재획득 계약으로 수정한다.
- 가시성은 같은 모니터의 unlock→lock 또는 volatile 등 happens-before로 설명한다. CPU 캐시 전체 flush와 동일시하지 않는다.
- libuv 파일 I/O와 JVM 잠금 최적화는 버전 의존이다. libuv 1.x 문서, JDK 공식 버전 자료를 사용한다.
- FD 고갈, accept backlog, 포트 고갈, 메모리 부족은 서로 다른 원인이다. 오류 코드와 관측 대상을 분리한다.

각 근거의 링크는 본문 해당 설명 가까이에 둔다. 실제 실행으로 확인한 범위와 공식 계약만 확인한 범위를 구분한다.

## 실행 전 확정한 검증 항목

- C1: 원문 38개 묶음의 주제를 모두 유지하고, 중복은 통합한다.
- C2: 동기/비동기, blocking, readiness/completion, coroutine/goroutine 경계를 반례와 함께 설명한다.
- C3: monitor, happens-before, 공유 클라이언트, deadlock의 잘못된 단정을 제거한다.
- C4: 실행 예제는 종료·인터럽트·결과를 확인하고, 개념 조각은 완성 프로그램과 구분한다.
- C5: 기존 유입 링크와 출처 식별을 보존하고 변경 범위를 확인한다.
- C6: 작성자와 분리된 검토 후 지적을 반영하고 필요한 검증을 거쳐 커밋한다.

성공 사례는 wait 이후 통지, wait 이전 상태 변경, atomic 증가다. 반례는 notify 없는 interrupt, 조건을 바꾸지 않은 통지, 일반 파일의 epoll 등록 거절이다. 마지막 항목은 Linux 전용으로, 해당 환경에서 실행하지 않으면 문서 근거 확인이라고만 기록한다.

## 영향 범위

README, core-interview-guide, 질문 색인, `_curriculum_manifest.json`, 생성 도구의 참조를 검색했다. 기존 파일 경로와 주제 anchor, 38개 source 식별자를 유지한다. source/는 검토 전 원문 저장소로 남긴다. 생성 도구 전체 실행은 다른 수동 편집 문서까지 덮어쓰므로 이 작업에서 실행하지 않는다.

## 검증 결과

2026-09-07에 아래를 확인했다.

- Java 실행 환경: macOS, Oracle GraalVM JDK 25.0.4. 본문 GateDemo를 그대로 추출하여 `javac --release 17 -Xlint:all`로 컴파일한 뒤 실행했고 `opened`를 확인했다. Java 17 호환 구문 확인이며 실제 JDK 17 런타임에서 실행한 것은 아니다.
- 별도 제한 시간 있는 probe에서 6개 결과를 확인했다: 먼저 열린 gate, WAITING 확인 후 open, notify 없는 interrupt의 InterruptedException, 조건을 바꾸지 않은 notify 후 작업 미완료, 모니터 미소유 wait의 IllegalMonitorStateException, 두 스레드의 AtomicInteger 증가 합계 20,000. 스레드 종료도 확인했다. 유한 실행 사례는 모든 스케줄을 증명하지 않으므로 언어 계약과 함께 판단했다.
- 기존 `ostep:latest` Linux 이미지를 네트워크 없이 일회성 컨테이너로 실행했다. C probe를 `cc -Wall -Wextra -Werror`로 빌드해 socketpair에서 LT 부분 읽기 후 재알림, 읽기 소진 후 EAGAIN, EOF=0, 일반 파일 epoll 등록 거절(errno=EPERM)을 확인했다. 컨테이너는 자동 제거했다. ET/ONESHOT/io_uring은 실행하지 않았다.
- 원문 38개 curriculum marker가 기존 내용과 동일하고, 모든 이전 heading anchor가 현재 heading 또는 명시적 anchor로 존재하며 중복 ID가 없는지 검사했다. 목차 목적지, 로컬 링크, 코드 fence도 확인했다.
- 외부 링크 72개를 점검했다. OkHttp와 교재의 변경된 주소를 고쳤고, systemd는 접근 가능한 공식 저장소 원문으로 연결했다. Little 원 논문 DOI는 직접 HTTP 요청이 403이었으나 웹 도구에서 출판사 논문 페이지와 내용을 확인했다. 이는 링크 접근 방식의 차이이며 모든 환경의 접속을 보장하지 않는다.
- Markdown을 HTML로 렌더링해 Chrome에서 서두와 epoll 절의 캡처를 직접 확인했다. 표 6개, 코드 블록 13개가 렌더링되며 1200px 화면에서 전체 페이지 가로 넘침이 없었다. 이 임시 미리보기는 VS Code의 모든 테마·창 폭 검증은 아니다.
- 작성자와 별도인 검토자가 문서 전체와 이전 원문의 질문·사례를 대조했다. 동기 API 정의 누락과 C _Atomic 직접 접근 설명의 모호함을 수정했다. 국소 재검토에서 recv의 반환값과 errno를 구분하는 추가 교정도 반영했고 최종 재검토에서 해당 지적이 해소되었다. 독립 검토는 실행 검증이나 링크 검사 자체를 대신하지 않았다.
- git diff 검사에서 이번에 변경한 추적 문서는 대상 파일뿐이다. WORK는 새 파일이며, 사전 존재했던 나머지 추적·미추적 변경은 커밋에서 제외한다. `git diff --check`를 통과했다.

## 최종 판정과 재검증 경로

C1–C6를 모두 충족했다. 요청한 문서 전체의 검토·수정은 완료이며 저장소의 다른 동시성 문서, 실제 서비스 성능, 모든 JDK·OS·라이브러리 조합의 실행 검증까지 의미하지 않는다. 본문과 기록을 같은 논리 변경으로 커밋한다. 원문 중복을 하나의 읽기 흐름으로 교체하므로 삭제량이 크지만 중간에 상충하는 설명을 남기는 분할 커밋은 하지 않는다.

후속 독자는 본문의 GateDemo 실행 명령, 각 공식 계약 링크, 면접 복습 질문을 이용해 다시 확인할 수 있다. 원문 해시와 이전 anchor는 출처·진입 위치의 보존만 증명하며 기술적 정확성의 증거로 재사용하지 않는다. 오류를 재발견하면 해당 API 경계와 실제 반환값부터 다시 확인한다.

재검토에서 바뀐 판단은 본문의 C atomic과 recv 설명에 직접 남겼다. 개인 메모리나 전역 지침으로 승격하지 않았다. 임시 코드·브라우저 캡처는 검증용이며 저장소의 추가 학습 자산으로 만들지 않았다.
