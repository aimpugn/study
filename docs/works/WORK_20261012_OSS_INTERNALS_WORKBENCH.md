## 요청과 목적

사용자가 원래 원한 것의 원문(2026-10-12, 이 대화에서 다시 인용): “오픈 소스들 소스코드가 나와 있습니다. 그리고 그걸 빌드도 가능합니다. 특히 도커 등을 통해서요. 그러면 브라우저로 치면 좌측에는 시각화가 있고 우측에는 소스코드가 나옵니다. 가령 제가 postgresql db에 대해 배우고 싶으면 좌측 면에는 제가 쿼리를 실행합니다. 그러면 쿼리 요청을 받는 소스 코드 라인으로 이동하고, 시각화는 어떤 일이 이뤄지는지 보여줍니다. interactive 학습을 할 수 있는 겁니다. 그리고 리눅스를 배우고 싶고 shell과 파일 처리 등을 배우고 싶으면 해당 커널의 코드 부분을 보여주고 어떤 일이 이뤄지는지 시각화하고 설명도 붙입니다.”

덧붙인 원문: “즉 브라우저에서 누구든 쉽게 내용을 확인할 수 있게 하는 것. 별도 gui를 만드는 것도 있겠지만, 브라우저가 더 좋을 거 같아서요.” “백엔드가 필요하다면 go를 사용하세요.” 위치에 대해서는 “상위는 ‘내부 로직과 코드와 알고리즘 등을 오픈 소스 기준으로 심도 깊게 학습하는 것’이고 그 하위에 여러 세부 DB, 리눅스, OS 등등이 들어가야 할 거 같습니다.”

이 작업 직전에 Claude가 제안한 범위는 “저장된 기록만 보여 주는 정적 재생 뷰어”였다. 사용자 원문은 브라우저에서 직접 쿼리를 실행하는 것을 요구하므로, 정적 재생만으로는 원문을 충족하지 못한다(AI 판단). 이번 시험의 범위를 아래처럼 다시 정한다.

이 시험이 판단할 것: **브라우저에서 쿼리를 실행하면, 그 쿼리를 처리하는 실제 소스 줄과 단계가 사실과 추론을 섞지 않고 보이는 작업대를, 지난 PostgreSQL 실습의 추적 도구 위에 만들 수 있는가.**

## 범위

포함한다.

1. 실시간 실행: 로컬 Go 서버가 브라우저 화면을 주고, 화면에서 입력한 SQL을 실습 컨테이너에서 gdb로 추적해 단계 목록으로 돌려준다. 화면은 첫 단계(쿼리를 받는 `exec_simple_query`)의 소스 줄로 옮겨 가고, 학습자가 단계를 넘기면 소스와 그림이 함께 바뀐다.
2. 누구나 보기: 같은 화면을, 서버와 Docker 없이 파일 하나로 여는 재생본으로 내보낸다. 원문의 “누구든 쉽게 내용을 확인”에 대한 답이다. 재생본에는 기록과 그 기록이 가리키는 소스 구간만 들어간다.
3. 첫 주제는 PostgreSQL 18.6, 감시 목록은 기존 `select.watch`와 `index.watch`. 실행 중에 `commit.watch`(INSERT와 커밋)를 더했다. `index.watch`는 실습 3과 같은 조건(순차 스캔 끔)이 필요해, 감시 목록별 세션 설정(`pgOptions`)을 만든 뒤 넣었다.

제외한다(AI 판단, 다시 열 조건 포함).

- Linux 커널 주제: 커널 추적은 별도 빌드·권한 설계가 필요하다. 작업대의 주제 경계가 PostgreSQL 하나로 동작한 뒤 연다.
- 주제별 그림(MVCC 페이지 상태, WAL 시간축): 공통 그림(층 흐름, 호출 스택, 값)이 학습에 쓸모 있는지 사용자가 본 뒤 연다.
- 단계마다 AI가 쓴 설명문: 근거 없는 문장이 화면에 섞이는 위험이 크다. 이번에는 소스의 함수 머리 주석(1차 자료)과 README의 해당 질문 링크만 보인다. 출처가 붙은 설명 데이터는 다음 단계에서 연다.
- 공개 서버 운영: 실행 기능은 임의 SQL을 컨테이너에서 돌리므로 로컬 전용이다. 누구나 보기는 재생본으로만 한다.

### 안전 경계

실행 기능은 학습자가 입력한 SQL을 실습 컨테이너에서 실행한다. 실습의 psql 사용자 `postgres`는 슈퍼유저이므로, `COPY ... TO PROGRAM`이나 `pg_read_file()` 같은 SQL만으로도 컨테이너 안에서 셸 명령을 실행하거나 파일을 읽을 수 있다. 따라서 **SQL을 거르는 것으로는 보안을 지킬 수 없다.** 보안 경계와 입력 검사를 나누어 둔다(설계 검토 1번 지적을 받아들여 고침).

보안 경계는 아래 둘이다.

1. 컨테이너 격리. 지난 실습과 같이 `SYS_PTRACE`만 더하고 `--network none`으로 띄우며, 호스트에서는 `scripts` 폴더만 읽기 전용으로 연결한다. SQL이 컨테이너 안에서 무엇을 하든 네트워크로 나가거나 호스트 파일을 쓸 수 없다.
2. 다른 사이트가 보낸 요청 차단. 서버는 `127.0.0.1`에만 열고, 모든 요청의 `Host`가 `127.0.0.1:포트`나 `localhost:포트`가 아니면 거부한다(DNS 재바인딩 방어). 실행 요청은 POST만 받고, 머리글 `X-Workbench: 1`이 있어야 하며(다른 사이트의 스크립트는 사전 확인 없이 이 머리글을 보낼 수 없다), `Origin`이 있으면 서버 주소와 같아야 하고, `Sec-Fetch-Site`가 있으면 `same-origin`이어야 한다. CORS 허용 머리글은 어떤 응답에도 붙이지 않는다.

입력 검사는 보안이 아니라 세션 형식을 지키기 위한 것이다. `session.sh`는 SQL을 psql 스크립트의 한 줄로 쓰므로 아래를 거부한다.

- 백슬래시: psql 메타 명령이 되어 세션 순서가 깨진다.
- 줄바꿈과 제어 문자(탭 제외): 한 줄이라는 전제가 깨진다.
- 끝이 아닌 자리의 `;`: 문장이 둘이면 psql이 따로 보내 추적이 첫 문장에서 끝난다.
- 빈 입력과 공백뿐인 입력: psql이 끝나 백엔드가 사라진 뒤 gdb가 분리된다.
- 1000바이트 초과.

그 밖의 실행 규칙.

- 감시 목록과 호출 스택 함수는 workbench.json의 목록에서만 고른다. 학습자 입력을 경로로 쓰지 않는다. `TRACE_WATCH`에 임의 경로가 들어가면 trace.py가 그 파일의 각 줄을 `NOBREAK`로 찍어 파일 읽기 통로가 되기 때문이다.
- 스크립트에는 서버가 정한 최소 환경만 넘긴다(`PATH`, `HOME`, Docker 연결 설정, 고정된 `PG_OPTIONS=-c statement_timeout=30s`). 학습자 입력은 환경 변수로 넘기지 않는다.
- 실행은 한 번에 하나이고, 실행 중에 온 요청은 409로 거부한다. `session.sh`가 컨테이너의 고정된 `/tmp` 파일을 쓰기 때문이다.
- 실행이 실패하거나 시간 한도(90초)를 넘거나 취소되면 컨테이너 안에 남은 gdb와 세션 psql을 끝낸다. 남은 psql이 다음 실행의 표시 파일에 함께 깨어나 출력을 섞는 것을 막기 위해서다(설계 검토 2번). 처음 설계는 실행 전에도 정리했으나, 실행 중 발견한 반례(아래 "실행 중 바뀐 설계" 4번) 때문에 실행 전에는 컨테이너 안에 다른 추적이 있는지 확인만 하고, 있으면 409로 거부하도록 바꿨다.
- 정리는 gdb에 SIGINT, 최대 5초 기다림, 남았으면 SIGKILL, `/tmp/ready` 만들기, `^psql -X -At -f /tmp/session\.sql$`만 SIGTERM 순서다. 이 순서의 이유는 "실행 중 바뀐 설계" 1·2번이다.
- 감시 목록별 세션 설정(`pgOptions`)은 `workbench.json`만 정하고, `-c 이름=값`을 공백으로 이은 꼴만 받는다.
- 소스 경로는 `src/`·`contrib/`로 시작하는 상대 경로만 받고, `..`과 절대 경로는 거부한다.
- 내보낸 재생본에는 호스트 경로와 사용자 이름을 넣지 않는다. 출처는 저장소 기준 상대 경로로 적는다.
