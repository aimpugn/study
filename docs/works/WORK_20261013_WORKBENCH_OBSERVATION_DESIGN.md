- I/O 워커는 첫 차가운 실행에서만 `openat("base/5/16384")`를 했고, 뒤에는 이미 연 파일 디스크립터 30을 다시 썼다.

- 행 머리의 세 번째 칸(`t_field3`)은 5다. 두 방법이 같은 값을 보였고, 뜻(삽입한 트랜잭션 안의 명령 번호)은 해석하지 않았다.
- gdb 기록에는 시각이 없어 백엔드와 I/O 워커의 사건을 시각으로 맞추지 못했다. 순서는 인과(버퍼가 이미 VALID)로만 말할 수 있다.

## 설계 방향(초안, 사용자 검토 대기)

### 화면: 그림이 먼저

글은 이름표, 값, 그림만으로 전해지지 않는 한 줄에만 쓴다(사용자 지시 3). 사실과 추론의 구분(지난 B4)은 글 대신 모양으로 표시한다: 실선은 기록, 점선은 추론, 빗금은 “보지 않음”이다. 출처는 각 그림의 작은 표지로 붙인다. 지금 만든 글 위주의 시안은 사용자 지시 3으로 무효가 되어 저장소에 남기지 않았다.

그림 후보(모두 같은 실행, 같은 사건 번호에 묶임):

1. 프로세스 시간선: 위에서 아래로 사건 순서, 열은 psql, 백엔드, I/O 워커, WAL writer. 함수 멈춤과 시스템 콜이 같은 줄에 놓인다.
2. 주소 공간 지도: 백엔드와 I/O 워커의 주소 공간을 나란히 세우고, 같은 주소의 공유 메모리 구역을 가로로 잇는다. P8의 `0xffff80ab7000`이 두 프로세스에서 같은 칸을 가리킨다.
3. 공유 메모리 안: `BufferDescriptors` 배열(칸마다 64바이트)과 `BufferBlocks` 배열(칸마다 8KB)을 같은 칸 번호로 잇고, 16384칸의 쓰임을 칸 지도로 칠한다.
4. 칸에서 바이트까지: 버퍼 칸, 8KB 페이지 배치, 줄 포인터에서 행으로 가는 화살표, 행 바이트(머리 23바이트, 맞춤 1바이트, 데이터).
5. 메모리 컨텍스트 나무: 크기에 비례한 상자로 그리고 지금 쓰는 컨텍스트를 강조한다.
6. 파일에서 버퍼로: `base/5/16384`의 블록 줄에서 공유 버퍼 칸으로 가는 화살표와, 그 일을 한 프로세스.

상호작용: 사건 단위로 넘긴다(시스템 콜과 다른 프로세스의 일도 한 칸). 그림의 대상(파일, 칸, 행, 컨텍스트)을 누르면 그 대상을 건드린 사건만 시간선에서 강조한다. 데운 실행과 차가운 실행을 나란히 비교한다. 다음 사건을 가린 채 먼저 예측하게 하는 방식은 선택 사항이다(결정 D4).

### 구현 언어: Go

- 추적기: Go 프로그램이 gdb를 GDB/MI(`gdb --interpreter=mi3`)로 조종한다. 중단점, 캐치포인트, 식 평가, 메모리 읽기를 MI 명령으로 하고, 멈춤 이유를 MI 응답에서 읽는다. QLL-07의 `trace.py`와 이번 시험의 `probe.py`를 대체한다. gdb, strace, psql은 외부 도구로 남는다.
- 세션 준비와 실행 조정: `session.sh`, `run-trace.sh`, `run-strace.sh`, `start-lab.sh` 같은 셸 스크립트의 일을 작업대의 Go 하위 명령으로 옮긴다.
- 브라우저 화면: 브라우저에서 도는 코드는 JavaScript로 둔다(AI 해석, 결정 D1). Go를 WebAssembly로 빌드하는 대안은 있지만, 화면 코드의 규모에 비해 빌드와 디버깅 비용이 크다고 본다(추론).
- 옮기는 계획(새 관례): QLL-07 실습 README가 부르는 스크립트(`run-trace.sh`, `run-strace.sh`, `mvcc-page.sh`, `session.sh`, `start-lab.sh`, `find-def.sh`, `check-readme.sh`, `trace.py`)를 Go 하위 명령으로 바꾸고, 같은 SQL에서 같은 기록이 나오는지 지난 B1 방식으로 대조한 뒤 지운다. README의 명령도 함께 바꾼다.
- 확인할 가정. A1: MI가 시스템 콜의 입구와 출구를 다른 멈춤 이유로 알려 준다(예상, 미확인). A2: 메모리 컨텍스트 117개를 MI로 순회하는 수백 번의 왕복이 실행 한 번에 몇 초 안에 끝난다(미측정). A3: 사건마다 시각을 붙여 백엔드와 워커의 기록을 같은 시계로 맞출 수 있다(같은 커널의 시계라서 가능하다고 봄, 미확인). 셋 중 하나라도 깨지면 이 절을 다시 연다.

### 판정 기준(초안, 결정을 받은 뒤 고정)

- O1 같은 실행: 화면의 모든 사건과 메모리 값이 한 번의 실행에서 나온다. 대조용 실행 직후 값은 그렇다고 표시한다.
- O2 메모리 값: 행 바이트와 줄 포인터는 `heap_page_items`, 칸의 태그와 사용 횟수는 `pg_buffercache`와 대조해 불일치 0.
- O3 파일: 차가운 실행에서 테이블 파일 읽기(누가, 어느 파일, 위치, 크기, 읽어 넣은 주소)가 보이고, 데운 실행에서는 0회로 보인다. strace 원문과 대조.
- O4 그림으로 답하기: 화면의 그림만 보고 다음에 답할 수 있다. (1) 쿼리 바이트는 어떤 시스템 콜로 들어왔나 (2) 테이블 파일을 누가 어느 위치에서 읽었나 (3) 그 바이트는 메모리의 어디에 들어갔고 백엔드는 어떻게 같은 바이트를 보나 (4) 페이지 안의 세 행은 어디에 있고 왜 모두 보이나 (5) 실행기는 어느 메모리 컨텍스트에서 일했나. 사용자와 분리 검토자가 판정한다.
- O5 글의 양: 그림 하나에 붙는 글이 이름표와 한 줄 설명을 넘으면 그 글이 왜 필요한지 검토 기록에 남긴다.
- O6 실패 경로: 시간 초과, 사건 수 한도 초과, 다른 추적 중 거부를 실제 프로세스로 일으켜 서버 재시작 0.
- O7 화면 기계 조건: 지난 B7(375px, 대비, 키보드)을 유지한다.
- L: 사용자 판단.

## 방향 전환: 정해 둔 부품을 실제 실행으로 조립하기

사용자 원문(2026-10-13, 이 대화):

> 그래서 제가 생각한 것은 당신이 말한 것처럼 디버깅 기능인데... select, create, insert 등등을 모두 미리 정리해둘 수는 없을 거 같아서요. 물론 설명이 필요할 수 있긴 한데, 그건 나중에 생각하고, 일단 요청이 들어가면 그 내부 코드를 어떻게 타는지를 보여주는 것을 먼저 해보면 어떨까 싶습니다. 그러면 미리 다 만들어 두는 게 아니게 되는 거죠. 시각화 요소, 디자인 컴포넌트들은 정의해두고, 그 내부 동작에 따라서 컴포넌트들을 조립해서 동적으로 시각화하는 거죠. 그리고 조립되면 리플레이 가능하게 뒤로 갈 수 있고 앞으로 갈 수도 있고요.

기존 목적과의 관계. “쿼리를 치면 그 쿼리에 따라 동작하는 내부가 보인다”는 원래 목적은 그대로다. 바뀌는 것은 방법이다. 쿼리마다 경로와 그림을 미리 정리하는 대신, 그림 부품과 부품을 고르는 규칙만 한 번 정하고, 화면은 실제 실행 기록에서 매번 조립한다. 설명 글은 뒤로 미룬다(사용자 결정). 앞 절의 “그림 후보 1~6”과 결정 D3(첫 그림)은 이 방식의 부품 목록으로 흡수된다. 컨셉 2(전체 구조 위, 누르면 펼침)는 따로 그리지 않고, 실제 기록이 나온 뒤 그 기록으로 조립한 모습으로 대신한다(AI 판단, 그림이 상상이 아니라 기록에서 나오게 하려는 것).

이 방식의 전제는 **감시 목록 없이 모든 함수 호출을 기록하는 것**이다. P12·P13에서 감시 목록이 `CatalogTuplesMultiInsertWithInfo`와 `table_index_build_scan`을 놓쳤으므로, 고른 함수만 보는 방식으로는 “요청마다 실제 경로”가 나오지 않는다.

### 기록 방법: 컴파일러가 모든 함수 입구와 출구에 기록 호출을 넣는다

gcc의 `-finstrument-functions`로 백엔드를 다시 컴파일하면, 모든 함수의 입구와 출구에서 `__cyg_profile_func_enter(this_fn, call_site)`와 `__cyg_profile_func_exit`가 불린다. 이 두 함수를 작은 C 파일로 만들어 백엔드에 함께 링크한다. 두 함수는 PostgreSQL 함수를 부르지 않고 libc만 쓴다(부르면 기록 호출이 다시 기록 호출을 부른다).

- Go 예외: 이 기록 함수는 PostgreSQL 프로세스 안에서 돌아야 하므로 C다. Go 공유 라이브러리로 만드는 대안은 postmaster가 exec 없이 fork하는 구조와 Go 런타임의 스레드가 맞지 않아 고르지 않았다(추론). 기록을 읽고 해석하고 화면에 보내는 쪽은 Go다.
- 기록 형식: 사건 하나에 고정 크기 레코드 하나(종류, 함수 주소, 부른 자리 주소, `CLOCK_REALTIME` 나노초)를 `/tmp/pgtrace/<pid>.bin`에 `O_APPEND`로 `write()` 한 번에 쓴다. 버퍼를 두지 않으므로 fork한 자식이 부모의 미기록분을 물려받지 않고, `_exit`로 끝나도 꼬리를 잃지 않는다. fork 뒤 자식은 `pthread_atfork`로 자기 파일을 새로 연다.
- 주소 해석: Debian gcc는 PIE로 링크하므로 실행 때 주소가 ELF 주소와 다르다. 파일 머리에 실행 때 `main`의 주소를 적어 차이를 구한다. Go의 `debug/elf`와 `debug/dwarf`로 주소를 함수 이름, 정의 파일, 부른 자리의 소스 줄로 바꾼다.
- 부른 자리(`call_site`)를 함께 남기면 DWARF 줄 표로 “부른 함수의 몇 번째 줄에서 불렀나”가 나온다. QLL-08부터 원한 “소스 줄로 이동”을 함수 단계마다 얻는 길이다.
- 이 방법은 ptrace를 쓰지 않는다. 그래서 “프로세스마다 추적자 하나” 제약(P1)이 사라져, 같은 실행에서 strace로 모든 프로세스의 시스템 콜을 함께 기록하고 시각으로 맞출 수 있다.
- `elog(ERROR)`의 `longjmp`는 중간 함수들의 출구 기록을 건너뛴다. 해석기는 입구와 출구가 맞지 않는 기록을 받아들여야 한다.
- 실행 위치: 실행 중인 `pg-lab` 컨테이너 안의 `/src`에서 `src/backend`만 다시 컴파일하고(`make install`은 하지 않음, `pg-lab` 서버의 실행 파일은 그대로), 새 실행 파일을 다른 데이터 디렉터리와 다른 소켓으로 두 번째 서버로 띄운다. 다운로드 0. 컨테이너를 지우면 사라지는 탐색용 구성이다.

예상하지 못한 관측:

- 서버를 다시 띄운 직후의 첫 접속(`pg_isready`, 5247)이 118만 번을 불렀다. 쿼리가 아니라 접속 준비(카탈로그 캐시 파일을 처음 만드는 일로 추정, 함수 이름으로 확인 필요)다. 다음 접속(S1)은 쿼리 전 준비가 그보다 훨씬 작다.
- 백엔드가 카탈로그 페이지 12장을 직접 `pread64`했다(`2663`, `2662`, `2659`, `2696`, `3379`, `global/2697`, `global/1213`). I/O 워커가 읽은 것은 `t`의 페이지 한 장뿐이다. 소스: `ReadBuffer_common`이 `READ_BUFFERS_SYNCHRONOUSLY`를 켜고(`bufmgr.c` 1241~1247행, “immediately waiting”이면 비동기의 이득이 없다는 주석), 이것이 `PGAIO_HF_SYNCHRONOUS`가 되고(`bufmgr.c` 1795~1796행), 이 표시가 있으면 I/O를 낸 프로세스가 직접 실행한다(`aio.c` 493~494행). 기록도 맞는다: 이 쿼리 구간에서 백엔드의 `pgaio_io_stage`는 13번, 그중 `pgaio_io_perform_synchronously`가 12번(백엔드의 `pread64` 12번과 같음), `pgaio_worker_submit`이 1번(I/O 워커가 읽은 한 장)이다. 순차 스캔은 read stream으로 비동기 읽기를 내므로 I/O 워커가 읽는다. 따라서 위 절 「그림과 다른 실제」의 첫 항목 “테이블 파일을 읽는 것은 I/O 워커다”는 넓게 말한 것이다. 고쳐 말하면 “한 장씩 바로 기다리는 읽기(`ReadBuffer`)는 백엔드가, read stream의 비동기 읽기는 I/O 워커가 한다”이다. 이 정정은 사용자에게도 알린다.
- `SELECT 1/0`의 오류는 실행기가 아니라 계획 단계의 상수 계산에서 났다: `eval_const_expressions_mutator` → `simplify_function` → `evaluate_function` → `evaluate_expr` → `ExecInterpExpr` → `int4div` → `errfinish`.
- postmaster와 logical replication launcher가 각각 6건을 버렸다(기록 도중 신호 처리기가 다시 들어온 경우). 기록 함수가 센 수다.
- 기록 크기: 약 5초 동안 인스턴스 전체를 기록해 198MB였다. 대부분은 postmaster, checkpointer, `pg_isready` 접속이다. 화면에 필요한 것은 세션 백엔드와 I/O 워커이므로 기록할 프로세스를 고르는 설정이 필요하다.
- 부른 자리 주소에서 4를 뺀 주소(aarch64의 `bl` 명령 자리)의 DWARF 줄이 소스와 맞았다: `postgres.c` 1065행 `pg_parse_query`, 1190행 `pg_analyze_and_rewrite_fixedparams`, 4770행 `exec_simple_query`.

설계에 생기는 일:

1. 기록은 세 겹이다. 함수 입구·출구(모든 함수, 이번 시험), 시스템 콜(strace, 같은 시계), 그리고 값(버퍼 칸, 페이지 바이트, 메모리 컨텍스트)이다. 셋째는 함수 기록에 들어 있지 않다. 값은 부품마다 정한 함수에서 읽어야 한다. 예를 들어 `ReadBuffer_common`이 돌려줄 때 버퍼 태그를 읽는다. 이것은 쿼리마다가 아니라 부품마다 한 번 정하는 일이므로 사용자 방향과 맞는다(추론, 아직 시험하지 않음). 이 시험 전까지 컨셉 1의 메모리 구조 그림은 새 방식에서 비어 있다.
2. 부품은 소스 디렉터리로 한 번 정한다. 헤더 함수는 가장 가까운 헤더 밖 조상의 부품으로 보낸다(P17).
3. 화면은 (기록, 커서 위치)만으로 정해진다. 앞뒤로 가기는 커서를 옮기는 일일 뿐이라, 거꾸로 실행하는 디버거가 필요 없다. 대신 기록하지 않은 값은 뒤로 가도 볼 수 없다.
4. 한 쿼리에 수천~수십만 번이므로, 단계는 묶음으로 넘긴다. 호출 깊이를 고르는 단계와, 부품을 눌러 그 부품에 들어간 순간만 넘기는 단계를 둔다(컨셉 2).

## 컨셉 2에 대한 사용자 판단과 요청의 여정

사용자 원문(2026-10-13, 이 대화):

> 음... 지금은 오히려 너무 난잡합니다. 제가 하는 것은 일종의 thread와 마찬가지입니다. 제가 요청하면 어떤 일련의 과정을 다 거치고 응답이 오고 데이터가 보이면서 끝납니다. create table이나 create index 등은 테이블 생성이나 인덱스 생성 등이 되고 성공했다는 응답을 받겠죠. 그러면 제가 SELECT ... 입력하고 Enter 치는 순간 요청이 DB 프로세스로 들어갑니다. 클라이언트 통해서. 그리고 어떤 과정을 거쳐서 저에게 옵니다. 저는 그 "어떤 과정"을 세세하게 보고 싶은 겁니다. select든 update든 insert든 create table든 create insert든, 뭐가 됐든. 앞서 보여준 전체 DB 요소들의 어떤 부분을 어떤 순서로 거쳐서 어떻게 요청이 처리되고 어떻게 응답이 오는지, 이걸 보고 싶은 겁니다. 그런데 이번에 새로 보여준 건 어떤 요청 하나에 대해 어떻게 처리되는지 전혀 모르겠네요. 그리고 제가 query를 타이핑해서 요청할 수 있어야 합니다. 지금은 그냥 고정된 요청인데... 고정된 요청이 아니라 제가 진짜 db client에서 쿼리 날리되, 제 요청에 따라 어떻게 DB가 동작하는지를 보고 싶은 겁니다.

컨셉 2 판정: 부족(사용자 판단). 원인(AI 해석): 컨셉 2는 기록 장치가 본 것(호출 나무, 부품별 횟수, 시간선)을 첫 화면에 그렸고, 요청 하나가 어느 구성 요소를 어떤 순서로 지나 응답으로 돌아오는지는 그리지 않았다. 기록 방법(모든 함수 호출 + strace)은 유지하고, 첫 화면을 바꾼다.

목적 대조. “요청 하나가 들어와 응답이 나갈 때까지 구성 요소를 어떤 순서로 지나는가”는 원래 원문의 “쿼리를 실행합니다. 그러면 … 시각화는 어떤 일이 이뤄지는지 보여줍니다”와 같은 뜻이고, 이번에 단위(요청 하나, thread처럼 처음부터 끝까지)와 입력 방식(사용자가 실제 클라이언트로 아무 쿼리나)을 분명히 했다. 실제 클라이언트가 무엇인지(컨테이너 안 psql인지, 호스트의 다른 도구인지)는 원문에 없으므로 사용자에게 확인한다.

### 설계: 단계는 PostgreSQL의 요청 처리 순서에서, 내용은 기록에서

- 단계 뼈대: 위 시험에서 `exec_simple_query` 바로 아래 함수들의 순서가 `SELECT`, `CREATE TABLE`, `CREATE INDEX`에서 같았다(`pg_parse_query` → `pg_analyze_and_rewrite_fixedparams` → `pg_plan_queries` → `PortalStart` → `PortalRun` → `PortalDrop` → `finish_xact_command` → `EndCommand`). 이것은 쿼리 종류가 아니라 PostgreSQL의 요청 처리 루프(`tcop/postgres.c`)가 정한 순서다. 그래서 단계(받기, 구문 분석, 의미 분석, 계획, 실행, 커밋, 응답)는 한 번 정하고, 단계마다의 내용은 기록에서 채운다.
- 단계 안의 일(“거친 곳”): 부품마다 한 번 정한 관측점으로 센다. 공유 버퍼(버퍼를 찾는 함수), 데이터 파일(백엔드나 I/O 워커의 `pread64`·`pwrite64`, 새 파일 `openat O_CREAT`), WAL 버퍼(`XLogInsert`), WAL 파일(`pg_wal`로 가는 `pwrite64`와 `fdatasync`), 클라이언트(`recvfrom`·`sendto`의 바이트와 메시지 종류). 같은 부품에 잇달아 간 일은 한 칸으로 묶고 횟수를 붙인다.
- 그림: 구성 요소 띠 하나(클라이언트, 백엔드, 공유 버퍼, WAL 버퍼, 데이터 파일, WAL 파일, I/O 워커) 위에 번호 붙은 이동을 시간 순서로 긋고, 그 아래 한 줄짜리 이동 목록을 둔다. 이동을 누르면 그때의 호출 스택과 소스 줄이 나온다. 컨셉 2의 시간선과 호출 나무는 이 펼침 안에만 남는다.

### 사전 등록(실행 전): 처음 보는 쿼리로 여정 만들기

| P25 | 이어서 보낸 `SELECT`는 같은 뼈대에 다른 이동을 갖는가 | 같은 뼈대. `t`의 페이지는 이미 공유 버퍼에 있어 파일 읽기 0, WAL 쓰기 0, 응답 한 번 | 다르면 그림이 쿼리마다 달라지는 이유를 다시 찾는다 |

### 결과: 요청 두 개의 여정(21:00~21:25)

`serve.sh`로 기록 서버를 새로 띄운 뒤, 컨테이너 안 psql로 `UPDATE t SET name='z' WHERE id=2`(백엔드 5531)를 보내고 다른 연결로 `SELECT * FROM t`(백엔드 5534)를 보냈다. 해석은 `decode journey`(Go)다.

해석기 결함 하나를 고쳤다. `-yy`가 소켓에 붙이는 표시(`9<UNIX-STREAM:[3150503->3150502,"/tmp/pgi/.s.PGSQL.5433"]>`) 안에 `->`와 따옴표가 있어서, 표시가 첫 `>`에서 끝난다고 본 정규식이 경로를 자르고 표시 안의 따옴표를 데이터의 시작으로 읽었다. 그래서 `Q` 메시지를 찾지 못했다. 표시의 끝을 “`>` 바로 뒤에 `, `가 오거나 줄이 끝나는 자리”로 바꿨다.

| 번호 | 결과 | 판정 |
| --- | --- | --- |
| P21 | 두 쿼리 모두 받기 → 구문 분석(`pg_parse_query`, `postgres.c:1065`) → 의미 분석(`:1190`) → 계획(`:1193`) → 실행(`PortalStart`, `:1235`) → 커밋(`finish_xact_command`, `:1298`) → 응답(`EndCommand`, `:1337`) | PASS |
| P22 | 요청 `Q` 수신과 다음 수신(종료 `X`) 사이의 `sendto`는 쿼리마다 한 번이다(5531: 20 B, 5534: 122 B). 그 순간의 스택은 `PostgresMain > ReadyForQuery > socket_flush > internal_flush > … > secure_raw_write`다. UPDATE는 `fdatasync`(80.1 ms) 다음에 `sendto`(82.8 ms)가 왔다. 경계: 응답은 `socket_putmessage`가 통신 버퍼(`PqSendBuffer`, `PQ_SEND_BUFFER_SIZE` 8192, `pqcomm.c:119`)에 쌓고, 버퍼가 차면 그 자리에서 내보낸다(`internal_putbytes`, `pqcomm.c:1284~1290`). 결과가 8 KB를 넘으면 실행 도중에도 `sendto`가 나가므로, 이 PASS는 작은 결과에 한정된다 | PASS(작은 결과) |
| P23 | 커밋의 `pwrite64` 8192 B와 `fdatasync`가 모두 `pg_wal/000000010000000000000001`로 풀렸다 | PASS |
| P24 | `t`(`base/5/16384`)의 페이지 8 KB를 pid 5514가 읽었다. `ps`로 이 pid가 `postgres: io worker 0`임을 확인했다. `heap_update` 1번, `XLogInsert` 3번(`XLogSaveBufferForHint`, `log_heap_update`, `XactLogCommitRecord`), 백엔드가 `pg_wal`에 8 KB를 쓰고 `fdatasync`, 응답은 `C "UPDATE 1"`과 `Z "I"`의 20 B다. 예상하지 못한 `XLogInsert` 하나는 아래 관측 1이다 | PASS |
| P25 | 단계 순서가 같다. 파일 읽기 0, WAL 0, 응답 한 번(122 B: `T` 하나, `D` 셋, `C`, `Z`) | PASS |

예상 밖 관측:

1. **행을 읽기만 해도 WAL이 생긴다.** UPDATE가 `t`를 순차 탐색하는 동안 `SetHintBits` → `MarkBufferDirtyHint` → `XLogSaveBufferForHint` → `XLogInsert`가 불렸다(`heapam_visibility.c:131`, `bufmgr.c:5542`, `xloginsert.c:1124`). 이 클러스터는 `data_checksums=on`, `wal_log_hints=off`다(`SHOW`로 확인). `serve.sh`의 `initdb`는 체크섬 옵션을 주지 않았고, 18.6의 `initdb.c:167`이 `data_checksums = true`로 시작하므로 기본값으로 켜진 것이다. `xloginsert.c:1043~1063` 주석에 따르면, 체크섬이 있으면 힌트 비트만 바꾼 페이지도 이번 체크포인트 이후 처음 바뀔 때 페이지 전체를 WAL에 남긴다. 체크섬이 깨진 페이지가 부분 기록되는 것을 막기 위해서다.
2. **요청 처리의 대부분은 카탈로그 조회다.** UPDATE의 이동 97개 가운데 81개가 시스템 카탈로그 읽기다. 판정 기준은 호출 스택에 `systable_*`(genam.c)가 있는지이고, 이 기준에 걸리지 않은 카탈로그 읽기는 없었다. 버퍼 찾기는 의미 분석 99번, 계획 86번, 실행 43번이고, 디스크에서 읽은 카탈로그 페이지는 각각 23장, 13장, 4장이다. 조회 목적은 스택에서 읽힌다. 13번 이동은 `GetSysCacheOid`가 이름 `t`를 찾느라 `pg_class_relname_nsp_index`를 읽은 것이고, 56번은 플래너의 `get_relation_statistics`가 `pg_statistic_ext_relid_index`를 읽은 것이다. 76번과 80번은 UPDATE가 논리 복제 대상인지 확인하는 `CheckCmdReplicaIdentity`가 `pg_publication_rel`과 `pg_index`의 인덱스를 읽은 것이다. 기록 중이라 늘어난 시간이지만 구간 비율로는 의미 분석과 계획이 0.5~61.8 ms(전체 82.8 ms)를 차지한다.
3. **두 번째 연결도 같은 조회를 다시 하지만 디스크에는 가지 않는다.** 5534의 SELECT도 의미 분석 51번, 계획 70번 카탈로그 버퍼를 찾았지만 디스크 읽기는 0이었다. 앞선 백엔드들(이 구간에서는 5531이 40장)이 공유 버퍼에 올린 페이지를 다시 쓴 것이다. 카탈로그 캐시(catcache·relcache)는 백엔드마다 따로 있으므로(`utils/cache/catcache.c`, 백엔드의 `CacheMemoryContext`) 새 연결마다 조회가 반복되고, 공유 버퍼는 프로세스 사이에 공유되므로 디스크 읽기는 반복되지 않는다.
4. **응답 메시지는 버퍼에 하나씩 쌓였다가 한 번에 나간다.** `socket_putmessage` 호출과 송신 바이트 안의 메시지를 순서대로 짝지으면 UPDATE는 2:2, SELECT는 6:6으로 정확히 맞았다. 쓴 함수는 스택에서 보인다. `T`는 `SendRowDescriptionMessage` 경로의 `pq_endmessage_reuse`, `D`는 `printtup`, `C`는 `EndCommand`, `Z`는 `ReadyForQuery`다.
5. **UPDATE는 행을 고치지 않고 새 버전을 만든다.** SELECT의 행 순서가 `1|a, 3|c, 2|z`였다. `SELECT ctid, * FROM t`로 확인하니 `id=2`는 `(0,4)`에 있고 `(0,2)`는 보이지 않는다. 순차 탐색은 물리 순서로 읽으므로, 새 버전이 페이지 끝에 붙었다는 것이 응답 순서에서 바로 보인다.

#### 컨셉 3: 요청 하나의 실(21:25)

[concept-3.html](../../open_source_internals/workbench/design/concept-3.html), [UPDATE 화면](../../open_source_internals/workbench/design/concept-3-update.png), [SELECT 화면](../../open_source_internals/workbench/design/concept-3-select.png).

- 위에는 psql 화면을 둔다. 쿼리를 보낸 뒤부터 응답이 소켓에 도착하는 단계까지는 “응답 기다리는 중”이고, 도착하면 psql이 보여 줄 결과(SELECT는 표, UPDATE는 `UPDATE 1`)가 나타난다.
- 가운데는 생명선 여덟 개(psql, 통신 버퍼, 백엔드, 공유 버퍼, WAL 버퍼, I/O 워커, 데이터 파일, WAL 파일)를 둔 순서도다. 프로세스와 메모리 종류(백엔드 메모리, 공유 메모리, 다른 프로세스, 디스크)로 묶어 색을 나눈다. 단계는 가로 띠이고, 띠마다 `exec_simple_query`가 부른 단계 함수 줄을 맨 위에 둔다.
- 카탈로그 조회는 단계마다 접힌 묶음 하나다(“버퍼 찾기 99번 · 디스크에서 23쪽”). 누르면 안의 이동이 각각 줄로 펼쳐지고, 읽은 파일은 `pg_class`의 이름으로 보인다. 이 접기 덕분에 UPDATE는 97개 이동이 25줄로, SELECT는 10개가 16줄로 줄었다.
- 오른쪽은 고른 줄의 내용이다. 소켓 이동이면 바이트를 메시지마다 종류 1 B · 길이 4 B · 내용으로 나눠 보이고, 통신 버퍼 쓰기면 그때까지 버퍼에 쌓인 메시지와 8 KB 중 쓴 양을 보인다. 그 아래는 호출 스택(칸마다 다음 칸을 부른 소스 줄)이고, 칸을 누르면 그 줄의 소스가 나온다. I/O 워커의 읽기를 고르면 I/O 워커 프로세스의 스택과 코드(`IoWorkerMain > pgaio_io_perform_synchronously > pg_preadv`)가 나온다.
- ◀ ▶ 와 재생으로 한 줄씩 앞뒤로 간다. 지나지 않은 줄은 흐리게, 지금 줄은 강조하고, 지금 이동의 점이 화살표를 따라 움직인다.

해석기에 더한 것: 이동마다 카탈로그 표시, 스택 칸마다의 소스 줄(가장 안쪽 칸은 함수 정의 줄, DWARF `DW_AT_decl_line`), 통신 버퍼 쓰기 관측점(`socket_putmessage`, 대신 `printtup` 관측점은 뺐다), 버퍼 쓰기와 송신 메시지의 짝짓기, `-src`로 가리킨 소스 트리에서 앞 8줄·뒤 12줄 발췌. 파일 번호와 이름의 대응표는 시안에서는 psql로 한 번 뽑아 넣었고, 제품에서는 Go 서버가 쿼리마다 `pg_class`에서 읽는다.

한계:

- 값이 없다. 어느 버퍼 칸에 들어갔는지, 페이지 안의 행 배치, WAL 레코드 내용은 아직 그리지 않는다. 부품별 값 관측점(D2와 함께 다시 본다)이 필요하다.
- 다른 프로세스의 데이터 파일 읽기는 모두 I/O 워커로 표시한다. 이번에는 `ps`로 확인했지만 체크포인터나 autovacuum의 읽기가 같은 구간에 있으면 잘못 붙는다.
- 시간은 기록 때문에 늘어나 있다. 화면은 시간 비례가 아니라 순서로 그린다.
- 시안은 실제 psql로 보낸 두 쿼리를 다시 재생한 것이다. 사용자가 치는 대로 바로 그리는 실시간 경로는 아직 없다.

### 다음 설계: 사용자가 친 쿼리를 바로 그리기

- 기록 서버를 계속 켜 두고(`serve.sh`가 하는 일), Go 감시기가 strace 출력을 따라 읽는다. 백엔드의 `sendto` 안에 `Z`(ReadyForQuery)가 보이면 쿼리 하나가 끝난 것이므로, 그 백엔드의 함수 기록에서 여정을 만들어 브라우저로 보낸다. 지금 해석은 200 MB 기록 전체를 읽어도 1초 안팎이었고, 감시기는 마지막 쿼리 구간만 읽으면 된다(추론, 시험 전).
- 클라이언트: 실습 컨테이너는 `--network none`이지만 컨테이너 안에 `lo`가 있다(`/proc/net/dev`로 확인). 그래서 컨테이너 안 psql이 Unix 소켓 또는 `127.0.0.1` TCP로 접속하면 네트워크 공개 없이 실제 클라이언트로 쓸 수 있다. 호스트의 GUI 클라이언트(DBeaver, DataGrip 등)를 쓰려면 포트 공개가 필요하다.
- 연결 끊김 관찰(사용자가 고른 뒤 사전 등록을 고정한다). 후보:
  - 유휴 만료: `SET idle_session_timeout = '3s'` 뒤 기다리면 서버가 먼저 연결을 끊는다. 예상: 백엔드가 `E`(FATAL, `57P05`)를 보내고 소켓을 닫는다. 다음 쿼리에서 psql은 연결이 닫혔다고 보고한다.
  - 상대가 사라짐: TCP(`127.0.0.1`)로 접속한 psql을 `pg_sleep` 도중 강제로 죽이면, 백엔드의 다음 송신이 실패한다. 예상: `sendto`가 `ECONNRESET` 또는 `EPIPE`로 끝난다. RST는 TCP에서만 생기므로 Unix 소켓에서는 `EPIPE`만 보일 것이다.
  - 사용자가 예로 든 “마지막 패킷을 N ms 전에 받았다”는 MySQL Connector/J의 오류 문구다. 서버의 유휴 시간 초과(`wait_timeout`)가 연결을 닫았는데 풀이 그 연결을 다시 쓴 경우에 주로 나오며, 위 유휴 만료와 같은 구조다. 이 실습은 PostgreSQL이므로 같은 구조를 PostgreSQL에서 본다.

## 컨셉 3에 대한 사용자 판단: 전체 구조를 미니맵으로

### 설계(AI 제안)

- 화면 배치. 위 줄에 미니맵(왼쪽)과 psql 창(오른쪽)을 두고, 아래 줄에 순서도(왼쪽)와 상세(오른쪽)를 둔다. 위 줄은 높이를 고정한다. psql 창은 높이 236 px에 안쪽 스크롤을 두어, 결과가 길어져도 아래 그림이 밀리지 않는다.
- 미니맵은 PostgreSQL 전체 구조를 한 번 정해 둔 지도다. 왼쪽에서 오른쪽 순서는 순서도의 생명선과 같다(클라이언트 | 백엔드 프로세스 | 공유 메모리 | 다른 서버 프로세스 | 디스크).
  - 백엔드 프로세스 안에는 처리 단계 칸 일곱 개, 통신 버퍼, 백엔드 메모리(카탈로그 캐시, work_mem)를 둔다.
  - 공유 메모리에는 공유 버퍼, WAL 버퍼, 락 테이블, 프로세스 배열, 커밋 로그(CLOG)를 둔다.
  - 다른 서버 프로세스에는 I/O 워커, WAL 라이터, 체크포인터, 백그라운드 라이터, autovacuum, 논리 복제 런처, postmaster를 둔다.
  - 디스크에는 데이터 파일, WAL 파일, 커밋 로그 파일을 둔다.
- 길. 순서도의 줄마다 미니맵의 노드 쌍을 정하고, 같은 쌍은 선 하나로 합친다. 백엔드가 한 일은 그 줄의 단계 칸에서 출발하므로, 어느 단계가 어디를 건드렸는지 보인다. 카탈로그 묶음은 단계 칸 → 카탈로그 캐시 → 공유 버퍼로 그리고, 디스크 읽기가 있으면 데이터 파일 → 공유 버퍼를, 락이 있으면 카탈로그 캐시 → 락 테이블을 더한다. 이렇게 그려도 되는 근거는 이번 실행의 카탈로그 읽기 83개가 모두 `utils/cache` 함수를 거쳤다는 관측이다. I/O 워커의 읽기는 데이터 파일 → 공유 버퍼로 긋고 I/O 워커 노드를 함께 강조한다. 데이터가 워커의 메모리를 거치지 않기 때문이다.
- 선의 상태는 셋이다. 지난 길은 실선, 지금 길은 주황 굵은 선에 움직이는 점, 앞으로 갈 길은 흐린 점선이다.
- 노드의 상태는 다섯이다. 지나감(색 채움), 지금(주황 테두리), 앞으로 지남(점선 테두리), 이 요청은 안 지남(회색), 파일 I/O로만 관측했고 이 요청 동안 I/O 없음(빗금)이다. 빗금은 다른 서버 프로세스에만 쓴다. 이 프로세스들은 strace의 파일 읽기·쓰기로만 보고, 함수 기록의 관측점은 대상 백엔드에만 적용하기 때문이다.
- 노드를 누르면 그 노드를 지나는 다음 줄로 옮기고, 상세 맨 위에 그 구성 요소의 역할을 한 줄로 보인다. 다시 누르면 그다음 줄로 간다.

미니맵이 회색으로 그린 노드는 “이 요청이 여기를 지나지 않았다”는 주장이 된다. 그래서 관측점이 없던 공유 메모리의 표들에 관측점을 더했다. 락은 `LockAcquireExtended`, 프로세스 배열은 `GetSnapshotData`·`GetNewTransactionId`·`ProcArrayEndTransaction`, 커밋 로그는 `TransactionIdCommitTree`·`TransactionLogFetch`, work_mem은 `ExecHashTableCreate`다. `pg_xact` 파일의 읽기와 쓰기도 strace 해석에 넣었다. 카탈로그 접기 규칙은 “스택에 `systable_*`가 있음”에서 “`systable_*`나 `utils/cache` 함수가 있음”으로 넓혔다. 카탈로그를 여느라 잡은 락(UPDATE 74번, SELECT 41번)이 이 규칙으로 묶인다.

결과로 순서도의 카탈로그가 아닌 줄은 UPDATE가 16개에서 25개로, SELECT가 8개에서 13개로 늘었다. 늘어난 줄과 거기서 관측한 것:

- 스냅숏: `exec_simple_query`가 구문 분석 뒤 `GetTransactionSnapshot`을 부르고, 실행 직전에 다시 부른다.
- 락: 의미 분석의 `RangeVarGetRelidExtended`가 이름 `t`를 찾으면서 그 테이블에 락을 잡는다.
- 트랜잭션 번호: 처음 행을 고치는 `heap_update` 안에서야 `AssignTransactionId`가 번호를 받는다. 이어서 그 번호에 대한 락(`XactLockTableInsert`)을 잡는다. SELECT는 번호를 받지 않았다.
- 커밋 상태: 행을 볼지 판단할 때 `TransactionIdDidCommit`이 커밋 로그를 읽는다. 커밋할 때는 WAL `fdatasync`(153번) 다음에 커밋 로그에 기록하고(154번), 그다음 프로세스 배열에서 트랜잭션을 뺀다(155번). 디스크에 남긴 뒤에야 다른 프로세스에 커밋이 보이는 순서가 그대로 보인다.

### 한계와 손으로 넣은 자료

- 프로세스 역할(pid와 이름)은 기록할 때 `ps`로 본 값을, 파일 번호와 이름은 `pg_class` 질의 결과를 시안에 손으로 넣었다. 제품에서는 Go 서버가 쿼리마다 `pg_stat_activity`와 `pg_class`를 읽는다. `_fsm`, `_vm`가 붙은 파일 이름은 지금 해석기가 카탈로그와 사용자 객체로 가르지 못한다(이번 자료에는 없었다).
- 미니맵의 노드 배치와 역할 문장은 사람이 한 번 정한 것이다. 노드의 상태와 길은 기록에서 나온다.
- 카탈로그 묶음을 펼치면 락 관측점 때문에 줄이 많다(UPDATE 의미 분석 67줄). 펼침은 누를 때만 일어난다.

## 사용자 질문: 다른 문장도 되는가, 커널은 어떻게 보는가

사용자 원문(2026-10-13, 이 대화에서 컨셉 4 작업 중에 받은 순서대로):

> 이러면 select update만 되나요? create indext 등은 어떻게 되나요? show status? 뭐 이런 것들은? 그런 것들도 다 커버되나요?

> fdatasync? fsync? 이런 것들은 커널일 텐데... 커널도 어떻게 동작하는지 같이 이해할 수 있으면 좋겠습니다. 어떤 파일에 어떻게 쓰기 되는지까지?

목적 대조. 첫 질문은 컨셉 2 판단 때의 원문(“select든 update든 insert든 create table든 create insert든, 뭐가 됐든”)을 확인하는 것이다. 새 요구가 아니다. 둘째 질문은 관측 범위를 시스템 콜 경계 아래로 넓히는 요구다. [QLL-08 행](../../ai/authoring/question-led-learning/PLAN.md)은 “Linux 커널 주제는 그 뒤에 연다”로 미뤄 두었다. 이 질문으로 그 순서를 사용자가 당겼다고 해석한다(AI 해석). 권한과 다운로드가 걸리므로 아래 D7로 확인한다.

### 확인: 한 접속에서 여섯 문장(22:11)

같은 기록 서버(21:04에 띄움)에 컨테이너 안 psql 접속 하나(백엔드 5903)로 아래 여섯 줄을 차례로 보냈다(strace 시각 22:11:26~22:11:27). 이번에는 예상을 미리 적지 않았다. 그래서 아래는 판정이 아니라 관측이다.

| 차례 | psql에 친 것 | 이동 | 접은 뒤 줄 | 본 것 |
| --- | --- | --- | --- | --- |
| 1 | `CREATE INDEX t_name_idx ON t(name);` | 329 | 31 | 새 파일, 카탈로그 기록, 정렬, 인덱스 페이지 쓰기, 커밋 때 무효화 알림 |
| 2 | `SHOW work_mem;` | 7 | 7 | 카탈로그 조회 0, 응답 64 B 한 번(`T` `D "4MB"` `C` `Z`) |
| 3 | `SHOW status;` | 7 | 7 | 오류. `E` 100 B가 먼저 나가고 `Z` 6 B가 따로 나감 |
| 4 | `INSERT INTO t VALUES (4,'d');` | 48 | 25 | 트랜잭션 번호, 행 넣기, 인덱스 항목 넣기, 인덱스 페이지 읽기 |
| 5 | `SELECT length(repeat('x', 20000)), repeat('x', 20000) AS big \gx` | 36 | 11 | 응답이 세 번에 나감(8,192 B, 11,882 B, 20 B) |
| 6 | `SELECT $1::int + 1 AS answer \bind 41 \g` | 29 | 12 | 확장 프로토콜. 요청 81 B에 `P` `B` `D` `E` `S`, 응답 75 B에 `1` `2` `T` `D` `C` `Z` |

기록 자체는 문장 종류를 가리지 않는다. 컴파일러가 넣은 함수 입구·출구 기록과 strace는 서버가 하는 일을 모두 남긴다. 빈틈은 기록을 요청 단위로 자르고 읽는 해석기(`decode journey`)에 있었다. 이 실행에서 세 가지를 찾았다.

1. **오류 응답은 두 번에 나간다.** 해석기는 응답 송신을 하나로 보고 있었다. 오류는 `EmitErrorReport → send_message_to_frontend → socket_flush`가 `E`를 쓰자마자 내보내고(elog.c:1737, :3695), `ReadyForQuery`가 `Z`를 따로 내보낸다. 고친 것: 요청의 경계를 `ReadyForQuery` 함수 입구 두 개 사이로 잡고, 그 안의 송신을 모두 읽는다. `E`를 버퍼에 쓴 순간부터는 “오류 처리” 단계로 둔다. 오류가 난 자리는 `PortalStart → UtilityTupleDescriptor → GetPGVariableResultDesc → GetConfigOptionByName → find_option → errfinish`였다. `SHOW`가 결과의 열 모양을 정하려고 설정 이름을 찾다가 실패한 것이다.
2. **8 KB보다 큰 응답은 실행 도중에 나가고, 메시지 하나가 송신 둘에 걸친다.** 해석기는 송신 하나를 메시지 경계로 보고 있었다. `T`와 `D`의 앞부분이 8,192 B 버퍼를 채우자 `internal_putbytes`가 버퍼를 비웠다(pqcomm.c:1288). 남은 `D` 11,882 B는 버퍼보다 크고 버퍼가 비어 있어서 버퍼를 거치지 않고 바로 나갔다(pqcomm.c:1302). 고친 것: 송신마다 앞 송신에서 남은 메시지 길이를 넘겨받아, 걸친 메시지를 잘린 쪽(cut)과 이어진 쪽(cont)으로 표시한다. P22의 “작은 결과에 한정” 경계가 이 관측으로 확인되었다.
3. **확장 프로토콜은 방향마다 같은 글자의 뜻이 다르고, 단계 함수를 부르는 함수도 다르다.** 클라이언트의 `D`는 Describe, `E`는 Execute이고 서버의 `D`는 DataRow, `E`는 ErrorResponse다. 해석기는 방향 없이 읽고 있었다. 고친 것: 메시지를 방향을 알고 읽고, Bind의 인자 값(이번에는 `41`)까지 푼다. 단계 함수는 깊이와 상관없이 요청 구간 안에서 처음 들어온 자리를 시각 순서로 놓는다. 이번 실행의 순서는 이렇다.
    - 구문 분석과 의미 분석: `exec_parse_message`가 부른다(postgres.c:1465, :1520). 의미 분석 함수는 `pg_analyze_and_rewrite_varparams`다.
    - 계획: Bind 때 `BuildCachedPlan`이 부른다(plancache.c:1082).
    - 실행 시작: `exec_bind_message`가 `PortalStart`를 부른다(postgres.c:2052).
    - `C` 쓰기: `exec_execute_message`의 `EndCommand`가 한다(postgres.c:2328).
    - 커밋: Sync를 받은 `PostgresMain`이 `finish_xact_command`를 부른다(postgres.c:4973).

    단순 쿼리는 커밋 다음에 `C`를 쓰지만, 확장 프로토콜은 `C`를 쓴 다음에 커밋한다. PgJDBC 같은 드라이버는 이 프로토콜로 보낸다고 알려져 있다(외부 지식, 이 실습에서는 확인하지 않음).

DDL의 줄 접기도 고쳤다. CREATE INDEX는 처음에 이동 329개 가운데 약 100개가 펼쳐져 있었다. 대부분 새 인덱스의 정의를 시스템 카탈로그에 행으로 쓰는 일이었다. 쓰기 하나마다 그 표의 빈 공간 지도(`_fsm`) 읽기, 카탈로그 인덱스 넣기, WAL 기록이 따라온다. 바꾼 규칙은 세 가지다.

- 스택에 `src/backend/catalog/indexing.c`의 함수(`CatalogTupleInsert`, `CatalogTuplesMultiInsertWithInfo`, `CatalogIndexInsert`, `CatalogOpenIndexes`)가 있으면 카탈로그 일로 접는다. 디렉터리 `catalog/` 전체로 넓히지 않은 이유가 있다. `index_create`(catalog/index.c)가 새 파일 만들기, 정렬, 인덱스 페이지 쓰기까지 부르므로, 디렉터리로 가르면 요청 전체가 접힌다.
- `utils/cache/inval.c`는 접지 않는다. 이 파일은 캐시 조회가 아니라, 커밋 때 다른 백엔드에 캐시를 버리라고 알리는 길이다. 이 규칙으로 커밋 단계의 무효화 알림(`AtEOXact_Inval → SendSharedInvalidMessages → SIInsertDataEntries`, 326번)이 보이게 되었다.
- 파일 이름의 `_fsm`, `_vm`, `_init`, `.1` 같은 접미사는 떼고 번호를 본다. 그래서 `base/5/1259_fsm`이 “카탈로그 페이지 읽기”로 분류된다.

결과로 CREATE INDEX는 31줄로 줄었다. 남은 줄이 이 문장이 하는 일이다.

- 표에 락을 잡는다(17번, `RangeVarGetRelidExtended`).
- 새 파일 `base/5/16393`을 만들고(107번, `mdcreate`), 그 사실을 WAL에 남긴다(108번, `log_smgrcreate`).
- 새 인덱스에 거는 배타 락 때문에 트랜잭션 번호를 받는다(110번, `LogAccessExclusiveLockPrepare`). 그 락을 WAL에 남긴다(112번, `LogAccessExclusiveLocks`).
- 정렬을 시작하고(284번), 표를 읽고(289번), 인덱스 페이지를 WAL에 남긴 뒤(292번, `log_newpages`) 파일에 쓴다(293번). strace로 보면 `base/5/16393`의 오프셋 0과 8192에 8 KB씩이다.
- 커밋한다. WAL `pg_wal/000000010000000000000001`의 오프셋 7,790,592에 90,112 B를 쓰고 같은 디스크립터에 `fdatasync`를 한다(321~323번). 이어서 커밋 로그와 프로세스 배열을 갱신하고(324~325번), 무효화 알림을 보낸다(326번).

카탈로그에 행을 쓴 함수는 `InsertPgClassTuple`, `InsertPgAttributeTuples`, `UpdateIndexRelation`, `recordMultipleDependencies`의 넷이다. 접힌 묶음을 고르면 이 이름이 보인다.

회귀 확인. 바꾼 해석기로 UPDATE(5531)와 SELECT(5534)를 다시 해석했다. 이동 수(158, 48), 단계, 이동마다의 종류·횟수·카탈로그 표시가 바꾸기 전 출력과 같았다. 두 출력에 새로 붙은 것은 단계마다 그 함수를 부른 함수 이름(`caller`)뿐이다. `go vet`과 `golangci-lint`는 문제 0개였다.

화면. [concept-4.html](../../open_source_internals/workbench/design/concept-4.html)에 여덟 문장의 단추를 두었다. 바뀐 것은 아래와 같다.

- 처리 단계 칸에 “오류”를 더했다.
- 공유 메모리에 무효화 큐 노드를 더했다. 순서도의 생명선 “락·트랜잭션”은 “공유 표”로 이름을 바꾸고 무효화 큐도 여기에 모았다.
- 메시지 색과 이름은 방향마다 나눈다.
- 송신이 일어난 이유를 스택으로 붙인다(ReadyForQuery, 버퍼가 참, 버퍼 없이 바로 보냄, 오류 즉시 송신).
- psql 창은 응답의 끝(`Z`)이 도착한 줄부터 결과를 그린다. psql이 정확히 어느 메시지를 받은 순간 화면에 쓰는지는 psql 쪽을 기록하지 않아 확인하지 않았다. 이번 자료에서 `C`와 `Z`가 다른 송신에 있던 것은 오류 하나뿐이다. `\gx`는 세로 출력으로 그린다.

찍은 화면은 다음과 같다. 헤드리스 Chrome으로 찍었고, 이번에는 내장 브라우저에서 누르지 않았다.

- [CREATE INDEX 326번](../../open_source_internals/workbench/design/concept-4-create-index.png)
- [SHOW 오류 4번](../../open_source_internals/workbench/design/concept-4-error.png)
- [`\bind` 1번](../../open_source_internals/workbench/design/concept-4-bind.png)
- UPDATE와 SELECT 다시 찍음

화면을 다시 보다가 잘못된 표시 하나를 찾아 고쳤다. INSERT의 36번(WAL 8 KB 쓰기)은 WAL 라이터(pid 5519)가 한 일인데, 화면은 다른 프로세스의 일을 모두 I/O 워커 생명선에 긋고 미니맵의 I/O 워커 노드를 켰다. 해석기도 다른 프로세스의 데이터 파일 읽기를 “페이지 읽기(I/O 워커)”로 적었다. 컨셉 3의 한계에 적어 둔 것이 이 자료에서 실제로 틀린 그림을 만든 것이다. 지금은 해석기가 pid만 남기고, 화면이 기록할 때 `ps`로 본 역할표로 노드를 고른다. 역할표에 없는 pid는 어느 노드도 켜지 않는다. 생명선 이름은 “다른 프로세스”로 바꾸었다. 고친 뒤 여덟 출력을 견주면, 바뀐 것은 UPDATE 140번의 종류 이름 하나뿐이다.

남은 한계:

- 다른 프로세스의 역할은 기록할 때 손으로 본 `ps` 값이다. 짧게 떴다 사라지는 프로세스(autovacuum 작업 프로세스 등)는 역할표에 없을 수 있다. 이 자료에는 WAL 라이터의 함수 기록을 담지 않아 그 줄에는 호출 스택이 없다.
- 락이 어느 표에 걸렸는지 모른다. 함수 인자를 기록하지 않기 때문이다. CREATE INDEX의 31줄 가운데 12줄이 락이다. `table_open`을 부른 함수로 미루어 보면 대부분 카탈로그 표의 락이다(추론). `REINDEX`의 `reindex_index`처럼 같은 디렉터리의 함수가 사용자 표를 여는 경우가 있어서 함수 이름으로 접지 않았다. 부품별 값 관측점이 생기면 락 대상의 OID로 가린다.
- 확장 프로토콜의 마지막 `Z` 쓰기와 송신은 “커밋” 띠 안에 그려진다. `ReadyForQuery`를 단계 함수로 두지 않았기 때문이다. 순서 자체(`C` → 커밋 → `Z`)는 기록과 같다.
- 이진 형식의 Bind 값은 바이트 수만 보인다.
- 해보지 않은 것: `BEGIN … COMMIT`처럼 커밋이 다른 요청에 있는 경우, `COPY`(복사 하위 프로토콜), `VACUUM`, `NOTICE`, 파이프라인, 이 해석기 버전으로 다시 본 `CREATE TABLE`.
- `SHOW status`는 MySQL의 `SHOW STATUS`에 해당하는 명령이 PostgreSQL에 없어서 오류가 났다. PostgreSQL에서 같은 정보는 `pg_stat_*` 뷰(예: `pg_stat_database`)와 `SHOW ALL`에 있다.

### 상시 기록은 70분에 2.8 GB

`serve.sh`는 모든 서버 프로세스의 함수 호출을 계속 기록한다. 21:04부터 약 70분 동안 기록 파일이 2.7~2.8 GB가 되었다. 가장 큰 파일 하나(1.29 GB)는 이미 끝난 프로세스의 것이었다(짧게 떴다 사라지는 autovacuum 작업 프로세스로 추정, pid의 역할은 확인하지 않음). 서버와 strace를 멈추고 `/tmp/pgtrace`를 지웠다(남은 strace 0개).

설계에 생기는 일. 사용자가 치는 대로 바로 그리는 실시간 경로는 이대로 켜 둘 수 없다. 대상 백엔드만 기록하고, 다른 프로세스는 시스템 콜만 보며, 요청이 끝나면 그 구간만 남기고 버리는 선택 기록이 필요하다. 방법은 실시간 경로를 설계할 때 정한다. 기록 함수 안의 켜고 끄는 표시와, 프로세스별 파일 크기 상한이 후보다.

### 커널: 지금 보이는 것과 보이지 않는 것

지금 기록으로 보이는 것은 시스템 콜 경계까지다. 어느 파일에 어느 위치부터 몇 바이트를 쓰라고 커널에 요청했는지, 그리고 동기화를 요청했는지가 보인다. 위 CREATE INDEX의 예를 들면 이렇다.

```text
pwrite64(13</tmp/pgi/data/base/5/16393>, …, 8192, 0) = 8192
pwrite64(13</tmp/pgi/data/base/5/16393>, …, 8192, 8192) = 8192
pwrite64(13</tmp/pgi/data/pg_wal/000000010000000000000001>, …, 90112, 7790592) = 90112
fdatasync(13</tmp/pgi/data/pg_wal/000000010000000000000001>) = 0
```

그 아래에서 커널이 하는 일은 기록되지 않는다. 이번 실행에서 관측한 것과 공식 문서가 말하는 것을 나눠 적는다.

- 공식 문서(man 2 write, man 2 fsync): `write` 계열은 성공해도 데이터가 디스크에 닿았다고 보장하지 않는다. `fsync`는 파일의 바뀐 데이터와 메타데이터를 저장 장치까지 내보내고 끝날 때까지 기다린다. `fdatasync`는 그 데이터를 다시 읽는 데 필요하지 않은 메타데이터(예: 수정 시각)는 내보내지 않는다. PostgreSQL이 WAL에 `fdatasync`를 쓰는 것은 `issue_xlog_fsync`의 스택에서 보였다.
- 관측하지 않은 것: 데이터가 페이지 캐시의 어느 페이지에 들어가고, 언제 더러운 페이지가 되고, overlayfs가 아래 파일 시스템에 어떻게 넘기고, 블록 계층과 virtio 장치가 언제 쓰는지. 아래 파일 시스템의 종류도 확인하지 않았다.

이 환경에서 확인한 사실(다운로드 없음):

- 커널: `7.2.9-orbstack-00391-g2b298d05fbd4`, aarch64(OrbStack VM). OrbStack이 원본 커널에 무엇을 고쳤는지는 확인하지 않았다.
- 실습 컨테이너 안에는 tracefs와 debugfs가 없다. `perf_event_paranoid=2`이고 perf, bpftrace, trace-cmd도 없다. 컨테이너의 루트 파일 시스템은 overlay다.
- 호스트의 `orb list`는 비어 있다. Docker 엔진 외의 OrbStack Linux 머신이 없다.

커널 안의 함수 경로(`vfs_fsync_range` → overlayfs → 아래 파일 시스템 → 블록 계층)를 실제로 보려면 커널 추적(ftrace나 eBPF)이 필요하다. 그러려면 둘 중 하나가 있어야 한다. 하나는 특권 컨테이너다. 지금까지 지킨 “특권 컨테이너를 쓰지 않는다”는 조건과 충돌한다. 다른 하나는 tracefs를 쓸 수 있는 OrbStack Linux 머신이다. 머신 이미지를 내려받아야 하고, 그 안에서 tracefs를 쓸 수 있는지는 아직 확인하지 않았다. 어느 쪽이든 추적 도구도 내려받아야 한다. 오른쪽 소스 창에 커널 코드를 보이려면 커널 소스(필요한 파일만 받거나 전체 소스)를 받아야 한다. 추적 없이 소스만 보이면 그 화면은 “읽은 코드, 관측 아님”으로 표시한다.

권한을 바꾸지 않고 더 볼 수 있는 것(후보, 시험 전):

- strace `-T`: 시스템 콜마다 커널 안에서 걸린 시간. `fdatasync`가 몇 ms 걸렸는지 보인다.
- `/proc/<pid>/io`의 `write_bytes`: 그 프로세스 때문에 저장 계층으로 실제로 보내진 바이트 수. `pwrite64` 바이트와 견줄 수 있다.
- `/proc/meminfo`의 `Dirty`와 `Writeback`: VM 전체의 값이라 다른 일이 섞인다.
- `/sys/block/*/stat`: 장치의 쓰기 횟수. 컨테이너 안에서 보이는지는 확인하지 않았다.

## 사용자 결정 D7: 커널 함수 경로까지(OrbStack Linux 머신)

사용자 원문(2026-10-13): “"B. A + OrbStack Linux 머신에서 커널 추적"가 좋겠습니다. UI/UX 관련해서도 피드백할 게 있을 거 같은데, 일단 끝까지 해보죠.”

해석. 권한을 바꾸지 않는 시스템 콜 경계 관측(A)에 더해, 실습 컨테이너는 특권 없이 두고 별도의 OrbStack Linux 머신에서 커널 추적을 연다. “끝까지”는 기록에서 화면까지 한 줄기가 실제로 이어지는 것으로 본다. `fdatasync` 이동 하나를 고르면 그 안의 커널 함수 경로와 소스가 보이는 데까지다. 화면 다듬기는 사용자 피드백 뒤로 미룬다(AI 해석).

추적의 범위. `function_graph`를 거르지 않으면 이 VM의 모든 프로세스(다른 컨테이너 포함)를 기록한다. 그래서 `set_graph_function`에 `pwrite64`·`fdatasync`·`pread64`의 시스템 콜 입구만 넣고, 깊이 상한을 두고, 요청 하나 동안만 켠다.

기록끼리 잇는 방법. 추적의 pid와 시각이 strace와 같다고 가정하지 않는다. 시스템 콜 이벤트의 인자(`fd`, `count`, `pos`)를 strace의 같은 호출과 순서대로 맞춰 잇고, pid의 대응은 맞춘 결과로 확인한다.

커널 소스. 실행 중인 커널은 `7.2.9-orbstack-00391-g2b298d05fbd4`이다. 원본 `v7.2.9`에 OrbStack의 커밋이 더해진 것으로 보이며(이름으로 미룬 추론), 그 수정 내용은 모른다. 소스 창에는 원본 `v7.2.9`에서 추적에 나온 함수가 든 파일만 받아 보이고, “원본 소스로 읽은 코드, 실행한 코드와 다를 수 있음”으로 표시한다.

| A3 | 컨테이너 안에서 `/sys/block/vd*/stat`이 보인다. 쓰는 장치는 vdb다. INSERT 동안 쓰기 112번·flush 4번, CREATE INDEX 동안 쓰기 16번·flush 8번이 늘었다. 값은 VM 전체라 다른 컨테이너의 쓰기가 섞인다 | PASS(보임), 프로세스별로는 못 나눔 |

`pwrite64` 8 KB의 커널 경로(1차 INSERT의 WAL 쓰기, 커널 기록 49.5 µs). 괄호 안은 추적에 나오지 않은 함수다.

```text
__arm64_sys_pwrite64            (ksys_pwrite64 → vfs_write, 인라인)
└ ovl_write_iter                 overlayfs: 컨테이너의 겹친 파일 시스템
  └ backing_file_write_iter      쓰기 층의 실제 파일로 넘김
    └ vfs_iter_write
      └ btrfs_file_write_iter    (btrfs_do_write_iter → btrfs_buffered_write → copy_one_range, 인라인)
        ├ prepare_one_folio      페이지 캐시에서 folio를 찾거나 새로 넣음(__filemap_get_folio_mpol)
        │  (copy_folio_from_iter_atomic, file.c:1261: 사용자 버퍼 8 KB를 folio로 복사)
        └ btrfs_folio_clamp_set_dirty → filemap_dirty_folio   더럽다고 표시하고 끝. 장치 요청 없음
```

`fdatasync`의 커널 경로(1차 INSERT, 51.8 ms). 바깥 `do_fsync → vfs_fsync → vfs_fsync_range`는 시스템 콜 안에 인라인되어 나오지 않았고, `ovl_fsync`가 실제 파일에 대해 `vfs_fsync_range`를 다시 부른다.

```text
__arm64_sys_fdatasync
└ ovl_fsync → vfs_fsync_range → btrfs_sync_file
   ├ filemap_fdatawrite_range → btrfs_writepages → btrfs_submit_bbio   더러운 데이터 페이지를 bio로 보냄
   ├ blk_finish_plug → blk_mq_flush_plug_list → virtio_queue_rq        모아 둔 요청을 virtio 디스크에 넣음
   ├ btrfs_log_dentry_safe                                             바뀐 inode를 tree log에 기록
   └ btrfs_sync_log
      ├ btrfs_write_marked_extents                                     tree log 블록을 씀
      ├ mutex_lock(&fs_info->tree_log_mutex)   tree-log.c:3562         40.8 ms 잠듦
      └ write_all_supers                       tree-log.c:3582         10.7 ms, superblock을 쓰고 완료를 기다림
```

두 번 돌린 결과. 구조는 네 호출 모두 같고, 시간이 간 곳만 달랐다.

| 기록 | 문장 | `fdatasync`(strace) | 3562줄 `mutex_lock` | `write_all_supers` | log root |
| --- | --- | --- | --- | --- | --- |
| 1차 | INSERT | 51.9 ms | 40,815 µs | 10,735 µs | `btrfs_insert_root`(새로 만듦) |
| 1차 | CREATE INDEX | 4.8 ms | 0.04 µs | 4,584 µs | `btrfs_update_root` |
| 2차 | INSERT | 6.4 ms | 0.04 µs | 5,867 µs | `btrfs_update_root` |
| 2차 | CREATE INDEX | 2.7 ms | 0.04 µs | 2,105 µs | `btrfs_update_root` |

1차 INSERT의 40.8 ms를 어떻게 읽는지. 사실은 셋이다. 그 `mutex_lock`은 형제 호출의 차례로 3562줄 `tree_log_mutex`로 좁혀진다. 같은 자리가 나머지 세 호출에서는 0.04 µs다. 1차 INSERT만 log root를 새로 만들었다. `update_log_root`(tree-log.c:3166)는 `log->log_transid == 1`일 때만 `btrfs_insert_root`를 부르고, 주석은 “insert root item on the first sync”라고 적는다. 그 log의 첫 동기화였다는 뜻이다. 소스 주석(3546~3561)은 트랜잭션 커밋이 시작부터 superblock을 쓸 때까지 이 mutex를 쥐고 있고, 앞 트랜잭션이 아직 커밋 중이면 기다린다고 말한다. 그래서 앞 트랜잭션의 커밋과 겹쳐 기다렸다고 추론한다. 누가 쥐고 있었는지는 확인하지 않았다(추적이 우리 백엔드의 pid만 본다). 후보는 둘이다. 같은 VM의 다른 컨테이너가 일으킨 커밋, 또는 우리 기록 도구가 일으킨 커밋이다. 함수 기록 훅은 컨테이너의 `/tmp/pgtrace`에 쓰는데, 그 `/tmp`는 컨테이너 루트(overlay)이고 그 위층은 같은 btrfs다. INSERT 한 문장 동안 백엔드 혼자 쓰기 시스템 콜 32,530번, 약 1.3 MB를 거기 썼다. 관찰 도구가 관찰 대상을 만들었을 수 있다. 확인하는 방법: 같은 실행에서 btrfs의 트랜잭션 tracepoint(`btrfs:btrfs_transaction_commit`)를 pid 거르지 않고 켜서, 커밋 하나가 기다린 구간과 겹치면 추론이 맞다. 그 커밋을 시작한 작업(btrfs 트랜잭션 커널 스레드인지, 어느 프로세스의 쓰기 뒤인지)이 두 후보를 가른다. 겹치는 커밋이 없으면 이 추론을 버린다.

해독기에 더한 것(`decode/kernel.go`).

- 짝짓기: 시스템 콜 이벤트의 이름·fd·바이트 수·위치를 strace의 같은 호출과 차례로 맞춘다. 커널 pid는 첫 짝에서 정한다.
- 층: 함수 정의가 있는 소스 디렉터리로 정한다(`fs/btrfs/` → btrfs). 정의를 못 찾으면 부모의 층을 물려받고 그렇다고 표시한다.
- 접기: 2 µs보다 짧은 호출은 접고, 장치 요청·잠듦·락·더럽힘 표지는 짧아도 남긴다. 1차 시도(층마다 남기기)는 `fdatasync` 하나가 392칸이었고, 표지 이름으로 바꾸자 158칸이 되었다.
- 부르는 줄: 추적에는 줄 번호가 없으므로 부모 본문에서 이름으로 찾는다. 바로 부르는 줄이 없으면 같은 파일의 함수를 세 개까지 거쳐 찾는다. 같은 파일로 좁히는 것은 작업 가정이다. LTO가 없으면 컴파일러는 다른 .c 파일의 함수를 인라인하지 못하는데, 이 커널에 LTO가 없다는 근거는 약하다. `/proc/config.gz`는 455줄짜리 축약본이라 LTO 항목이 없다는 것만으로는 부족하고, `/proc/kallsyms` 57,294개에 Clang ThinLTO가 붙이는 `.llvm.` 꼬리가 없다는 것도 커널이 꼬리를 지워 보일 수 있어 결정적이지 않다. 이번에 본 인라인 길은 모두 같은 파일 안에서 찾아졌다. `available_filter_functions`로 보면 `copy_one_range`는 추적할 수 있는 함수가 아니고, `btrfs_buffered_write`·`vfs_write`·`ksys_pwrite64`는 추적할 수 있지만 이 자리에서는 나오지 않았다(그 자리에 인라인됨). 같은 이름을 여러 줄에서 부르면 형제 호출의 차례에 맞는 줄만 남긴다(`narrow`, 단위 시험 셋. 범위 검사를 지운 변이는 실패로 잡았고, 앞쪽 실패 검사를 지운 변이는 뒤쪽 검사가 같은 일을 해 결과가 같다).
- 소스: 정의 줄은 앞뒤 몇 줄을, 호출 줄은 그 줄이 든 함수의 본문 전체를 담는다. 인라인된 `copy_one_range` 본문에서 복사 줄(1261)을 읽게 하기 위해서다.

화면([concept-4.html](../../open_source_internals/workbench/design/concept-4.html)). 커널 나무가 붙은 이동은 이름에 시스템 콜 시간이 붙고(“fdatasync · 51.9 ms”), 고르면 오른쪽에 “커널 안”과 “PostgreSQL 쪽 호출 스택”을 고르는 단추가 생긴다. 커널 안에는 사실 문장(걸린 시간, 장치에 요청을 넣었는지, 페이지를 더럽게 했는지), 지나간 층, 시간이 간 곳(자기 시간이 10% 이상인 자리와 잠든 이유), 가로 막대 나무(누르면 폭 전체로 펼침), 고른 함수의 부르는 줄·부른 함수·소스가 나온다. 소스에는 원본 v7.2.9이며 실행 커널과 다를 수 있다고 적는다. 프로세스 역할표는 기록마다 따로 두고, ps를 보지 않은 ft5·ft6은 fork 순서와 하는 일로 추정해 “(추정)”을 붙였다(pid 6404, 6559는 WAL `pwrite64`와 `fdatasync`만 하므로 WAL 라이터로 봄).

사전 등록과 다르게 한 것.

- `set_graph_function`에 `pread64` 대신 `pwritev`를 넣었다. G4·G5는 쓰기와 동기화만 묻고, PostgreSQL은 여러 블록을 `pwritev`로 쓰기 때문이다. 이번 두 문장에서 `pwritev`는 없었다.
- 깊이 상한을 두지 않았다. 대신 pid로 거르고 버퍼가 차면 멈추게 했다(2차 실행 overrun 0, dropped 0. 1차의 통계는 남기지 않았다).
- 요청 하나가 아니라 두 문장(INSERT, CREATE INDEX) 동안 켰다.
- pid 범위가 넓었다. fork 이벤트를 `parent_comm == "postgres"`로 걸러 후보를 잡았는데, 같은 VM의 다른 컨테이너의 postgres(헬스 체크 접속)도 걸렸다. 그 프로세스들의 시스템 콜 안 함수 이름도 날 기록에 들어갔다. 사용자 버퍼 복사는 껐고(`syscall_user_buf_size` 0), 해독기는 우리 백엔드의 strace와 짝지은 호출만 쓰며, 날 기록은 커밋하지 않는다. `docker top`의 pid(932982)와 ftrace의 pid(934874 근처)가 달라, Docker 엔진의 pid 네임스페이스를 거쳐 정확히 거르는 방법은 찾지 못했다.

실패와 교정.

- 1차 시도는 추적기 인스턴스를 썼다. 인스턴스에는 `set_graph_function`이 없어 VM 전체 함수가 기록되었고, 32 MB 버퍼가 50 ms 만에 덮였다. 최상위 추적기와 `overwrite 0`으로 바꿨다.
- 설정 되돌리기의 `eval` 반복이 값을 엉뚱한 곳에 써서 “Invalid argument”로 실패했고, 1차 뒤에는 손으로 되돌렸다. `kernel.sh`는 이름 있는 변수로 되돌리며, 2차 실행 전후의 설정 일곱 값(버퍼 7, 옵션 0·0·0·1·1, `syscall_user_buf_size` 63)과 `nop`, 빈 pid·함수 필터가 같았다.
- 화면의 오래된 소스 칸 스크롤 코드가 `#code`가 없는 커널 소스 칸에서 null을 읽어, 주소로 상태를 여는 시작 코드가 중간에 멈췄다. 헤드리스 Chrome의 DOM에 오류를 써 넣어 찾았고, `#code`가 있을 때만 맞추게 고쳤다.
- 커널 소스를 받을 때 kernel.org가 부분 복제 필터를 지원하지 않아, 예상(수십 MB)과 달리 depth 1 전체 복제로 약 301 MB(.git)와 31 MB(필요한 디렉터리만 꺼냄)를 받았다. “300 MB를 넘으면 다시 묻는다”는 약속을 넘었고, 받기 전에 묻지 않았다. 사용자에게 알린다. 위치는 이 세션의 임시 디렉터리다.

남은 한계.

- 소스는 원본 v7.2.9다. OrbStack 패치가 줄을 바꿨는지 확인하지 않았다.
- 커널 시간은 function_graph의 기록 비용을 포함한다. 짧은 함수가 많을수록 부풀고, 잠든 시간은 거의 그대로다.
- 백엔드만 추적했다. WAL 라이터의 `fdatasync`, 읽기(`pread64`)의 커널 경로, 체크포인터가 데이터 파일을 나중에 동기화하는 경로는 보지 않았다. CREATE INDEX가 쓴 인덱스 파일(16389)은 이 요청 동안 `fsync`되지 않았고, 응답 약 3초 뒤 `kernel.sh`가 서버를 내릴 때 pid 6401(체크포인터로 추정)이 `fsync`했다(1차 strace, 종료 체크포인트로 추정). 그 커널 경로는 기록하지 않았다.
- `tracelab` 머신(지금 35.5 MB)은 켜 둔 채다. 지울지는 사용자가 정한다.
