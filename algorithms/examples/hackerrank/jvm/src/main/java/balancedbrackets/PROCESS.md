# Balanced Brackets (HackerRank) — 풀이 회고

> **이 문서를 쓰는 법.** 이 문서의 일은 두 가지입니다. 다음에 비슷한 문제를 만났을 때 핵심을 빠르게 깨우는 것(인출 단서), 그리고 깨우기에 실패했을 때 사고를 처음부터 다시 쌓아 주는 것(복원 경로). 그래서 위에서부터 읽지 않습니다. **먼저 바로 아래 30초 카드만 보고 코드를 머릿속으로 떠올려 봅니다.** 떠오르면 통과입니다. 안 떠오르면 정상이니, 막힌 칸만 골라 아래 산문을 펼치면 됩니다. 스택이 어떻게 움직이는지 안 그려지면 같은 폴더 `PROCESS.html`을 열어 push/pop을 단계별로 넘겨 봅니다.

## 30초 카드

```
문제 신호 : "괄호 문자열이 균형잡혔는가(YES/NO)" — (), [], {} 가 올바르게 중첩/짝맞춤
한 줄     : 여는 괄호는 스택에 쌓고, 닫는 괄호는 맨 위와 짝 맞춰 pop. 다 돌고 스택이 비면 YES
키워드    : 1) 여는 건 push  2) 닫는 건 top과 짝맞춰 pop  3) 끝에 스택이 비어야 함
함정 단서 : 끝에서 무조건 YES 아닌가?(여는 괄호만 남는 경우) / 닫는데 스택이 비었을 때 pop 하지 않았나?
```

## 어디서 막혔나 — 실제 실수의 기록

이 절은 자기비난이 아니라 재발 방지 장치입니다. 같은 자리에서 또 막혔을 때 "아, 그 함정"이라고 5초 만에 빠져나오려면, 실수를 일반론이 아니라 그날 실제로 한 형태 그대로 적어야 합니다.

HackerRank에서 **3/21 케이스가 실패**했습니다. 실수는 하나였습니다 — **루프를 다 돈 뒤 무조건 `return "YES"`** 했습니다. 균형의 조건은 둘인데(닫을 때 짝이 맞아야 하고, 끝에 열린 채 남은 게 없어야 함), 앞의 것만 검사하고 **"끝에 스택이 비었는가"를 빠뜨린** 것입니다.

더 뼈아픈 건, 맨 앞에 둔 `if (sLen % 2 != 0) return "NO"` 가드가 **"남는 경우는 처리됐다"는 착각**을 준 점입니다. 그 가드는 홀수 길이만 거릅니다. 짝수 길이인데 여는 괄호만 남는 입력 — `"(((("`, `"{}(("`, `"(())(("` 같은 — 은 가드를 통과하고, 닫는 괄호가 오지 않으니 짝 검사에도 안 걸려, 그대로 끝의 `"YES"`로 샜습니다. 실패한 3건이 정확히 이 유형이었습니다.

막힘의 본질을 한 문장으로 줄이면 이렇습니다. **루프 안에서의 검사만으로 끝냈고, 루프가 끝난 뒤의 상태(스택이 비었는가)도 정답 조건이라는 걸 놓쳤습니다.** 고친 것은 한 줄이었습니다: `return stack.isEmpty() ? "YES" : "NO";`.

## 핵심 사고 — 왜 이렇게 푸는가

카드가 떠오르지 않을 때, 이 절만 읽고 같은 결론에 다시 도달할 수 있도록 사고 순서대로 적습니다.

괄호 균형의 핵심은 **중첩(nesting)** 입니다. 가장 최근에 연 괄호가 가장 먼저 닫혀야 합니다 — `{[()]}` 에서 마지막에 연 `(`가 가장 먼저 `)`로 닫히는 식입니다. "가장 최근 것을 가장 먼저 꺼낸다"는 건 곧 **LIFO**, 그래서 자료구조는 스택입니다. 여는 괄호를 만나면 "아직 안 닫힌 것"으로 스택에 쌓고, 닫는 괄호를 만나면 스택 맨 위(가장 최근에 연 것)와 짝이 맞는지 봅니다.

닫을 때 실패하는 경우는 둘입니다. 스택이 비어 있는데 닫는 괄호가 오면(열린 게 없는데 닫으려 함) 실패고, 맨 위 여는 괄호와 종류가 안 맞으면(`[`인데 `)`로 닫으려 함) 실패입니다. 이 풀이는 이 둘을 `if (stack.isEmpty()) return "NO"` 와 종류별 비교로 잘 잡았습니다.

마지막 조각이 빠졌던 부분입니다. 닫을 때의 검사를 다 통과했더라도, **다 돌고 났을 때 스택에 무언가 남아 있으면** 그건 "열었는데 끝내 닫지 않은" 괄호입니다 — 역시 불균형입니다. 그래서 끝에서 `return "YES"`가 아니라 `return stack.isEmpty() ? "YES" : "NO"` 여야 합니다. **균형 = (닫을 때마다 짝 맞음) AND (끝에 스택 빔)**, 이 두 조건이 함께여야 완성됩니다.

## 손으로 따라가기 — 실제로 막혔던 입력

`"(()("` 는 실패했던 유형 그대로입니다. 길이 4라 홀수 가드를 통과하고, 짝 검사도 안 깨지는데, 끝에 스택이 안 빕니다. 스택은 밑에서 위로 쌓입니다.

```
입력  동작         스택(밑->위)
(     push (       (
(     push (       ( (
)     pop ( (짝)   (
(     push (       ( (
끝    --           ( (   <- 열린 ( 둘이 남음
```

끝에 `( (` 둘이 남았으니 `"NO"` 여야 합니다. 그런데 옛 코드는 이 자리에서 무조건 `"YES"` 였습니다. 비교로 통과하는 입력 `"{[()]}"` 를 같은 방식으로 따라가면 끝에 스택이 완전히 비어 `"YES"` 가 됩니다 — 차이는 오직 **끝의 스택 상태**입니다. 이 한 칸이 정답과 오답을 가릅니다.

## 뼈대 압축

```
각 문자마다:
  여는 괄호( ( [ { )  ->  스택에 push
  닫는 괄호           ->  스택 비었으면 NO,
                          아니면 pop 해서 짝(종류) 안 맞으면 NO
끝나고:
  스택 비었으면 YES, 남았으면 NO

시간 O(n), 공간 O(n).
```

## 복잡도 분석

문자열 길이를 n이라 하겠습니다.

**시간 O(n).** 각 문자를 정확히 한 번 봅니다. 한 문자당 하는 일은 push 한 번 또는 (pop + 상수 번 비교)인데, ArrayDeque의 push/pop은 O(1)입니다. 그래서 n개 문자 × 상수 작업 = O(n)입니다. "각 문자를 한 번씩 만지고, 만질 때마다 상수 시간"이 이 차수의 직관입니다. 입력 모양에 따라 best/worst가 갈리지 않습니다 — 닫을 때 일찍 NO로 끝나면 더 빠르지만, 차수로는 항상 O(n)입니다.

**공간 O(n).** 스택이 차지하는 메모리가 전부입니다. 스택이 최대로 커지는 건 여는 괄호만 계속 들어올 때라(예: `"((((..."`), 그때 깊이가 입력 길이에 비례해 O(n)입니다. 균형잡힌 입력이면 닫으면서 줄어들지만, 최악은 O(n)입니다.

**naive 대비.** 더 단순한 접근을 떠올리기 어려운 문제입니다 — 스택 없이 "괄호 쌍을 반복해서 지운다(`()` 를 찾아 지우고 또 찾고)" 같은 방법은 매번 문자열을 다시 훑어 O(n²)가 됩니다. 스택은 "가장 최근 열기"를 O(1)에 꺼내 주기 때문에 한 번의 패스로 끝납니다. 즉 스택이 이 문제를 O(n)으로 만드는 핵심입니다.

**제약 대입.** HackerRank 제약은 문자열 길이가 대략 10³ 수준이라 O(n)은 즉시 통과합니다.

## 패턴 전이 — 이 뼈대가 다시 나오는 곳

이 문제의 뼈대는 **"가장 최근 것과 매칭/되돌리기가 필요하면 스택"** 입니다. 중첩 구조를 검사하거나, 가장 최근 항목을 먼저 처리해야 할 때 스택이 등장합니다. Valid Parentheses(LC 20)는 사실상 같은 문제이고, Minimum Add to Make Valid(LC 921)·Remove Invalid Parentheses는 같은 스택 매칭에 "몇 개를 고쳐야 하나"를 더한 변형입니다. 단조 스택(Daily Temperatures, 이미 푼 문제)은 "가장 최근의 더 작은/큰 값"을 스택으로 들고 가는 사촌이고, 후위표기식(postfix) 평가나 함수 콜스택도 같은 LIFO 원리 위에 있습니다.

한 층 더 내려가면 **LIFO(후입선출)** 라는 공통 원리가 보입니다. "마지막에 시작한 것을 가장 먼저 끝낸다"는 중첩의 본질이고, 재귀의 콜스택이 바로 이걸 자동으로 해 주는 것이기도 합니다. 그래서 "중첩/짝맞춤/되돌리기"라는 신호가 보이면 스택(또는 재귀)을 먼저 떠올립니다.

## 코드에서 배운 것

끝의 불변식 검사를 빠뜨린 게 이 세션의 핵심 교훈입니다. **루프 중의 검사와 루프 후의 상태 검사는 별개**이고, 둘 다 정답 조건일 수 있습니다. 스택 문제에서 "끝에 스택이 비었는가"는 거의 항상 확인해야 하는 마지막 조건입니다.

베스트 프랙티스 하나도 배웠습니다 — **여는 괄호를 만나면 "기대하는 닫는 괄호"를 스택에 적어두는** 방법입니다(`(` 를 보면 `)` 를 push). 그러면 닫는 괄호가 왔을 때 `stack.pop() != ch` 한 줄로 짝 검사가 끝나, `leftBracket == '(' && ch != ')'` 식의 세 갈래 비교가 사라집니다. "무엇을 기대하는지"를 미리 적어두면 비교가 단순해진다는 발상은 다른 문제에도 옮겨집니다.

빈 스택 판정은 `stack.peek() == null` 보다 `stack.isEmpty()` 가 의도가 분명합니다(ArrayDeque는 null을 못 담아 둘이 같은 뜻이지만, 읽는 사람에게는 `isEmpty()`가 바로 읽힙니다).
