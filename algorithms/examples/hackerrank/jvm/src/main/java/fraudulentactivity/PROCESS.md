```
문제 신호 : "직전 d일의 중앙값의 2배 이상 쓰면 알림" — 매일 윈도우 중앙값이 필요
한 줄     : 값이 0~200으로 갇혀 있으니, 정렬 말고 count 배열로 중앙값을 찾고 윈도우는 한 칸씩 갱신
키워드    : 1) 윈도우 중앙값  2) 값 갇힘 -> counting  3) count 누적 walk로 k번째  4) 슬라이드는 -1/+1
함정 단서 : 윈도우마다 정렬하지 않았나?(O(n*d log d) -> TLE) / 중앙값을 count 누적으로 찾는 게 안 잡히나?
```

## 어디서 막혔나 — 실제 기록

이 절은 자기비난이 아니라 재발 방지 장치입니다. 이번엔 두 군데서 막혔습니다.

첫째, **TLE**. 윈도우마다 `subList` 복사 + `sort`로 중앙값을 구했습니다. 로직은 정확했지만(샘플과 무작위 교차검증 모두 통과) O(n·d log d)라 큰 입력에서 시간 초과했습니다. 작은 케이스만 통과하고 큰 케이스가 터진 게 그 신호였습니다.

둘째, 고친 버전의 **`twiceMedian`(정렬 없이 count로 중앙값 찾기)이 어떻게 동작하는지 이해되지 않았습니다.** "count 배열을 누적해서 k번째를 찾는다"가 머릿속에 안 그려진 것입니다. 이 회고의 무게는 여기에 둡니다 — 아래 핵심 사고와 손 트레이스, 그리고 `PROCESS.html`이 이 한 가지를 풀어 줍니다.

## 핵심 사고 — 왜 이렇게 푸는가

카드가 떠오르지 않을 때, 이 절만 읽고 같은 결론에 다시 도달할 수 있도록 사고 순서대로 적습니다.

매일 "직전 d일의 중앙값"이 필요한데, 중앙값을 구하는 교과서 방법은 정렬한 뒤 가운데를 집는 것입니다. 그런데 매일 윈도우가 한 칸씩만 움직이는데도 매번 d개를 새로 정렬하면, 같은 일을 거의 그대로 반복하느라 O(n·d log d)가 됩니다. 줄이는 두 가지 열쇠가 있습니다.

**첫째 열쇠 — 값이 갇혀 있다(0~200).** 지출액이 0부터 200까지만 나온다는 제약이 결정적입니다. 값의 종류가 201개로 고정이면, 정렬 대신 "각 값이 몇 번 나왔는가"를 길이 201짜리 count 배열로 셀 수 있습니다. 그리고 여기서 핵심 깨달음 — **count 배열을 값 0부터 차례로 읽는 것은, 정렬된 배열을 처음부터 읽는 것과 같습니다.** count가 `값2->2개, 값3->2개, 값4->1개`라면, 정렬하면 `2,2,3,3,4`이고, 이건 곧 "0의 개수만큼 0, 1의 개수만큼 1, ..."을 늘어놓은 것이기 때문입니다. 그러니 **정렬된 배열을 만들지 않고도** 그 안의 k번째 원소를 찾을 수 있습니다.

찾는 방법이 "누적 walk"입니다. 값 0부터 count를 더해 나가다가, **누적 개수가 처음으로 k에 도달하는 그 값이 k번째 원소**입니다. d=5(홀수)면 중앙값은 3번째(`k = d/2 + 1 = 3`)이고, `값2까지 누적 2(아직 3 미만) -> 값3까지 누적 4(3 이상!)`이므로 중앙값은 3입니다. 정렬된 `2,2,3,3,4`의 3번째가 3인 것과 정확히 같습니다 — 줄을 세우지 않고 "몇 번째까지 채워졌나"만 세서 같은 답에 도달한 것입니다. (이 코드는 비교가 `2*중앙값 <= 그날 지출`이라, 중앙값 대신 `2*중앙값`을 바로 돌려줍니다. 짝수 d면 가운데 두 값 a, b를 같은 walk로 찾아 `a+b`를 돌려주는데, 이게 곧 `2*(a+b)/2`입니다.)

**둘째 열쇠 — 윈도우는 한 칸씩만 움직인다.** 다음 날로 넘어가면 윈도우에서 가장 오래된 하루가 빠지고 새 하루가 들어옵니다. count 배열을 통째로 다시 셀 필요 없이, **나가는 날의 값은 count에서 1 빼고, 들어오는 날의 값은 1 더하면** 됩니다. 이 갱신이 O(1)이라, 매일 d개를 다시 훑던 비용이 사라집니다.

이 둘을 합치면, 매일 하는 일은 "count를 최대 201칸 walk(중앙값)" + "두 칸 갱신(슬라이드)"뿐이라 윈도우당 O(201)로 떨어집니다.

## 손으로 따라가기 — count로 중앙값 찾기

`[2, 3, 4, 2, 3, 6, 8, 4, 5]`, d=5의 첫 판정(6번째 날, 값 6)을 따라갑니다. 윈도우는 앞 5일 `[2, 3, 4, 2, 3]`입니다.

```
1) 윈도우의 값을 센다(count, 인덱스 = 값):
   값:    0  1  2  3  4  5  6  7  8
   개수:  0  0  2  2  1  0  0  0  0

2) 중앙값 = 3번째 원소(k = 5/2 + 1 = 3). 값 0부터 누적:
   값 0,1: 누적 0
   값 2  : 누적 0+2 = 2     (아직 3 미만)
   값 3  : 누적 2+2 = 4     (3 이상! -> 여기서 멈춤)
   => 3번째 원소는 값 3. 중앙값 = 3,  2*중앙값 = 6.

3) 그날 지출 6 >= 6 ?  예 -> 알림 1.

4) 슬라이드(다음 날): 나가는 날 값 2 -> count[2]--,  들어오는 날 값 6 -> count[6]++
   값:    0  1  2  3  4  5  6  7  8
   개수:  0  0  1  2  1  0  1  0  0     (이제 윈도우는 [3,4,2,3,6])
```

2)가 이 문제의 전부입니다. 정렬된 `2,2,3,3,4`를 만들지 않고, "값 2까지 두 개 채워졌고, 값 3까지 네 개 채워졌으니 3번째는 값 3"이라고 **개수만 세서** 같은 중앙값에 도달했습니다.

## 뼈대 압축

```
count[201] 만들고 첫 d일을 센다.
각 날 i (d부터 n-1):
  twiceMedian(count, d) 구해서  그날 지출 >= 그 값 이면  알림++
  슬라이드: count[나가는 날]--,  count[들어오는 날]++

twiceMedian: k = (홀수면) d/2+1. 값 0부터 누적하다 누적 >= k 인 첫 값 v -> 2*v.
             (짝수면 가운데 두 값 a,b를 같은 walk로 찾아 a+b)

시간 O(n * 201) ≈ O(n), 공간 O(201) = O(1).
```

## 복잡도 분석

n = 일수, d = 윈도우 크기, V = 값 종류 수(여기 201, 상수)라 하겠습니다.

**브루트포스(원래 풀이): O(n·d log d).** 바깥 루프가 약 n번, 한 번마다 윈도우 복사 O(d) + 정렬 O(d log d)이라 곱하면 O(n·d log d)입니다. n=2×10⁵, d=10⁵면 약 3.4×10¹¹ 연산이라 1초(약 10⁸ 연산)로는 어림없어 TLE입니다.

**고친 풀이: O(n·V).** 첫 윈도우 채우기 O(d), 그 뒤 바깥 루프 약 n번에 한 번마다 중앙값 walk O(V) + 슬라이드 O(1)이라 O(n·V)입니다. V=201이 상수라 사실상 O(n)이고, 2×10⁵×201 ≈ 4×10⁷이라 즉시 통과합니다. "각 날을 상수 번 만진다"가 이 차수의 직관입니다.

**공간.** count 배열 201칸이 전부라 O(V) = O(1)입니다(입력 크기와 무관한 상수). 브루트포스는 매 윈도우 subset 복사라 O(d)였습니다.

핵심 한 줄: **차수를 바꾼 건 알고리즘 아이디어가 아니라 "입력 제약(값 0~200)"입니다.** 값이 작은 범위에 갇히면 비교 정렬(O(d log d))을 counting(O(V))으로 바꿀 수 있다는 게 이 문제가 가르치는 것입니다.

## 패턴 전이 — 이 뼈대가 다시 나오는 곳

이 문제의 뼈대는 **"값이 작은 범위에 갇히면 counting sort"** 입니다. 비교 정렬은 원소를 서로 비교해 줄 세우느라 O(n log n)이지만, 값이 0~K로 제한되면 "각 값의 개수"만 세서 O(n+K)에 정렬(또는 k번째 찾기)이 됩니다. HackerRank의 Counting Sort 1·2·3, The Full Counting Sort가 같은 도구를 직접 다루고, "버킷"으로 일반화하면 Bucket Sort, Radix Sort로 이어집니다. 슬라이딩 윈도우 + 빈도 배열의 조합은 "윈도우 안의 최빈값/특정 값 개수"를 묻는 문제들에도 그대로 나옵니다.

한 층 더 내려가면 **"제약이 알고리즘을 고른다"** 는 원리가 보입니다. 같은 '중앙값 구하기'라도 값이 제한 없으면 두 개의 힙이나 균형 트리(LeetCode 480, Hard)가 필요하지만, 값이 0~200으로 갇히면 count 배열 하나로 충분합니다(Medium). 문제를 읽을 때 입력 제약(값 범위, 길이 상한)을 먼저 보는 습관이, 어떤 도구를 쓸지를 정해 줍니다.

## 코드에서 배운 것

`twiceMedian`이 중앙값 대신 `2*중앙값`을 바로 돌려주는 건, 비교식이 `2*중앙값 <= 그날 지출`이라 정수 나눗셈의 반올림 오차를 피하려는 선택입니다. 짝수 d일 때 중앙값은 `(a+b)/2`(소수일 수 있음)인데, `2*중앙값 = a+b`는 항상 정수라 깔끔합니다.

`k = d/2 + 1`은 1-based로 "가운데 번째"입니다. d=5면 3번째, d=7이면 4번째 — 정렬된 d개의 한가운데입니다. 누적이 처음 k 이상이 되는 값이 그 k번째 원소라는 게 walk의 핵심이고, 이건 "정렬 배열에 인덱스로 접근하기"를 count로 흉내 낸 것입니다.
