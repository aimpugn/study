# 프롬프트 캐시는 무엇을 저장하는가

## 짧은 답

**텍스트가 아니라 계산 결과를 저장합니다.** 정확히는 프롬프트 앞부분 토큰들에 대해 이미 계산해 둔 K/V 텐서입니다. 다음 요청이 같은 앞부분으로 시작하면 그 계산을 건너뜁니다.

"고정적인 부분을 캐싱해서 토큰을 효율화한다"는 설명이 부족한 이유가 여기 있습니다. 그 문장은 **무엇이 저장되는지**를 말하지 않고, 그래서 왜 하필 접두사여야 하는지, 왜 중간이나 뒷부분은 안 되는지, 한 글자만 바꿔도 왜 그 뒤가 전부 날아가는지를 설명할 수 없습니다. 접두사 제약은 누군가 정한 규칙이 아니라 **계산 구조에서 그냥 따라 나오는 성질**입니다. 4절에서 코드로 증명합니다.

[툴 콜링 문서](tool_calling.md)를 먼저 읽으면 좋지만 필수는 아닙니다. 9절에서 두 주제가 만나는 자리를 다시 짚습니다.

## 1. 추론 한 번에 무슨 일이 일어나는가

캐시 이야기를 하려면 무엇이 계산되는지부터 알아야 합니다. 필요한 만큼만 봅니다.

모델은 토큰 배열 하나를 받습니다. 각 토큰은 먼저 벡터가 됩니다. 그 벡터들이 같은 모양의 층을 수십 개 통과하는데, 각 층에서 **모든 토큰이 각자 세 개의 벡터를 만듭니다.**

| 이름 | 하는 일 |
|---|---|
| Q (query) | 내가 무엇을 찾고 있는지 |
| K (key) | 나는 어떤 정보를 갖고 있는지 |
| V (value) | 실제로 넘겨줄 내용 |

각 토큰은 자기 Q를 다른 토큰들의 K와 맞춰 보고, 잘 맞는 쪽의 V를 더 많이 가져옵니다. 이게 attention입니다. 이 문서에는 이 정도만 필요합니다.

여기서 중요한 제약이 하나 걸립니다. **각 토큰은 자기보다 뒤에 있는 토큰을 볼 수 없습니다.** 다음 단어를 예측하는 모델이 정답을 미리 보면 안 되니까 학습 때부터 뒤쪽을 가려 놓고 훈련합니다. 구현은 간단합니다 — 점수 행렬에서 뒤쪽에 해당하는 칸을 `-무한대`로 만들어 버리면 softmax를 거치며 가중치가 0이 됩니다. 이걸 **causal mask**라고 부릅니다.

이 한 가지 제약에서 이 문서의 나머지가 전부 따라 나옵니다.

## 2. KV 캐시는 왜 애초에 생겼는가

모델은 답변을 한 번에 쓰지 않습니다. 토큰 하나를 만들고, 그걸 입력 끝에 붙여서 다시 돌리고, 또 하나를 만듭니다.

```text
1회차:  [프롬프트 500토큰]                    -> "서"
2회차:  [프롬프트 500토큰] + "서"             -> "울"
3회차:  [프롬프트 500토큰] + "서" + "울"      -> "은"
...
```

여기서 순진하게 구현하면 매 회차마다 501개, 502개, 503개 토큰의 K/V를 전부 새로 계산합니다. 그런데 **앞의 500개는 회차가 바뀌어도 값이 똑같습니다.** 뒤에 뭐가 붙든 앞 토큰들의 K/V는 변하지 않으니까요 (4절에서 증명합니다).

그래서 한 번 계산한 K/V를 메모리에 들고 있다가 다음 회차에 재사용합니다. 이게 **KV 캐시**입니다. 새로 계산하는 건 방금 추가된 토큰 하나의 K/V뿐입니다.

여기까지는 **한 번의 응답을 만드는 동안** 벌어지는 일이고, 모든 추론 엔진이 기본으로 합니다. 우리가 켜고 끄는 기능이 아닙니다.

**프롬프트 캐시는 이 KV 캐시를 요청과 요청 사이에도 살려두는 것입니다.** 보통은 응답이 끝나면 그 메모리를 놓아 줍니다. 다음 요청이 오면 처음부터 다시 계산하죠. 프롬프트 캐시는 "이 앞부분은 잠시 들고 있어 달라"고 부탁해서, 다음 요청이 같은 앞부분으로 시작하면 그 계산을 통째로 건너뛰게 만듭니다.

정리하면 이렇습니다.

| | KV 캐시 | 프롬프트 캐시 |
|---|---|---|
| 범위 | 한 응답을 생성하는 동안 | 요청과 요청 사이 |
| 켜고 끄기 | 불가능. 엔진의 기본 동작 | 가능. API로 지정 |
| 저장 위치 | 추론 서버 메모리 | 같음 (수명만 연장) |
| 저장 대상 | K/V 텐서 | 같음 |

**프롬프트 캐시는 KV 캐시의 수명을 늘려 API로 노출한 것**입니다. 그래서 "무엇이 캐싱되는가"의 답이 텍스트가 아니라 K/V인 겁니다.

## 3. prefill과 decode는 병목이 다르다

캐시가 무엇을 아껴 주는지 정확히 알려면 추론이 두 단계라는 걸 봐야 합니다.

**prefill.** 입력 프롬프트 전체를 읽는 단계입니다. 500토큰이면 500개 토큰의 K/V를 계산합니다. 중요한 건 **이걸 한꺼번에 병렬로 할 수 있다**는 점입니다. 각 토큰의 K/V는 서로를 기다릴 필요가 없거든요. GPU가 잘하는 큰 행렬 곱 하나로 처리됩니다. 그래서 이 단계는 **연산량**에 묶입니다.

**decode.** 답변을 한 토큰씩 만드는 단계입니다. 다음 토큰을 만들려면 방금 만든 토큰이 있어야 하니 병렬화가 안 됩니다. 토큰 하나 만들 때마다 모델의 모든 가중치를 메모리에서 한 번씩 읽어 와야 하는데, 정작 계산량은 토큰 하나 분량뿐입니다. 그래서 이 단계는 **메모리 대역폭**에 묶입니다.

```text
prefill                          decode
[■■■■■■■■■■] 500토큰 한 번에      [■] [■] [■] [■] ...  한 개씩
연산량이 병목                      메모리 읽기가 병목
캐시로 건너뛸 수 있는 구간          캐시와 무관
```

여기서 실무적으로 중요한 결론이 나옵니다.

**프롬프트 캐시는 prefill을 건너뛰는 것이지 decode를 빠르게 하는 게 아닙니다.** 그래서 첫 토큰이 나오기까지의 시간은 크게 줄지만, 일단 답변이 시작된 뒤의 생성 속도는 그대로입니다. 긴 시스템 프롬프트에 짧은 답변이면 이득이 크고, 짧은 프롬프트에 긴 답변이면 이득이 거의 없습니다.

## 4. 왜 접두사여야만 하는가

이 절이 문서의 핵심입니다. 그리고 말로 설명하는 대신 계산해서 보여 줄 수 있습니다.

### 주장

> 위치 i의 K와 V는 토큰 0부터 i까지에만 의존한다. i보다 뒤에 무엇이 오든 영향받지 않는다.

왜 그런지는 1절의 causal mask에서 나옵니다. 첫 층에서 위치 i의 K는 토큰 i의 벡터만으로 계산됩니다. 그 층의 출력은 attention을 거치는데, causal mask 때문에 위치 i는 0..i만 봅니다. 그러니 둘째 층에 들어가는 위치 i의 값은 토큰 0..i에만 의존합니다. 이게 층마다 반복되므로, 몇 층을 쌓든 **위치 i의 K/V는 뒤쪽 토큰을 절대 참조하지 못합니다.**

이 성질이 캐시의 전부입니다. 접두사가 같으면 그 구간의 K/V가 전 층에서 비트 단위로 같고, 뒤에 무엇이 붙든 상관없습니다. 반대로 앞이 한 글자라도 바뀌면 그 위치부터 끝까지 전부 다시 계산해야 합니다.

### 확인

작은 모형을 만들어 직접 재 봤습니다. 어휘 20개, 차원 8, 층 3개짜리 장난감이지만 causal mask가 들어간 attention의 의존 구조는 실제 모델과 같습니다.

```text
길이 8 토큰 기준
  마지막 토큰만 변경 -> 앞에서 7 개 위치의 K/V가 동일
  첫 토큰만 변경     -> 앞에서 0 개 위치의 K/V가 동일
  뒤에 2개 덧붙임    -> 앞에서 8 개 위치의 K/V가 동일
```

세 줄이 각각 하나씩 말해 줍니다.

**마지막 토큰만 바꿨더니 앞 7개가 그대로입니다.** 뒤쪽 변경은 앞쪽에 영향을 주지 않습니다. 바뀐 건 그 위치 하나뿐입니다.

**첫 토큰을 바꿨더니 0개가 남았습니다.** 위치 0의 K/V가 바뀌었고, 그러면 위치 1이 attention으로 위치 0을 참조하므로 위치 1도 바뀌고, 연쇄적으로 전부 무너집니다. **"한 바이트만 달라져도 그 뒤 전부 무효"가 바로 이 줄입니다.**

**뒤에 두 개 덧붙였더니 원래 8개가 전부 그대로입니다.** 대화를 이어 가는 것 — 즉 앞은 두고 뒤에만 추가하는 것 — 은 캐시를 하나도 깨지 않습니다. 툴 콜링 루프가 캐시 친화적인 구조적 이유가 이것입니다.

재현 코드는 부록 A에 있습니다. 30줄이고 넘파이만 있으면 돌아갑니다.

### 그래서 중간 캐싱은 왜 안 되는가

"앞부분은 매번 바뀌지만 중간에 큰 고정 문서가 있으니 그것만 캐싱하면 안 되나?"

안 됩니다. 그 문서가 놓인 위치의 K/V는 **그 앞에 무엇이 있었는지에 의존**합니다. 앞부분이 매 요청 달라지면 같은 문서라도 K/V 값이 매번 다르게 나옵니다. 저장해 봐야 다시 쓸 수가 없습니다.

방법은 하나뿐입니다 — 그 문서를 앞으로 옮기는 것.

## 5. 렌더링 순서가 설계 제약이 되는 이유

4절의 결론은 "앞에 있는 것일수록 캐시에 유리하다"입니다. 그러면 무엇이 앞에 오는지가 곧 설계 문제가 됩니다.

Anthropic API의 렌더링 순서는 고정입니다.

```text
[ tools ] ──> [ system ] ──> [ messages ]
   맨 앞                          맨 뒤
   
   ← 안정적일수록 여기            자주 바뀔수록 여기 →
```

[툴 콜링 문서](tool_calling.md) 2절에서 열린 모델의 채팅 템플릿을 렌더링해 이 순서를 눈으로 확인했습니다. 도구 정의가 시스템 메시지 안, 프롬프트 가장 앞쪽에 텍스트로 박혀 있었습니다.

그래서 규칙이 하나 나옵니다. **안정성 순서와 물리적 순서를 맞추십시오.**

| 얼마나 자주 바뀌는가 | 어디에 두는가 |
|---|---|
| 절대 안 바뀜 (도구 목록, 고정 지침) | 맨 앞. 캐시 지점 이전 |
| 세션마다 바뀜 (사용자 프로필, 문서) | 그 다음. 세션 단위로 캐싱 |
| 턴마다 바뀜 (대화 내용) | 맨 뒤. 마지막 캐시 지점 이후 |
| 요청마다 바뀜 (시각, 요청 ID) | **없애거나 맨 뒤로** |

이 순서가 어긋나면 캐시 지정을 아무리 해도 소용없습니다. 시스템 프롬프트 첫머리에 현재 시각을 넣어 두고 그 뒤에 캐시 지점을 찍으면, 접두사가 매번 달라지니 저장만 하고 읽지는 못합니다.

## 6. 무효화에는 층위가 있다

모든 변경이 전부를 날리지는 않습니다. Anthropic API의 캐시는 세 층으로 나뉘고, 변경은 자기 층과 그 아래만 무효화합니다.

| 바꾼 것 | tools 캐시 | system 캐시 | messages 캐시 |
|---|:---:|:---:|:---:|
| 도구 정의 추가·삭제·순서 변경 | 무효 | 무효 | 무효 |
| 모델 교체 | 무효 | 무효 | 무효 |
| 시스템 프롬프트 내용 | 유지 | 무효 | 무효 |
| `tool_choice`, 이미지, thinking 켜고 끄기 | 유지 | 유지 | 무효 |
| 메시지 내용 추가 | 유지 | 유지 | 무효 |

표가 5절의 순서 그림과 정확히 대응합니다. 앞쪽 것을 건드릴수록 더 많이 날아갑니다.

실용적인 함의 두 가지가 있습니다.

**`tool_choice`는 매 요청 바꿔도 됩니다.** 도구 정의와 시스템 프롬프트 캐시가 살아 있습니다. 반면 도구를 **추가하거나 빼면** 전부 다시 계산합니다. "모드에 따라 도구 세트를 갈아 끼우는" 설계가 비싼 이유입니다. 도구 목록은 고정해 두고 모드는 메시지로 전달하는 편이 훨씬 쌉니다.

**모델을 바꾸면 캐시는 없습니다.** 캐시는 모델별로 따로 잡힙니다. 대화 중간에 싼 모델로 갈아탄다는 발상은 캐시를 통째로 버리는 대가를 치릅니다. 보조 작업이 필요하면 메인 루프는 한 모델로 유지하고 별도 호출로 분리하는 편이 낫습니다.

## 7. 몇 번 재사용해야 이득인가

캐시는 공짜가 아닙니다. **쓸 때 더 비싸고 읽을 때 훨씬 쌉니다.**

Anthropic API 기준으로 캐시에 쓰는 토큰은 기본 입력가의 1.25배(5분 유지), 읽는 토큰은 0.1배입니다. 산수를 해 보면 손익분기가 나옵니다.

```text
같은 프롬프트를 2번 보낸다 (5분 유지 기준)

  캐시 없이 :  1.0 + 1.0            = 2.0
  캐시 쓰고 :  1.25(쓰기) + 0.1(읽기) = 1.35   → 이득
```

1시간 유지를 고르면 쓰기가 2배로 오릅니다.

```text
  2번 :  캐시 없이 2.0   vs   2.0 + 0.1 = 2.1   → 거의 본전
  3번 :  캐시 없이 3.0   vs   2.0 + 0.2 = 2.2   → 이득
```

**5분 유지는 두 번만 재사용해도 이득, 1시간 유지는 세 번은 넘어야 이득**입니다. 1시간 유지는 요청이 뜸하게 몰려 오는 경우에 쓰는 선택지이지 그냥 오래 두면 좋은 옵션이 아닙니다.

한 가지 함정이 있습니다. **같은 접두사로 N개를 동시에 쏘면 전부 제값을 냅니다.** 캐시는 첫 응답이 나오기 시작해야 읽을 수 있는데, 동시에 출발한 요청들은 서로가 쓰는 중인 캐시를 읽을 수 없습니다. 병렬 처리를 할 거면 하나를 먼저 보내고 첫 토큰이 오는 걸 본 다음 나머지를 보내십시오.

## 8. 걸렸는지 확인하는 법

응답의 `usage`를 봅니다. 추측하지 말고 숫자를 보십시오.

**PASS**: 같은 접두사로 두 번째 요청을 보냈을 때 `cache_read_input_tokens`가 0보다 큽니다.
**FAIL**: 반복 요청인데 계속 0입니다. 접두사를 깨는 요소가 있습니다. 9절을 보십시오.

읽을 때 주의할 게 하나 있습니다. **`input_tokens`는 전체 프롬프트 크기가 아니라 캐시에 걸리지 않은 나머지입니다.** 세 값을 더해야 전체입니다. 에이전트를 몇 시간 돌렸는데 `input_tokens`가 4천으로 찍혀 있다면 나머지가 캐시에서 온 것이지 프롬프트가 작은 게 아닙니다.

접두사가 깨진 지점을 찾으려면 두 요청의 렌더링 결과를 파일로 떨궈서 `diff`를 뜨는 게 가장 빠릅니다.

## 9. 캐시를 조용히 깨뜨리는 것들

전부 오류를 내지 않습니다. 그냥 캐시가 안 걸릴 뿐이고, 청구서를 보기 전까지는 모릅니다.

**시스템 프롬프트의 현재 시각.** 가장 흔합니다.

```python
system = f"당신은 도우미입니다. 현재 시각은 {datetime.now()}입니다."
```

프롬프트 맨 앞이 매 요청 달라지므로 캐시가 사실상 없습니다. [툴 콜링 문서](tool_calling.md) 9절에서 실제로 재 봤을 때, 시각 문자열을 시스템 프롬프트에 넣으니 **18번째 문자부터** 달라졌습니다. 시각이 정말 필요하면 대화 마지막에 넣으십시오.

**요청 ID나 UUID를 앞쪽에 넣는 것.** 같은 이유입니다.

**정렬하지 않은 JSON 직렬화.** `json.dumps(d)`는 딕셔너리 순서를 그대로 씁니다. 집합을 순회해서 목록을 만들면 순서가 실행마다 달라질 수 있습니다. 같은 내용인데 바이트가 달라지면 캐시는 남남입니다. `sort_keys=True`를 쓰거나 명시적으로 정렬하십시오.

**사용자마다 다른 시스템 프롬프트.** 이름이나 사용자 ID를 시스템 프롬프트에 끼워 넣으면 캐시가 사용자 수만큼 쪼개집니다. 공유 가능한 부분을 앞에 두고 개인화된 부분은 뒤로 미십시오.

**조건부로 붙이는 시스템 절.** `if 관리자: system += "..."` 같은 코드는 플래그 조합 수만큼 서로 다른 접두사를 만듭니다.

**사용자마다 다른 도구 목록.** 도구는 맨 앞에 렌더링되므로 이건 캐시를 사용자 단위로 완전히 갈라 놓습니다. 6절의 첫 줄입니다.

**곁가지 호출에서 프롬프트를 다시 조립하는 것.** 요약이나 하위 작업을 위해 별도 API 호출을 만들 때 `system`과 `tools`를 새로 만들면 부모 요청의 캐시를 하나도 못 씁니다. 부모의 것을 그대로 복사하고 뒤에만 덧붙이십시오.

## 10. 최소 크기가 있다

접두사가 너무 짧으면 캐시 지정을 해도 **조용히 무시됩니다.** 오류는 나지 않고 `cache_creation_input_tokens`가 0으로 찍힐 뿐입니다.

문제는 이 값이 모델마다 다르고, **세대순으로 단조롭지 않다**는 점입니다. 512, 1024, 2048, 4096 토큰이 섞여 있고 최신 모델이 항상 더 작지도 않습니다. 최신 모델에서 캐시되던 3천 토큰짜리 프롬프트가 한 세대 전 모델에서는 안 될 수 있습니다.

여기서 단위에 주의해야 합니다. **기준은 문자 수가 아니라 토큰 수입니다.** 이 문서와 툴 콜링 문서의 측정값은 전부 문자 수인데, 렌더링 결과를 다루기에는 편하지만 최소 크기 판정에는 쓸 수 없습니다. 실제 토큰 수는 토크나이저를 돌리거나 벤더가 제공하는 토큰 계산 엔드포인트로 확인하십시오. 영어 기준 대략 문자 4개가 토큰 하나쯤이지만 한국어와 코드는 비율이 다릅니다.

## 11. 흔한 오해

**"텍스트를 저장한다."** 아닙니다. K/V 텐서, 즉 계산 결과입니다. 1~2절.

**"토큰을 안 보내도 된다."** 아닙니다. 매 요청 전체를 다시 보냅니다. 아끼는 건 전송량이 아니라 **재계산**입니다.

**"캐시를 켜면 응답이 전반적으로 빨라진다."** prefill만 건너뜁니다. 첫 토큰까지의 시간은 줄지만 생성 속도는 그대로입니다. 3절.

**"중간에 큰 고정 문서가 있으니 그것만 캐싱하면 된다."** 안 됩니다. 그 위치의 K/V는 앞에 무엇이 있었는지에 의존합니다. 앞으로 옮기십시오. 4절.

**"파라미터를 조금 바꾸는 정도는 괜찮다."** 무엇을 바꾸느냐에 따라 다릅니다. `tool_choice`는 안전하고 도구 목록은 전부 날립니다. 6절.

**"오래 유지할수록 좋다."** 1시간 유지는 쓰기가 2배입니다. 세 번 넘게 재사용할 게 아니면 손해입니다. 7절.

**"캐시 지정을 했으니 걸렸을 것이다."** `cache_read_input_tokens`를 보기 전까지는 모릅니다. 8절.

## 부록 A. 재현 방법

### 접두사 성질 증명 (모델 불필요)

4절의 세 줄을 만든 코드입니다. 넘파이만 있으면 됩니다.

```python
# causal.py — uv run --with numpy python causal.py
import numpy as np

rng = np.random.default_rng(0)
VOCAB, D, LAYERS = 20, 8, 3

W_e = rng.normal(size=(VOCAB, D))
W_q = [rng.normal(size=(D, D)) for _ in range(LAYERS)]
W_k = [rng.normal(size=(D, D)) for _ in range(LAYERS)]
W_v = [rng.normal(size=(D, D)) for _ in range(LAYERS)]


def forward(tokens):
    """각 층의 (K, V)를 그대로 돌려준다. 이게 KV 캐시에 담기는 값이다."""
    x = W_e[list(tokens)]
    T = len(tokens)
    causal = np.tril(np.ones((T, T)))          # 자기 위치와 그 앞만 1
    kv_per_layer = []
    for l in range(LAYERS):
        Q, K, V = x @ W_q[l], x @ W_k[l], x @ W_v[l]
        kv_per_layer.append((K, V))
        s = Q @ K.T / np.sqrt(D)
        s = np.where(causal == 1, s, -np.inf)  # 뒤쪽 토큰을 완전히 가린다
        w = np.exp(s - s.max(axis=-1, keepdims=True))
        w /= w.sum(axis=-1, keepdims=True)
        x = w @ V
    return kv_per_layer


def same_prefix_len(a, b):
    """두 실행의 K/V가 모든 층에서 일치하는 위치가 앞에서 몇 개인가."""
    n = min(a[0][0].shape[0], b[0][0].shape[0])
    for i in range(n):
        for (Ka, Va), (Kb, Vb) in zip(a, b):
            if not (np.array_equal(Ka[i], Kb[i]) and np.array_equal(Va[i], Vb[i])):
                return i
    return n


base = [3, 1, 4, 1, 5, 9, 2, 6]
tail = [3, 1, 4, 1, 5, 9, 2, 7]      # 마지막 토큰만 다름
head = [8, 1, 4, 1, 5, 9, 2, 6]      # 첫 토큰만 다름
longer = base + [7, 7]               # 뒤에 덧붙이기만 함

kv_base = forward(base)
print("길이", len(base), "토큰 기준")
print("  마지막 토큰만 변경 ->", same_prefix_len(kv_base, forward(tail)), "개 위치 동일")
print("  첫 토큰만 변경     ->", same_prefix_len(kv_base, forward(head)), "개 위치 동일")
print("  뒤에 2개 덧붙임    ->", same_prefix_len(kv_base, forward(longer)), "개 위치 동일")
```

**PASS 조건**: 차례로 7, 0, 8이 나옵니다.
**FAIL 신호**: `causal` 마스크 줄을 지우고 돌리면 첫 줄이 7이 아니라 0이 됩니다. 뒤쪽 토큰이 앞쪽 K/V에 영향을 주게 되기 때문인데, 마스크가 접두사 성질의 유일한 근거라는 것을 거꾸로 확인하는 실험입니다.

가중치가 무작위라서 값 자체는 실제 모델과 무관합니다. 여기서 확인하는 건 값이 아니라 **의존 구조**입니다.

### 렌더링 접두사 측정

시스템 프롬프트 변경이 접두사를 어디서 깨는지는 채팅 템플릿으로 잽니다. [툴 콜링 문서](tool_calling.md) 부록 A의 스크립트를 그대로 쓰고 메시지만 바꾸면 됩니다.

### 확인한 것과 확인하지 못한 것

| 항목 | 상태 |
|---|---|
| causal mask 아래서 위치 i의 K/V가 뒤쪽 토큰과 무관하다 | **직접 계산으로 확인** (위 스크립트, 7/0/8) |
| 앞 토큰 변경이 전체를 무너뜨린다 | **직접 계산으로 확인** |
| 덧붙이기는 기존 K/V를 보존한다 | **직접 계산으로 확인** |
| 렌더링 순서가 tools → system → messages | **직접 관측** (열린 모델 템플릿) + 벤더 문서 |
| 실제 모델의 prefill 시간이 캐시로 줄어든다 | **미검증.** 가중치를 돌리지 않았습니다. prefill/decode의 병목 구분은 구조에서 나오는 성질이고 널리 확인된 사실이지만, 이 문서는 직접 측정하지 않았습니다 |
| 상용 API의 실제 캐시 적중 동작 | **미검증.** API 호출을 하지 않았습니다. 6~10절의 벤더 사실은 문서 확인이며 부록 B에 날짜를 적었습니다 |

3절의 prefill/decode 구분은 **직접 잰 게 아닙니다.** 실측하려면 로컬에서 모델을 돌려 같은 접두사로 두 번 호출하고 첫 토큰까지의 시간을 비교해야 합니다. 4bit 3~8B 모델 하나면 됩니다.

## 스스로 확인할 질문

1. 프롬프트 캐시에 저장되는 것은 정확히 무엇인가. 텍스트가 아니라면 무엇인가.
2. 위치 i의 K/V가 i보다 뒤의 토큰에 영향받지 않는 이유는 무엇인가. 그 성질이 없어지면 캐시는 어떻게 되는가.
3. 프롬프트 중간에 있는 큰 고정 문서를 그 부분만 캐싱할 수 없는 이유는 무엇인가.
4. 캐시를 켰는데도 응답 생성 속도가 그대로다. 버그인가, 정상인가. 왜 그런가.
5. 같은 시스템 프롬프트로 요청을 2번 보낼 예정이다. 5분 유지와 1시간 유지 중 무엇을 골라야 하며 그 이유는 무엇인가.
