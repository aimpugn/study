# 프롬프트 캐시는 무엇을 저장하는가

## 짧은 답

**텍스트 사본만 저장하는 것이 아니라, 프롬프트 앞부분을 처리하며 만든 계산 상태를 재사용합니다.** Anthropic은 현재 이를 attention의 key/value 표현(K/V)과 일치 여부를 확인할 암호학적 해시로 설명합니다. 다음 요청의 토큰화된 앞부분과 관련 설정이 같으면 그 구간의 계산을 다시 하지 않습니다.

"고정적인 부분을 캐싱해서 토큰을 효율화한다"는 설명이 부족한 이유가 여기 있습니다. 그 문장은 **무엇이 저장되는지**를 말하지 않고, 그래서 왜 하필 접두사여야 하는지, 왜 중간의 같은 문자열만 떼어 재사용할 수 없는지를 설명할 수 없습니다. 뒤쪽 토큰을 보지 못하는 표준 생성 모델(causal decoder)에서 접두사 뒤에 토큰을 덧붙여도 기존 위치의 상태가 바뀌지 않는 이유를 4절에서 층별로 따져 봅니다.

[툴 콜링 문서](tool_calling.md)를 먼저 읽으면 좋지만 필수는 아닙니다. 9절에서 두 주제가 만나는 자리를 다시 짚습니다.

## 1. 추론 한 번에 무슨 일이 일어나는가

캐시 이야기를 하려면 무엇이 계산되는지부터 알아야 합니다. 필요한 만큼만 봅니다.

모델은 토큰 배열 하나를 받습니다. 각 토큰은 먼저 벡터가 됩니다. 그 벡터들이 같은 모양의 층을 수십 개 통과하는데, 각 층에서 **모든 토큰이 각자 세 개의 벡터를 만듭니다.**

| 이름 | 하는 일 |
|---|---|
| Q (query) | 내가 무엇을 찾고 있는지 |
| K (key) | 나는 어떤 정보를 갖고 있는지 |
| V (value) | 실제로 넘겨줄 내용 |

각 토큰은 자기 Q를 다른 토큰들의 K와 맞춰 보고, 잘 맞는 쪽의 V를 더 많이 가져옵니다. 이게 attention입니다. 이 문서에는 이 정도만 필요합니다.

여기서 중요한 제약이 하나 걸립니다. **각 토큰은 자기보다 뒤에 있는 토큰을 볼 수 없습니다.** 다음 단어를 예측하는 모델이 정답을 미리 보면 안 되니까 학습 때부터 뒤쪽을 가려 놓고 훈련합니다. 구현은 간단합니다 — 점수 행렬에서 뒤쪽에 해당하는 칸을 `-무한대`로 만들어 버리면 softmax를 거치며 가중치가 0이 됩니다. 이걸 **causal mask**라고 부릅니다.

이 제약에서 접두사 계산 상태를 재사용할 수 있다는 수학적 근거가 나옵니다.

## 2. KV 캐시는 왜 애초에 생겼는가

2017년에 제안된 Transformer는 한 번에 여러 위치를 처리해 학습과 긴 입력 처리를 병렬화했습니다. 하지만 텍스트를 생성할 때는 방금 만든 토큰을 다음 입력으로 써야 하므로 한 토큰씩 순서대로 진행합니다. 이 incremental decoding에서는 기존 위치의 K/V를 재사용해 같은 attention 상태를 매번 다시 계산하지 않을 수 있습니다. 2019년의 multi-query attention 연구도 이 상태를 반복해서 읽는 비용을 직접 다뤘습니다.

모델은 답변을 한 번에 쓰지 않습니다. 토큰 하나를 만들고, 그걸 입력 끝에 붙여서 다시 돌리고, 또 하나를 만듭니다.

```text
1회차:  [프롬프트 500토큰]                    -> "서"
2회차:  [프롬프트 500토큰] + "서"             -> "울"
3회차:  [프롬프트 500토큰] + "서" + "울"      -> "은"
...
```

여기서 순진하게 구현하면 매 회차마다 501개, 502개, 503개 토큰의 K/V를 전부 새로 계산합니다. 그런데 4절의 조건을 만족하면 **앞의 500개는 회차가 바뀌어도 수학적으로 같은 상태를 만듭니다.** 뒤에 토큰을 붙여도 앞 위치에서 미래를 볼 수 없기 때문입니다.

그래서 한 번 계산한 K/V를 메모리에 들고 있다가 다음 회차에 재사용합니다. 이게 **KV 캐시**입니다. 새로 계산하는 건 방금 추가된 토큰 하나의 K/V뿐입니다.

요청 하나가 끝나면 이 상태도 보통 수명을 다합니다. 그러나 긴 시스템 지침이나 문서 묶음을 같은 서비스가 요청마다 다시 읽는 사용 사례가 늘면서, 같은 접두사의 계산 상태를 요청 사이에도 재사용할 이유가 생겼습니다. Anthropic은 2024년 8월 prompt caching을 공개했습니다. 따라서 prompt cache는 새로운 attention 원리를 추가한 기능이라기보다, **생성 중에만 쓰던 접두사 계산 상태의 수명과 공유 범위를 API 요청 사이로 넓힌 기능**으로 이해하는 편이 정확합니다.

여기까지는 **한 번의 응답을 만드는 동안** 벌어지는 일입니다. 대부분의 생성용 추론 엔진이 성능을 위해 KV cache를 기본으로 쓰지만, 엔진 설정에 따라 끌 수도 있습니다. 예를 들어 Hugging Face Transformers는 `use_cache=False`를 지원합니다. API 사용자가 보통 직접 제어하지 못한다는 사실과 기술적으로 비활성화할 수 없다는 주장은 구분해야 합니다.

**프롬프트 캐시는 접두사의 KV 상태를 요청과 요청 사이에도 재사용하는 기능입니다.** 보통은 응답이 끝나면 요청 전용 상태를 놓아 줍니다. 프롬프트 캐시는 "이 앞부분은 잠시 들고 있어 달라"고 지정하거나 자동 정책에 맡겨, 다음 요청이 같은 앞부분으로 시작하면 그 구간의 계산을 건너뛰게 만듭니다.

정리하면 이렇습니다.

| | KV 캐시 | 프롬프트 캐시 |
|---|---|---|
| 범위 | 한 응답을 생성하는 동안 | 요청과 요청 사이 |
| 제어 주체 | 추론 엔진 설정. 보통 기본 활성 | API 제공자와 요청의 캐시 설정 |
| 저장 위치 | 주로 추론 장치 메모리. 엔진에 따라 offload 가능 | 제공자가 관리하는 서버 메모리 |
| 저장 대상 | 층별 K/V 상태 | 접두사의 K/V 표현과 일치 확인용 메타데이터 |

개념적으로는 **KV cache의 수명을 요청 사이로 늘린 것**입니다. 다만 실제 저장 형식, 배치 방식, 메모리 배치는 엔진과 API 제공자마다 다르므로 동일한 메모리 객체를 그대로 보존한다고 단정하지 않습니다.

## 3. prefill과 decode는 병목이 다르다

캐시가 무엇을 아껴 주는지 정확히 알려면 추론이 두 단계라는 걸 봐야 합니다.

**prefill.** 입력 프롬프트 전체를 읽는 단계입니다. 500토큰이면 층을 하나씩 통과하면서 각 층의 500개 위치를 병렬로 처리해 K/V를 만듭니다. causal mask는 뒤쪽을 보지 못하게 하지만, 같은 층의 위치들을 행렬 연산으로 함께 계산하는 것은 막지 않습니다. 긴 입력과 충분한 배치에서는 큰 행렬 연산의 비중이 커져 연산 처리량의 영향을 많이 받습니다.

**decode.** 답변을 한 토큰씩 만드는 단계입니다. 다음 토큰을 만들려면 방금 만든 토큰이 있어야 하므로 한 요청 안의 시간축을 prefill처럼 한꺼번에 계산할 수 없습니다. 배치가 작으면 토큰 하나를 만들 때 적은 연산을 위해 모델 가중치와 기존 KV 상태를 반복해서 읽어야 하므로 메모리 대역폭의 영향을 많이 받습니다.

```text
prefill                          decode
[■■■■■■■■■■] 500토큰 한 번에      [■] [■] [■] [■] ...  한 개씩
긴 입력에서는 연산 비중이 큼         작은 배치에서는 메모리 읽기 비중이 큼
prompt cache가 줄이는 구간           생성 중 KV cache를 계속 사용
```

이 구분은 흔한 경향이지 모든 하드웨어와 배치 크기에 적용되는 절대 법칙은 아닙니다. 짧은 입력, 큰 decode batch, KV offload, attention 구현에 따라 병목은 달라질 수 있습니다.

**프롬프트 캐시가 직접 줄이는 것은 적중한 접두사의 prefill 계산입니다.** 따라서 주된 효과는 첫 토큰까지의 시간과 입력 처리 비용 감소입니다. 생성 중 decode도 KV cache에 의존하지만, 이전 요청의 prompt cache가 토큰 생성 자체를 생략하지는 않습니다. 실제 지연 시간 개선 폭은 적중한 접두사 길이, 새 suffix 길이, 모델, 배치와 서비스 구현에 따라 측정해야 합니다.

## 4. 왜 접두사여야만 하는가

이 절이 문서의 핵심입니다. 먼저 어떤 조건에서 결론이 성립하는지 고정하고, 그다음 작은 계산으로 의존 방향을 확인합니다.

### 성립 조건

아래 결론은 다음 조건을 만족하는 **표준 decoder-only Transformer의 self-attention에서** 성립합니다.

- 모든 self-attention 층이 위치 i에서 0..i만 볼 수 있도록 causal mask를 적용합니다.
- 같은 모델, 같은 토큰과 추론 설정을 비교하고, attention mask의 기존 접두사 영역이 같은 연결을 허용합니다.
- 끝에 토큰을 덧붙여도 기존 접두사의 position id와 실제 position encoding 값·scaling이 바뀌지 않습니다.
- 미래 위치의 정보를 앞 위치에 섞는 별도 연산이 없습니다.

학습된 절대 위치 임베딩, sinusoidal encoding, 고정된 RoPE, ALiBi 같은 일반적인 위치 처리 방식은 **같은 접두사에 같은 위치 값을 적용한다**는 조건 아래 결론을 흔들지 않습니다. 반면 전체 sequence length에 따라 기존 위치의 회전 계수까지 바꾸는 dynamic RoPE scaling, sliding-window rebasing처럼 기존 위치나 attention 범위를 다시 정하는 구현, 미래 정보를 섞는 bidirectional 층, 요청 사이에 달라지는 외부 상태가 있다면 별도 검토가 필요합니다.

### 층별 논증

> 위 조건에서 층 l, 위치 i의 hidden state와 그 상태에서 만든 K/V는 토큰 0..i에만 의존한다.

입력층에서 위치 i의 hidden state는 토큰 i의 embedding과 위치 i의 position 정보로 만들어집니다. 접두사 뒤에 토큰을 붙여도 이 둘은 바뀌지 않습니다.

첫 self-attention 층에서 위치 i의 Q/K/V는 그 위치의 hidden state로부터 만들어집니다. attention 출력은 causal mask 때문에 위치 0..i의 V만 모읍니다. MLP, layer normalization, residual connection은 각 위치의 현재 값에 적용되므로 미래 위치를 새로 끌어오지 않습니다. 따라서 첫 층을 지난 위치 i의 상태도 토큰 0..i에만 의존합니다.

어떤 층 l에서 이 성질이 참이라고 가정하면, 다음 층도 같은 causal attention과 위치별 연산만 수행하므로 위치 i에 토큰 i+1 이후의 정보가 들어올 길이 없습니다. 수학적 귀납법에 따라 층을 몇 개 쌓아도 결론이 유지됩니다.

따라서 같은 토큰 접두사를 같은 위치와 설정으로 처리하면 그 접두사의 층별 K/V는 수학적으로 같습니다. 실제 GPU 실행에서는 커널, 배치, 부동소수점 연산 순서 때문에 새로 계산한 값이 비트 단위까지 같다고 보장할 수는 없습니다. API 캐시는 두 실행의 텐서를 사후 비교하는 대신 토큰 접두사와 관련 설정의 일치 여부로 재사용 가능성을 판정합니다.

### 작은 모형으로 의존 방향 확인

부록 A의 모형은 어휘 20개, 차원 8, 층 3개인 causal attention 계산입니다. 이 실험은 위 층별 논증의 **예시와 반대 조건 실험(negative control)**이지, 모든 실제 모델 구현을 표본 하나로 증명하는 실험은 아닙니다.

```text
길이 8 토큰 기준
  마지막 토큰만 변경 -> 앞에서 7 개 위치의 K/V가 동일
  첫 토큰만 변경     -> 앞에서 0 개 위치의 K/V가 동일
  뒤에 2개 덧붙임    -> 앞에서 8 개 위치의 K/V가 동일
```

세 줄은 이 고정된 가중치와 입력에서 다음 현상을 보여 줍니다.

**마지막 토큰만 바꿨더니 앞 7개가 그대로입니다.** 뒤쪽 변경은 앞쪽에 영향을 주지 않습니다. 바뀐 건 그 위치 하나뿐입니다.

**첫 토큰을 바꿨더니 공통 K/V 접두사가 0개가 됐습니다.** 이 모형에서는 바뀐 위치 0이 이후 위치의 attention 계산에도 영향을 주었습니다. 일반 정리는 "이후 위치가 앞 토큰에 의존할 수 있으므로 기존 캐시를 그대로 쓸 수 없다"입니다. 모든 가중치와 입력에서 이후의 모든 수치가 반드시 달라진다는 뜻은 아닙니다.

**뒤에 두 개 덧붙였더니 원래 8개가 전부 그대로입니다.** 같은 설정에서 앞은 두고 뒤에만 추가하면 기존 접두사의 계산 상태는 바뀌지 않습니다. 실제 API 적중에는 20-block 탐색 범위와 TTL 같은 별도 조건도 필요하지만, 툴 콜링 루프가 구조적으로 캐시 친화적인 이유는 이 접두사 보존에 있습니다.

재현 코드는 부록 A에 있습니다. 넘파이만 있으면 돌아가며, causal mask를 실제 점수에 적용하는 한 줄을 제거하는 negative control도 함께 설명합니다.

### 그래서 중간 캐싱은 왜 안 되는가

"앞부분은 매번 바뀌지만 중간에 큰 고정 문서가 있으니 그것만 캐싱하면 안 되나?"

일반적인 prefix cache로는 안 됩니다. 그 문서가 놓인 위치의 K/V는 **그 앞에 무엇이 있었는지에 의존할 수 있습니다.** 앞부분이 매 요청 달라지면 캐시 시스템은 같은 문서 문자열만 보고 K/V가 같다고 가정할 수 없습니다.

재사용하려면 공통 부분을 앞으로 옮겨 안정적인 접두사를 만들거나, 제공자가 별도로 지원하는 다른 캐시·컨텍스트 재사용 기능을 써야 합니다.

## 5. 캐시 계층 순서가 설계 제약이 되는 이유

4절의 결론은 "앞에 있는 것일수록 캐시에 유리하다"입니다. 그러면 무엇이 앞에 오는지가 곧 설계 문제가 됩니다.

Anthropic은 prompt cache가 접두사를 구성하는 **논리적 계층 순서**를 다음과 같이 공개합니다.

```text
[ tools ] ──> [ system ] ──> [ messages ]
   맨 앞                          맨 뒤
   
   ← 안정적일수록 여기            자주 바뀔수록 여기 →
```

[툴 콜링 문서](tool_calling.md#2-qwen에서는-도구-정의가-시스템-메시지-안에-들어간다)에서는 고정한 Qwen revision의 채팅 템플릿을 렌더링해 도구 정의가 시스템 턴 앞부분에 놓이는 한 구현을 확인했습니다. Anthropic의 내부 직렬화 전문은 공개되지 않으므로 Qwen 관측으로 대신 증명하지 않습니다. Anthropic에 대해서는 공식 문서의 캐시 계층과 usage 값만 확인할 수 있습니다.

그래서 규칙이 하나 나옵니다. **안정성 순서와 캐시 계층 순서를 맞추십시오.**

| 얼마나 자주 바뀌는가 | 어디에 두는가 |
|---|---|
| 절대 안 바뀜 (도구 목록, 고정 지침) | 맨 앞. 캐시 지점 이전 |
| 세션마다 바뀜 (사용자 프로필, 문서) | 그 다음. 세션 단위로 캐싱 |
| 턴마다 바뀜 (대화 내용) | 맨 뒤. 마지막 캐시 지점 이후 |
| 요청마다 바뀜 (시각, 요청 ID) | **없애거나 맨 뒤로** |

이 순서가 어긋나면 캐시 지정을 아무리 해도 소용없습니다. 시스템 프롬프트 첫머리에 현재 시각을 넣어 두고 그 뒤에 캐시 지점을 찍으면, 접두사가 매번 달라지니 저장만 하고 읽지는 못합니다.

## 6. 무효화에는 층위가 있다

모든 변경이 전부를 날리지는 않습니다. Anthropic API의 캐시는 세 층으로 나뉘고, 변경은 자기 층과 그 아래만 무효화합니다.

| 바꾼 것 | tools 캐시 | system 캐시 | messages 캐시 |
|---|:---:|:---:|:---:|
| 도구 정의 추가·삭제·순서 변경 | 무효 | 무효 | 무효 |
| 모델 교체 | 무효 | 무효 | 무효 |
| 시스템 프롬프트 내용 | 유지 | 무효 | 무효 |
| 웹 검색·웹 가져오기·인용(citation)·속도(speed) 설정 켜고 끄기 | 유지 | 무효 | 무효 |
| `tool_choice`, `disable_parallel_tool_use`, 이미지 켜고 끄기 | 유지 | 유지 | 무효 |
| 사고(thinking) 설정 변경 | 모델별 | 모델별 | 무효 |
| 추론 노력(effort) 설정 변경 | 모델별 | 모델별 | 무효. 단, 모델 기본값을 명시하는 것은 생략과 동등 |
| 이전 메시지 수정·삭제·재정렬 | 유지 | 유지 | 무효 |
| 메시지를 끝에 추가 | 유지 | 유지 | 무효화 안 됨. 20-block 탐색 범위 안이면 기존 접두사 적중 |

표가 5절의 순서 그림과 정확히 대응합니다. 앞쪽 것을 건드릴수록 더 많이 날아갑니다.

실용적인 함의 두 가지가 있습니다.

**`tool_choice`는 매 요청 바꿔도 됩니다.** 도구 정의와 시스템 프롬프트 캐시가 살아 있습니다. 반면 도구를 **추가하거나 빼면** 전부 다시 계산합니다. "모드에 따라 도구 세트를 갈아 끼우는" 설계가 비싼 이유입니다. 도구 목록은 고정해 두고 모드는 메시지로 전달하는 편이 훨씬 쌉니다.

**모델을 바꾸면 캐시는 없습니다.** 캐시는 모델별로 따로 잡힙니다. 대화 중간에 싼 모델로 갈아탄다는 발상은 캐시를 통째로 버리는 대가를 치릅니다. 보조 작업이 필요하면 메인 루프는 한 모델로 유지하고 별도 호출로 분리하는 편이 낫습니다.

## 7. 몇 번 재사용해야 이득인가

캐시는 공짜가 아닙니다. **쓸 때 더 비싸고 읽을 때 훨씬 쌉니다.**

Anthropic API 기준으로 캐시에 쓰는 토큰은 기본 입력가의 1.25배(5분 유지), 읽는 토큰은 0.1배입니다. 산수를 해 보면 손익분기가 나옵니다.

```text
같은 프롬프트를 2번 보낸다 (5분 유지 기준)

  캐시 없이 :  1.0 + 1.0            = 2.0
  캐시 쓰고 :  1.25(쓰기) + 0.1(읽기) = 1.35   → 이득
```

1시간 유지를 고르면 쓰기가 2배로 오릅니다.

```text
  2번 :  캐시 없이 2.0   vs   2.0 + 0.1 = 2.1   → 거의 본전
  3번 :  캐시 없이 3.0   vs   2.0 + 0.2 = 2.2   → 이득
```

**5분 유지는 처음 캐시에 쓴 뒤 한 번만 재사용해도, 즉 총 2회 호출부터 이득입니다. 1시간 유지는 두 번 재사용해 총 3회 호출할 때부터 이득입니다.** 출력 비용과 적중하지 않은 뒷부분의 비용이 같다는 단순 비교이며, 실제 판단은 usage에 찍힌 적중 토큰 수로 해야 합니다.

한 가지 함정이 있습니다. **아직 캐시 항목(cache entry)이 없는 접두사로 N개를 동시에 시작하면 그 요청들은 서로가 쓰는 중인 항목을 읽을 수 없습니다.** 항목은 첫 응답이 시작된 뒤에야 사용할 수 있습니다. 비어 있는 캐시에서 병렬 요청을 보낼 거면 하나를 먼저 보내고 응답 시작을 확인한 다음 나머지를 보내십시오.

## 8. 걸렸는지 확인하는 법

응답의 `usage`를 봅니다. 추측하지 말고 숫자를 보십시오.

| 필드 | 의미 |
|---|---|
| `cache_creation_input_tokens` | 이번에 캐시에 쓴 토큰 수 (1.25배 냄) |
| `cache_read_input_tokens` | 이번에 캐시에서 읽은 토큰 수 (0.1배 냄) |
| `input_tokens` | 캐시를 못 쓰고 새로 처리한 토큰 수 (제값 냄) |

**PASS**: 같은 접두사로 두 번째 요청을 보냈을 때 `cache_read_input_tokens`가 0보다 큽니다.
**FAIL**: 반복 요청인데 계속 0입니다. 접두사 불일치뿐 아니라 최소 크기 미달, cache write 실패, TTL 만료, 설정 변경도 후보입니다. 9~10절과 cache diagnostics를 함께 확인하십시오.

읽을 때 주의할 게 하나 있습니다. **`input_tokens`는 전체 프롬프트 크기가 아니라 캐시에 걸리지 않은 나머지입니다.** 세 값을 더해야 전체입니다. 에이전트를 몇 시간 돌렸는데 `input_tokens`가 4천으로 찍혀 있다면 나머지가 캐시에서 온 것이지 프롬프트가 작은 게 아닙니다.

상용 API의 내부 렌더링 결과는 받을 수 없습니다. 대신 두 요청의 `tools`, `system`, `messages`와 모델·이미지·thinking·`tool_choice` 같은 캐시 관련 설정을 안정적으로 직렬화해 diff하고, 두 번째 응답의 usage에서 실제 적중 여부를 확인합니다. 열린 모델을 직접 운영한다면 채팅 템플릿의 렌더링 결과와 토큰 번호 배열까지 비교할 수 있습니다.

## 9. 캐시를 조용히 깨뜨리는 것들

전부 오류를 내지 않습니다. 그냥 캐시가 안 걸릴 뿐이고, 청구서를 보기 전까지는 모릅니다.

**시스템 프롬프트의 현재 시각.** 가장 흔합니다.

```python
system = f"당신은 도우미입니다. 현재 시각은 {datetime.now()}입니다."
```

프롬프트 앞쪽이 매 요청 달라지므로 그 뒤의 긴 고정 구간을 같은 접두사로 재사용할 수 없습니다. [툴 콜링 문서](tool_calling.md#직접-측정한-결과)의 고정 예제에서는 시스템 프롬프트의 시각을 1초 바꾸자 공통 문자 접두사가 56자였고 **57번째 문자부터** 달라졌습니다. 정확한 위치는 문장과 템플릿에 따라 달라집니다. 시각이 정말 필요하면 가능한 한 메시지 뒤쪽에 두십시오.

**요청 ID나 UUID를 앞쪽에 넣는 것.** 같은 이유입니다.

**순서가 불안정한 배열.** 도구 목록과 콘텐츠 블록처럼 순서가 프롬프트 의미의 일부인 배열을 집합에서 만들면 요청마다 순서가 달라질 수 있습니다. 이런 배열은 명시적인 기준으로 정렬하십시오. JSON 객체의 key 순서만 달라져도 Anthropic 캐시가 반드시 무효화된다는 규칙은 공식 문서로 확인되지 않았으므로, 원시 요청 바이트 diff만으로 원인을 단정하지 않습니다.

**사용자마다 다른 시스템 프롬프트.** 이름이나 사용자 ID를 시스템 프롬프트에 끼워 넣으면 캐시가 사용자 수만큼 쪼개집니다. 공유 가능한 부분을 앞에 두고 개인화된 부분은 뒤로 미십시오.

**조건부로 붙이는 시스템 절.** `if 관리자: system += "..."` 같은 코드는 플래그 조합 수만큼 서로 다른 접두사를 만듭니다.

**사용자마다 다른 도구 목록.** 도구 정의는 캐시 접두사 계층의 맨 앞에 있으므로 이건 캐시를 사용자 단위로 완전히 갈라 놓습니다. 6절의 첫 줄입니다.

---

## 10. 최소 크기가 있다

접두사가 너무 짧으면 캐시 지정을 해도 **조용히 무시됩니다.** 오류는 나지 않고 `cache_creation_input_tokens`가 0으로 찍힐 뿐입니다.

문제는 이 값이 모델마다 다르고, **세대순으로 단조롭지 않다**는 점입니다. 512, 1024, 2048, 4096 토큰이 섞여 있고 최신 모델이 항상 더 작지도 않습니다. 최신 모델에서 캐시되던 3천 토큰짜리 프롬프트가 한 세대 전 모델에서는 안 될 수 있습니다.

여기서 단위에 주의해야 합니다. **기준은 문자 수가 아니라 토큰 수입니다.** 툴 콜링 문서는 Qwen에서 문자 접두사와 토큰 접두사를 모두 재지만, Anthropic의 최소 크기 판정에는 Qwen 토큰 수도 쓸 수 없습니다. 해당 API가 제공하는 토큰 계산과 usage 필드로 확인해야 합니다.

## 11. 흔한 오해

**"텍스트를 저장한다."** 아닙니다. K/V 텐서, 즉 계산 결과입니다. 1~2절.

**"토큰을 안 보내도 된다."** 아닙니다. 매 요청 전체를 다시 보냅니다. 아끼는 건 전송량이 아니라 **재계산**입니다.

**"캐시를 켜면 응답이 전반적으로 빨라진다."** 적중한 접두사의 prefill을 건너뛰므로 주로 첫 토큰까지의 시간을 줄입니다. 생성 토큰 자체의 계산은 남으며, 실제 개선 폭은 측정해야 합니다. 3절.

**"중간에 큰 고정 문서가 있으니 그것만 캐싱하면 된다."** 안 됩니다. 그 위치의 K/V는 앞에 무엇이 있었는지에 의존합니다. 앞으로 옮기십시오. 4절.

**"파라미터를 조금 바꾸는 정도는 괜찮다."** 무엇을 바꾸느냐에 따라 다릅니다. `tool_choice`는 안전하고 도구 목록은 전부 날립니다. 6절.

**"오래 유지할수록 좋다."** 1시간 유지는 쓰기가 2배입니다. 최초 write 뒤 두 번 이상 재사용할 때, 즉 총 3회 이상 호출할 때부터 단순 입력 비용이 이득입니다. 7절.

**"캐시 지정을 했으니 걸렸을 것이다."** `cache_read_input_tokens`를 보기 전까지는 모릅니다. 8절.

## 부록 A. 재현 방법

### causal 의존 방향 확인 (모델 불필요)

4절의 세 줄을 만든 코드입니다. 토큰 embedding뿐 아니라 고정된 절대 위치 embedding도 넣어, 뒤에 덧붙일 때 기존 위치 번호가 유지되는 조건을 드러냅니다. 넘파이만 있으면 됩니다.

```python
# causal.py — uv run --with numpy python causal.py
import numpy as np

rng = np.random.default_rng(0)
VOCAB, D, LAYERS, MAX_LEN = 20, 8, 3, 16

W_e = rng.normal(size=(VOCAB, D))
W_p = rng.normal(size=(MAX_LEN, D))
W_q = [rng.normal(size=(D, D)) for _ in range(LAYERS)]
W_k = [rng.normal(size=(D, D)) for _ in range(LAYERS)]
W_v = [rng.normal(size=(D, D)) for _ in range(LAYERS)]


def forward(tokens, apply_causal_mask=True):
    """각 층의 K/V를 돌려준다."""
    x = W_e[list(tokens)] + W_p[:len(tokens)]
    T = len(tokens)
    causal = np.tril(np.ones((T, T)))          # 자기 위치와 그 앞만 1
    kv_per_layer = []
    for l in range(LAYERS):
        Q, K, V = x @ W_q[l], x @ W_k[l], x @ W_v[l]
        kv_per_layer.append((K, V))
        s = Q @ K.T / np.sqrt(D)
        if apply_causal_mask:
            s = np.where(causal == 1, s, -np.inf)  # 뒤쪽 토큰을 가린다
        w = np.exp(s - s.max(axis=-1, keepdims=True))
        w /= w.sum(axis=-1, keepdims=True)
        x = w @ V
    return kv_per_layer


def same_at(a, b, i):
    return all(
        np.array_equal(Ka[i], Kb[i]) and np.array_equal(Va[i], Vb[i])
        for (Ka, Va), (Kb, Vb) in zip(a, b)
    )


def same_prefix_len(a, b):
    """두 실행의 K/V가 모든 층에서 일치하는 위치가 앞에서 몇 개인가."""
    n = min(a[0][0].shape[0], b[0][0].shape[0])
    return next((i for i in range(n) if not same_at(a, b, i)), n)


def equal_positions(a, b):
    """공통 길이 안에서 모든 층의 K/V가 같은 위치를 전부 찾는다."""
    n = min(a[0][0].shape[0], b[0][0].shape[0])
    return [i for i in range(n) if same_at(a, b, i)]


base = [3, 1, 4, 1, 5, 9, 2, 6]
tail = [3, 1, 4, 1, 5, 9, 2, 7]      # 마지막 토큰만 다름
head = [8, 1, 4, 1, 5, 9, 2, 6]      # 첫 토큰만 다름
longer = base + [7, 7]               # 뒤에 덧붙이기만 함

kv_base = forward(base)
kv_tail = forward(tail)
kv_head = forward(head)
kv_longer = forward(longer)

print("길이", len(base), "토큰 기준")
print("  마지막 토큰만 변경 ->", same_prefix_len(kv_base, kv_tail), "개 위치 동일")
print("  첫 토큰만 변경     ->", same_prefix_len(kv_base, kv_head), "개 위치 동일")
print("  뒤에 2개 덧붙임    ->", same_prefix_len(kv_base, kv_longer), "개 위치 동일")

# same_prefix_len=0만으로 모든 위치가 달랐다고 단정하지 않도록 전 위치를 확인한다.
assert equal_positions(kv_base, kv_tail) == list(range(7))
assert equal_positions(kv_base, kv_head) == []
assert equal_positions(kv_base, kv_longer) == list(range(8))

unmasked_base = forward(base, apply_causal_mask=False)
unmasked_tail = forward(tail, apply_causal_mask=False)
print("  마스크를 적용하지 않음 ->",
      same_prefix_len(unmasked_base, unmasked_tail), "개 위치 동일")
```

**PASS 조건**: 앞의 세 측정이 차례로 7, 0, 8이고 assertion이 모두 통과합니다.
**negative control**: 마지막 줄은 0입니다. `apply_causal_mask=False`는 점수에 마스크를 적용하는 `s = np.where(...)` 줄을 건너뜁니다. 이때 마지막 토큰 변경이 앞 위치에도 전파되어 첫 측정이 7에서 0으로 바뀝니다.

가중치가 무작위이고 residual connection, MLP, normalization 같은 실제 모델 구성요소도 생략했습니다. 이들은 위치별 연산이라 4절의 causal 의존 방향을 바꾸지 않지만, 이 스크립트는 어디까지나 그 방향을 보여 주는 최소 모형입니다. 일반 결론의 근거는 4절의 조건과 층별 논증입니다.

### 렌더링 접두사 측정

시스템 프롬프트 변경이 접두사를 어디서 깨는지는 채팅 템플릿으로 잽니다. [툴 콜링 문서](tool_calling.md) 부록 A의 스크립트를 그대로 쓰고 메시지만 바꾸면 됩니다.

### 확인한 것과 확인하지 못한 것

| 항목 | 상태 |
|---|---|
| 표준 causal decoder에서 위치 i의 K/V가 뒤쪽 토큰과 무관하다 | **층별 논증.** 4절의 명시한 조건 아래 성립하며, 위 모형의 7/0/8과 negative control로 의존 방향을 예시 |
| 첫 토큰 변경 뒤 모든 위치의 K/V가 달라진다 | **이 모형에서 직접 계산.** `equal_positions == []`. 모든 실제 모델과 입력에 항상 성립하는 정리는 아님 |
| 끝에 덧붙이면 기존 위치의 K/V가 보존된다 | **층별 논증 + 이 모형에서 직접 계산.** 같은 위치 번호와 설정을 유지한다는 조건이 필요 |
| Qwen에서 도구 정의가 시스템 턴 앞부분에 놓인다 | **직접 관측** (고정 revision의 열린 모델 템플릿) |
| Anthropic 캐시 접두사 계층이 `tools` → `system` → `messages`다 | **공식 문서 확인.** 내부 렌더링 문자열은 관측하지 못함 |
| 실제 모델의 prefill 시간이 캐시로 줄어든다 | **미검증.** 가중치를 돌리지 않았습니다. prefill/decode의 병목 구분은 구조에서 나오는 성질이고 널리 확인된 사실이지만, 이 문서는 직접 측정하지 않았습니다 |
| 상용 API의 실제 캐시 적중 동작 | **미검증.** API 호출을 하지 않았습니다. 6~10절의 벤더 사실은 문서 확인이며 부록 B에 날짜를 적었습니다 |

3절의 prefill/decode 구분은 **직접 잰 게 아닙니다.** 실측하려면 단순히 같은 로컬 모델을 두 번 호출하는 것으로는 부족합니다. 한 경로는 매번 prefill하고, 다른 경로는 첫 실행의 `past_key_values`를 명시적으로 넘기거나 vLLM 같은 prefix-caching 엔진을 사용해야 합니다. 두 경로 모두 warm-up, 동기화, 같은 suffix와 반복 횟수를 맞춘 뒤 첫 토큰까지의 시간을 비교해야 합니다.
