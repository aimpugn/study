## 1. 시작 질문 — 메모리가 늘어나는데 누수인가

서버를 띄워 두고 모니터링 화면을 보면 이런 그림을 자주 만납니다.

```
메모리 사용량
  400MB ┤        ╭╮      ╭╮      ╭╮
  300MB ┤    ╭╮  ││  ╭╮  ││  ╭╮  ││
  200MB ┤  ╭╮││╭╮││╭╮││╭╮││╭╮││╭╮││
  100MB ┤╭╮││││││││││││││││││││││││
        └┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴→ 시간
```

톱니처럼 오르내립니다. 이게 누수일까요? **아닙니다.** 오히려 정상입니다. 객체를 만들면 메모리가 차고, GC가 돌면 비워집니다. 이 톱니는 "일을 하고 있다"는 신호입니다.

그럼 이건 어떨까요.

```
  400MB ┤                    ╭╮  ╭╮
  300MB ┤          ╭╮  ╭╮  ╭╯╰╮╭╯╰╮
  200MB ┤    ╭╮  ╭╯╰╮╭╯╰╮╭╯  ╰╯  ╰╯
  100MB ┤╭╮╭╯╰╮╭╯  ╰╯  ╰╯
        └┴┴┴──┴┴──────────────────→ 시간
```

**톱니의 저점(바닥)이 계단처럼 올라갑니다.** 이것이 누수입니다. 아무리 치워도 남는 양이 계속 늘어난다는 뜻입니다.

그런데 실제 운영 화면에서 이 둘을 구별하기는 생각보다 어렵습니다. 이 문서는 **왜 어려운지**, 그리고 **어떤 지표를 어떻게 조합하면 판정할 수 있는지**를 다룹니다.

핵심 주장을 미리 적어 둡니다.

> **지표 하나로는 절대 판정할 수 없습니다.** 성격이 다른 여러 신호가 같은 방향을 가리킬 때만 판정합니다.
> 그리고 판정 전에 **측정기가 실제로 누수를 잡아낼 수 있는지** 먼저 확인해야 합니다.

## 2. 누수의 정의를 먼저 좁힌다

"메모리 누수"라는 말이 세 가지 다른 상황에 쓰입니다. 섞어 쓰면 대화가 어긋납니다.

| 상황 | 무슨 일인가 | JVM에서 부르는 이름 |
|---|---|---|
| ① 더 이상 쓰지 않는데 참조가 남아 GC가 못 치움 | 캐시에 넣고 안 빼기, 리스너 등록하고 해제 안 하기 | **힙 누수** |
| ② 힙 밖 자원을 해제하지 않음 | 파일·소켓 닫지 않기, 직접 버퍼 반납 안 하기 | **네이티브 누수** |
| ③ 지금 필요해서 붙들고 있음 | 처리 대기 중인 요청 데이터 | **누수가 아님 — 설계된 보유** |

③을 ①로 오해하는 일이 잦습니다. 대기열에 1만 건이 쌓여 있으면 메모리를 붙들고 있지만, 그건 **일이 끝나면 풀립니다.** 판정 기준은 하나입니다.

> **부하를 멈추고 GC를 강제로 돌린 뒤에도 남아 있으면 누수, 사라지면 보유였다.**

그래서 소크 테스트(장시간 부하 시험)는 반드시 **부하를 멈추는 구간**을 포함해야 합니다. 부하를 계속 걸면서 "메모리가 안 줄어든다"고 하는 것은 판정이 아닙니다.

이 문서는 ①과 ②의 진단을 다룹니다. ③과의 구별 방법도 함께 다룹니다. 자원의 종류와 `close()`의 역할 같은 개념 층위는 [자원과 누수](./java/resource_management_and_leaks.md)에 있습니다.

## 3. `used heap`을 보면 안 되는 이유

대부분의 모니터링 도구가 기본으로 보여주는 값이 **사용 중인 힙(used heap)** 입니다. 이 값으로 누수를 판정하면 안 됩니다.

### 왜냐하면 쓰레기가 섞여 있습니다

`used heap`은 "지금 힙에 들어 있는 것 전부"입니다. 여기에는

- 살아 있어서 계속 쓰이는 객체
- 이미 버려졌지만 **아직 안 치운** 객체

가 함께 들어갑니다. GC는 필요할 때 치웁니다. CPU에 여유가 있고 힙에 자리가 있으면 서둘 이유가 없습니다.

실측 예시를 보겠습니다. 어떤 TCP 수신 서버에 초당 500건씩 60분간 부하를 걸었을 때의 값입니다.

| 시점 | 사용 중 힙 | 회수 후 남은 힙 |
|---|---:|---:|
| 기동 직후 | 106.9MB | 20.9MB |
| 30분 경과 | 271.2MB | 19.0MB |
| 60분 경과 | 223.1MB | 19.0MB |

**사용 중 힙은 107MB에서 271MB로 2.5배가 됐습니다.** 이것만 보면 "메모리가 늘고 있다"고 읽힙니다.

그런데 **회수 후 남은 힙은 20.9MB에서 19.0MB로 오히려 줄었습니다.** 실제로 살아있는 양은 늘지 않았습니다. 늘어난 252MB는 전부 아직 안 치운 쓰레기입니다.

### 그럼 무엇을 봐야 하나

**GC가 돈 직후에 남아 있는 양**입니다. 이것을 여러 이름으로 부릅니다.

| 이름 | 어디서 나오나 |
|---|---|
| live set | 일반 용어 |
| `jvm.gc.live.data.size` | Micrometer 지표 |
| GC 로그의 `->` 오른쪽 값 | JVM이 직접 기록 |

이 값의 **바닥선**이 시간에 대해 평평하면 누수가 없고, 계단처럼 오르면 누수입니다.

### 그런데 Micrometer 지표에도 함정이 있습니다

`jvm.gc.live.data.size`는 **old 영역을 수집할 때만 갱신됩니다.** G1 같은 세대별 수집기는 young 영역만 치우는 경우가 많고, 그때는 이 값이 갱신되지 않습니다.

무슨 문제가 생기는지 실측으로 보겠습니다. 위 서버에 순간 폭주(초당 2,000건 20초 + 40초 쉬기)를 8번 반복한 뒤의 값입니다.

| 시점 | 회수 후 남은 힙(지표) | 대기 건수 | CPU |
|---|---:|---:|---:|
| 폭주 중 | 70.9MB | 3,236 | 39.1% |
| 폭주 종료 직후 | **71.3MB** | **0** | **1.0%** |
| 강제 회수 후 | **18.8MB** | 0 | 1.0% |

**폭주 종료 직후를 보십시오.** 대기가 0이고 CPU가 1%인데 지표는 71.3MB를 가리킵니다. 일이 없는데 71MB가 살아 있다는 말입니다.

이유는 이렇습니다. 일이 없으니 새 객체가 만들어지지 않고, 새 객체가 없으니 GC가 돌 이유가 없고, GC가 안 도니 **지표가 폭주 때 값에서 멈춰 있습니다.** 강제로 회수를 한 번 걸면 18.8MB로 떨어집니다.

여기서 배울 것.

> **폴링으로 읽는 지표는 갱신 시점에 좌우됩니다.** 유휴 구간의 값은 신뢰할 수 없습니다.
> 판정은 **GC 로그**로 합니다. GC 로그는 회수가 일어날 때마다 JVM이 직접 기록하므로 누락이 없습니다.

## 4. GC 로그 — 정답지를 켜고 읽는다

### 어떻게 켜나

Java 9부터 통합 로깅(`-Xlog`)을 씁니다.

```bash
java -Xlog:gc,gc+heap=info:file=gc.log:time,uptime,level,tags:filecount=20,filesize=50m \
     -jar app.jar
```

콜론으로 네 토막이 끊깁니다. 각 토막이 무엇을 정하는지 알면 필요에 맞게 조립할 수 있습니다.

| 토막 | 예시 값 | 무엇을 정하나 |
|---|---|---|
| **선택자** | `gc,gc+heap=info` | 어떤 태그를 어느 수준으로 남길지 |
| **출력** | `file=gc.log` | 어디에 쓸지 |
| **데코레이터** | `time,uptime,level,tags` | 각 줄 앞에 붙일 정보 |
| **로테이션** | `filecount=20,filesize=50m` | 파일을 몇 개까지, 얼마씩 |

각 토막의 실무 감각을 짚어 둡니다.

**선택자 — `gc`와 `gc*`의 차이**

```
gc      → 회수 완료 줄만
gc*     → 하위 태그 전부 (gc+start, gc+init, gc+metaspace, gc+heap …)
```

`gc*`는 GC 시작 줄까지 남겨 시작·종료를 짝지을 수 있지만 줄 수가 몇 배로 늘어납니다. 12시간 실행에서는 용량이 부담이 됩니다. **긴 실행은 `gc`로 좁히고, 짧은 진단은 `gc*`로 넓히는** 것이 보통입니다.

**데코레이터 — `uptime`이 핵심입니다**

`time`(벽시계)만 켜면 "실행 시작으로부터 몇 초인지"를 직접 계산해야 합니다. `uptime`을 켜면 그 값이 각 줄에 붙어 **시계열 x축으로 바로 쓸 수 있습니다.**

**로테이션 — 작게 잡으면 앞부분이 사라집니다**

`filecount=3`으로 두고 12시간을 돌리면 초반 로그가 덮여 없어집니다. 누수 판정은 **초반과 후반을 비교하는 일**이라, 앞부분을 잃으면 판정 자체가 불가능해집니다. 넉넉히 잡으십시오.

### 한 줄을 조각별로 읽는다

실제 로그입니다.

```
[2026-07-15T17:53:38.954+0900][1.802s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 43M->5M(512M) 13.421ms
```

조각을 갈라 보겠습니다.

```
[2026-07-15T17:53:38.954+0900]  ← time: 벽시계. 다른 로그와 시각 맞출 때
[1.802s]                        ← uptime: 시작 후 경과. 시계열 x축
[info]                          ← level
[gc]                            ← tags
GC(0)                           ← 일련번호. 시작 줄과 완료 줄을 짝짓는 키
Pause Young (Normal)            ← 종류: 무엇을 회수했나
(G1 Evacuation Pause)           ← 사유: 왜 촉발됐나
43M->5M(512M)                   ← 힙: 회수 전 → 회수 후 (전체 용량)
13.421ms                        ← 애플리케이션이 멈춘 시간
```

**`43M->5M(512M)` 이 핵심입니다.**

```
43M    →    5M   ( 512M )
 │           │       └ 힙 전체 용량 (-Xmx)
 │           └ 회수 후 사용량  ← 이 값이 live set
 └ 회수 전 사용량 (쓰레기 포함)
```

**`->` 오른쪽 값만 시간축에 찍으면 그것이 live set의 직접 측정입니다.** 이 그림을 그리는 것이 누수 판정의 출발점입니다.

### 종류가 신뢰도를 가른다

같은 로그에 세 종류가 섞여 나옵니다.

```
GC(0) Pause Young (Normal)           43M->5M(512M)     ← young 영역만
GC(4) Pause Young (Mixed)            25M->20M(512M)    ← young + old 일부
GC(7) Pause Full                    102M->20M(512M)    ← 전체
```

| 종류 | 회수 범위 | 판정 신뢰도 |
|---|---|---|
| `Pause Young (Normal)` | young 영역만 | **낮음** — old에 쌓인 것을 못 본다 |
| `Pause Young (Mixed)` | young + old 일부 | 중간 |
| `Pause Full` | 전체 | **높음 — 진짜 바닥** |

왜 이 구별이 중요한가 하면, **Young GC의 회수 후 값만 보면 누수로 오판할 수 있습니다.** young에서 살아남은 객체가 old로 승격되면 young 쪽 회수 후 값에는 그 양이 계속 남아 보입니다. old를 치우지 않았으니까요. 실제로 새는 게 아니라 아직 안 치운 것입니다.

그래서 판정 문구는 "Mixed/Full의 회수 후 값이 평평하다"로 씁니다.

### 사유를 읽으면 맥락이 보인다

사유 필드가 판독을 돕습니다.

| 사유 | 뜻 |
|---|---|
| `G1 Evacuation Pause` | 일반적인 young 회수 |
| `Metadata GC Threshold` | 클래스 메타데이터가 임계에 닿음 → **기동·워밍업 구간의 신호** |
| `Heap Inspection Initiated GC` | **외부에서 강제로 촉발** — 힙 조사 명령이 회수를 유발한 것 |
| `System.gc()` | 코드에서 명시적으로 호출 |

마지막 두 개가 실무에서 헷갈립니다. `jcmd <pid> GC.class_histogram`을 실행하면 JVM이 **정확한 결과를 주기 위해 Full GC를 먼저 돕니다.** 그 흔적이 `Heap Inspection Initiated GC`로 남습니다.

이걸 모르면 "왜 여기서 갑자기 Full GC가 돌았지?"로 헤맵니다. 반대로 알고 있으면 **히스토그램 스냅샷과 강제 회수 바닥값이 같은 시점의 값**이라는 유용한 사실을 얻습니다.

### 종료 시 강제 회수 두 번 — 가장 강한 증거

누수 판정에서 가장 결정적인 로그는 이런 모양입니다.

```
GC(574) Pause Full (Heap Inspection Initiated GC) 18M->18M(512M) 19.443ms
GC(575) Pause Full (Heap Inspection Initiated GC) 39M->18M(512M) 19.382ms
```

첫 줄을 보십시오. **`18M->18M`** — 전체 회수를 했는데 사용량이 줄지 않았습니다.

이것이 뜻하는 바는 명확합니다. **그 18MB는 치울 수 없는 것, 즉 진짜 살아있는 상주분입니다.** 더 치울 게 없어서 안 줄어든 것입니다.

둘째 줄에서는 그 사이 새로 생긴 21MB를 치우고 **다시 같은 18MB**로 떨어집니다.

**두 번 연속 같은 바닥이 나오면 그 값이 이 애플리케이션의 상주 크기입니다.** 그리고 이 값이 기동 시점(위 예에서 20.9MB)보다 낮으면, 실행 기간 동안 상주분이 늘지 않았다는 뜻입니다.

소크 테스트를 설계할 때 **종료 직전에 강제 회수를 두 번 걸도록** 만들어 두면 판정이 훨씬 쉬워집니다.

## 5. GC 로그 파싱 실무

수천 줄을 눈으로 볼 수는 없으니 파싱해서 그림을 그립니다. 파싱 코드에는 실전에서 부딪히는 함정이 몇 개 있습니다.

```python
import re

UNIT = {"B": 1, "K": 1024, "M": 1024**2, "G": 1024**3}
GC_RE = re.compile(r"(\d+)([BKMG])->(\d+)([BKMG])\((\d+)([BKMG])\)")

def parse_gc_after(path):
    """(uptime_초, 회수_후_바이트, 종류) 목록을 돌려준다."""
    points = []
    for line in open(path, encoding="utf-8", errors="replace"):
        m = GC_RE.search(line)
        if not m:
            continue
        after = int(m.group(3)) * UNIT[m.group(4)]          # -> 오른쪽만 쓴다
        um = re.search(r"\[(\d+[.,]\d+)s\]", line)          # uptime 데코레이터
        if not um:
            continue
        uptime = float(um.group(1).replace(",", "."))
        kind = ("Full"  if "Pause Full"  in line else
                "Mixed" if "Mixed"       in line else
                "Young" if "Pause Young" in line else "other")
        points.append((uptime, after, kind))
    return points
```

이 짧은 코드에 담긴 판단 다섯 개를 짚습니다.

**① 정규식은 여섯 그룹을 잡지만 쓰는 것은 두 개다**

`43M->5M(512M)`에서 세 숫자와 세 단위, 총 여섯 그룹이 잡힙니다. 그런데 누수 판정에 쓰는 것은 **회수 후 값(`group(3)`)과 그 단위(`group(4)`)** 뿐입니다. 회수 전 값은 쓰레기가 섞여 있어 판정에 쓰지 않습니다.

**② 단위를 반드시 곱해야 한다**

JVM은 값 크기에 따라 `K`/`M`/`G`를 바꿔 씁니다. 문자열 그대로 비교하면 `"5M"`이 `"512K"`보다 작다고 판정합니다. 표에서 곱해 바이트로 통일합니다.

**③ 소수점이 쉼표일 수 있다**

`.replace(",", ".")`가 왜 있는가. 로케일에 따라 uptime이 `1,802s`로 찍힙니다. 이 처리가 없으면 `float()`가 예외를 던지고 **그 줄이 통째로 버려집니다.** 로그 절반을 잃고도 모를 수 있습니다.

**④ 깨진 바이트에 파싱을 멈추지 않는다**

`errors="replace"`로 엽니다. 12시간 로그 한 줄에 이상한 바이트가 섞였다고 전체를 잃을 이유가 없습니다.

**⑤ 종류를 함께 남긴다**

앞서 본 대로 Young과 Full의 신뢰도가 다릅니다. 파싱 단계에서 분류해 두면 나중에 "Full만 골라 기울기 계산" 같은 일을 할 수 있습니다.

### 기울기를 낼 때 주의할 것

바닥선이 오르는지 보려면 기울기를 계산하게 됩니다. 그런데 **단순 최소제곱 회귀는 구간이 섞이면 엉뚱한 답을 냅니다.**

앞서 본 실측에서, 정상 부하 60분 뒤에 폭주 구간을 붙인 전체 데이터로 기울기를 내면 **양수**가 나옵니다(분당 +0.27MB). 폭주 구간의 큰 값이 뒷부분에 몰려 있어 직선이 우상향하는 것입니다.

그러나 실제로는 누수가 없었습니다. 구간을 나눠 보면

- 정상 부하 60분 구간의 기울기: 분당 −0.04 ~ −0.18MB (평평하거나 하강)
- 폭주 구간: 값이 크지만 종료 후 원래 바닥으로 복귀

**구간 성격이 다르면 기울기를 따로 냅니다.** 그리고 이상값에 둔감한 방법(Theil–Sen 같은 중앙값 기반 회귀)을 쓰면 한 점이 직선을 끌고 가는 일을 줄일 수 있습니다.

### 원본을 직접 볼 때

파싱 결과가 의심스러우면 전용 도구로 원본을 엽니다. GCViewer, GCeasy 같은 도구가 `->` 오른쪽 값 추세를 그려 줍니다.

> **주의**: 사내 시스템의 GC 로그를 외부 웹 서비스에 업로드하면 애플리케이션 구조·부하 패턴·클래스 이름이 밖으로 나갑니다. 오프라인 도구를 쓰거나, 업로드 정책을 먼저 확인하십시오.

## 6. 힙 밖을 보는 도구 — NMT

### 왜 필요한가

"회수 후 힙은 평평한데 프로세스 메모리(RSS)가 계속 오른다"는 상황이 있습니다. 이때 범인은 힙 밖에 있습니다.

- 직접 버퍼(direct ByteBuffer) — 네트워크·파일 I/O 버퍼
- 스레드 스택
- 클래스 메타데이터(Metaspace)
- JIT 컴파일 결과(코드 캐시)

이들은 **힙 지표에 전혀 안 잡힙니다.** Native Memory Tracking(NMT)이 이 영역을 카테고리별로 보여 줍니다.

### 어떻게 켜나

```bash
java -XX:NativeMemoryTracking=summary -jar app.jar
```

**기동 플래그입니다. 나중에 켤 수 없습니다.** 진단이 필요할 수 있는 실행이면 처음부터 켜 두십시오. `summary`는 카테고리별 합계만 남기고, `detail`은 호출 지점까지 남기지만 오버헤드가 큽니다.

### 어떻게 찍나

```bash
jcmd <pid> VM.native_memory summary
```

주기적으로 찍어 **차이(diff)** 를 봅니다. 한 장만 찍으면 절대량만 알고 증가 여부를 모릅니다.

### 출력 읽기 — `reserved`와 `committed`를 구별한다

```
Total: reserved=2044164KB, committed=710436KB
-                 Java Heap (reserved=524288KB, committed=524288KB)
-                     Class (reserved=1049355KB, committed=7307KB)
-                    Thread (reserved=44163KB, committed=2603KB)
-                      Code (reserved=252213KB, committed=27565KB)
-                        GC (reserved=56424KB, committed=56424KB)
```

| 항목 | 뜻 |
|---|---|
| **reserved** | 주소 공간을 **예약만** 한 것. 실제 물리 메모리를 쓰지 않는다 |
| **committed** | 실제로 쓰겠다고 **확정**한 것 |

`Class`의 reserved가 1TB에 가까운 것을 보고 놀랄 필요가 없습니다. 64비트 주소 공간을 넉넉히 예약해 둔 것이고 실제 사용은 7MB입니다.

**진단할 때 보는 값은 `committed`입니다.**

### 실측 diff — 카테고리가 원인을 지목한다

앞서 본 73분 소크의 시작·종료 차이입니다.

| 카테고리 | 시작(KB) | 종료(KB) | 증감 | 해석 |
|---|---:|---:|---:|---|
| **Code** | 20,400 | 27,565 | **+7,165** | JIT 컴파일 누적 — 워밍업의 정상 거동 |
| **Metaspace** | 38,706 | 42,508 | **+3,802** | 클래스 메타데이터 |
| Tracing | 22,795 | 19,382 | −3,413 | 계측 자체가 쓰는 영역 |
| Class | 7,108 | 7,307 | +199 | |
| Thread | 2,418 | 2,603 | +185 | 스택 |
| Java Heap | 524,288 | 524,288 | 0 | `-Xmx` 고정 확인용 |
| **Total** | 702,884 | 710,436 | **+7,552** | |

총 7.4MB가 늘었습니다. **어느 카테고리가 늘었는지가 판정을 가릅니다.**

| 카테고리가 오르면 | 의심할 것 |
|---|---|
| `Code` | JIT 워밍업. 시간이 지나면 수렴한다. **정상** |
| `Metaspace` / `Class` | 클래스로더 누수 — 동적 프록시·스크립트 엔진이 클래스를 계속 만드나 |
| `Thread` | 플랫폼 스레드 누수 — 풀이 스레드를 반납하나 |
| `Internal` / `Other` | 직접 버퍼가 안 풀리나 |
| `Java Heap` | `-Xmx`가 의도대로 적용됐나 (상수여야 정상) |

위 예시에서 `Code +7.0MB`가 주도했고 이는 워밍업의 정상 거동입니다. 다만 `Metaspace +3.8MB`도 함께 올랐습니다. 이 값이 **계속** 오르면 클래스로더 누수를 의심해야 하지만, 73분 실행에서 3.8MB는 워밍업 범위로 봅니다.

여기서 배울 실무 감각.

> "총량이 +7.4MB 늘었으니 누수" 라고 판정하면 안 됩니다.
> **어느 카테고리가, 얼마나, 수렴하는지**를 봐야 합니다. 그리고 카테고리마다 정상 거동이 다릅니다.

## 7. 무엇이 쌓이는지 보는 도구 — 클래스 히스토그램

### 왜 필요한가

"힙이 늘었다"를 확인했다면 다음 질문은 **"무엇이 늘었나"** 입니다. 클래스별 인스턴스 수와 크기를 보면 답이 좁혀집니다.

### 어떻게 찍나

```bash
jcmd <pid> GC.class_histogram
```

**이 명령이 Full GC를 유발합니다.** 정확한 결과를 주기 위해 JVM이 먼저 회수하기 때문이며, GC 로그에 `Heap Inspection Initiated GC`로 남습니다.

이 성질에는 장단이 있습니다.

- **장점** — 쓰레기가 걸러진 상태의 히스토그램을 얻습니다. 그리고 강제 회수 바닥값을 동시에 얻습니다
- **단점** — 운영 중인 서비스에 걸면 그 순간 애플리케이션이 멈춥니다(위 예시에서 약 20~30ms). 운영 적용은 신중해야 합니다

### 출력 읽기

```
 num     #instances         #bytes  class name (module)
   1:         72,729      5,555,600  [B (java.base@25.0.3)
   2:         70,771      1,698,504  java.lang.String
   3:         11,267      1,421,080  java.lang.Class
   4:         40,314      1,290,048  java.util.concurrent.ConcurrentHashMap$Node
   5:         12,067        731,392  [Ljava.lang.Object;
```

클래스 이름이 JVM 내부 표기법으로 나옵니다. 처음 보면 암호처럼 보이므로 규칙을 알아 두면 좋습니다.

| 표기 | 뜻 | 규칙 |
|---|---|---|
| `[B` | `byte[]` | `[`가 배열, `B`가 byte |
| `[I` | `int[]` | `I`가 int |
| `[C` | `char[]` | `C`가 char |
| `[J` | `long[]` | `J`가 long (`L`이 아님 — 참조 타입과 겹치므로) |
| `[Ljava.lang.String;` | `String[]` | `L…;`이 참조 타입 |
| `[[I` | `int[][]` | `[`가 겹치면 다차원 |

기본 타입 문자는 `B`(byte) `C`(char) `D`(double) `F`(float) `I`(int) `J`(long) `S`(short) `Z`(boolean)입니다. `Z`가 boolean인 것과 `J`가 long인 것만 기억하면 나머지는 첫 글자입니다.

### 어떻게 읽나 — 절대량이 아니라 diff

상위 목록은 대개 `[B`(바이트 배열)와 `String`입니다. 이건 어느 애플리케이션이나 비슷합니다. **판정은 시작·종료 diff로 합니다.**

위 소크의 결과는 "바이트 배열 +0.6MB 외 전부 증가 없음"이었습니다. 바이트 배열은 네트워크 수신 버퍼와 전문 데이터라 부하 중 변동이 정상 범위입니다.

만약 이런 결과가 나오면 의심합니다.

| 늘어난 클래스 | 의심할 것 |
|---|---|
| `ConcurrentHashMap$Node`가 수만 개씩 | 어떤 맵에 항목이 쌓인다 — 캐시에서 안 빼거나, 처리 완료 후 정리 안 함 |
| 사용자 정의 도메인 객체 | 그 객체를 담고 있는 컬렉션 추적 |
| `java.lang.Class`가 계속 증가 | 클래스로더 누수 (NMT의 Metaspace와 함께 확인) |
| `Thread` 관련 객체 | 스레드 누수 |

## 8. 어디서 만들어졌는지 보는 도구 — JFR

### 왜 필요한가

히스토그램은 "무엇이 쌓이나"까지 답합니다. 마지막 질문은 **"어디서 만들어졌나"** 입니다. 코드의 어느 줄이 그 객체를 만들었는지 알아야 고칠 수 있습니다.

Java Flight Recorder(JFR)의 `jdk.OldObjectSample` 이벤트가 이 질문에 답합니다. **오래 살아남은 객체를 할당 스택 트레이스와 함께 표본화**합니다.

### 어떻게 켜나

두 가지 방법이 있습니다.

```bash
# 방법 1: 기동 플래그
java -XX:StartFlightRecording=name=rec,settings=profile,maxsize=250m -jar app.jar

# 방법 2: 실행 중에 jcmd (권장)
jcmd <pid> JFR.start name=rec settings=profile maxsize=250m disk=true
jcmd <pid> JFR.dump  name=rec filename=dump.jfr
```

**실행 중 시작을 권하는 이유**는 기동 구간의 워밍업 이벤트로 기록을 채우지 않기 위해서입니다. 클래스 로딩과 JIT가 몰리는 초반은 정상 거동인데도 이벤트가 폭증합니다.

옵션 선택의 감각을 정리합니다.

| 옵션 | 값 | 언제 |
|---|---|---|
| `settings` | `default` | 장시간 실행. 오버헤드 낮음 |
| | `profile` | 짧은 진단. 표본 밀도 높지만 오버헤드 큼 |
| `maxsize` | `250m` 등 | 넘으면 오래된 이벤트를 버린다. 장시간 실행이 디스크를 채우지 않게 |
| `disk` | `true` | 디스크에 흘려 쓴다. 프로세스가 죽어도 앞부분이 남는다 |

**성능을 측정하는 실행에 `settings=profile`을 켜면 안 됩니다.** 계측 부하가 측정값에 섞입니다. 성능 실행과 진단 실행을 분리하는 것이 원칙입니다.

### 무엇을 보나

| 이벤트 | 무엇을 알려주나 | 용도 |
|---|---|---|
| `jdk.OldObjectSample` | 오래 살아남은 객체 + **할당 스택 트레이스** | **누수 지점 특정** |
| `jdk.GCHeapSummary` | GC 시점 힙 요약 | GC 로그와 교차 확인 |
| `jdk.ObjectAllocationSample` | 할당 핫스팟 | 누수보다 생성·폐기 회전 분석 |
| `jdk.ThreadStart` / `jdk.ThreadEnd` | 스레드 생성·종료 | 생성만 많고 종료가 적으면 누적 |

### 어떻게 읽나

```bash
# 커맨드라인
jfr print --events jdk.OldObjectSample dump.jfr

# GUI
JDK Mission Control → Memory → Old Object Sample
```

### 실측 예시 — 나이를 보면 답이 나온다

앞서 본 73분 소크의 결과입니다.

```
OldObjectSample 27건, 대부분 objectAge "1h12m"
```

**나이가 1시간 12분**입니다. 시험 전체 길이(73분)와 거의 같습니다. 즉 **기동 시부터 상주하던 객체**입니다.

누수라면 나이 분포가 다르게 나옵니다.

| 나이 분포 | 해석 |
|---|---|
| 전부 실행 길이와 비슷 | 기동 상주분. **누수 아님** |
| 다양하게 흩어짐 | 계속 새로 쌓이고 있다 — 누수 의심 |
| 최근 것이 많음 | 최근 유입분이 안 빠진다 |

그리고 스택 트레이스가 함께 있으니 **의심 객체가 어느 코드에서 만들어졌는지**를 바로 볼 수 있습니다. 이것이 히스토그램에는 없는 정보입니다.

## 9. 신호 여덟 개를 교차하는 판정 절차

지금까지 본 도구를 정리하면 각 도구가 답하는 질문이 다릅니다.

```
회수 후 힙 게이지 (폴링)  ── "총량이 늘었나?"  단, 갱신 시점에 좌우됨
        │
GC 로그 (이벤트 기록)     ── "정말 늘었나?"    누락 없는 정답지
        │  늘었다면
클래스 히스토그램         ── "무엇이 늘었나?"
        │  힙은 평평한데 프로세스가 오른다면
NMT                       ── "힙 밖 어느 영역인가?"
        │  무엇인지 알았다면
JFR OldObjectSample       ── "어디서 만들어졌나?"
```

한 도구만 켜면 그 질문에서 멈춥니다. 그리고 **판정은 여러 신호가 같은 방향을 가리킬 때만** 내립니다.

실제 판정에 쓰인 신호 여덟 개를 예로 들면 이렇습니다.

| # | 신호 | 관측 예시 | 이 신호가 배제하는 것 |
|---|---|---|---|
| 1 | 회수 후 힙 바닥선 (폴링) | 60분간 20.9 → 19.0MB | 힙 누수 |
| 2 | GC 로그의 회수 후 값 | Mixed/Full 바닥 20 → 18MB | 폴링 누락·게이지 지연 |
| 3 | 강제 회수 후 잔량 | `18M->18M`, 두 번 연속 같은 바닥 | 보유 누수 |
| 4 | 클래스별 인스턴스 diff | 바이트 배열 +0.6MB 외 증가 없음 | 특정 클래스 축적 |
| 5 | NMT 카테고리 diff | Total +7.4MB, 주도는 JIT 코드 | 힙 밖 누수 |
| 6 | 플랫폼 스레드 수 | 23~26으로 불변 | 스레드·풀 누수 |
| 7 | JFR 장수명 객체 표본 | 27건, 나이가 실행 길이와 같음 | 새로 눌러앉은 것 |
| 8 | 대기 건수의 복귀 | 부하 정지마다 0으로 복귀 | 처리 티켓·permit 누수 |

**8번을 특히 강조할 만합니다.** 처리 대기열이 있는 애플리케이션이라면, 부하를 멈춘 뒤 대기가 0으로 돌아오는지 봐야 합니다.

```
부하 정지 후
  대기 = 0  AND  회수 후 힙 = 바닥 복귀    → 건강
  대기 ≠ 0  AND  회수 후 힙 = 미복귀       → 티켓·permit 누수
  대기 = 0  BUT  회수 후 힙 = 미복귀       → 다른 곳에 누수
```

**둘이 함께 움직여야 합니다.** 대기 항목을 담는 내부 맵이 비워지지 않으면 그 항목들이 힙에 눌러앉고, 두 지표가 함께 미복귀 상태가 됩니다.

### 판정 요약표

| 관찰 | 결론 |
|---|---|
| 회수 후 바닥 평평 + 폭주 후 복귀 + NMT·스레드 평탄 | 시험 범위 내 누수 없음 |
| 회수 후 바닥이 우상향 | 힙 누수 → 히스토그램 diff → JFR로 지점 특정 |
| 회수 후 바닥 평평인데 RSS 상승 | 네이티브 누수 → NMT 카테고리 확인 |
| 부하 정지 후 대기 ≠ 0 이고 힙 미복귀 | 티켓·permit 누수 |
| 플랫폼 스레드 단조 증가 | 스레드·풀 누수 |
| Metaspace 단조 증가 | 클래스로더 누수 |
| `used heap` 톱니 고점만 상승, 저점 평평 | **정상** |
| `Pause Full`이 `18M->18M`, 두 번 연속 같음 | 그 값이 상주분. 확정 |

## 10. 측정기가 실제로 누수를 잡는지 먼저 확인한다

여기까지 잘 해도 남는 문제가 있습니다.

> 결과가 "누수 없음"으로 나왔을 때, 그것이 **정말 없는 것인지** 아니면 **내 측정기가 못 잡는 것인지** 어떻게 아는가?

이 질문에 답하지 않으면 "없다"와 "못 찾았다"가 구별되지 않습니다.

### 방법 — 가짜 누수를 일부러 넣어 본다

측정 데이터에 **인위적인 증가를 주입**하고, 판정 절차가 그것을 잡아내는지 셉니다. 통계에서 말하는 검정력(power) 측정입니다.

실제로 이렇게 나왔습니다.

| 주입한 증가율 | 검출률 |
|---:|---:|
| 시간당 0MB (증가 없음) | 0.0585 |
| 시간당 0.1MB | 1.00 |
| 시간당 0.25MB | 1.00 |
| 시간당 0.5MB | 1.00 |
| 시간당 1.0MB | 1.00 |
| 시간당 2.0MB | 1.00 |

읽는 법입니다.

- **증가가 없을 때 5.85%로 잘못 경보**합니다. 거짓양성률을 0.05로 설정했으니 부합합니다
- **시간당 0.1MB부터는 빠짐없이 검출**합니다. 이것이 **검출 하한**입니다

이제 관측값과 비교할 수 있습니다. 같은 실행의 실제 기울기는 **시간당 0.0013MB**였습니다.

```
검출 하한  0.1     MB/시간
관측값     0.0013  MB/시간
비율       약 1/77
```

**"안 늘었다"가 아니라 "시간당 0.1MB 이상이면 반드시 잡는 측정기로 쟀고, 관측값은 그 한계의 1/77이었다"** 라고 말할 수 있습니다. 결론의 크기가 정해집니다.

### 결론에 범위를 함께 적는다

검출력을 재도 **유한한 시간 동안 잰 것**이라는 한계는 남습니다. 12시간을 재고 "누수 없음"이라 하면, 시간당 0.001MB씩 새는 경우는 못 봤을 수 있습니다.

그래서 판정문에 범위를 함께 적는 습관이 좋습니다.

> 유한한 실행 시간 안에서의 상한일 뿐이며, 통과가 모든 누수의 부재를 뜻하지는 않는다.

### 자동 판정이 실패를 냈을 때 — 무시하지 말고 귀속시킨다

여러 신호를 자동으로 검사하면 일부가 "증가 가능성 있음"으로 걸릴 수 있습니다. 이때 두 가지 대응이 있습니다.

| 대응 | 결과 |
|---|---|
| 임계를 완화해 통과시킨다 | 검사가 무력해진다 |
| **각 의심 신호의 원인을 밝힌다** | 설명이 붙은 통과 |

후자가 맞습니다. 앞서 본 12시간 실행에서 자동 판정의 1차 결과는 **실패**였습니다. 두 신호(회수 후 힙, 프로세스 점유 메모리)의 신뢰구간 하한이 양수였기 때문입니다. 각각의 원인을 추적해 설명을 붙인 뒤에야 통과로 확정됐고, **미해결로 남은 의심 신호는 0건**이었습니다.

통과 조건을 이렇게 구성하면 의심을 무시할 수 없습니다.

```
① 종료 시 증거가 유효하게 남았다
② 장기 실행 증거로 쓸 자격이 있다
③ 의심 신호가 전부 원인까지 귀속됐다      ← 무시하면 여기서 걸린다
④ 확정 누수 신호가 없다
⑤ 상계가 기준 미만이고 검출력이 확보됐다
```

## 11. 가상 스레드가 뒤집는 상식

Java 21부터 정식 도입된 가상 스레드(virtual thread)는 기존 진단 상식 두 개를 뒤집습니다. 모르면 정반대로 읽습니다.

### ① 스레드 수 지표가 가상 스레드를 세지 않는다

`jvm.threads.live`(Micrometer), `ThreadMXBean.getThreadCount()`는 **플랫폼 스레드만** 셉니다.

그래서 가상 스레드 기반 애플리케이션에서는 이런 그림이 나옵니다.

```
초당 2,000건 요청 처리 중
  jvm.threads.live = 24        ← 부하와 무관하게 낮고 일정
```

이걸 보고 "일을 안 하고 있다"고 읽으면 틀립니다. 요청마다 가상 스레드가 만들어지지만 그 값에 안 잡히는 것입니다.

**진단 함의**: 가상 스레드가 누적되는 상황을 스레드 수 지표로는 못 봅니다.

### ② 가상 스레드 스택은 네이티브가 아니라 힙에 있다

플랫폼 스레드의 스택은 OS가 잡는 네이티브 메모리입니다(기본 1MB 수준). NMT의 `Thread` 카테고리에 잡힙니다.

**가상 스레드의 스택은 힙의 객체(`StackChunk`)로 삽니다.**

| 스레드 종류 | 스택 위치 | 어디서 보이나 |
|---|---|---|
| 플랫폼 스레드 | 네이티브 | NMT `Thread`, `jvm.threads.live` |
| 가상 스레드 | **힙** | **회수 후 힙 live set** |
| carrier 스레드 | 네이티브 | NMT `Thread` (≈ CPU 코어 수로 유지) |

**진단 함의**: 가상 스레드가 폭증하면 NMT `Thread`가 아니라 **힙 live set이 오릅니다.** 
"힙이 늘었는데 무엇이 늘었는지 모르겠다"면 히스토그램에서 `StackChunk` 관련 항목을 확인해 보십시오.

그리고 carrier 스레드 수(가상 스레드를 실제로 실행하는 플랫폼 스레드)는 CPU 코어 수 수준으로 유지되는 것이 정상입니다. 이 값이 늘어난다면 가상 스레드가 블로킹 호출에 붙들려 carrier를 점유하고 있을 가능성을 봅니다.

## 12. 자주 하는 오판 일곱 가지

| 오판 | 왜 틀렸나 | 어떻게 확인하나 |
|---|---|---|
| "used heap이 오르니 누수" | 쓰레기 포함. 회수하면 준다 | 회수 후 값(live set)의 바닥선을 본다 |
| "RSS가 안 줄어드니 누수" | JVM은 OS에 메모리를 잘 반납하지 않는다. 힙 안에서 재사용한다 | NMT `committed` diff와 힙 live set을 함께 본다 |
| "톱니가 크니 문제" | 톱니 크기는 할당률을 반영. 저점이 중요 | 저점만 이어서 본다 |
| "Young GC 회수 후 값이 오른다" | old로 승격된 것이 안 치워진 상태일 수 있다 | Mixed/Full의 회수 후 값으로 판정 |
| "유휴 구간에 메모리가 안 빠진다" | 일이 없으면 GC가 안 돈다. 게이지도 갱신 안 된다 | 강제 회수를 걸고 다시 본다 |
| "대기열이 메모리를 먹으니 누수" | 처리 대기 중인 데이터는 설계된 보유 | 부하 정지 후 대기가 0으로 가는지 본다 |
| "스레드 수가 일정하니 부하가 없다" | 가상 스레드는 그 지표에 안 잡힌다 | 요청 처리량 지표를 함께 본다 |

두 번째 항목을 조금 더 풀어 둡니다. **JVM은 한 번 확보한 힙을 OS에 잘 돌려주지 않습니다.** `-Xms`와 `-Xmx`를 같게 잡으면 아예 처음부터 최대치를 잡고 시작합니다. 그래서 RSS는 높은 채로 평평하게 유지되는 것이 정상이고, RSS로 누수를 보려는 시도는 대개 헛돕니다.

RSS가 **힙 최대치를 넘어서** 계속 오른다면 그때는 힙 밖을 봅니다. NMT가 그 자리에 필요합니다.

## 13. 실습 — 한 시간짜리 소크 테스트 만들기

지금까지의 내용을 하나로 엮어, 직접 돌려 볼 수 있는 최소 구성을 정리합니다.

### 준비 — 플래그

```bash
java \
  -Xms512m -Xmx512m \
  -XX:+UseG1GC \
  -XX:NativeMemoryTracking=summary \
  -Xlog:gc,gc+heap=info:file=gc.log:time,uptime,level,tags:filecount=20,filesize=50m \
  -jar app.jar
```

각 플래그의 이유입니다.

| 플래그 | 이유 |
|---|---|
| `-Xms = -Xmx` | 힙 크기가 변하면 지표 해석이 복잡해진다. 고정하면 `committed`가 상수여야 한다는 검증점이 생긴다 |
| 힙을 **작게** (512MB) | old 영역 수집을 자주 유도해 live set 게이지가 갱신되게 한다. 힙이 크면 Full GC가 안 돌아 판정이 어렵다 |
| `NativeMemoryTracking` | 기동 플래그라 나중에 켤 수 없다 |
| `-Xlog:gc` | 정답지 |

### 실행 절차

```
① 기준선 스냅샷
   jcmd <pid> VM.native_memory summary    > nmt-start.log
   jcmd <pid> GC.class_histogram          > histo-start.log

② 부하 걸기 (예: 60분간 일정 속도)
   그 사이 10초 간격으로 지표 폴링 → metrics.jsonl
   5분 간격으로 NMT·히스토그램 스냅샷

③ 부하 정지 후 유휴 구간 확보 (필수)
   대기 지표가 0으로 가는지 확인

④ 강제 회수 두 번
   jcmd <pid> GC.class_histogram          > histo-end-1.log
   jcmd <pid> GC.class_histogram          > histo-end-2.log
   → GC 로그에 Pause Full 두 줄이 남는다

⑤ 종료 스냅샷
   jcmd <pid> VM.native_memory summary    > nmt-end.log
   jcmd <pid> JFR.dump name=rec filename=dump.jfr
```

③이 빠지면 판정이 불가능합니다. **부하 중에는 보유와 누수를 구별할 수 없습니다.**

### 판정 체크리스트

```
□ GC 로그의 Mixed/Full 회수 후 값 — 바닥선이 평평한가?
□ 강제 회수 두 줄 — 같은 바닥이 나오는가? (X->X 형태)
□ 그 바닥이 기동 시점보다 낮거나 같은가?
□ NMT diff — 오른 카테고리가 무엇인가? 수렴하는 종류인가?
□ 히스토그램 diff — 특정 클래스가 계속 늘었는가?
□ 플랫폼 스레드 수 — 부하와 무관하게 늘었는가?
□ JFR 장수명 객체 — 나이 분포가 기동 상주분인가?
□ 부하 정지 후 대기 지표가 0으로 복귀했는가?
□ (가능하면) 인위적 증가를 주입해 검출 하한을 쟀는가?
```

여덟 개가 모두 같은 방향을 가리킬 때만 "이 시험 범위에서 누수 신호 없음"이라고 씁니다. **"누수 없음"이 아니라 "이 시험 범위에서"** 라는 한정을 붙이는 것이 정직한 서술입니다.
