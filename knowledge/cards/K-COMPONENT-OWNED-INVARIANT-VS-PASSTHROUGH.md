# K-COMPONENT-OWNED-INVARIANT-VS-PASSTHROUGH

## 1) 이 카드가 답하는 질문

계층형 구조(진입점 / 유스케이스 / 업무 규칙 / 지속성)를 가진 코드베이스에서 아래 질문이 반복됩니다.

"CRUD가 대부분인 업무에서, 등록·수정·삭제를 처리하는 공통 컴포넌트를 하나 잘 만들어 각 서비스가 주입받아 쓰는 것이 좋습니까? 그리고 새 컴포넌트를 만들 때 그것이 존재할 근거를 무엇으로 판정합니까? 위임만 하는 얇은 층은 언제 지워야 하고 언제 남겨야 합니까?"

여기서 답해야 하는 것은 "재사용이 좋은가 나쁜가"가 아닙니다. **재사용되어야 하는 단위와 규칙을 소유해야 하는 단위가 서로 다른 층에 있다**는 점을 판정 기준으로 고정하는 것입니다.

---

## 2) 배경: 왜 이 문제가 실무에서 비싸게 터지는가

비용은 "규칙이 사라질 때"가 아니라 **"규칙이 숨을 때"** 발생합니다. 이 구분이 중요합니다.

임의의 필드 묶음을 받아 그대로 저장 계층에 전달하는 공통 수정 컴포넌트를 만들면, 그 컴포넌트는 아무 불변식도 지키지 않습니다. 그러면 원래 지켜야 했던 규칙(존재 확인, 변경 허용 필드 제한, 이전 값 감사, 상태 전이 허용)이 없어지는 것이 아니라, 호출부의 조건 분기 안으로 흩어집니다. 흩어진 규칙은 두 가지 방식으로 비싸게 터집니다.

첫째, 어떤 경로에서 어떤 규칙이 적용되는지 아무도 알 수 없게 됩니다. Ruby on Rails 대규모 코드베이스의 대표적 붕괴 모드로 알려진 콜백 지옥(callback hell)이 정확히 이 형태입니다. 저장 훅에 규칙을 붙이다 보면, 어떤 저장 경로가 어떤 규칙을 통과하는지 추적이 불가능해집니다.

둘째, 층이 하나 더 늘었는데 경계는 늘지 않습니다. 위임만 하는 층은 Fowler가 『Refactoring』에서 Middle Man 냄새로 분류한 것이고, 처방은 Remove Middle Man입니다. 층이 늘면 변경할 때 항상 두 파일을 같이 고쳐야 하는데, 그 대가로 얻는 격리는 없습니다.

그리고 이름이 의도를 담지 않으면 판단 자체가 불가능해집니다. `Update`라는 이름은 "무엇이 왜 바뀌는가"를 말하지 않으므로, 그 지점에서 어떤 규칙을 적용해야 하는지 결정할 근거가 없습니다. 커맨드 이름이 업무 의도여야 한다는 규율(CQRS 계열에서 intent loss로 불리는 문제)과, Udi Dahan이 CRUD 화면을 비판할 때 지적한 지점이 같습니다. 화면이 "저장" 하나만 보내면 서버는 무엇이 왜 바뀌었는지 모르고, 그러면 동시성 해결·감사·규칙 적용이 모두 불가능해집니다.

## 3) 핵심 제어점(왜 하필 이 축인가)

제어점 3개로 축을 좁힙니다. 셋 다 코드에서 즉시 관측 가능하고, 각각 서로 다른 실패와 연결됩니다.

첫째는 **소유물의 종류**입니다. 어떤 단위든 존재 근거는 "무엇을 지키는가"이고, 답은 셋 중 하나입니다. 업무 규칙을 지키거나, 실행 경계(트랜잭션·연결 대상·감사 지점)를 지키거나, 아무것도 지키지 않습니다. 셋째면 그 단위는 만들지 않거나 제거 후보입니다. 이 셋을 명시하지 않고 "규칙이 있는가"로 이분하면, 실행 경계를 소유하는 정당한 얇은 층까지 함께 제거하게 됩니다.

둘째는 **재사용 단위와 규칙 단위의 층 분리**입니다. `특정 테이블의 일부 컬럼을 조건에 맞게 갱신한다`는 것은 지속성 원시연산이고, 이것은 재사용되어야 합니다. `연락처가 바뀌면 존재를 확인하고 이전 값을 감사에 남기고 상태를 전이한다`는 것은 유스케이스이고, 이것은 재사용되지 않습니다. 각각 이름이 다르기 때문입니다. 두 개를 같은 층에 겹치면 그 층은 아래층의 별칭이 됩니다.

셋째는 **이름이 변경 의도를 담는가**입니다. 이름에 "무엇이 바뀌는지"가 들어가면 그 단위가 지켜야 할 규칙이 자동으로 결정됩니다. 반대로 이름을 지을 수 없다면 그 단위가 필요하지 않다는 신호입니다. 이름은 문서가 아니라 판정 도구입니다.

## 4) 기본 결론(기본값)과 선택 이유

기본값은 다음 셋입니다.

첫째, **새 단위는 소유물이 있을 때만 만듭니다.** 소유물 질문에 "없음"이 답이면 만들지 않고, 이미 있으면 제거 후보로 다룹니다. 만들 근거가 있는 조건은 실무적으로 셋 중 하나입니다. 둘 이상의 호출자가 같은 규칙을 실제로 필요로 하거나(장래 가능성은 근거가 아닙니다), 규칙이 여러 단계의 상태 전이·불변식을 소유해 호출자에 두면 호출자가 비대해지거나, 실행 경계를 소유해야 합니다.

둘째, **CRUD 원시연산의 재사용은 지속성 층에서 합니다.** 조건부 갱신을 지원하는 저장 계층 문장을 잘 만들어 두는 것이 정답이고, 그 위에 공통 수정 컴포넌트를 얹는 것은 층만 늘립니다. 다만 부분 갱신 원시연산에는 함정이 둘 있습니다. 갱신 절이 비어 문법 오류가 되는 것과 허용되지 않은 필드가 주입되는 것입니다. 그래서 **허용 필드 집합을 호출자(유스케이스 단위)가 소유해야** 합니다. 역설적으로 이 요구가 유스케이스 단위에 실제 역할을 줍니다. "이 유스케이스에서 바꿀 수 있는 필드 집합"은 진짜 업무 규칙입니다.

셋째, **이름에 변경 의도를 넣습니다.** `UserUpdate`가 아니라 `ChangeUserPhone`입니다. 그리고 등록과 수정을 upsert 하나로 합치지 않습니다. 두 규칙 집합이 다르기 때문입니다. 등록은 중복 없음·필수값 전량·초기 상태를 지키고, 수정은 존재함·변경 허용 필드·이전 값 감사·상태 전이 허용을 지킵니다. 합치면 두 집합의 합집합이 `if (exists)` 분기 안에 들어가고, 그것이 규칙이 숨는 경로입니다. 그리고 멱등성 의미가 지워집니다. 같은 등록 요청이 두 번 왔을 때 거부해야 하는지 갱신해야 하는지는 업무 결정인데, upsert는 후자를 코드 기본값으로 박습니다.

정당한 공통화는 따로 있습니다. 감사 컬럼 채우기, 일련번호 발급, 처리 이력 기록처럼 **업무 규칙이 아니라 기술 관심사**인 것은 공통 컴포넌트로 두는 것이 맞습니다. 구분선은 "업무 규칙인가 기술 규칙인가"입니다.

## 5) 핵심 용어 정의(이 카드 기준)

**소유 불변식(owned invariant)**은 그 단위가 없으면 깨지는 성질입니다. 업무 규칙(도메인이 요구하는 제약)과 실행 경계(트랜잭션 범위·연결 대상 전환·감사 지점) 둘을 포함하고, 단순 위임·타입 변환·필드 복사는 포함하지 않습니다.

**pass-through 단위**는 입력의 모든 필드를 변형·검증 없이 하위 호출로 전달하고, 그 외에 분기·예외·불변식 검사를 갖지 않는 단위입니다. 이 카드는 얇음 자체를 문제로 보지 않고, 얇으면서 소유물이 없는 상태만 문제로 봅니다.

**지속성 원시연산**은 저장 계층에서 한 번 잘 정의하면 여러 유스케이스가 그대로 쓰는 연산입니다. "이 테이블의 지정된 컬럼을 조건에 따라 갱신한다"가 그 예입니다.

**유스케이스**는 외부에서 요청되는 하나의 업무 의도이며, 이름이 곧 그 의도입니다. 유스케이스는 재사용 단위가 아닙니다. 두 유스케이스가 같아 보이면 대개 둘 중 하나의 규칙이 아직 드러나지 않은 상태입니다.

**intent loss**는 요청이 "무엇이 왜 바뀌는가"를 잃고 "무엇이 지금 이 값이다"로만 표현되는 상태입니다. 이 상태에서는 규칙 적용·감사·동시성 해결이 모두 불가능해집니다.

## 6) 메커니즘(입력 -> 변환 규칙 -> 산출물 -> 소비자)

입력은 "새 단위를 만들려는 충동"입니다. 반복되는 코드를 발견했거나, 호출자가 길어졌거나, 계층 규칙이 층을 요구하는 상황입니다.

변환은 네 단계입니다. 첫째, 소유물을 셋 중 하나로 판정합니다(업무 규칙 / 실행 경계 / 없음). 둘째, "없음"이면 만들지 않고 종료합니다. 이때 반복 코드는 지속성 원시연산이나 기술 헬퍼로 흡수합니다. 셋째, 소유물이 있으면 그것이 업무 규칙인지 기술 관심사인지로 층을 결정합니다. 업무 규칙은 유스케이스 층, 기술 관심사는 공통 컴포넌트입니다. 넷째, 이름에 소유물을 반영합니다. 이름을 지을 수 없으면 첫째 판정이 틀렸다는 뜻이므로 되돌아갑니다.

산출물은 단위 하나 또는 "단위 없음"입니다. "단위 없음"이 정당한 산출물이라는 점이 이 메커니즘의 핵심입니다.

소비자는 둘입니다. 호출부(이 단위를 주입받아 조립하는 코드)와 리뷰어(이 단위가 존재할 근거를 판정하는 사람)입니다.

이 흐름에서 넷째 단계가 첫째 단계의 검산으로 작동합니다. 이름이 안 나오면 소유물 판정을 다시 하게 되므로, 이름 짓기를 마지막에 두는 것이 아니라 판정의 일부로 두는 것이 중요합니다.

## 7) 조건 변경 시 예측(무엇이 깨지고 어떻게 관측되는가)

### 7.1 소유물이 "없음"인데 단위를 만들면

위임만 하는 층이 생깁니다. 이 층은 격리를 제공하지 않으면서 변경 비용을 늘립니다.

관측 신호는 셋입니다. 첫째, 그 단위의 메서드 본문에서 하위 호출을 제거하면 남는 코드가 없습니다. 둘째, 그 단위를 고칠 때 아래층 파일을 항상 같이 고칩니다(커밋 이력에서 두 파일의 동반 변경률을 세면 나옵니다). 셋째, 그 단위에 대한 테스트가 mock 호출 검증만으로 이루어져 있습니다. 검증할 관찰 결과가 없기 때문입니다.

### 7.2 재사용을 업무 층에서 하면(공통 CRUD 컴포넌트)

규칙이 호출부와 공통 컴포넌트의 조건 분기로 흩어집니다.

관측 신호는 한 진입점의 분기 수 증가입니다. 특히 `if (exists)`, `if (params.containsKey(...))` 형태의 분기가 늘어나는지 보십시오. 그리고 감사 요구가 분기별로 갈리는 순간이 결정적 신호입니다. 등록 경로에는 이전 값이 없고 수정 경로에는 있어야 하므로, 하나의 진입점이 두 감사 정책을 갖게 됩니다. 이 상태에서 감사 누락은 특정 분기에서만 나타나므로 발견이 늦습니다.

### 7.3 이름이 의도를 담지 않으면

같은 진입점에 서로 다른 유스케이스가 파라미터 값으로 갈립니다.

관측 신호는 진입점의 입력 타입이 넓어지는 것입니다. 임의 키를 받는 맵이나 대부분이 선택 필드인 DTO가 나타나면 이미 여러 유스케이스가 합쳐진 상태입니다. 또 하나는 그 진입점의 테스트 이름입니다. 테스트 이름이 "연락처_변경시_..."처럼 유스케이스로 읽히는데 대상 클래스 이름은 `Update`라면, 이름이 한 단계 뒤처져 있습니다.

### 7.4 실행 경계 갈래를 없애고 "규칙 없으면 제거"로 이분하면

트랜잭션 경계나 연결 대상 전환을 소유한 얇은 층이 함께 제거됩니다. 이 실패는 컴파일과 단위 테스트를 모두 통과하고 운영에서만 드러나므로 가장 비쌉니다.

관측 신호는 제거 후에 나타나는 트랜잭션 범위 변화입니다. 롤백 범위가 달라지거나, 중첩 트랜잭션 전파 설정이 사라지거나, 다른 연결 대상으로 가야 할 조회가 기본 대상으로 갑니다. 그래서 얇은 층을 제거하기 전에 "이 층이 지키는 실행 경로 의미가 무엇인가"를 먼저 적고 동등 동작을 확인해야 합니다.

## 8) 코드 예시

### 8.1 나쁜 패턴 — 임의 필드를 받는 공통 수정 컴포넌트

```java
// 모든 서비스가 주입받아 쓰는 "공통 수정" 컴포넌트
public class GenericUpdate {
    private final UserMapper userMapper;

    public int execute(Map<String, Object> params) {
        return userMapper.updateDynamic(params);   // 받은 키를 그대로 SET 절로
    }
}

// 호출부: 규칙이 여기 분기로 흩어진다
if (userMapper.selectOne(id) == null) {
    genericUpdate.execute(insertParams);          // 사실은 등록
} else {
    genericUpdate.execute(updateParams);          // 사실은 수정
}
```

`GenericUpdate`는 아무 불변식도 지키지 않습니다. 허용 필드 제한이 없어 호출부가 실수로 넣은 키가 그대로 반영되고, 이전 값 감사 지점이 없고, 등록·수정 판단이 호출부 분기로 새어 나갑니다. `execute`에서 `userMapper` 호출을 지우면 남는 코드가 없다는 점이 이 단위가 껍데기라는 직접 증거입니다.

### 8.2 권장 패턴 — 유스케이스가 규칙을 소유하고 원시연산만 재사용

```java
// 이름이 무엇이 바뀌는지 말한다. 그래서 지킬 규칙이 결정된다.
public class ChangeUserPhone {
    // 이 유스케이스에서 바꿀 수 있는 필드 집합 = 업무 규칙
    private static final Set<String> MUTABLE = Set.of("phone_no", "phone_vrf_yn");

    private final UserMapper userMapper;
    private final AuditRecorder auditRecorder;   // 기술 관심사는 공통화가 정당

    public void execute(String userId, String newPhone) {
        User before = userMapper.selectForUpdate(userId);
        if (before == null) {
            throw new IllegalStateException("존재하지 않는 사용자: " + userId);
        }
        if (newPhone.equals(before.phoneNo())) {
            return;                               // 변경 없음은 갱신도 감사도 하지 않는다
        }

        Map<String, Object> patch = Map.of("phone_no", newPhone, "phone_vrf_yn", "N");
        assertOnlyMutable(patch);                 // 허용 필드 밖의 키를 거부

        userMapper.updateDynamic(userId, patch);  // 원시연산은 재사용
        auditRecorder.record(userId, "PHONE", before.phoneNo(), newPhone);
    }

    private void assertOnlyMutable(Map<String, Object> patch) {
        if (patch.isEmpty()) {
            throw new IllegalArgumentException("갱신 대상 필드가 없음");
        }
        for (String key : patch.keySet()) {
            if (!MUTABLE.contains(key)) {
                throw new IllegalArgumentException("이 유스케이스에서 변경 불가한 필드: " + key);
            }
        }
    }
}
```

등록은 별도 유스케이스(`RegisterUser`)로 둡니다. 두 유스케이스는 `UserMapper.updateDynamic`과 `insertOne`이라는 원시연산을 공유하지만, 규칙은 공유하지 않습니다. 재사용은 아래층에서 일어나고 규칙은 위층이 소유합니다.

### 8.3 권장 패턴 — 소유물이 실행 경계인 얇은 층

```java
// 본문이 한 줄이지만 소유물이 있다: 별도 트랜잭션 경계
public class ReserveSequenceInNewTransaction {
    private final SequenceMapper sequenceMapper;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public long execute(String key) {
        return sequenceMapper.nextValue(key);   // 바깥 롤백에 발급된 번호가 되돌아가지 않게
    }
}
```

이 단위는 위임만 하지만 제거하면 동작이 달라집니다. 소유물 질문에 "실행 경계 — 별도 트랜잭션"으로 답할 수 있으므로 정당합니다. 이 갈래를 남겨두지 않으면 `GenericUpdate`와 이 클래스가 같은 판정을 받게 됩니다.

## 9) 최소 실험(검증)

### 9.1 실험 1 — 껍데기 판정

의심되는 단위의 메서드에서 하위 호출 한 줄을 주석 처리하고 컴파일하십시오.

기대 결과: 남는 코드가 반환문뿐이거나, 반환 타입 때문에 컴파일이 깨지는 것 외에 아무 의미도 남지 않으면 그 단위는 pass-through입니다. 반대로 검증·분기·상태 전이·감사 호출이 남으면 소유물이 있습니다. 이 실험은 "얇다"는 인상을 관측으로 바꿉니다.

### 9.2 실험 2 — 소유 주장의 증명(실패 관측)

그 단위가 소유한다고 주장한 규칙 하나를 코드에서 제거하고 테스트를 실행하십시오. 예를 들어 `assertOnlyMutable` 호출을 지웁니다.

기대 결과: 특정 테스트가 red가 되어야 합니다. `IllegalArgumentException: 이 유스케이스에서 변경 불가한 필드: role_cd` 같은 기대 예외가 나오지 않게 되는 테스트가 실패해야 합니다. **아무 테스트도 red가 되지 않으면 그 규칙은 소유되고 있지 않습니다.** 코드에 있다는 사실은 소유의 증거가 아니고, 깨질 때 관측된다는 사실이 증거입니다. 확인 후 원복합니다.

### 9.3 실험 3 — 임의 필드 주입의 결과 관측(실패 관측)

임의 키를 받는 공통 수정 경로에 허용되지 않은 키(`role_cd` 등)를 넣어 호출하십시오.

기대 결과: 두 가지 중 하나가 나옵니다. 조용히 반영되어 권한 필드가 바뀌거나, 저장 계층에서 컬럼 불일치 예외가 납니다. 어느 쪽이든 문제이며, 전자가 더 나쁩니다. 이 실험은 "허용 필드 집합을 누가 소유해야 하는가"를 추상 논의에서 관측으로 끌어내립니다. 그리고 빈 패치를 넣어 갱신 절이 비는 경우도 함께 확인하십시오.

## 10) 트레이드오프 / 대안 / Variants

### 10.1 트레이드오프 — 유스케이스 단위는 개수가 늘어난다

`ChangeUserPhone`, `ChangeUserAddress`, `SuspendUser`처럼 나누면 파일 수가 늘어납니다. 이것은 사실이며 부정할 필요가 없습니다. 완화되는 부분은 탐색 비용입니다. 이름이 업무 의도이므로 "연락처 변경이 어디서 처리되나"를 이름으로 찾을 수 있고, 변경 반경도 한 파일에 머무릅니다. 대가는 초기 작성량과 파일 수이고, 이득은 변경 반경과 탐색 비용입니다. 유스케이스가 실제로 여러 개인데 하나로 뭉쳐 두면 파일 수는 줄지만 그 하나가 계속 커집니다.

### 10.2 트레이드오프 — 소유물 질문 자체의 비용

모든 클래스마다 이 질문을 하면 의례가 됩니다. 완화책은 트리거를 좁히는 것입니다. 이 질문은 답이 "없음"일 수 있는 순간에만 값을 냅니다. 그 순간은 둘입니다. 새 단위를 신설할 때, 그리고 pass-through 냄새가 탐지될 때. 기존 코드를 읽거나 좁게 고칠 때는 켜지 않습니다.

### 10.3 Variant — 외부 소유 데이터를 미러링하는 경우

전제가 바뀝니다. 우리 시스템이 데이터의 소유자가 아니고 외부 상태의 사본을 유지하는 경우, "현재 상태를 반영한다"가 진짜 업무 규칙입니다. 이때는 upsert가 정확한 표현이고 등록·수정을 나누는 것이 오히려 규칙을 왜곡합니다. 판정 기준은 "이 요청이 상태 변경 의도를 담고 있는가, 아니면 상태 동기화인가"입니다. 동기화 유스케이스는 이름도 `SyncUserFromDirectory`처럼 그렇게 지어야 합니다.

### 10.4 Variant — 프레임워크가 제공하는 공통 CRUD

ORM의 `save()`나 리포지토리 기본 메서드처럼 프레임워크가 공통 CRUD를 제공하고 그것으로 방대한 코드가 성공적으로 도는 사례가 있습니다. 전제가 셋 다릅니다. 그 공통 CRUD가 업무 층이 아니라 지속성 층에 있고, 규칙은 그 위에 별도로 있고, 프레임워크가 만들어 유지하므로 우리가 유지비를 내지 않습니다. 우리가 업무 층에 같은 것을 만들면 첫째 전제를 어기고 셋째 비용을 우리가 집니다. 그래서 "널리 쓰이는 방식"이라는 사실이 우리 상황을 지지하지 않습니다.

### 10.5 Variant — 진짜 공통인 기술 관심사

감사 컬럼 채우기, 일련번호 발급, 처리 이력 기록, 잠금 획득은 업무 규칙이 아니라 기술 관심사이며 공통 컴포넌트가 정당합니다. 전제는 "여러 유스케이스에서 의미가 동일하다"이고, 이 전제가 깨지는 순간(어떤 유스케이스만 다른 감사 정책이 필요해지는 순간) 그 부분은 유스케이스로 되돌려야 합니다.

## 11) 흔한 오해

### 11.1 "얇은 층은 지워야 한다"

그럴듯한 이유는 위임만 하는 코드가 실제로 대부분 불필요하기 때문입니다. 깨지는 지점은 실행 경계입니다. 트랜잭션 전파, 연결 대상 전환, 감사 지점은 코드 한 줄로 보이지만 제거하면 동작이 달라지고, 그 차이는 컴파일과 단위 테스트를 모두 통과합니다. 그래서 판정은 "얇은가"가 아니라 "소유물이 있는가"로 해야 하며, 소유물 갈래에 실행 경계를 반드시 포함해야 합니다.

### 11.2 "등록과 수정을 upsert로 합치면 중복이 줄어든다"

그럴듯한 이유는 두 경로가 같은 테이블을 건드리고 대부분의 필드가 겹치기 때문입니다. 깨지는 지점은 규칙 집합입니다. 규칙이 줄어드는 것이 아니라 `if (exists)` 분기 안으로 숨습니다. 특히 개인정보 변경 이력처럼 등록 경로에는 존재하지 않는 요구가 수정 경로에만 있으면, 하나의 진입점이 두 정책을 갖게 되고 누락은 특정 분기에서만 나타납니다. 그리고 중복 요청에 어떻게 응답할지가 업무 결정인데 upsert는 그것을 코드 기본값으로 박아 버립니다.

### 11.3 "지금은 하나뿐이지만 나중에 재사용될 것이다"

그럴듯한 이유는 실제로 나중에 재사용되는 경우가 있기 때문입니다. 깨지는 지점은 두 번째 사용처가 나타났을 때입니다. 그때 대개 규칙이 조금 다르고, 그 차이가 조건 분기로 들어갑니다. 그래서 실무 문턱은 "장래 가능성"이 아니라 "지금 둘 이상이 실제로 같은 규칙을 요구한다"입니다. 하나일 때는 응집된 채 두고, 두 번째가 나타났을 때 공통점이 정말 같은지 확인한 뒤 추출하는 편이 되돌리기 쉽습니다.

### 11.4 "규칙을 컴포넌트에 넣었으니 소유하는 것이다"

그럴듯한 이유는 코드가 그 파일에 있기 때문입니다. 깨지는 지점은 그 규칙이 깨졌을 때 아무것도 관측되지 않는 경우입니다. 검증문이 있지만 그 검증을 우회하는 다른 경로가 있거나, 그 검증을 겨냥한 테스트가 없으면 소유는 주장일 뿐입니다. 소유의 증거는 코드의 존재가 아니라 "그 규칙만 제거했을 때 특정 테스트가 red가 되는 것"입니다.

## 12) 팀 적용 질문(순서대로)

첫째, 지금 만들려는 단위의 소유물을 셋 중 하나로 말할 수 있습니까? 말할 수 없으면 만들지 않는 것이 기본값입니다.

둘째, 그 소유물이 업무 규칙입니까 기술 관심사입니까? 기술 관심사면 공통 컴포넌트가 맞고, 업무 규칙이면 유스케이스 단위가 맞습니다.

셋째, 이름에 "무엇이 바뀌는지"를 넣을 수 있습니까? 넣을 수 없다면 첫째 답을 다시 보십시오. 대개 유스케이스가 여러 개 합쳐져 있습니다.

넷째, 그 규칙을 하나 제거하면 red가 되는 테스트가 있습니까? 없으면 소유는 아직 증명되지 않았습니다.

다섯째, 재사용하고 싶은 것이 원시연산입니까 규칙입니까? 원시연산이면 아래층으로 내리고, 규칙이면 재사용하지 않는 편이 안전합니다.

## 13) 확인한 사실과 추론

**확인한 사실**(한 계층형 코드베이스와 그 규범 문서에서 직접 관측).

- 그 저장소의 규범 문서에 각 층이 소유해야 할 책임이 이미 열거되어 있었고, 얇은 wrapper가 실행 경계를 소유할 수 있으므로 제거 전에 그 의미를 확인하라는 예외 조항도 별도로 있었다.
- 반면 유스케이스 층이 지속성 층을 직접 호출하는 것을 금지하는 규칙은 없었다. 금지 대상은 진입점 층이 지속성·업무 층에 직접 닿는 것뿐이었다.
- 그 저장소의 정적 검사 카탈로그에 "이 코드 단위가 무엇을 지키는가"를 묻는 검사는 0건이었다. 생산 코드 대상 검사는 전부 관용구·형식 규칙이었다.

**독립 도달**(근거 강도에 관한 기록).

- 같은 시기에 다른 세션이 같은 코드베이스를 놓고 독립적으로 작업한 결과가 `design/design_mutation_boundary.md`에 있고, "재사용 단위를 update가 아니라 업무 단위로 잡는다", "거절할 수 없는 추상화는 경계가 아니라 파이프다"라는 같은 결론에 도달했다. 서로를 참조하지 않고 도달했으므로 이 결론의 근거는 한 세션의 귀납보다 강하다. 다만 **같은 코드베이스를 봤다는 공통 전제는 남아 있어**, 다른 조직에서 반복되는지는 여전히 확인되지 않았다.

**추론.**

- 소유물 3갈래 판정과 "재사용은 지속성 층, 규칙은 유스케이스 층"이라는 층 분리 기준은 위 관측과 문헌을 결합한 일반화다. 타입 시스템이 강한 언어에서는 등급표를 시그니처로 표현할 수 있어 판정 기준의 적용 범위가 달라진다.
- 등록·수정을 upsert로 합치지 않는 편이 낫다는 결론은 규칙 집합의 차이와 감사 요구에서 끌어낸 것이며, 두 구현을 실제로 만들어 유지 비용을 비교 측정한 사례는 없다.

**미확인.**

- 이론 계보로 적은 인용(Fowler의 Anemic Domain Model과 Middle Man, Evans의 애그리게이트 불변식, generic repository 논쟁, CQRS 계열의 커맨드 명명과 intent loss, Dahan의 task-based UI 대 CRUD-based UI, Rails 콜백 지옥)은 **원문을 확인하지 않고 기억에 근거해 적었다.** 규범 문서의 근거로 인용하기 전에 원문 확인이 필요하다.
- "유스케이스 단위로 나누면 파일 수는 늘지만 탐색 비용은 줄어든다"는 대가 비교를 실제로 측정하지 않았다.
