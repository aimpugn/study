# 비대면 카드 결제에서 본인 인증·거래 승인·돈의 흐름을 분리하기

온라인에서 카드 결제를 누르면 발급기관 화면이나 앱으로 이동할 때가 있습니다. 이때 발급기관이 확인하는 것은 보통 **주민등록상 자연인이 누구인지 매번 처음부터 증명하는 일**이 아닙니다. 발급기관 영역의 인증 서버는 이미 관리 중인 카드 계정과 이번 거래·기기 신호를 바탕으로 인증 기준이 충족되는지 평가합니다. 추가 확인이 필요할 때는 카드 계정에 허용된 앱·기기·비밀번호 같은 인증수단을 현재 행위자가 통제하는지도 확인합니다.

이 판단이 성공해도 결제는 아직 끝나지 않습니다. 인증 결과는 뒤이은 거래 승인 요청의 입력이 될 뿐입니다. 발급기관은 다시 한도, 계정 상태, 거래 위험 등을 보고 승인하거나 거절합니다. 인증 중에는 돈이 움직이지 않고, 거래 승인이 나도 가맹점 계좌에 돈이 최종 입금된 것은 아닙니다. 이후 매출 확정, 청산, 기관 간 결제, 가맹점 정산이 이어집니다.

이 문서는 전자상거래의 **비대면 카드 결제(card-not-present payment)**를 중심으로 이 전체 흐름을 설명합니다. 대면 IC 카드와 PIN, 지역별 독자 인증 방식, 특정 계약의 메시지 경로는 다를 수 있습니다. 여기서 설명하는 3-D Secure는 비대면 카드 인증의 대표적인 표준 모델이지, 모든 카드 거래가 반드시 거쳐야 하는 유일한 경로는 아닙니다.

계좌를 등록해 결제하는 흐름은 [결제 인증·거래 허용·자금 이동을 분리하는 간편 계좌이체 설계](payment_authentication_authorization_and_easy_account_transfer.md)에서 별도로 설명합니다.

## 핵심 요약

> 발급기관은 보통 매 결제마다 고객의 법적 신원을 새로 확인하지 않습니다. 3-D Secure를 사용하면 발급기관 영역의 인증 서버가 카드회원 계정, 거래·기기 신호, 과거 관계 정보를 보고 이번 거래가 인증 기준을 충족하는지 평가합니다. 위험이 낮으면 사용자의 추가 입력 없이 결과를 낼 수 있고, 추가 확인이 필요할 때는 등록된 앱·기기·비밀번호 같은 인증수단을 현재 행위자가 통제하는지 확인합니다. 비밀번호·PIN·일회용 인증번호 같은 자격증명은 발급기관의 인증 경계에 입력되고, 생체정보 원본은 보통 기기 보안영역에서 처리됩니다. 커머스와 결제대행 계층에는 자격증명 원본이 아니라 인증 상태, 거래 식별자, 후속 승인에 사용할 수 있는 인증 증거가 돌아옵니다. 그다음 발급기관이 한도·계정 상태·위험을 다시 판단해 거래를 승인하거나 거절합니다. 3-D Secure 인증 메시지는 3DS 서버·디렉터리 서버·발급기관 인증 서버 경로로 움직이고, 금융 승인 메시지는 계약된 매입 처리 경계를 거쳐 발급기관 승인계로 움직입니다. 이 승인 경로에는 카드망이나 VAN이 포함될 수 있지만 언제나 같은 경로를 거치는 것은 아닙니다.

기억할 문장은 세 개입니다.

1. **법적 신원 확인과 등록된 인증수단의 통제 확인은 다릅니다.**
2. **인증 결과는 승인 판단의 입력이지 승인 결과가 아닙니다.**
3. **인증, 거래 승인, 청산·결제는 메시지와 돈의 효과가 다릅니다.**

## 1. 42,800원 결제를 먼저 따라가기

고객이 온라인 상점에서 42,800원짜리 상품을 선택하고 저장된 카드를 사용한다고 가정하겠습니다. 아래 그림은 **3-D Secure를 사용하는 대표적인 비대면 카드 결제**입니다. 모든 카드·지역·계약에 그대로 적용되는 유일한 경로는 아닙니다. 아직 낯선 약어는 뒤에서 풀고, 여기서는 역할을 쉬운 한국어로만 적겠습니다.

```text
고객
  │ 1. 42,800원 주문과 저장 카드를 선택
  ▼
커머스 ── 2. 결제 의도 생성 ──> 결제 연동 계층
  │                                  │
  │                                  │ 3. 카드 인증 시작
  │                                  ▼
  │                         발급기관의 인증 경계
  │                           ├─ 위험이 낮음: 추가 입력 없이 판단
  │                           └─ 추가 확인 필요: 인증 화면·앱에서 확인
  │                                  │
  │                                  │ 4. 인증 상태와 인증 증거 반환
  │                                  ▼
  │                         결제 연동 계층
  │                                  │
  │                                  │ 5. 인증 증거를 포함한 거래 승인 요청
  │                                  ▼
  │                         발급기관의 승인 판단
  │                           ├─ 승인
  │                           └─ 거절
  │                                  │
  │ 6. 서버가 검증한 승인 결과       │
  ◀──────────────────────────────────┘
  │
  ├─ 7-a. 커머스 정책에 따라 주문을 한 번만 확정하고 이행
  │
  └·· 7-b. 승인된 매출의 확정·청산·기관 간 결제·가맹점 지급은
          서버 간 후속 절차와 각자의 일정으로 진행
```

이 작은 흐름에서 같은 발급기관이 두 번 등장합니다. 3번과 4번에서는 “이 카드 계정을 정당하게 사용하는 행위인가?”를 확인합니다. 5번과 6번에서는 “이 거래를 한도·계정 상태·위험 정책상 받아들일 것인가?”를 결정합니다.

두 결과는 독립적입니다. 고객이 발급기관 앱에서 인증을 마쳐도 한도 부족으로 거래가 거절될 수 있습니다. 반대로 위험이 낮다고 판단된 거래는 고객이 비밀번호나 일회용 번호를 추가로 입력하지 않는 무마찰 인증을 거쳐 승인될 수 있습니다.

또한 고객이 발급기관 앱을 닫고 커머스 화면으로 돌아왔다는 사실은 4번이나 6번의 성공 증거가 아닙니다. 화면 이동은 사용자 경험을 위한 동작입니다. 커머스 서버는 결제 연동 계층의 서버 응답·조회·서명된 서버 콜백으로 인증과 승인 상태를 확인해야 합니다. 승인에 따라 주문을 확정했더라도 청산이나 가맹점 지급까지 끝났다는 뜻은 아닙니다.

## 2. “그 사람이 그 사람인가”에는 네 가지 질문이 숨어 있다

“본인을 인증한다”는 말을 하나의 절차로 생각하면 카드 결제가 이해되지 않습니다. 실제로는 서로 다른 시점과 증거를 가진 네 가지 질문이 있습니다. 이 네 질문은 매 거래마다 차례대로 실행되는 고정 단계가 아닙니다. 앞의 두 질문은 카드 발급이나 인증수단 등록 시점에 이미 처리되었을 수 있고, 무마찰 인증에서는 고객이 결제 화면에서 아무 값도 추가로 입력하지 않을 수 있습니다.

| 질문 | 쉬운 뜻 | 대표 시점 | 만드는 관계·증거 | 매 결제마다 필요한가 |
| --- | --- | --- | --- | --- |
| 법적 신원 확인(identity proofing) | “제시한 이름과 신원 자료가 실제 자연인과 연결되는가?” | 카드 발급, 회원 가입, 중요한 정보 변경·복구 | 확인된 신원 속성과 카드회원 계정 | 보통 아닙니다. |
| 계정과 인증수단 연결(binding) | “이 카드회원 계정에 어떤 기기·앱 키·비밀번호·인증서가 등록되어 있는가?” | 인증수단 등록·교체 | 카드회원 계정과 인증수단의 결합 | 보통 등록·변경 때 수행합니다. |
| 현재 행위자 인증(authentication) | “지금 요청한 사람이 계정에 묶인 인증수단을 통제하는가?” | 로그인, 위험 거래, 3-D Secure challenge | 인증 상태, 강도, 거래 식별자 | 정책과 위험도에 따라 다릅니다. |
| 거래 맥락 확인(transaction authentication) | “이번 금액·통화·가맹점 맥락에서 인증 결과가 만들어졌는가?” | 비대면 카드 인증 | 거래에 연결된 인증 결과·증거 | 3-D Secure를 사용한다면 해당 인증 거래와 연결합니다. |

일반 디지털 신원 지침은 인증자를 “가입자 계정에 묶인 하나 이상의 인증수단을 사용자가 보유·통제하는지 확인하는 주체”로 설명합니다. 이 정의는 **법적 신원을 처음 세우는 일**과 **이미 등록된 인증수단을 지금 통제하는지 확인하는 일**을 분리하는 데 유용합니다. 다만 이 지침은 카드 결제 규칙 자체가 아니므로 카드 메시지 경로는 카드 인증 표준을 따로 봐야 합니다. ([디지털 신원 모델](https://pages.nist.gov/800-63-4/sp800-63.html#digital-identity-model))

여기서 법적 신원이 같다고 커머스 회원, 카드 계약의 명의자, 지금 결제하는 행위자까지 자동으로 같은 것은 아닙니다. 법인카드, 가족카드, 추가 카드, 적법하게 위임된 사용처럼 계약상 카드회원과 실제 사용자가 다를 수 있기 때문입니다. 발급기관은 상품·계약에 따라 카드 계정과 정당한 사용자 또는 유효한 위임 관계를 관리하고, 인증에서는 그 관계에 허용된 인증 기준이 충족되었는지를 판단합니다. 커머스는 자기 회원의 로그인과 주문 권한을 확인하지만, 그 사실만으로 카드의 법적 명의나 사용 권한까지 판정하지 않습니다.

### 2.1 카드번호와 보안코드를 안다고 본인이 되는 것은 아니다

카드번호, 유효기간, 카드 뒷면의 보안코드 같은 정적 정보는 카드 결제에 필요한 데이터일 수 있습니다. 하지만 이 정보는 복사되거나 유출될 수 있으므로 그 자체만으로 자연인이나 정당한 카드 사용자를 강하게 증명하지 못합니다.

발급기관 앱에 등록된 기기, 앱 안의 암호키, 일회용 인증번호, 비밀번호, 기기에서 확인하는 생체정보 같은 수단은 “현재 사용자가 등록된 인증수단을 통제한다”는 증거를 보강합니다. 이때도 생체정보 원본이 반드시 발급기관으로 전송되는 것은 아닙니다. 기기 보안영역에서 생체 확인을 마치고, 앱이 보호된 키로 만든 결과만 서버에 보낼 수 있습니다. 정확한 구현은 인증수단과 발급기관 정책에 따라 달라집니다.

### 2.2 인증 성공은 금액에 전자서명했다는 뜻과 같지 않다

3-D Secure 인증 요청에는 구매 금액, 통화, 가맹점, 기기와 고객 관계 정보 등이 포함될 수 있습니다. 발급기관 인증 서버는 이 정보를 위험 판단과 challenge 화면에 사용할 수 있습니다. 그러나 모든 인증 방식이 고객에게 금액과 가맹점을 같은 형태로 보여 주고 암호학적 서명을 받는다고 일반화하면 안 됩니다.

따라서 시스템은 인증 결과를 범용 로그인 토큰이나 “어떤 금액이든 결제할 수 있는 승인권”으로 다루면 안 됩니다. 인증을 시작한 결제 의도, 금액, 통화, 가맹점, 카드 결제수단, 3DS 거래 식별자의 관계를 보존하고, 계약이나 프로그램 규칙이 허용한 방식으로만 후속 승인 요청에 사용해야 합니다.

## 3. 서로 다른 식별자 공간은 어떻게 연결되는가

커머스와 발급기관이 같은 고객 ID를 공유해야 발급기관이 고객을 알아보는 것은 아닙니다. 각 참여자는 자기 책임 범위의 식별자를 가집니다.

| 식별자 | 소유 경계 | 무엇을 가리키는가 |
| --- | --- | --- |
| `commerceCustomerId` | 커머스 | 커머스 회원 계정 |
| `paymentCustomerId` | 결제 서비스 | 결제 서비스 내부 고객 또는 연결 관계 |
| `paymentMethodId` | 결제 서비스 | 저장 카드나 토큰을 가리키는 내부 별칭 |
| 카드번호 또는 결제 토큰 | 카드 생태계 | 발급기관이 관리하는 카드 계정으로 라우팅할 수 있는 결제 자격 정보 |
| `threeDSServerTransId` | 3DS 서버 | 한 번의 3DS 서버 인증 거래 |
| `dsTransId` | 디렉터리 서버 | 상호운용 구간의 인증 거래 |
| `acsTransId` | 발급기관 인증 서버 | 발급기관 영역의 인증 거래 |
| `authorizationRequestId` | 승인 연동 계층 | 한 번의 금융 승인 요청 |
| 승인 코드와 네트워크 거래 ID | 발급기관·카드망 | 승인 결과와 후속 매입·취소를 연결하는 식별 정보 |

커머스의 `commerceCustomerId="cust_271"`가 발급기관의 카드회원 번호와 같을 필요도 없고, 보통 같아서도 안 됩니다. 연결은 다음처럼 이루어집니다.

1. 고객이 커머스에서 특정 저장 카드 별칭을 선택합니다.
2. 결제 서비스는 그 별칭이 해당 커머스 고객에게 사용 허용된 결제수단인지 확인합니다.
3. 카드번호나 결제 토큰의 라우팅 정보로 해당 발급기관 영역을 찾습니다.
4. 발급기관 인증 서버는 자기 카드 계정, 정당한 사용 권한·위임 관계, 등록 인증수단, 위험 정보를 기준으로 인증을 수행합니다.
5. 커머스에는 발급기관의 내부 카드회원 번호나 고객의 자격증명이 아니라, 결제 의도와 연결할 수 있는 인증·승인 결과가 돌아옵니다.

즉 결제 서비스가 “이 사람은 커머스의 누구인가”를 발급기관에 주민등록상 신원으로 증명하는 구조가 아닙니다. 커머스가 소유한 고객과 저장 결제수단의 사용 허용 관계, 카드 생태계가 소유한 카드 계정과 정당한 사용 권한·인증수단의 관계를 각각 검증하고, 이번 결제 거래의 식별자로 두 관계를 안전하게 이어 붙입니다.

커머스가 3DS 인증 요청에 회원 가입 기간이나 과거 거래 같은 고객 관계 정보를 제공할 수는 있습니다. 이 정보는 발급기관 인증 서버의 위험 판단을 돕는 신호이지, 커머스의 문자열 하나가 카드 계정의 정당한 사용 권한을 증명한다는 뜻은 아닙니다. 국제 카드 인증 표준도 고객과 가맹점의 관계 정보를 위험 분석에 사용할 수 있다고 설명합니다. ([위험 분석에 쓰이는 카드회원 정보](https://www.emvco.com/dynamic/emv-3-d-secure-whitepaper-v2/improving-risk-emv-3-d-secure-whitepaper-v2-analysis-and-frictionless-flow/technical-features/))

## 4. 누가 무엇을 책임지는가

한 회사가 여러 역할을 수행할 수 있고, 한 역할을 외부에 위탁할 수도 있습니다. 그래서 회사 이름보다 **판단 책임과 메시지 역할**을 먼저 구분해야 합니다.

| 역할 | 쉬운 설명 | 책임지지 않는 것 |
| --- | --- | --- |
| 카드회원(cardholder) | 발급된 카드 계정을 사용할 계약상 주체 | 모든 인증이 성공한다는 보장 |
| 커머스·가맹점(merchant) | 주문, 금액, 상품, 고객 경험을 소유 | 카드회원 계정의 인증 정책과 한도 승인 |
| 전자지급결제대행 계층(PG) | 지급결제정보 송수신과 정산 대행·매개를 제공할 수 있는 결제 통합 경계 | 항상 3DS 서버를 직접 운영하거나 발급기관 대신 인증·승인한다는 보장 |
| 3DS 요청자(3DS Requestor) | 카드회원 인증을 요청하는 가맹점 또는 그 대리 역할 | 발급기관의 최종 인증 판단 |
| 3DS 서버(3DS Server) | 요청자 영역에서 인증 요청을 만들고 결과를 받는 구성요소 | 카드 비밀번호를 직접 판정하는 일 |
| 디렉터리 서버(Directory Server, DS) | 카드 범위에 맞는 발급기관 인증 서버로 3DS 메시지를 연결하는 상호운용 구성요소 | 발급기관 계정의 최종 인증 정책 |
| 발급기관 인증 서버(Access Control Server, ACS) | 발급기관 영역에서 위험을 평가하고 무마찰 또는 추가 인증을 결정하는 구성요소 | 금융 승인 결과 자체 |
| 매입사(acquirer) | 가맹점의 카드 거래를 받아 카드망과 청산·결제 관계를 관리 | 카드회원의 한도와 계정 상태 결정 |
| 처리자(processor)·VAN | 승인·매입 관련 메시지를 가공하거나 중계하는 역할 | 발급기관의 최종 승인 판단 |
| 카드망(payment card network) | 매입 측과 발급 측 사이에서 승인·청산·결제 정보를 라우팅하는 규칙과 기반 | 고객 자격증명을 대신 보관하는 일 |
| 발급기관(issuer) | 카드회원 계정·한도·위험 정책을 관리하고 거래를 승인하거나 거절 | 커머스 주문의 재고·상품 적합성 판단 |

발급기관은 카드회원 계정에 대한 신뢰와 인증 정책의 책임을 집니다. ACS는 그 정책에 따라 위험평가와 challenge를 수행합니다. ACS의 기술 운영을 외부 사업자가 맡거나 위임 인증 구조를 사용할 수 있으므로 `ACS = 발급기관이 직접 운영하는 서버 한 대`로 고정하면 안 됩니다.

국내 법률에서 전자지급결제대행은 전자적 구매에서 지급결제정보를 송수신하거나 대가의 정산을 대행·매개하는 업무로 정의되어 있습니다. 이 법적 범위는 PG가 결제 통합 경계가 될 수 있음을 보여 주지만, PG가 모든 3DS 구성요소를 직접 운영한다거나 발급기관의 인증·승인 판단을 소유한다는 뜻은 아닙니다. 이 문서는 **2025년 12월 16일부터 시행 중인 조문**, 즉 2026년 7월 현재 적용되는 정의를 사용합니다. 2026년 12월 17일부터 시행될 개정은 전자지급결제대행 정의를 바꾸므로 현재 설명의 근거와 섞지 않습니다. ([현재 시행 전자금융거래법 제2조·제28조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1026289295), [2026년 12월 17일 시행 예정 개정문](https://law.go.kr/lsRvsDocInfoR.do?lsiSeq=280277))

## 5. 인증과 승인은 왜 별도 경로로 발전했는가

카드 거래에는 오래전부터 발급기관의 거래 승인 판단이 있었습니다. 발급기관은 카드 계정 상태와 가용 한도 등을 확인하고 거래를 받아들일지 결정합니다. 대면 거래에서는 카드 자체, IC 칩, PIN, 서명, 단말기 같은 현장 증거를 활용할 수 있습니다.

전자상거래에서는 카드와 사람을 눈앞에서 볼 수 없습니다. 카드번호 같은 정적 정보만으로는 복제·도용 위험을 충분히 줄이기 어려웠습니다. 그래서 비대면 카드 거래에 **카드회원 인증 정보를 교환하는 별도 계층**이 추가되었습니다. 3-D Secure의 초기 버전은 2001년에 개발되었고, 더 많은 거래·기기 정보를 사용해 위험 기반 인증을 지원하는 2.0은 2016년에 공개되었습니다. 표준 자료도 카드회원 인증이 끝난 뒤 통상적인 거래 승인이 별도로 이어진다고 설명합니다. ([비대면 카드 인증 표준 개요](https://www.emvco.com/wp-content/uploads/2022/09/Quick-Resource_-EMV-3DS-for-E-Commerce.pdf))

분리된 이유는 단순히 서버가 달라서가 아닙니다.

| 구분 | 카드회원 인증 | 금융 승인 | 청산·기관 간 결제 |
| --- | --- | --- | --- |
| 핵심 질문 | 등록 카드 계정의 정당한 사용으로 볼 근거가 충분한가? | 이 금액의 거래를 계정·한도·위험 정책상 받아들일 것인가? | 승인·매입된 거래로 기관별 채권·채무를 얼마로 확정하고 이행할 것인가? |
| 대표 메시지 | AReq/ARes, CReq/CRes, RReq/RRes | 금융 승인 요청/응답 | 매입·청산 자료와 결제 지시 |
| 대표 판단 주체 | 발급기관 영역의 ACS | 발급기관 승인계 | 카드망·청산기관·발급/매입기관의 계약에 따른 주체 |
| 돈의 효과 | 없음 | 가용한도 반영·금액 확보가 생길 수 있으나 최종 입금은 아님 | 기관 간 자금 의무 이행, 이후 가맹점 지급 |
| 독립 실패 예 | challenge 포기, 인증 실패 | 한도 부족, 정지 카드, 위험 거절 | 매입 누락, 금액 불일치, 정산 지연 |

같은 HTTP 요청 안에 여러 의미를 실을 수 있고, 한 시스템이 여러 역할을 맡을 수도 있습니다. 그래도 각 판단의 책임, 결과, 유효기간, 실패 복구는 분리해야 합니다.

## 6. 무마찰 인증과 추가 인증은 어떻게 동작하는가

3-D Secure는 발급기관이 카드회원 인증에 필요한 데이터를 받고 결과를 돌려주는 메시지 프로토콜입니다. 대표 흐름은 **무마찰 인증(frictionless flow)**과 **추가 인증(challenge flow)**입니다.

아래 범례를 먼저 고정하겠습니다.

```text
──▶ 3DS 표준이 정의하는 대표 인증 메시지 경로
··▶ 계약·제품·국가·채널에 따라 달라지는 연동 경로
══▶ 금융 승인 메시지 경로
==> 매입·청산·기관 간 결제의 자금 의무 경로
```

### 6.1 무마찰 인증: 추가 입력이 없다고 인증이 없는 것은 아니다

```text
3DS 요청자 ··▶ 3DS 서버 ──AReq──▶ 디렉터리 서버 ──AReq──▶ ACS
                                                         │
                                                         │ 거래·기기·계정 정보로 위험평가
                                                         ▼
3DS 요청자 ◀·· 3DS 서버 ◀─ARes── 디렉터리 서버 ◀─ARes── ACS
```

ACS는 구매 금액과 통화, 가맹점 정보, 카드회원과 가맹점의 관계, 기기·브라우저 정보, 과거 인증 정보처럼 허용된 데이터를 바탕으로 위험을 평가할 수 있습니다. 위험이 낮고 정책상 추가 확인이 필요하지 않으면, 사용자에게 PIN이나 일회용 번호를 더 입력시키지 않고 인증 결과를 반환합니다.

무마찰이라는 말은 **고객에게 추가 상호작용을 요구하지 않는다**는 뜻입니다. ACS의 판단이 없다는 뜻도, 모든 거래가 무조건 성공한다는 뜻도 아닙니다. 이후 금융 승인은 여전히 거절될 수 있습니다.

### 6.2 추가 인증: 자격증명은 발급기관 인증 경계로 간다

ACS가 추가 확인이 필요하다고 판단하면 ARes로 challenge 필요 상태를 알립니다.

```text
3DS 서버 ──AReq──▶ 디렉터리 서버 ──AReq──▶ ACS
3DS 서버 ◀─ARes(challenge)─ 디렉터리 서버 ◀─ARes── ACS
    │
    │ 브라우저 iframe 또는 앱의 3DS SDK를 준비
    ▼
3DS Client ──CReq·인증 상호작용──▶ ACS
3DS Client ◀─CRes·화면 진행 정보── ACS
                                      │
                                      │ 최종 백엔드 인증 결과
                                      ▼
3DS 서버 ◀─RReq── 디렉터리 서버 ◀─RReq── ACS
3DS 서버 ──RRes(수신 확인)──▶ 디렉터리 서버 ──RRes──▶ ACS
```

대표적인 브라우저·앱 흐름에서는 3DS Client가 보호된 연결로 ACS와 상호작용합니다. 채널과 버전에 따라 3DS 서버가 일부 통신을 중계하거나, 분리된 SDK, 발급기관 앱을 사용하는 별도 채널, 나중에 끝나는 분리 인증이 사용될 수 있습니다. 따라서 위 그림은 대표 경로이지 모든 구현의 물리 연결도는 아닙니다.

중요한 신뢰 경계는 다음과 같습니다.

- 비밀번호, PIN, 일회용 인증번호 같은 자격증명은 발급기관·ACS가 통제하는 화면과 채널에 입력합니다.
- 생체정보 원본은 보통 기기 보안영역에서 확인하며, 커머스·PG·3DS 서버가 원본을 받지 않습니다.
- challenge 화면의 진행 정보인 CRes나 브라우저 복귀만으로 최종 인증 성공을 확정하지 않습니다.
- challenge의 최종 백엔드 결과는 ACS가 RReq로 디렉터리 서버를 거쳐 3DS 서버에 알리고, 3DS 서버는 RRes로 수신을 확인합니다.

국제 표준 자료는 challenge에서 3DS Client가 ACS와 보호된 연결로 직접 상호작용하고, ACS가 RReq로 최종 결과를 제공하는 대표 흐름을 설명합니다. ([challenge 기술 흐름](https://www.emvco.com/dynamic/emv-3-d-secure-whitepaper-v2/challenge-flow/technical-features/))

## 7. 발급기관 앱에서 무엇을 확인하고 무엇이 돌아오는가

발급기관 앱으로 이동하는 흐름은 3-D Secure의 **별도 채널 인증(out-of-band authentication, OOB)**으로 구현될 수 있습니다. OOB는 결제 화면 안에서 자격증명을 입력하는 대신, 발급기관이 미리 등록한 앱이나 다른 인증 채널에서 거래를 확인하는 방식입니다.

```text
결제 화면
  │ 1. ACS가 별도 인증 앱 사용을 안내
  ▼
발급기관 인증 앱
  │ 2. 등록 기기·앱 키·PIN·기기 생체 확인 등 정책별 인증
  │ 3. 앱 또는 인증 시스템이 결과를 ACS에 전달

[서버 결과 경로]
인증 앱·인증 시스템 ──▶ ACS ──RReq──▶ 디렉터리 서버 ──RReq──▶ 3DS 서버

[사용자 화면 경로]
운영체제의 앱 전환 ──▶ 결제 화면으로 복귀
                         └─ 진행 재개·상태 조회만 담당
```

두 경로는 서로 독립적이어서 어느 쪽이 먼저 끝날지 보장할 수 없습니다. 결제 화면이 먼저 돌아와도 서버 결과가 아직 처리 중일 수 있고, 서버 결과가 먼저 도착해도 사용자는 인증 앱에 머물 수 있습니다. 따라서 화면 복귀 여부와 관계없이 3DS 서버를 통해 전달된 결과를 조회해야 합니다.

ACS는 다음을 조합해 판단할 수 있습니다.

- 이 카드 계정에 등록된 인증 앱이나 기기인가
- 앱이 등록된 암호키를 실제로 통제하는가
- 사용자가 앱 PIN이나 기기 생체 확인을 통과했는가
- 결제 금액·통화·가맹점·기기·위치·과거 패턴이 위험 정책에 맞는가
- 추가 확인을 요구하거나 거래를 거절해야 하는 신호가 있는가

여기서 “생체 확인을 통과했다”가 “지문·얼굴 원본이 ACS로 전송되었다”는 뜻은 아닙니다. 보통 기기가 생체 일치 여부를 확인하고, 앱은 보호된 키를 사용할 수 있게 됩니다. 발급기관은 그 키를 사용해 만들어진 프로토콜 결과를 확인할 수 있습니다. 다만 세부 구현은 앱과 인증 정책에 따라 달라집니다.

발급기관이 되돌려주는 것은 고객이 입력한 비밀번호나 생체정보가 아닙니다. 대표적으로 다음과 같은 **결과와 연결 정보**입니다.

- 인증 거래 상태: 성공, 실패, 추가 인증 필요, 시도되었으나 완료되지 않음 등
- 3DS 서버·디렉터리 서버·ACS의 거래 식별자
- 사용한 인증 방식이나 challenge 관련 상태
- 프로그램 규칙에 따라 후속 금융 승인 요청에 전달할 인증값(authentication value)과 전자상거래 지표(ECI) 같은 증거
- 오류나 취소 이유를 구분하는 상태 정보

정확한 필드, 값의 의미, 필수 여부, 금융 승인망에 운반하는 방식은 카드 프로그램과 프로토콜 버전에 따라 다릅니다. 인증값이나 ECI를 PG가 독자적으로 소비하는 범용 승인 토큰, 한 번만 쓸 수 있는 결제 비밀번호, 돈을 움직일 권한으로 해석하면 안 됩니다.

OOB 표준 설명도 ACS가 카드회원에게 발급기관 앱 같은 별도 채널을 사용하도록 지시하고, 인증 결과가 RReq로 디렉터리 서버와 3DS 서버에 전달되는 흐름을 보여 줍니다. ([별도 채널 인증 개요](https://www.emvco.com/dynamic/emv-3-d-secure-whitepaper-v2/out-of-band-oob-authentication/oob-introduction/), [앱 전환과 결과 반환 흐름](https://www.emvco.com/dynamic/emv-3-d-secure-whitepaper-v2/out-of-band-oob-authentication/oob-flow-app-channel-automatic-switching-to-the-oob-app/))

### 7.1 결제 화면으로 돌아오면 누가 누구에게 무엇을 알려 주는가

사용자 눈에는 앱 A에서 앱 B로 갔다가 돌아오는 한 흐름처럼 보입니다. 서버에서는 다음 세 사건을 나누어야 합니다.

1. 운영체제가 앱이나 브라우저를 전환합니다.

    이 사건은 화면 전환입니다. 딥링크가 열렸거나 원래 앱이 화면 맨 앞(foreground)으로 돌아왔다는 사실만 알려 줍니다.

2. ACS가 인증 결과를 만듭니다.

    발급기관 정책에 따라 자격증명과 위험 신호를 검증한 뒤 인증 상태와 증거를 만듭니다.

3. 인증 결과가 3DS 서버 경로로 전달됩니다.

    challenge에서는 RReq가 ACS에서 디렉터리 서버를 거쳐 3DS 서버로 이동합니다. 3DS 서버 이후 결제 서비스와 커머스가 결과를 주고받는 API는 계약별 연동입니다. 국제 3DS 표준이 모든 PG의 외부 API 모양까지 정하는 것은 아닙니다.

따라서 “인증 앱에서 돌아왔으니 결제 성공”은 잘못된 상태 전이입니다. 올바른 규칙은 “화면 복귀 후에도 서버가 검증한 인증 결과를 기다리고, 그다음 금융 승인을 별도로 확인한다”입니다.

## 8. 통신사 가입자 기반 본인확인은 언제 쓰이는가

국내 온라인 본인확인은 주민등록번호를 서비스마다 직접 사용하지 않고 휴대전화, 카드, 인증서 같은 대체수단으로 이용자를 식별·인증하는 제도입니다. 휴대전화 방식은 문자 일회용 번호나 통신사 인증 앱의 PIN·생체 확인 등을 사용할 수 있습니다. ([온라인 본인확인 제도와 대체수단](https://identity.kisa.or.kr/web/main/contents/M010-01), [휴대전화 본인확인 방식](https://identity.kisa.or.kr/web/main/contents/M030-02))

이 본인확인은 카드 결제의 어느 곳에서든 **사용될 수 있는 별도 수단**입니다. 예를 들면 다음과 같습니다.

- 카드회원 가입이나 카드 발급 과정에서 법적 신원 자료를 보강할 때
- 새 기기나 인증 앱을 등록할 때
- 비밀번호를 잊어 인증수단을 복구할 때
- 저장 카드를 처음 등록하거나 중요한 정보를 변경할 때
- 발급기관 정책이 고위험 거래에 추가 본인확인을 요구할 때

그러나 다음과 같이 일반화하면 안 됩니다.

- 모든 PG가 카드 결제 때마다 통신사 본인확인을 직접 호출하는 것은 아닙니다.
- 통신사 명의자가 확인되었다고 해서 현재 카드의 정당한 사용자가 자동으로 증명되는 것은 아닙니다.
- 통신사 인증 앱이 곧 3-D Secure 프로토콜인 것도 아닙니다.
- 발급기관 앱의 PIN·생체 challenge와 통신사 가입자 명의 확인은 화면이 비슷해도 판단 대상과 책임자가 다를 수 있습니다.

결제 시스템은 “휴대전화 본인확인 성공”을 범용 카드 승인권으로 저장하지 않아야 합니다. 어떤 기관이 무엇을 확인했고, 그 결과가 어느 계정·인증수단·거래에 어떤 범위로 적용되는지를 분리해 기록해야 합니다.

## 9. 인증 결과는 승인 요청에 어떻게 연결되는가

인증이 끝나면 결제 연동 계층은 같은 결제 거래의 금융 승인을 요청합니다. 이때 인증 결과와 거래 식별자를 프로그램 규칙에 맞게 승인 요청에 포함할 수 있습니다.

```text
[인증 경로]
ACS ──ARes·RReq──▶ 디렉터리 서버 ──▶ 3DS 서버 ··▶ 결제 연동 계층
                                      인증 상태·거래 ID·인증 증거

[승인 경로]
결제 연동 계층
  ··▶ 계약된 매입 측 처리 경계
        ══ 카드 결제정보 + 금액·통화·가맹점 + 인증 증거 ══▶
        [별도 카드망이 있는 구조라면 카드망] ══▶ 발급기관 승인계
        ◀══════ 승인/거절 + 응답코드 + 승인 식별자 ════════
  ◀·· 계약된 역경로
```

토큰화된 저장 카드의 한 공식 사용 사례는 3DS 인증 결과로 받은 인증값을 후속 카드 승인 요청에 포함하고, 발급기관의 별도 승인 응답을 받는 순서를 보여 줍니다. 이 자료는 **토큰화된 비대면 거래의 예시**이며, 모든 카드 프로그램에서 같은 필드와 형식을 사용한다는 증거는 아닙니다. ([카드 토큰화와 3DS 인증 후 승인 예시](https://www.emvco.com/wp-content/uploads/2023/03/EMVCo-Payment-Tokenisation-A-Guide-To-Use-Cases-v2.2.1.pdf))

인증 증거는 승인 판단을 돕지만, 다음 질문에는 답하지 못합니다.

- 사용 가능한 한도가 42,800원 이상인가
- 카드가 정지·해지·분실 신고 상태인가
- 승인 시점의 거래 위험이 허용 범위인가
- 가맹점·업종·국가·시간대 제한에 걸리지 않는가
- 중복 승인이나 이미 취소된 주문은 아닌가

그래서 다음 상태는 모두 정상적으로 가능합니다.

```text
AUTHENTICATION_SUCCEEDED + AUTHORIZATION_APPROVED
AUTHENTICATION_SUCCEEDED + AUTHORIZATION_DECLINED
AUTHENTICATION_FAILED    + AUTHORIZATION_NOT_REQUESTED
AUTHENTICATION_UNAVAILABLE + 계약상 정한 대체 정책 또는 거래 중단
```

### 9.1 인증 결과를 범용 토큰처럼 쓰지 않는다

결제 서비스가 보존해야 할 최소 관계는 다음과 같습니다.

```text
(paymentId,
 merchantId, merchantOrderId,
 amount, currency,
 paymentMethodId,
 threeDSServerTransId, dsTransId, acsTransId,
 authenticationStatus,
 authorizationRequestId)
```

금액·통화·가맹점·카드 결제수단이 달라지면 기존 인증 결과를 그대로 다른 승인 요청에 붙이지 않습니다. 다만 “이 모든 필드가 표준 인증값 안에 반드시 암호학적으로 결합된다”고 공개 규격보다 넓게 단정해서도 안 됩니다. 서비스는 자기 결제 의도와 3DS 거래의 관계를 보존하고, 카드 프로그램과 연동 계약이 요구하는 검증·운반 규칙을 적용해야 합니다.

반복 결제도 단순한 인증 결과 재사용이 아닙니다. 최초 고객 주도 설정과 이후 가맹점 주도 거래는 성격이 다르며, 후속 인증에서 이전 3DS 거래 식별자와 인증 정보를 참고할 수 있습니다. 정확한 처리 방식은 반복 결제 약정, 카드 프로그램, 3DS 버전에 따라 달라집니다.

## 10. 카드 승인도 VAN 망을 거치는가

짧게 답하면 다음과 같습니다.

> 3-D Secure 인증 메시지가 보편적으로 VAN 승인망을 왕복하는 것은 아닙니다. 인증은 3DS 서버·디렉터리 서버·ACS 경로를 사용합니다. 인증이 끝난 뒤의 금융 승인 요청은 국내 계약과 채널에 따라 PG, 처리자, VAN, 매입사, 카드망 중 일부를 거쳐 발급기관으로 갈 수 있습니다. 같은 사업자나 물리 인프라가 양쪽 역할을 맡을 수 있어도 인증과 승인의 논리 경로와 결과는 합쳐지지 않습니다.

금융 승인 경로는 역할이 분리된 구조와 결합된 구조를 나누어 보아야 합니다. 점선 구간과 실제 사업자 수는 계약별입니다.

```text
발급·매입 역할이 분리된 대표 경로:
커머스 ··▶ PG·처리자 ··▶ 매입사 ══▶ 카드망 ══▶ 발급기관 승인계
커머스 ◀·· 서버 결과    ◀·· 매입사 ◀══ 카드망 ◀══ 승인·거절 응답

발급·매입 역할이 결합되거나 국내 계약망이 직접 연결된 경로:
커머스 ··▶ PG·처리자·VAN 중 계약된 경로 ══▶ 발급기관 승인계
커머스 ◀·· 서버가 검증한 결과              ◀══ 승인·거절 응답
```

카드망은 매입 측에서 발급 측으로 승인·청산·결제 정보를 라우팅하는 기반을 제공합니다. 처리자는 발급기관, 매입사, 가맹점을 위해 메시지를 처리하거나 라우팅할 수 있습니다. 이 두 역할은 계약과 시장 구조에 따라 한 조직에 모일 수도, 여러 조직으로 나뉠 수도 있습니다. ([발급사·매입사·처리자·카드망의 공식 정의](https://www.federalreserve.gov/frrs/regulations/section-2352-definitions.htm))

국내 법률은 신용카드등부가통신업에 가맹점과 발급기관 등을 연결해 승인·중계하고 매출전표를 매입·정산하는 업무가 포함될 수 있다고 직접 정의합니다. 이는 VAN이 승인 관련 메시지를 중계할 수 있다는 근거입니다. 그러나 VAN이 발급기관 대신 승인 여부를 최종 판단하거나, 모든 온라인 3DS 인증 메시지의 필수 통로라는 뜻은 아닙니다. ([현재 시행 여신전문금융업법 제2조의 신용카드등부가통신업 정의](https://www.law.go.kr/LSW/lsSideInfoP.do?chrClsCd=010202&docCls=jo&joBrNo=00&joNo=0002&lsId=&lsiSeq=277267&urlMode=lsScJoRltInfoR))

### 10.1 “카드사로 이동한다”는 화면과 승인망을 구분한다

고객 눈에 보이는 발급기관 화면 이동은 인증 사용자 경험입니다. 화면이나 앱은 ACS가 요구한 challenge를 수행하도록 돕습니다. 이때 백엔드의 3DS 메시지는 디렉터리 서버와 ACS 사이에서 움직입니다.

금융 승인 전문은 고객 화면과 별개로 서버 사이에서 움직입니다. 고객이 발급기관 화면에서 커머스로 돌아오는 브라우저 경로를 승인 전문이 그대로 역주행한다고 생각하면 안 됩니다.

```text
사용자 화면 경로: 커머스 화면 → 인증 화면·앱 → 커머스 화면
3DS 인증 경로:    3DS 서버 → 디렉터리 서버 → ACS → 결과 역경로
금융 승인 경로:   매입 측 처리 경계 → [별도 카드망이 있는 구조라면 카드망]
                  → 발급기관 승인계 → 계약된 응답 역경로
```

세 경로는 시간상 이어질 수 있지만 같은 연결은 아닙니다.

## 11. 실제 돈은 언제 움직이는가

여기서는 **대표적인 4당사자·이중 메시지(dual-message) 카드 흐름**을 기준으로 설명합니다. 이중 메시지는 실시간 승인과 나중의 매입·청산 자료가 분리되는 구조입니다. 단일 메시지 직불 거래, 발급과 매입 역할이 한 기관에 모인 구조, 카드망의 대행승인, 지역별 계약에서는 단계와 시점이 달라질 수 있습니다.

### 11.1 시간축으로 보는 42,800원

| 시점 | 단계 | 주요 판단·기록 | 돈의 효과 |
| --- | --- | --- | --- |
| T0 | 카드회원 인증 | 카드 계정의 정당한 사용으로 볼 근거를 평가합니다. | 돈은 움직이지 않습니다. |
| T1 | 금융 승인 | 발급기관이 42,800원 거래를 승인·거절합니다. | 승인 시 가용한도 감소나 금액 확보가 생길 수 있지만 기관 간 최종 자금 이동은 아닙니다. |
| T2 | 매출 확정·매입 제출(capture/presentment) | 가맹점이 실제 매출 금액을 확정해 매입·청산 대상으로 제출합니다. | 거래가 청산 대상 의무로 구체화됩니다. |
| T3 | 청산(clearing) | 참여기관이 거래 자료를 맞추고 수수료·조정을 반영해 채권·채무를 계산합니다. | 누가 얼마를 지급할지 의무가 확정됩니다. |
| T4 | 기관 간 결제(settlement) | 발급 측과 매입 측 사이의 결제 의무를 실제 자금으로 이행합니다. | 기관 사이에서 자금이 이동합니다. |

청산은 거래를 맞추고 결제할 포지션을 계산하는 과정이며, 결제는 그 의무를 자금 이전으로 이행하는 과정입니다. 중앙은행 용어집도 청산을 결제 전 거래 대조·확인과 순포지션 계산을 포함할 수 있는 절차로 설명합니다. ([지급결제 용어집의 clearing 정의](https://www.ecb.europa.eu/services/glossary/html/act7c.en.html), [국제 지급결제 용어집](https://www.bis.org/cpmi/glossary.pdf))

T0부터 T4까지는 대표적인 이중 메시지 거래의 논리 순서입니다. 이 표와 별도로 관리할 가맹점 지급과 카드회원 청구·납부는 서로를 기다리는 하나의 직렬 절차가 아니라, 각 계약과 청구 주기에 따라 독립적으로 진행되는 일정입니다.

| 독립 후속 일정 | 주요 판단·기록 | 돈의 효과 |
| --- | --- | --- |
| 가맹점 정산·지급 | 매입사나 결제대행 계약에 따라 수수료·보류·환불 등을 반영합니다. | 가맹점 계좌에 계약상 금액이 입금됩니다. |
| 카드회원 청구·납부 | 신용카드라면 발급기관이 회원에게 청구하고 회원이 정한 납부일에 대금을 냅니다. | 카드회원과 발급기관 사이의 별도 채권이 이행됩니다. |

환불도 하나의 고정된 날짜에만 생기지 않습니다. 기관 간 결제 전에 취소·조정될 수도 있고, 결제나 가맹점 지급 뒤에 반대 방향 거래로 처리될 수도 있습니다. 어떤 원거래 효과를 되돌리는지와 현재 처리 단계를 함께 기록해야 합니다.

### 11.2 서로 다른 세 가지 “정산”을 한 단어로 부르지 않는다

실무에서 `정산`이라는 말은 다음 셋을 섞어 쓰기 쉽습니다.

1. 카드망과 발급·매입기관 사이의 기관 간 결제
2. 매입사·결제대행 계층이 가맹점에 지급하는 가맹점 정산
3. 카드회원이 발급기관에 카드대금을 납부하는 회원 청구·상환

42,800원 승인이 났다고 이 세 자금 흐름이 동시에 완료되는 것은 아닙니다. 각각 주체, 시점, 금액, 수수료, 실패 복구가 다릅니다.

### 11.3 승인과 매출 확정 금액이 달라질 수 있다

업종과 계약에 따라 처음 승인한 금액과 최종 매출 금액이 달라질 수 있습니다. 사전 승인, 증액 승인, 부분 매입, 지연 매입 같은 정책이 존재할 수 있기 때문입니다. 시스템은 `authorizedAmount`와 `capturedAmount`, `settledAmount`, `merchantPayoutAmount`를 한 필드로 합치지 않아야 합니다.

## 12. 결제 시스템은 어떤 상태와 식별자를 보관해야 하는가

`SUCCESS/FAIL` 하나로는 인증, 승인, 매입, 돈 이동을 복구할 수 없습니다. 최소한 다음 축을 분리합니다.

```text
authenticationStatus:
  NOT_STARTED
  PROCESSING
  CHALLENGE_REQUIRED
  SUCCEEDED
  FAILED
  UNAVAILABLE
  UNKNOWN

authorizationStatus:
  NOT_REQUESTED
  PROCESSING
  APPROVED
  DECLINED
  UNKNOWN

captureStatus:
  NOT_CAPTURED
  PARTIALLY_CAPTURED
  CAPTURED

reversalStatus:
  NONE
  PROCESSING
  REVERSED
  UNKNOWN

clearingStatus:
  NOT_CLEARED
  PROCESSING
  CLEARED
  UNKNOWN

interbankSettlementStatus:
  NOT_SETTLED
  PROCESSING
  SETTLED
  UNKNOWN

merchantPayoutStatus:
  NOT_SCHEDULED
  SCHEDULED
  PROCESSING
  PAID
  HELD
  UNKNOWN

refundStatus:
  NONE
  PROCESSING
  PARTIALLY_REFUNDED
  REFUNDED
  UNKNOWN

disputeStatus:
  NONE
  OPEN
  CHARGEBACK
  RESOLVED
```

이 상태명은 설명용 예시입니다. 실제 카드 프로그램과 회사의 상태 코드를 그대로 복사하라는 뜻은 아닙니다. 중요한 것은 한 축의 성공이 다른 축의 성공을 덮어쓰지 않게 하는 것입니다.

### 12.1 운영에서 연결해야 할 식별자

| 범위 | 대표 식별자 | 용도 |
| --- | --- | --- |
| 주문 | `merchantOrderId` | 주문과 결제 관계 확인 |
| 결제 의도 | `paymentId` | 전체 결제 상태의 내부 기준점 |
| 멱등성 | `idempotencyKey` | 동일 논리 요청의 중복 생성 방지 |
| 3DS | `threeDSServerTransId`, `dsTransId`, `acsTransId` | 인증 요청·응답·challenge·장애 추적 |
| 금융 승인 | `authorizationRequestId`, 카드망 거래 ID, 승인 코드 | 승인 결과 조회·취소·매입 연결 |
| 매입·청산 | 매입 참조 ID, 청산 배치·거래 ID | 승인과 매입 대사 |
| 가맹점 정산 | 정산 배치·지급 ID | 가맹점 지급과 내부 원장 대사 |
| 사후 조정 | 원거래 ID, reversal·refund·chargeback ID | 원거래와 조정 거래 연결 |

카드번호 전체, 인증 비밀번호, PIN, 일회용 인증번호, 생체 원본은 이 운영 식별자 표에 들어가지 않습니다. 카드 데이터는 토큰화·마스킹·접근 통제 등 별도의 보안 범위로 관리해야 합니다.

## 13. API와 신뢰 경계를 어떻게 설계하는가

커머스와 결제 서비스 사이의 API는 3DS 내부 메시지를 그대로 노출하기보다, 결제 의도의 상태와 다음 행동을 표현하는 편이 안전합니다. 다음은 업체 중립적인 예시입니다.

### 13.1 결제 의도를 만든다

```http
POST /v1/card-payment-intents
Idempotency-Key: 4d39f653-ff51-4975-87df-29b17fc8e552
Content-Type: application/json
```

```json
{
  "merchantOrderId": "order_20260719_0428",
  "amount": 42800,
  "currency": "KRW",
  "paymentMethodId": "pm_card_7H2K",
  "customerReference": "cust_271",
  "returnUrl": "https://shop.example.invalid/payments/return"
}
```

```json
{
  "paymentId": "pay_01K0A8M5JX",
  "status": "REQUIRES_AUTHENTICATION",
  "clientAction": {
    "type": "START_3DS",
    "url": "https://payments.example.invalid/actions/act_01K0A8"
  }
}
```

`customerReference`는 커머스 고객을 추적하기 위한 참조일 뿐 인증 증거가 아닙니다. 커머스는 먼저 자기 로그인·세션에서 주문을 요청한 회원을 인증하고, 자기 서버 자격증명으로 결제 서비스를 호출합니다. 결제 서비스는 호출한 가맹점 서버를 인증한 뒤, 저장 카드 등록 때 만들어 둔 `(merchantId, commerceCustomerId, paymentMethodId)`의 사용 허용 관계를 서버 측에서 조회합니다. 요청 본문에 같은 문자열을 다시 보냈다는 이유로 그 관계를 만들면 안 됩니다.

발급기관은 이 커머스 회원 ID를 신원 판정의 기준으로 삼지 않습니다. 카드번호나 결제 토큰으로 자기 카드 계정과 계약상 사용 관계를 찾고, 3DS 거래 식별자와 위험 신호를 사용해 인증 결과를 만듭니다. 결제 서비스는 커머스 쪽의 사용 허용 관계와 카드 쪽의 인증 결과를 `paymentId`에 연결합니다. 따라서 어느 한 참여자도 다른 참여자의 고객 데이터베이스를 복제할 필요가 없고, `customerReference` 문자열 하나가 고객과 카드의 관계를 증명하지도 않습니다.

### 13.2 고객은 인증 경계에서 직접 인증한다

고객 브라우저나 앱은 `clientAction`을 수행해 3DS 인증을 진행합니다. 커머스 API에는 다음 필드를 두지 않습니다.

```json
{
  "cardPassword": "금지",
  "issuerAppPin": "금지",
  "otp": "금지",
  "biometricTemplate": "금지"
}
```

이 값들은 커머스 서버를 통과하지 않습니다. 인증을 맡은 발급기관·ACS 채널 또는 기기 보안영역에서 처리합니다.

### 13.3 브라우저 복귀는 완료 통지가 아니다

```http
GET /payments/return?paymentId=pay_01K0A8M5JX
```

이 URL은 고객을 적절한 화면으로 돌려보내기 위한 것입니다. 쿼리 문자열의 `success=true`, 화면에 표시된 문구, 앱 복귀 이벤트로 주문을 완료하면 안 됩니다.

커머스 서버는 결제 서비스의 서버 API를 조회하거나 서명된 서버 콜백을 받아 현재 상태를 확인합니다.

```http
GET /v1/card-payment-intents/pay_01K0A8M5JX
Authorization: Bearer <merchant-server-credential>
```

```json
{
  "paymentId": "pay_01K0A8M5JX",
  "authenticationStatus": "SUCCEEDED",
  "authorizationStatus": "PROCESSING",
  "captureStatus": "NOT_CAPTURED",
  "reversalStatus": "NONE",
  "clearingStatus": "NOT_CLEARED",
  "interbankSettlementStatus": "NOT_SETTLED",
  "merchantPayoutStatus": "NOT_SCHEDULED",
  "refundStatus": "NONE"
}
```

이 응답은 인증은 성공했지만 금융 승인 결과가 아직 확정되지 않았음을 보여 줍니다. 주문을 `PAID`로 바꾸기에는 이릅니다.

### 13.4 금융 승인을 멱등하게 요청한다

결제 서비스가 인증 뒤 자동으로 승인을 요청할 수도 있고, 커머스가 주문을 재확인한 뒤 confirm API를 호출할 수도 있습니다. 어느 구조든 한 논리 결제에 안정된 승인 요청 ID를 사용해야 합니다.

```http
POST /v1/card-payment-intents/pay_01K0A8M5JX/confirm
Idempotency-Key: confirm-order_20260719_0428-v1
```

```json
{
  "merchantOrderId": "order_20260719_0428",
  "expectedAmount": 42800,
  "expectedCurrency": "KRW"
}
```

결제 서비스는 인증 때와 금액·통화·가맹점·결제수단이 일치하는지 확인하고, 최초 실행자만 `authorizationStatus`를 `PROCESSING`으로 바꿔 하나의 안정된 `authorizationRequestId`를 만듭니다. 네트워크 재시도는 같은 논리 ID와 연동 규칙을 사용합니다.

### 13.5 상태 변경은 서버 콜백과 조회로 수렴시킨다

```json
{
  "eventId": "evt_01K0A9C2",
  "type": "card_payment.authorization_updated",
  "occurredAt": "2026-07-19T05:28:17Z",
  "resourceVersion": 7,
  "data": {
    "paymentId": "pay_01K0A8M5JX",
    "authenticationStatus": "SUCCEEDED",
    "authorizationStatus": "APPROVED",
    "authorizedAmount": 42800,
    "captureStatus": "NOT_CAPTURED",
    "reversalStatus": "NONE",
    "clearingStatus": "NOT_CLEARED",
    "interbankSettlementStatus": "NOT_SETTLED",
    "merchantPayoutStatus": "NOT_SCHEDULED",
    "refundStatus": "NONE"
  }
}
```

수신자는 서명, 전송 시각 허용 범위, 이벤트 중복, `resourceVersion`의 단조 증가, 결제 소유권을 확인합니다. 버전이 건너뛰거나 허용되지 않은 상태 전이가 보이면 이벤트 내용을 추측하지 말고 결제 조회 API로 원본 상태를 다시 읽습니다.

## 14. 실패와 응답 유실을 어떻게 복구하는가

### 14.1 인증 성공 뒤 승인 거절

```text
authenticationStatus = SUCCEEDED
authorizationStatus  = DECLINED
```

이는 모순이 아닙니다. 3DS 인증 기준은 충족되었지만 발급기관이 한도·계정 상태·승인 시점의 위험 정책상 거래를 거절한 것입니다. 무마찰 흐름이라면 고객이 등록 인증수단을 직접 조작하지 않았을 수도 있습니다. 인증을 다시 반복하기보다 거절 사유 정책에 따라 다른 결제수단을 안내하거나 주문을 보류합니다.

### 14.2 challenge 실패·포기

고객이 인증 화면을 닫거나 자격증명 검증에 실패하면 금융 승인을 요청하지 않는 것이 기본입니다. 결제 의도는 `AUTHENTICATION_FAILED`, `CANCELED`, `EXPIRED`처럼 원인을 보존합니다. 단순 `FAIL` 하나로 만들면 사용자가 다시 시도할 수 있는지 판단하기 어렵습니다.

### 14.3 인증망 장애

ACS나 디렉터리 서버가 일시적으로 응답하지 않을 수 있습니다. 이때 무조건 인증 실패로 확정할지, 표준과 프로그램 규칙이 허용하는 대체 흐름을 사용할지, 거래를 중단할지는 결제수단·지역·위험 정책에 따라 다릅니다. 서비스가 임의로 인증 성공을 만들어 내면 안 됩니다.

### 14.4 인증 성공 뒤 승인 요청의 응답 시간 초과

승인 요청을 보낸 뒤 응답 시간이 초과(timeout)되었다면 결과는 `DECLINED`가 아니라 `UNKNOWN`일 수 있습니다. 발급기관이 승인하고 응답만 유실했을 가능성이 있기 때문입니다.

```text
1. authorizationRequestId = authz_01K0A9 생성
2. 승인 요청 전송
3. 응답 시간 초과
4. 같은 거래를 새 ID로 즉시 재승인하지 않음
5. 결과 조회 또는 계약상 안전한 동일 요청 재전송
6. APPROVED / DECLINED / 수동 대사 필요 상태로 수렴
```

연동망이 중복 제거 키나 결과 조회를 제공하지 않으면 자동 재시도를 보수적으로 제한하고, 미확정 거래 대기열과 대사 절차를 마련해야 합니다.

뒤늦게 `APPROVED`가 확인되면 주문 상태와 다시 대조합니다. 주문이 아직 이행 가능하면 동일한 승인 결과로 주문을 **정확히 한 번만** 확정합니다. 주문이 이미 만료·취소되었거나 재고를 제공할 수 없다면 새 승인을 만들지 않고, 원래 `authorizationRequestId`와 승인 식별자에 연결된 승인 취소를 멱등하게 요청합니다. 이때 `reversalStatus`를 `PROCESSING`, `REVERSED`, `UNKNOWN`으로 분리해 승인 사실을 지우지 않고 보상 처리의 진행 상태를 남깁니다.

### 14.5 승인 성공 뒤 응답 유실

발급기관이 승인했지만 커머스가 결과를 받지 못하면 사용자는 결제 실패로 보고 다시 시도할 수 있습니다. 이 경우 같은 주문에 두 번째 논리 결제를 만들기 전에 기존 `paymentId`와 `authorizationRequestId`의 상태를 조회합니다. 서버 콜백, 승인 결과 조회, 카드망·매입 자료 대사를 통해 한 주문의 승인 효과가 한 번인지 확인합니다.

조회 결과가 뒤늦게 승인으로 확정되었을 때도 주문이 이행 가능하면 한 번만 확정하고, 이미 취소·만료되었다면 원승인에 연결한 승인 취소로 보상합니다. 승인 취소 응답마저 유실되면 실패로 단정해 다른 취소를 새로 만들지 않습니다. 동일한 취소 식별자로 결과를 조회하거나 계약상 안전하게 재전송하고, 끝내 확정하지 못하면 `reversalStatus=UNKNOWN`으로 두어 대사 대상에 올립니다.

### 14.6 브라우저는 성공인데 서버 결과가 없다

성공 화면은 주문 완료 조건이 아닙니다. 커머스는 `PROCESSING` 화면을 보여 주고 서버 상태를 조회합니다. 일정 시간 뒤에도 결과가 없으면 결제를 `UNKNOWN` 또는 수동 확인 상태로 남깁니다. 사용자의 화면 새로고침이 새 금융 승인을 만들지 않아야 합니다.

## 15. 승인 이후의 취소·환불·차지백을 구분하기

사후 처리를 `취소` 하나로 합치면 어떤 돈의 효과를 되돌리는지 알 수 없습니다.

| 처리 | 대표 시점 | 되돌리려는 것 | 원거래에 남겨야 할 관계 |
| --- | --- | --- | --- |
| 승인 취소(reversal) | 승인 직후, 매입 전 | 승인으로 잡힌 한도·금액 확보 | 원승인 요청·승인 ID |
| 매입 전 취소 | 승인되었지만 매출 확정 전 | 매출 제출을 중단하고 필요하면 승인을 해제 | 원결제와 취소 사유 |
| 매입 후 환불(refund) | 매출 확정·청산 이후 | 이미 성립한 매출의 전부 또는 일부를 반대 방향 거래로 반환 | 원매입·환불 ID, 금액 |
| 차지백(chargeback) | 카드회원 분쟁과 규칙 절차 이후 | 분쟁 결과에 따라 거래 책임과 자금을 조정 | 원거래·분쟁·증빙·판정 ID |

승인 취소나 환불이 성공해도 원결제의 과거 승인 기록을 삭제하면 안 됩니다. 원거래와 반대 방향의 조정 거래를 연결해야 대사와 감사를 재구성할 수 있습니다.

부분 환불과 여러 차례 환불을 허용한다면 다음 불변식을 검사합니다.

```text
sum(successfulRefundAmounts) <= capturedAmount
```

동시 환불 요청에서도 이 불변식이 깨지지 않도록 원자적 상태 전이와 멱등성 키가 필요합니다.

## 16. 자주 생기는 오해를 바로잡기

### “발급기관은 매번 주민등록상 본인인지 확인합니다.”

보통 그렇지 않습니다. 법적 신원 확인은 카드 발급·등록·복구 같은 시점에 수행될 수 있습니다. 결제 시점의 3DS 인증은 카드 계정과 거래·기기 신호가 발급기관의 인증 기준을 충족하는지 평가합니다. 추가 확인이 필요한 경우에만 등록 인증수단의 통제를 확인합니다.

### “통신사 인증 앱을 PG가 호출해 본인 인증을 끝냅니다.”

가능한 구현 중 하나일 뿐입니다. 통신사 가입자 기반 본인확인은 별도 신원확인 수단이며 카드 등록·복구·추가 확인 등에 사용될 수 있습니다. 모든 PG와 모든 카드 결제의 공통 3DS 단계는 아닙니다.

### “카드사 화면으로 이동했으니 승인망에 들어간 것입니다.”

화면 이동은 카드회원 인증을 위한 사용자 경험일 수 있습니다. 3DS 인증 메시지와 금융 승인 전문은 별도 경로입니다. 승인 요청은 인증 결과를 받은 뒤 계약된 매입 측 처리 경계를 거쳐 발급기관 승인계로 갑니다. 역할이 분리된 구조에서는 별도 카드망을 거칠 수 있고, 역할이 결합되거나 직접 연결된 계약에서는 경로가 더 짧을 수 있습니다.

### “인증에 성공하면 카드 결제도 승인됩니다.”

아닙니다. 인증 결과는 승인 판단의 입력입니다. 발급기관은 한도, 계정 상태, 업종·지역 제한, 부정 사용 위험 등을 다시 판단합니다.

### “무마찰 인증은 인증을 생략한 것입니다.”

아닙니다. 사용자에게 추가 값을 입력받지 않았다는 뜻입니다. ACS는 거래·기기·계정 정보를 바탕으로 위험을 평가하고 인증 결과를 만듭니다.

### “승인 시점에 가맹점이 돈을 받습니다.”

아닙니다. 승인은 거래를 받아들이겠다는 발급기관의 판단이며 가용한도 반영이 생길 수 있습니다. 매출 확정, 청산, 기관 간 결제, 가맹점 지급은 뒤의 별도 단계입니다.

### “VAN이 카드 결제를 승인합니다.”

VAN은 승인 관련 메시지를 중계할 수 있습니다. 최종 승인 판단은 발급기관 책임입니다. 제한된 상황의 대행승인처럼 예외적인 규칙이 있을 수 있지만, 이를 모든 거래의 기본 구조로 일반화하면 안 됩니다.

### “성공 화면으로 돌아오면 주문을 완료하면 됩니다.”

아닙니다. 화면 복귀(redirect)는 조작되거나 중복될 수 있고, 인증 뒤 승인이 아직 처리 중일 수 있습니다. 서버가 인증·승인 상태를 조회하거나 검증된 서버 콜백을 받아야 합니다.

## 17. 문서를 덮고 다시 설명해 보기

다음 질문에 자기 말로 답할 수 있으면 핵심 구조를 이해한 것입니다.

1. 카드 발급 때의 법적 신원 확인과 결제 때의 카드회원 인증은 무엇이 다른가요?
2. 커머스 고객 ID와 발급기관 카드회원 ID가 같지 않은데도 어떻게 같은 결제를 연결하나요?
3. 무마찰 인증에서 고객이 값을 입력하지 않아도 왜 “인증 없음”이 아닌가요?
4. challenge에서 비밀번호·PIN·일회용 번호·생체 원본은 어느 경계에 머물러야 하나요?
5. ARes와 RReq는 각각 어느 상황에서 인증 결과를 운반하나요?
6. 발급기관 앱에서 결제 앱으로 돌아온 사실만으로 결제 성공을 확정하면 왜 안 되나요?
7. 3-D Secure 인증 경로와 금융 승인 경로는 어떻게 다른가요?
8. 국내 VAN은 어느 경로에서 어떤 역할을 할 수 있나요?
9. 인증 성공 뒤 발급기관이 거래를 거절할 수 있는 이유는 무엇인가요?
10. 인증→승인→매출 확정→청산→기관 간 결제의 대표 순서와, 가맹점 지급·카드회원 납부가 왜 독립 일정인지 설명해 보세요.
11. 승인 요청의 응답 시간 초과를 곧바로 실패로 기록하면 어떤 중복 결제가 생길 수 있나요?
12. reversal, 매입 전 취소, refund, chargeback은 각각 무엇을 되돌리나요?

작은 설계 검증도 해 볼 수 있습니다. 42,800원 결제 한 건에 대해 인증 성공 뒤 승인 응답을 잃어버리는 상황을 적고, 다음을 확인합니다.

1. 브라우저를 새로고침해도 새 `paymentId`나 승인 요청이 생기지 않아야 합니다.
2. 같은 `authorizationRequestId`로 결과를 조회하거나 계약상 안전한 재전송을 해야 합니다.
3. 조회 결과가 승인이라면 주문은 한 번만 완료되어야 합니다.
4. 결과를 확인할 방법이 없다면 자동 실패·재결제 대신 `UNKNOWN`과 수동 대사 대상으로 남아야 합니다.
