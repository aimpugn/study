# 결제 인증·거래 허용·자금 이동을 분리하는 간편 계좌이체 설계

등록된 계좌로 결제한다는 말에는 서로 다른 네 가지 판단이 숨어 있습니다. 고객이 누구인지 확인하는 **고객 인증**, 그 고객이 지금 이 금액과 수취인에 동의했는지 확인하는 **고객 거래 허용**, 실제 출금 요청을 처리할지 금융기관이 판단하는 **기관 승인·접수**, 주문이 아직 유효한지 커머스가 확인하는 **주문 재확인**입니다. 이 네 판단을 `승인`이라는 단어 하나와 `SUCCESS/FAIL` 상태 하나로 합치면 비밀번호 노출, 금액 바꿔치기, 중복 출금, 타임아웃 오판, 정산 불일치를 막기 어렵습니다.

이 문서는 인증과 거래 허용의 역사적 맥락에서 출발해 실제 돈이 움직이는 단계, 등록 계좌 결제 API의 신뢰 경계, 중복과 타임아웃을 복구하는 방법까지 한 흐름으로 연결합니다. 특정 지급망의 구현을 보편적인 구조로 단정하지 않고, 계약에 따라 달라지는 부분과 여러 결제 시스템에 공통으로 적용할 설계 원칙을 구분합니다.

## 핵심 요약

> 등록 계좌는 사용할 수 있는 결제수단이 준비되었다는 뜻이지, 앞으로의 모든 출금이 허용되었다는 뜻은 아닙니다. 먼저 커머스 서버가 금액·통화·수취인·결제수단이 고정된 결제 의도를 만들고, 고객은 결제 서버가 통제하는 채널에서 직접 인증한 뒤 그 거래를 허용해야 합니다. 커머스 서버는 고객 비밀번호나 재사용 가능한 거래 허용 토큰을 받지 않습니다. 고객 허용이 끝나면 커머스 서버가 주문 금액과 재고를 다시 확인하고 결제 실행을 요청합니다. 결제 서버는 하나의 논리적 지급 지시와 안정된 외부 요청 ID만 만들도록 상태를 원자적으로 바꿉니다. 전송 재시도는 같은 ID를 사용하며, 실제 자금 효과가 한 번이라는 보장은 외부 지급망의 중복 제거 또는 결과 조회 계약과 함께 닫습니다. 결과는 서버 조회, 결제 서버가 상태 변화를 밀어 주는 서명된 웹훅(webhook), 내부 기록과 기관 기록을 맞추는 대사로 확정합니다. 인증 성공은 돈 이동 성공이 아니며, 외부 호출의 타임아웃도 곧바로 실패가 아닙니다.

가장 중요한 문장은 “등록은 준비이고, 현재 거래 허용은 별도다”입니다. 나머지 API와 상태는 이 구분을 시스템으로 보존하기 위해 따라옵니다.

## 1. 설계에서 먼저 분리해야 할 문제

계좌 결제 설계는 API 이름이나 데이터베이스 개수부터 정하면 쉽게 꼬입니다. 먼저 각 단계가 누구의 질문에 답하는지, 어떤 증거를 만들며, 실제 돈은 언제 움직이는지를 분리해야 합니다. 다음 혼합은 특히 자주 발생합니다.

| 흔한 혼합 | 왜 문제가 되는가 | 설계에서 분리할 것 |
| --- | --- | --- |
| 인증과 승인 | 고객 확인, 현재 거래 허용, 기관 처리 판단, 주문 재확인이 `승인` 하나에 섞인다. | 판단 주체·입력·증거·실패·유효기간 |
| API 응답과 돈의 이동 | `202`나 내부 `SUCCEEDED`만 보고 계좌 증감·최종성·정산까지 끝났다고 오해한다. | 지급 지시, 계좌 반영, 청산·최종 결제, 가맹점 정산 |
| 처리계·정보계·정산 저장소 | 물리적인 데이터베이스를 먼저 나누면 상태를 누가 바꿀 수 있는지가 흐려진다. | 원본 상태의 소유자, 쓰기 권한, 조회 모델, 대사 입력 |
| 결제 중계와 최종 판단 | 중계 계층이 고객·커머스·기관의 결정을 모두 대신한다고 오해한다. | 오케스트레이션 책임과 각 판단 주체의 책임 |
| 등록 계좌와 현재 출금 허용 | 등록된 식별자가 있으면 어떤 금액과 수취인으로도 바로 출금할 수 있다고 오해한다. | 등록 관계, 위임 범위, 현재 거래 내용, 기관 처리 결과 |
| 자격증명 보호와 암호화 | 비밀번호를 암호화해 전달하면 중간 서버가 받아도 안전하다고 오해한다. | 자격증명을 보지 않는 직접 인증 경계와 거래별 증거 |
| `used=true`와 `SUCCESS/FAIL` | boolean 하나로 동시 실행·미확정 결과·반환·정산을 표현하려 한다. | 원자적 상태 전이, 안정된 외부 요청 ID, 다축 상태, 대사 |

여기서 처리계·정보계·정산 데이터베이스를 반드시 물리적으로 세 개 둬야 한다는 결론은 나오지 않습니다. 먼저 하나의 결제 상태를 누가 바꿀 수 있는지, 어떤 조회 모델이 필요한지, 정산과 대사가 어떤 원본 기록을 읽는지를 정해야 합니다. 물리 분리는 부하, 장애 격리, 보존 기간이 실제로 달라질 때 선택할 구현 문제입니다.

## 2. `승인`이라는 말을 네 질문으로 풀어야 한다

한국어의 `승인`은 결제 대화에서 여러 영어 용어와 업무 판단을 한꺼번에 가리킵니다. 설계할 때는 단어보다 **누가 무엇을 판단하는가**를 먼저 말해야 합니다.

| 구분 | 판단하는 주체 | 실제 질문 | 산출물 | 대표 실패 | 보통의 유효기간 |
| --- | --- | --- | --- | --- | --- |
| 고객 인증(authentication) | 고객 인증을 맡은 결제·금융 경계 | “지금 조작하는 사람이 등록된 고객인가?” | 인증 세션, 인증 결과, 인증 강도 | 자격증명 불일치, 추가 인증 필요, 잠금 | 짧은 세션 또는 인증 정책 범위 |
| 고객 거래 허용(transaction authorization/consent) | 고객 | “이 금액·통화·수취인·결제수단의 거래를 허용하는가?” | 특정 결제 의도에 결합된 내부 증거 | 고객 거절, 의도 변경, 만료 | 한 거래 또는 명시된 위임 범위 |
| 기관 승인·접수(payment authorization/acceptance) | 계좌를 관리하거나 지급을 처리하는 기관 | “잔액·계좌 상태·위험·규정상 이 요청을 처리할 수 있는가?” | 접수 ID, 승인/거절 결과, 처리 상태 | 잔액 부족, 계좌 제한, 위험 거절 | 해당 지급망과 거래 생명주기 |
| 주문 재확인(merchant confirmation) | 커머스 서버 | “주문·금액·재고·취소 상태가 아직 유효한가?” | 실행 명령, 취소 결정 | 금액 불일치, 재고 만료, 주문 취소 | 해당 주문 확인 시점 |

접근 제어 문맥의 **권한 부여(authorization)**도 별도입니다. 예를 들어 “이 서버가 이 결제 의도를 조회할 권한이 있는가?”는 객체 접근 권한 문제입니다. “금융기관이 이 출금 거래를 처리하기로 했는가?”라는 거래 승인과 이름은 같지만 질문이 다릅니다. 그래서 이 문서에서는 가능한 한 `고객 거래 허용`, `기관 승인·접수`, `주문 재확인`, `객체 접근 권한`처럼 주체나 목적을 붙입니다.

다음 두 문장은 동시에 참일 수 있습니다.

- 고객 인증은 성공했지만 잔액이 부족해 기관이 거래를 거절한다.
- 사전 위임의 범위 안에서 반복 출금이 실행되어, 그 시점에 대화형 고객 인증이 없더라도 유효한 거래가 될 수 있다.

즉 인증 성공은 결제 성공의 충분조건도 아니고, 모든 합법적인 결제가 매번 대화형 인증을 요구하는 것도 아닙니다.

## 3. 인증과 거래 승인은 왜 따로 발전했는가

인증과 거래 승인의 역사를 하나의 직선으로 설명하면 안 됩니다. 카드 비대면 인증이 발전한 축과 계좌 기반 서비스에서 동의·등록·거래 허용이 발전한 축은 출발점과 규칙이 다릅니다. 다만 두 축 모두 “누구인가”와 “이 거래를 처리할 것인가”가 다른 질문이라는 공통 원리를 보여 줍니다.

### 3.1 카드 거래에는 원래 기관의 거래 판단이 있었다

카드 거래에서 발급 측 기관은 계정 상태, 사용 가능 한도, 부정 사용 위험 등을 바탕으로 거래를 승인하거나 거절합니다. 거래 승인과 구매자 인증을 별도 절차로 설명하는 현재 표준을 바탕으로 보면, 기관의 거래 판단에 비대면 구매자 확인 문제가 추가되었다고 이해할 수 있습니다. 다만 이는 두 절차의 관계를 설명하는 역사적 해석이지, 모든 지급망이 같은 순서로 발전했다는 뜻은 아닙니다. 비대면 거래에서는 카드를 직접 제시하거나 서명을 눈앞에서 확인할 수 없으므로 “지금 결제하는 사람이 정당한 사용자라는 증거가 충분한가?”라는 문제가 특히 커졌습니다.

비대면 카드 인증 표준의 초기 버전은 2001년에 개발되었고, 더 다양한 기기·위험 기반 인증을 지원하는 2.0은 2016년에 공개되었습니다. 이 표준의 설명도 구매자 인증과 그 뒤의 통상적인 거래 승인 처리를 구분합니다. 인증 결과는 기관 승인 판단의 **입력**이 될 수 있지만, 잔액·한도·계정 상태·위험 판단을 대신하지는 않습니다. ([비대면 카드 인증 표준 개요](https://www.emvco.com/wp-content/uploads/2022/09/Quick-Resource_-EMV-3DS-for-E-Commerce.pdf))

### 3.2 메시지가 한 번이라고 의미가 하나인 것은 아니다

어떤 지급망은 승인 메시지와 청산 메시지를 나누고, 어떤 지급망은 한 메시지 흐름에 결합합니다. 전자는 흔히 dual-message, 후자는 single-message 구조라고 부릅니다. 이 차이는 네트워크 왕복과 처리 방식의 차이이지, 고객 인증·기관 판단·회계상 최종성이 모두 같은 개념이라는 뜻이 아닙니다. ([직불카드 메시지 구조 설명](https://www.federalreserve.gov/paymentsystems/regii-average-interchange-fee.htm))

따라서 “반드시 HTTP API를 세 번 호출해야 분리된 설계”도 아니고, “한 호출에 실렸으니 같은 단계”도 아닙니다. 분리의 핵심은 다음 세 가지입니다.

1. 각 판단의 입력과 책임자가 구분된다.
2. 각 판단의 결과와 유효기간이 따로 기록된다.
3. 한 판단의 성공을 다른 판단의 성공으로 오해하지 않는다.

### 3.3 계좌 기반 서비스에서는 등록과 거래 실행이 분리된다

국내 공공 오픈뱅킹 안내는 사용자 인증·동의·계좌 등록을 서비스 API 사용을 위한 준비 과정으로 두고, 출금·입금 같은 금융 API를 별도로 제공합니다. 이는 계좌 등록이 실제 모든 출금을 완료했다는 뜻이 아니라, 이후 서비스가 참조할 수 있는 관계와 식별자를 준비했다는 뜻입니다. ([사용자 인증 안내](https://openapi.kftc.or.kr/openapi/openbanking/userAuth), [서비스 안내](https://openapi.kftc.or.kr/service/openBanking))

국내 법에서도 추심이체처럼 수취 측이 출금을 시작하는 유형은 지급인의 사전 동의를 별도로 다룹니다. 철회 가능 시점과 예외는 거래 유형과 약정에 따라 달라집니다. 이 조문은 모든 계좌이체가 같은 동의 구조라는 증거가 아니라, **출금 권한의 근거와 범위를 명시해야 한다**는 국내 추심이체의 경계입니다. ([전자금융거래법 제15조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0015&lsiSeq=280277&urlMode=lsScJoRltInfoR))

미국의 계좌 기반 결제 사례에서는 고객의 은행 로그인 자격증명이 제3자에게 전달되지 않고, 고객이 금액과 수취인을 확인한 뒤 백엔드의 승인·청산·최종 결제가 이어지는 흐름을 설명합니다. 이 사례는 “자격증명 직접 채널”과 “거래 내용 확인”의 좋은 비교 자료지만, 국내 또는 모든 지급망의 규칙으로 일반화해서는 안 됩니다. ([계좌 기반 결제 연구 노트](https://www.federalreserve.gov/econres/notes/feds-notes/pay-by-bank-and-the-merchant-payments-use-case-benefits-20250707.html))

## 4. 분리는 보안 기능이 아니라 전체 결제 계약이다

인증과 거래 허용을 나누는 이유를 “보안상 좋다”로만 끝내면 실제 설계로 이어지지 않습니다. 분리해야 하는 이유는 증거의 대상, 생명주기, 실패 복구가 다르기 때문입니다.

### 4.1 인증 증거와 거래 증거가 가리키는 대상이 다르다

인증은 사람이나 세션을 가리킵니다. 거래 허용은 다음과 같은 **거래 내용 묶음**을 가리켜야 합니다.

```text
(merchantId, merchantOrderId, paymentId,
 amount, currency, payee, paymentMethodId,
 authorizationNonce, expiresAt)
```

이 묶음을 불변 거래 tuple이라고 부르겠습니다. tuple은 여러 값을 순서 있는 한 묶음으로 본다는 뜻이고, `authorizationNonce`는 증거 재사용을 막기 위한 일회성 난수(nonce)입니다. 고객이 42,800원 결제를 허용한 뒤 커머스가 금액을 52,800원으로 바꿀 수 있다면, 고객 인증은 진짜여도 거래 허용 증거는 더 이상 유효하지 않습니다. 금액·통화·수취인·결제수단 중 하나라도 바뀌면 기존 증거를 폐기하고 새 결제 의도에서 다시 허용받아야 합니다.

### 4.2 증거의 생명주기가 다르다

로그인 세션은 여러 화면에서 일정 시간 재사용할 수 있습니다. 반면 일회성 거래 허용은 한 결제 의도에만 쓰이고 짧게 만료되는 편이 안전합니다. 반복 출금 위임은 더 오래 지속될 수 있지만, 그 대신 다음 범위가 계약에 들어가야 합니다.

- 허용된 수취인과 결제 목적
- 건별·일별·월별 한도
- 시작일과 종료일
- 고객 통지와 철회 방법
- 실패·재시도 횟수
- 위임을 식별하고 감사할 수 있는 식별자

따라서 `accountRegistered=true`나 범용 로그인 token 하나로 모든 생명주기를 표현할 수 없습니다.

### 4.3 실패 영역이 다르다

고객 인증이 실패하면 자격증명 재입력이나 추가 인증으로 돌아갑니다. 고객이 거래를 거절하면 결제 의도를 취소하거나 다른 수단을 선택합니다. 기관이 잔액 부족으로 거절하면 주문을 유지한 채 다른 수단을 시도할 수도 있습니다. 커머스의 재확인이 실패하면 이미 얻은 거래 허용 증거를 사용하지 않고 주문부터 다시 계산해야 합니다.

실패를 모두 `FAIL`로 만들면 사용자에게 무엇을 안내할지, 재시도가 안전한지, 같은 거래를 다시 실행해도 되는지 알 수 없습니다.

### 4.4 최소 권한과 침해 반경이 달라진다

커머스 서버가 고객 비밀번호를 받으면 그 서버의 로그, 추적 도구, 오류 수집, 운영자 권한, 백업까지 자격증명 보호 범위에 들어옵니다. 비밀번호를 암호화해 전달해도 커머스 서버가 평문을 입력받는 순간 노출 경계는 이미 넓어졌습니다.

일반적인 안전 원칙은 고객 자격증명을 인증을 맡은 경계에 직접 입력하게 하는 것입니다. OAuth 보안 표준이 중간 애플리케이션(client)이 사용자의 비밀번호를 받아 전달하는 방식을 금지하는 이유도 같은 공격면을 보여 줍니다. 다만 이 표준은 결제 API 자체의 직접 규범이 아니라, 비밀번호 대리 수집(proxy)이 왜 위험한지 보여 주는 유사 보안 근거입니다. ([OAuth 2.0 보안 모범 사례](https://www.rfc-editor.org/rfc/rfc9700.html))

## 5. 계좌가 등록되었다는 말의 정확한 뜻

등록된 계좌는 보통 다음 중 일부가 준비되었다는 뜻입니다.

- 고객과 결제수단을 연결하는 내부 식별자가 있다.
- 계좌 실재·예금주·사용 가능 여부를 정해진 절차로 확인했다.
- 필요한 동의나 위임의 근거와 버전을 보관한다.
- 원본 계좌번호 대신 실제 값을 감춘 참조 토큰(token) 또는 별칭을 사용한다.
- 동의 철회, 계좌 해지, 만료, 위험 차단 상태를 조회할 수 있다.

그러나 등록만으로는 다음 질문에 답하지 못합니다.

- 이번 결제 금액이 얼마인가?
- 수취인은 누구인가?
- 고객이 바로 이 거래를 보았는가?
- 주문 금액과 재고는 아직 유효한가?
- 계좌에 지금 충분한 잔액이 있는가?
- 외부 금융망이 이 요청을 처리했는가?

이를 자료구조로 보면 더 분명합니다.

```json
{
  "paymentMethodId": "pm_bank_7f2a",
  "customerReference": "cust_81d4",
  "status": "ACTIVE",
  "mandate": {
    "type": "ONE_TIME_ACTION_REQUIRED",
    "scope": null
  }
}
```

이 객체는 “사용 가능한 계좌 결제수단이 있다”는 사실을 표현합니다. 42,800원 주문을 결제한다는 현재 의도는 별도 객체입니다.

```json
{
  "paymentId": "pay_01J0W8G6K9",
  "merchantOrderId": "order_20260714_1042",
  "amount": { "value": 42800, "currency": "KRW" },
  "payee": "merchant_account_default",
  "paymentMethodId": "pm_bank_7f2a",
  "executionStatus": "REQUIRES_CUSTOMER_ACTION"
}
```

반복 출금 위임이 있다면 `mandate.type`과 `scope`가 달라지고, 매번 대화형 허용을 요구하지 않을 수 있습니다. 그래도 현재 거래가 위임의 수취인·금액·기간·횟수 범위 안인지 검사해야 합니다. “등록되어 있으니 바로 출금”이 아니라 “현재 의도가 등록 또는 위임 범위에 맞는지 판정한 뒤 실행”입니다.

## 6. 실제 돈은 언제 어디로 움직이는가

결제 시스템 디자인에서 가장 흔한 오류는 API 응답, 내부 상태, 실제 자금 이동을 같은 것으로 보는 것입니다. 아래 세 줄은 서로 다른 세계입니다.

```text
정보의 흐름: 고객 허용 증거, 주문 확인, 기관 응답, 웹훅
장부의 흐름: payment 상태, 원장 항목, 미수·미지급·정산 상태
자금의 흐름: 고객 계좌 감소, 수취 계좌 증가, 기관 간 최종 결제
```

### 6.1 단계별로 보면 인증 때는 돈이 움직이지 않는다

| 단계 | 일어나는 일 | 돈의 변화 |
| --- | --- | --- |
| 계좌 등록 | 고객·계좌·동의 관계와 참조 식별자를 준비한다. | 없음 |
| 결제 의도 생성 | 주문·금액·통화·수취인·결제수단을 고정한다. | 없음 |
| 고객 인증 | 지금 조작하는 고객을 확인한다. | 없음 |
| 고객 거래 허용 | 고객이 고정된 거래 내용을 확인하고 허용한다. | 없음 |
| 주문 재확인 | 커머스가 주문·금액·재고를 다시 검사하고 실행을 명령한다. | 아직 없음 |
| 지급 지시 송신 | 결제 서버가 안정된 외부 요청 ID로 금융 연결망에 출금을 요청한다. | 처리 방식에 따라 아직 미확정 |
| 기관 승인·접수와 계정 반영 | 기관이 잔액·계좌·위험을 판단하고 계좌 감소(debit)·증가(credit)를 기록한다. | 이 지점부터 실제 예금채권이 변할 수 있음 |
| 청산과 최종 자금 결제 | 기관 사이 채권·채무를 계산하고 최종 결제한다. | 기관 간 의무가 최종적으로 정리됨 |
| 가맹점 정산 | 집금형 계약이라면 수수료·취소·조정을 반영해 가맹점에 지급한다. | 집금 계좌에서 가맹점 계좌로 별도 이동 |

지급망에 따라 기관 승인·접수와 계좌 반영이 거의 동시에 보일 수도 있고, 중간 상태가 더 길 수도 있습니다. 따라서 `SUCCEEDED`가 “요청 접수”인지 “고객 계좌 감소 완료”인지 “수취 계좌 증가 완료”인지, 또는 “되돌릴 수 없다고 보는 최종성(finality)에 도달한 결제”인지 계약으로 정의해야 합니다.

### 6.2 돈의 경로는 계약에 따라 달라진다

**직접 수취형**에서는 고객 계좌에서 가맹점 계좌로 바로 이체될 수 있습니다.

```text
고객 계좌 ── 42,800원 ──> 가맹점 수취 계좌
                 ▲
        결제 서버는 지시·상태·대사를 중계
```

이 구조에서 결제 서버 운영 주체가 고객 돈을 보관한다고 단정할 수 없습니다. 수수료 청구나 별도 정산은 다른 흐름일 수 있습니다.

**집금 후 정산형**에서는 먼저 계약된 집금·정산 계좌로 받고, 이후 가맹점별 지급액을 계산해 정산합니다.

```text
고객 계좌 ── 42,800원 ──> 계약된 집금 계좌
                                  │
                    수수료·취소·조정·대사
                                  │
                                  └──> 가맹점 계좌
```

이 구조에서는 고객 결제 성공과 가맹점 정산 완료가 다른 상태입니다. 예를 들어 고객 출금은 성공했지만 가맹점 지급이 다음 영업일 배치에 포함될 수 있습니다.

**선불 잔액형**에서는 고객이 예전에 충전한 외부 자금과 지금 결제에서 줄어드는 내부 부채 원장이 서로 다른 시점에 움직일 수 있습니다.

```text
과거 충전: 고객 외부 자금 ──> 보관 계정
현재 결제: 고객 선불 잔액 원장 -42,800 / 가맹점 지급채무 +42,800
후속 정산: 보관 자금 ──> 가맹점 계좌
```

어느 구조가 실제인지는 계약, 인허가, 지급망 규칙, 자금 보관 방식으로 확인해야 합니다. 공개된 API 이름만 보고 집금 계좌나 내부 원장 구조를 추정하면 안 됩니다.

## 7. 흔한 4단계 API 초안을 검토하기

계좌 결제 API를 `prepare -> auth -> withdrawal -> query`로 나누는 접근은 준비·고객 행동·실행·복구를 구분한다는 장점이 있습니다. 그러나 단계 이름만으로 인증과 거래 허용이 분리되지는 않습니다. 각 endpoint의 신뢰 경계와 상태 전이를 함께 정해야 합니다.

### 7.1 준비 API

가맹점 주문 ID와 결제 ID를 분리하고 실행 전에 결제 상태를 만드는 방향은 타당합니다.

보완할 점은 다음과 같습니다.

- `/easy_withdrawal/prepare`처럼 지급 수단을 경로에 박으면 다른 결제수단과 공통 상태를 만들기 어렵습니다. `payment-intents`처럼 “무엇을 하려는가”를 API 자원(resource) 이름으로 둡니다.
- 금액만 저장하지 말고 통화·수취인·결제수단까지 불변으로 묶습니다.
- 같은 가맹점 주문을 재시도할 때 새 결제가 계속 생기지 않도록 멱등성 계약을 둡니다.
- 가맹점 주문 ID의 유일성은 가맹점 범위 안에서 보장합니다. 다른 가맹점이 같은 문자열을 쓸 수 있기 때문입니다.

### 7.2 인증 API

고객 인증을 실행과 분리하는 방향은 타당합니다. 그러나 커머스 서버가 `userId + password + paymentId`를 받아 결제 서버로 보내는 모양은 바꿔야 합니다.

1. 커머스 서버가 고객의 결제 비밀번호를 보게 됩니다.
2. 요청의 `userId`를 다른 값으로 바꾸는 객체 접근 권한 문제가 생깁니다.
3. 응답의 `authToken`이 일정 시간 돈을 움직일 수 있는 bearer token이면 유출·재사용 위험이 큽니다.
4. token이 금액·통화·수취인·결제수단에 결합되지 않으면 다른 거래에 붙일 수 있습니다.

고객은 결제 서버가 통제하는 결제 화면(hosted page), 소프트웨어 개발 키트(SDK) 또는 앱 채널에서 직접 인증하고 거래 내용을 확인해야 합니다. 어떤 UI를 쓰든 커머스 서버는 비밀번호·PIN·금융기관 로그인 정보를 받지 않습니다. 결제 서버가 만든 거래 허용 증거는 내부에 두고, 커머스에는 결제 상태만 알립니다.

### 7.3 출금 API

한 번만 쓸 수 있게 `used=true`를 두는 방식은 중복 출금을 막으려는 시도입니다. 다만 boolean을 읽고 나중에 쓰는 구현은 동시 요청 두 개가 모두 `false`를 읽는 경쟁 상태를 막지 못합니다.

```text
요청 A: used=false 읽음 ─┐
                         ├─ 둘 다 외부 출금 요청 가능
요청 B: used=false 읽음 ─┘
```

필요한 것은 다음과 같은 원자적 전이입니다.

```sql
UPDATE payment_intent
SET execution_status = 'PROCESSING', external_request_id = :stableId
WHERE payment_id = :paymentId
  AND merchant_id = :authenticatedMerchantId
  AND execution_status = 'CUSTOMER_AUTHORIZED';
```

영향받은 행이 정확히 하나일 때만 최초 실행자가 됩니다. 이미 `PROCESSING` 이상이면 새 외부 요청을 만들지 않고 기존 상태와 `external_request_id`를 반환합니다. 실제 구현은 조건부 UPDATE, 낙관적 잠금, 행 잠금, 멱등성 레코드 선점 중 하나를 쓸 수 있지만, **승자는 한 명이고 외부 요청 ID는 안정적이어야 한다**는 불변식은 같습니다.

### 7.4 결과 조회 API

결과 조회 endpoint는 타임아웃 뒤 복구에 필요합니다. 다만 `GET` body에 `userId`를 다시 받거나 요청자가 넘긴 사용자 ID만 믿으면 안 됩니다.

- 커머스 서버는 서버 간 인증으로 `merchantId`가 정해집니다.
- `paymentId`가 그 가맹점 소유인지 매 요청에서 검사합니다.
- 고객 화면 조회라면 짧고 대상이 제한된 고객 세션으로 해당 결제만 읽게 합니다.
- redirect query string이나 브라우저 화면을 최종 성공의 근거로 쓰지 않습니다.
- 최종 상태는 서버 조회, 서명된 웹훅, 외부 기관 대사로 확인합니다.

사용자가 넘긴 객체 ID마다 소유권을 검사해야 한다는 원칙은 일반 API 보안에서도 중요하게 다룹니다. ([API 객체 수준 권한 검증 가이드](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/))

## 8. 두 설계안을 같은 기준으로 비교하기

고객 거래 허용 뒤 누가 실행을 시작할지에는 두 가지 타당한 설계가 있습니다.

| 비교축 | A. 고객 허용 직후 자동 실행 | B. 고객 허용 뒤 커머스 재확인 |
| --- | --- | --- |
| 왕복 수 | 적다. 고객 흐름이 짧다. | confirm 호출이 하나 더 필요하다. |
| 주문 변경 대응 | 인증 전에 주문이 불변으로 봉인되어야 안전하다. | 실행 직전에 금액·재고·취소 상태를 다시 볼 수 있다. |
| 실패 책임 | 고객 허용과 실행이 붙어 있어 단순하다. | 허용 완료 후 confirm이 오지 않는 만료 상태를 관리해야 한다. |
| 지연 민감도 | 지연이 적고 단순 결제에 유리하다. | 추가 왕복과 커머스 장애의 영향을 받는다. |
| 적합한 조건 | 금액·수취인·재고가 이미 확정되고 즉시 실행이 계약인 경우 | 인증 중 주문이 바뀔 수 있고 실행 전 재검증이 필요한 경우 |

이 문서의 권장 기본안은 **B. 고객 허용 뒤 커머스 재확인**입니다. 커머스 주문, 할인, 포인트, 재고가 인증 화면을 보는 동안 바뀔 수 있다는 전제를 두기 때문입니다. 그러나 이것은 모든 계좌이체의 표준 명령이 아니라 조건부 설계 판단입니다. 주문이 이미 불변으로 확정되고 자동 실행의 단순성이 더 중요하면 A가 더 낫습니다.

중요한 것은 HTTP 호출 수가 아니라 두 안이 모두 다음 불변식을 지키는가입니다.

- 고객이 본 거래 내용과 실제 실행 내용이 같다.
- 커머스 서버는 고객 자격증명을 보지 않는다.
- 같은 결제 의도에는 논리적 지급 지시와 외부 요청 ID가 하나만 생긴다. 전달은 재시도될 수 있지만 외부 효과는 계약된 중복 제거·조회로 한 건에 수렴한다.
- timeout 뒤 결과를 조회하고 대사할 수 있다.

## 9. 권장 API: 결제 의도와 실행을 분리한다

### 9.1 신뢰 경계를 먼저 그린다

```text
고객 앱/브라우저
  │
  │ ① 주문 요청
  ▼
커머스 프론트 ───────> 커머스 서버
  │                         │
  │ ③ 고객 직접 채널       │ ② 결제 의도 생성, ⑤ confirm
  ▼                         ▼
결제 서버/인증 경계 ─────> 금융 연결망 ─────> 계좌 관리 기관
        │ ④ 내부 거래 허용 증거      ⑥ 기관 처리 결과
        └──── 조회·서명 웹훅 ───────> 커머스 서버
```

서버 간 호출은 커머스 서버 자격증명(client credential), 양방향 TLS(mutual TLS), 서명 요청 등 계약된 방식으로 인증합니다. 구체 수단보다 중요한 것은 인증된 `merchantId`를 요청 body의 값으로 덮어쓰지 않는 것입니다. 고객 채널은 한 결제 의도만 다룰 수 있는 짧은 세션을 사용합니다.

### 9.2 결제 의도 생성

```http
POST /v1/payment-intents
Authorization: <merchant-server-credential>
Idempotency-Key: 4cf0c4a8-4692-4cb6-9f6f-971a825dd1a4
Content-Type: application/json
```

```json
{
  "merchantOrderId": "order_20260714_1042",
  "amount": {
    "value": 42800,
    "currency": "KRW"
  },
  "customerReference": "customer_81d4",
  "paymentMethodId": "pm_bank_7f2a",
  "payee": "merchant_account_default",
  "executionMode": "MERCHANT_CONFIRM"
}
```

```http
HTTP/1.1 201 Created
Location: /v1/payment-intents/pay_01J0W8G6K9
```

```json
{
  "paymentId": "pay_01J0W8G6K9",
  "executionStatus": "REQUIRES_CUSTOMER_ACTION",
  "customerAction": {
    "type": "REDIRECT_OR_SDK",
    "session": "ca_opaque_short_lived",
    "expiresAt": "2026-07-14T08:05:00+09:00"
  }
}
```

`Idempotency-Key`는 이 API가 자체 계약으로 정의하는 멱등성 식별자입니다. 같은 키와 같은 요청 지문(request fingerprint), 즉 금액·통화·주문·수취인·결제수단의 요약값이 오면 같은 결과를 반환합니다. 같은 키로 다른 요청 본문(payload)이 오면 `409 Conflict`로 거부합니다. 헤더 이름만 붙였다고 멱등성이 생기는 것은 아니며, 키 보존 기간·동시 요청 선점·기존 `PROCESSING` 응답을 함께 정의해야 합니다.

`payee`는 임의의 계좌번호를 받는 필드가 아닙니다. 위 예시의 값은 서버 인증으로 확인된 가맹점의 기본 수취 설정을 가리키며, 결제 서버가 내부 계약 정보로 해석합니다. 여러 하위 수취인을 지원한다면 인증된 가맹점이 사용할 수 있도록 미리 등록된 `payeeId`만 허용하고 매 요청에서 소유권을 확인해야 합니다. `customerReference`와 `paymentMethodId`도 문자열이 같다는 이유만으로 연결하지 않고, 해당 가맹점 범위의 고객과 그 고객이 사용할 수 있는 등록 수단인지 검사합니다.

응답의 고객 세션은 결제 실행 권한이 아닙니다. 한 결제 의도와 고객 행동 화면이라는 대상(audience)에만 결합되고, 짧게 만료되며, 커머스 서버가 이것으로 출금을 실행할 수 없어야 합니다.

### 9.3 고객이 직접 인증하고 거래 내용을 허용

고객 행동 화면에는 적어도 다음 내용이 보여야 합니다.

- 42,800원과 통화
- 수취인 또는 수취 목적을 식별할 수 있는 정보
- 선택한 등록 계좌의 마스킹된 표시
- 일회성 결제인지 반복 출금 위임인지
- 취소·만료 조건

고객의 비밀번호·PIN·금융기관 로그인 자격증명은 결제·금융 인증 경계에 직접 입력됩니다. 이 경계는 인증 결과가 가리키는 고객 주체(subject)가 결제 의도에 연결된 고객, 등록 결제수단의 소유자 또는 유효한 위임의 주체와 일치하는지도 다시 검사합니다. 요청의 `customerReference` 문자열만 같다고 고객과 계좌의 관계가 증명되지는 않습니다. 커머스 서버에는 다음과 같은 상태 변화만 보입니다.

```text
REQUIRES_CUSTOMER_ACTION
  ├─ 고객 인증 실패 ──> 같은 상태에서 재시도 또는 시도 한도 후 EXPIRED
  ├─ 고객 거절 ──────> CANCELED
  └─ 인증 + 거래 허용 ─> CUSTOMER_AUTHORIZED
```

`CUSTOMER_AUTHORIZED`는 **고객 거래 허용 증거가 내부에 생겼다**는 상태입니다. 아직 기관이 출금을 승인했다거나 돈이 움직였다는 뜻이 아닙니다. 내부 증거는 불변 거래 tuple, 인증 강도, 생성 시각, 만료 시각, nonce에 결합합니다. 커머스에 범용 `authToken`으로 노출하지 않습니다.

### 9.4 커머스가 주문을 재확인하고 실행 요청

커머스 서버는 고객 redirect를 받았다는 이유만으로 주문을 결제 완료로 바꾸지 않습니다. 자기 데이터베이스에서 주문 금액·통화·재고·취소 상태를 다시 확인한 뒤 confirm합니다.

```http
POST /v1/payment-intents/pay_01J0W8G6K9/confirm
Authorization: <merchant-server-credential>
Idempotency-Key: 99f342d1-12c5-48cd-9a5e-80cb989e04e0
Content-Type: application/json
```

```json
{
  "expectedMerchantOrderId": "order_20260714_1042",
  "expectedAmount": {
    "value": 42800,
    "currency": "KRW"
  }
}
```

결제 서버는 body의 가맹점 ID나 고객 ID를 신뢰하지 않습니다. 서버 인증으로 정해진 가맹점이 이 `paymentId`의 소유자인지 확인하고, 저장된 tuple과 `expectedAmount`가 같은지 비교합니다. 그 뒤 `CUSTOMER_AUTHORIZED -> PROCESSING`을 원자적으로 바꾸는 최초 요청만 논리적 지급 지시와 outbox 레코드(row)를 만들 수 있습니다. 전송 작업자(worker)의 실제 전달은 장애 복구 중 여러 번 시도될 수 있지만 모두 같은 `externalRequestId`를 사용합니다.

```http
HTTP/1.1 202 Accepted
```

```json
{
  "paymentId": "pay_01J0W8G6K9",
  "executionStatus": "PROCESSING",
  "nextAction": "POLL_OR_WAIT_FOR_WEBHOOK"
}
```

`202 Accepted`는 처리 요청을 받아들였다는 뜻이지 자금 이동 성공을 보장하지 않습니다. 외부 지급망이 동기적으로 최종 결과를 보장하는 계약이면 같은 endpoint가 확정 상태를 응답할 수도 있지만, API 소비자는 상태 의미를 계약으로 확인해야 합니다.

### 9.5 조회와 서명된 웹훅

```http
GET /v1/payment-intents/pay_01J0W8G6K9
Authorization: <merchant-server-credential>
```

```json
{
  "paymentId": "pay_01J0W8G6K9",
  "merchantOrderId": "order_20260714_1042",
  "amount": { "value": 42800, "currency": "KRW" },
  "executionStatus": "SUCCEEDED",
  "institutionOutcome": "POSTED",
  "fundsStatus": "POSTED",
  "finalityStatus": "NOT_ASSERTED",
  "processedAt": "2026-07-14T07:58:19+09:00",
  "reconciliationStatus": "PENDING",
  "merchantSettlementStatus": "NOT_APPLICABLE",
  "resourceVersion": 7
}
```

웹훅은 중복되거나 순서가 바뀌어 도착할 수 있다고 가정합니다.

```http
POST /merchant-webhooks/payments
Webhook-Id: evt_01J0W8J2SC
Webhook-Timestamp: 1783983499
Webhook-Signature: <contracted-signature>
```

```json
{
  "eventType": "payment_intent.succeeded",
  "paymentId": "pay_01J0W8G6K9",
  "merchantOrderId": "order_20260714_1042",
  "executionStatus": "SUCCEEDED",
  "resourceVersion": 7,
  "occurredAt": "2026-07-14T07:58:19+09:00"
}
```

수신자는 서명, 허용 시간 오차, `Webhook-Id` 중복, 결제 소유권을 검사합니다. 순서는 결제 서버가 상태 변경마다 단조 증가시키는 `resourceVersion`으로 판단합니다. 현재 버전보다 낮거나 같은 이벤트는 상태를 되돌리지 않고, 버전이 건너뛰거나 허용되지 않은 상태 전이가 보이면 결제 조회 API로 원본 결제 자원(resource)을 다시 확인합니다. `occurredAt`은 관측과 감사에 쓰는 시각이지 순서의 증명이 아닙니다. 브라우저 redirect는 사용자 경험을 위한 이동일 뿐 결제 완료의 진실이 아닙니다.

### 9.6 오류 응답과 결제 상태를 섞지 않는다

HTTP 오류는 요청 형식·인증·권한·충돌을 표현하고, 결제 상태는 도메인 진행 상황을 표현합니다.

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.example.invalid/problems/payment-intent-mismatch",
  "title": "결제 의도의 금액이 주문 금액과 일치하지 않습니다.",
  "status": 409,
  "code": "PAYMENT_INTENT_MISMATCH",
  "paymentId": "pay_01J0W8G6K9"
}
```

기계가 구조적으로 읽을 수 있는 문제 상세(problem detail)는 HTTP API 오류 표준을 따를 수 있습니다. 다만 `DECLINED_INSUFFICIENT_FUNDS`처럼 기관이 정상적으로 내린 거래 거절은 네트워크 오류와 다릅니다. 조회 가능한 결제 상태와 거절 사유로 보존해야 합니다. ([HTTP API 문제 응답 표준](https://www.rfc-editor.org/rfc/rfc9457.html))

## 10. 상태 머신과 반드시 지켜야 할 불변식

### 10.1 결제 의도의 실행 상태

```text
CREATED
  │
  ▼
REQUIRES_CUSTOMER_ACTION
  ├──────────────> CANCELED
  ├──────────────> EXPIRED
  │ 고객 인증 + 특정 거래 허용
  ▼
CUSTOMER_AUTHORIZED
  ├──────────────> CANCELED / EXPIRED
  │ 커머스 confirm, 원자적 최초 실행
  ▼
PROCESSING ──────> SUCCEEDED
  ├──────────────> DECLINED
  └─ timeout ────> PROCESSING(externalOutcome=UNKNOWN)
                         │ 조회·웹훅·대사
                         ├──> SUCCEEDED
                         └──> DECLINED
```

고객 인증 실패를 곧바로 결제 전체의 최종 실패 상태 `FAILED`로 만들 필요는 없습니다. 재시도 가능하면 `REQUIRES_CUSTOMER_ACTION`을 유지하고 인증 시도 결과를 별도 기록합니다. 시도 한도나 세션 만료가 닫히면 `EXPIRED`로 끝낼 수 있습니다.

외부 timeout도 `DECLINED`가 아닙니다. 기관이 처리했지만 응답만 잃었을 수 있으므로 `PROCESSING`과 `externalOutcome=UNKNOWN`을 보존합니다. 이때 새 외부 요청 ID로 재출금하지 않습니다.

### 10.2 성공, 자금 최종성, 대사, 가맹점 정산은 별도 축이다

위 상태 머신의 `SUCCEEDED`는 이 문서의 예제 계약에서 **연결 기관이 지급 지시의 debit과 credit을 `POSTED`로 응답했다**는 실행 결과입니다. 되돌릴 수 없는 최종 결제까지 보장한다는 뜻은 아닙니다. 지급망과 거래 유형에 따라 성공 뒤 반환(return)이나 반대 거래(reversal)가 생길 수 있습니다.

| 상태 축 | 예시 값 | 답하는 질문 |
| --- | --- | --- |
| `executionStatus` | `PROCESSING`, `SUCCEEDED`, `DECLINED` | 결제 서버의 지급 지시 실행이 어디까지 갔는가? |
| `institutionOutcome` | `UNKNOWN`, `ACCEPTED`, `POSTED`, `DECLINED` | 연결 기관이 어떤 처리 결과를 응답했는가? |
| `fundsStatus` | `NOT_OBSERVED`, `POSTED`, `RETURNED`, `REVERSED` | 실제 자금 기록에 어떤 후속 변화가 관측되었는가? |
| `finalityStatus` | `NOT_ASSERTED`, `FINAL` | 해당 지급망 계약상 되돌릴 수 없는 지점에 도달했는가? |
| `reconciliationStatus` | `PENDING`, `MATCHED`, `MISMATCH` | 내부 기록과 기관 기록이 맞는가? |
| `merchantSettlementStatus` | `NOT_APPLICABLE`, `PENDING`, `PAID_OUT` | 집금형 계약의 가맹점 지급이 끝났는가? |

성공 뒤 반환이 생겨도 원래 실행이 성공했다는 역사까지 `DECLINED`로 되감지 않습니다. 원결제는 `executionStatus=SUCCEEDED`로 보존하고, 반환·반대 거래를 별도 후속 거래로 연결해 `fundsStatus`와 원장에 반영합니다. 그래야 당시 기관 응답, 현재 자금 상태, 가맹점 정산 조정을 각각 재구성할 수 있습니다.

### 10.3 불변식

| 불변식 | 지키지 않으면 생기는 일 | 구현·검증 방법 |
| --- | --- | --- |
| 인증된 가맹점만 자기 결제를 읽고 confirm한다. | 다른 가맹점 결제 조회·실행 | `merchant_id + payment_id` 소유권 조건, 모든 endpoint 권한 검사 |
| 고객 허용 뒤 amount/currency/payee/paymentMethod는 바뀌지 않는다. | 고객이 보지 않은 거래 실행 | 거래 묶음의 해시값 또는 버전 결합, 변경 시 새 intent |
| 한 멱등성 키는 한 요청 지문에만 쓴다. | 같은 키로 다른 주문 덮어쓰기 | 고유 키 제약 + 요청 지문 불일치 거절 |
| `CUSTOMER_AUTHORIZED -> PROCESSING` 승자는 한 요청뿐이다. | 동시 confirm의 중복 출금 | 조건부 UPDATE/낙관적 잠금/행 잠금과 영향 행 1개 확인 |
| 한 결제에는 안정된 `externalRequestId`가 있다. | timeout 재시도 때 새 출금 | 최초 전이와 함께 ID 저장, 재시도는 조회 또는 같은 ID 사용 |
| 고객 자격증명은 커머스 서버를 지나지 않는다. | 침해·로그·운영 노출 범위 확대 | 직접 인증 채널, 로그 민감정보 가림(redaction), API 입력 구조에 password 필드 없음 |
| redirect는 최종 진실이 아니다. | 위조·중간 이탈로 주문 오판 | 서버 조회·서명 웹훅·대사로 상태 확정 |
| 웹훅은 중복·역순·버전 누락(version gap)을 견딘다. | 상태 역전·누락된 후속 처리 | event ID 중복 제거, 단조 증가 `resourceVersion`, 버전이 건너뛰면 조회 |
| 실행 성공과 자금 최종성·대사·정산을 분리한다. | 접수·성공·반환·가맹점 지급을 혼동 | execution/funds/finality/reconciliation/settlement 상태 축 분리 |
| 대사는 예외 기능이 아니라 정상 복구 경로다. | 장기 미확정·유령 출금 | 기관 거래 ID·금액·일자 대조, mismatch queue와 수동 처리 |

## 11. 42,800원 결제를 처음부터 끝까지 따라가기

작은 예제로 정보, 장부, 돈을 함께 따라가 보겠습니다.

### 11.1 결제 의도를 만든다

커머스 서버는 주문 `order_20260714_1042`의 금액이 42,800원이고 아직 결제 가능하다는 것을 확인합니다. `Idempotency-Key=create-1042`로 결제 의도를 만듭니다.

```text
payment.executionStatus = REQUIRES_CUSTOMER_ACTION
payment.amount = 42,800 KRW
payment.payee = merchant_account_default
실제 돈 변화 = 0원
```

같은 생성 요청이 네트워크 재시도로 다시 와도 같은 `paymentId`가 반환됩니다.

### 11.2 고객이 직접 인증하고 거래를 허용한다

고객은 결제 서버가 통제하는 화면에서 42,800원, 수취 정보, 등록 계좌를 확인합니다. 인증과 확인이 성공하면 결제 서버는 내부 거래 허용 증거를 저장합니다.

```text
authorizationGrant.boundTo = hash(
  merchant + order + payment + 42,800 KRW + payee + paymentMethod
)
authorizationGrant.expiresAt = 짧은 만료 시각
payment.executionStatus = CUSTOMER_AUTHORIZED
실제 돈 변화 = 0원
```

커머스 서버는 이 내부 거래 허용 증거의 원문을 받지 않습니다.

### 11.3 커머스가 주문을 다시 확인한다

커머스 서버는 할인·포인트·재고·취소 상태를 다시 계산합니다. 여전히 42,800원이면 `confirm-1042`라는 멱등성 키로 confirm합니다.

결제 서버는 소유권, 금액, 허용 증거, 만료를 검사하고 다음 전이를 한 트랜잭션에서 선점합니다.

```text
CUSTOMER_AUTHORIZED -> PROCESSING
externalRequestId = ext_pay_01J0W8G6K9
outbox = "금융 연결망에 ext_pay_01J0W8G6K9 전송"
```

outbox는 데이터베이스 변경과 외부 전송 의도를 같은 로컬 트랜잭션에 남기는 방식입니다. 전송 작업자가 중간에 죽어도 전송 의도를 잃지 않고 다시 처리할 수 있지만, **전달을 정확히 한 번으로 만들지는 않습니다**. 작업자는 같은 레코드를 재처리할 수 있고 외부 연동 모듈(adapter) 호출도 여러 번 일어날 수 있습니다. 모든 재전송이 같은 `externalRequestId`를 사용하고 외부 지급망이 그 ID를 중복 제거하거나 기존 결과를 조회할 수 있어야 자금 효과를 한 건에 수렴시킬 수 있습니다.

외부 지급망이 동일 ID 중복 제거도 결과 조회도 지원하지 않는다면, 응답이 불명확한 요청을 자동으로 재전송해서는 안 됩니다. `UNKNOWN`을 유지하고 기관 기록 대사 또는 수동 확인으로 실제 처리 여부를 먼저 닫은 뒤 다음 행동을 결정해야 합니다. 핵심은 내부 outbox가 재전송할 작업을 잃지 않게 할 뿐, 외부 자금 효과까지 정확히 한 번으로 만들어 주지는 않는다는 점입니다.

### 11.4 기관 결과가 도착한다

기관이 거래를 받아 고객 계좌를 42,800원 줄이고 계약된 수취 계좌를 늘렸다고 합시다.

```text
외부 기관 기록:
  externalRequestId = ext_pay_01J0W8G6K9
  institutionTransactionId = bank_tx_4b19
  outcome = POSTED

내부 결제 기록:
  payment.executionStatus = SUCCEEDED
  institutionOutcome = POSTED
  fundsStatus = POSTED
  finalityStatus = NOT_ASSERTED
  reconciliationStatus = PENDING
  merchantSettlementStatus = NOT_APPLICABLE
```

이 예제의 `SUCCEEDED`는 기관이 debit과 credit을 `POSTED`로 확인했다는 실행 결과입니다. 되돌릴 수 없는 최종성은 아직 주장하지 않습니다. 내부 상태를 성공으로 썼다는 사실만으로 기관 기록과 영원히 일치한다고 가정하지 않고, 웹훅과 조회를 처리한 뒤에도 일별 대사에서 금액·통화·기관 거래 ID를 맞춥니다.

### 11.5 가맹점 정산은 계약에 따라 갈린다

직접 수취형이면 42,800원이 이미 가맹점 수취 계좌에 들어갔을 수 있습니다. 집금형이면 결제 성공 뒤에도 가맹점 지급채무가 남고, 후속 정산에서 수수료·취소·조정을 반영한 금액을 지급합니다. 따라서 결제 `SUCCEEDED`와 정산 `PAID_OUT`은 같은 상태가 아닙니다.

## 12. 정상·장애 시나리오로 설계를 검증하기

### 12.1 성공 시나리오 세 가지

1. **일반적인 일회성 결제**

    고객이 직접 인증하고 42,800원 거래를 허용합니다. 커머스가 같은 금액으로 confirm하고, 원자적 전이의 승자 한 명만 논리적 지급 지시와 outbox row를 만듭니다. 기관 결과와 대사가 일치하면 실행 상태와 대사 상태가 각각 `SUCCEEDED`, `MATCHED`로 닫힙니다.

2. **생성·confirm 재시도**

    응답을 받지 못한 커머스가 같은 멱등성 키와 같은 payload로 재시도합니다. 생성은 같은 `paymentId`, confirm은 같은 상태와 `externalRequestId`를 반환합니다. 논리적 지급 지시와 outbox row는 하나입니다. worker의 전달 시도는 여러 번일 수 있지만 같은 외부 요청 ID를 쓰고, 중복 제거를 지원하는 기관의 자금 효과는 한 건입니다.

3. **느린 외부 결과의 수렴**

    confirm 응답은 `PROCESSING`이고 몇 초 뒤 서명된 웹훅이 옵니다. 웹훅을 놓친 소비자는 조회로 같은 결과를 얻고, 일별 대사가 최종 기관 기록과 일치함을 확인합니다.

### 12.2 실패·경계 시나리오 여덟 가지

1. **인증 뒤 금액 변경**

    고객은 42,800원을 허용했지만 커머스 주문이 52,800원으로 바뀌었습니다. confirm의 expected amount와 저장된 tuple이 다르므로 `409`로 거부하고 새 결제 의도를 만들게 합니다. 기존 허용 증거를 새 금액에 재사용하지 않습니다.

2. **다른 고객·결제수단 또는 계약 밖 수취인 대입**

    요청자가 다른 고객의 `paymentId`·`paymentMethodId`, 또는 가맹점 계약에 등록되지 않은 `payeeId`를 넣습니다. 생성 단계에서는 가맹점-고객 연결과 결제수단 소유권을, 고객 행동 단계에서는 직접 인증한 고객 주체와 결제수단 또는 위임 주체를, confirm 단계에서는 가맹점과 결제 소유권을 각각 검사합니다. 하나라도 다르면 `404` 또는 정책상 `403`으로 거부하며 body의 `customerReference`만 믿지 않습니다.

3. **동시 confirm 두 건**

    같은 결제에 두 요청이 동시에 도착합니다. `CUSTOMER_AUTHORIZED -> PROCESSING` 조건부 전이에 성공한 하나만 논리적 지급 지시와 outbox 레코드를 만들고, 다른 요청은 이미 선점된 상태와 같은 `externalRequestId`를 반환합니다.

4. **외부 요청 timeout**

    기관이 처리했는지 모릅니다. `FAILED`로 바꾸고 새 ID로 재출금하지 않습니다. 외부 지급망이 동일 ID 중복 제거와 결과 조회를 지원하면 `PROCESSING(externalOutcome=UNKNOWN)`을 유지하고 기존 ID로 조회하거나 같은 ID로 재전송한 뒤 웹훅·대사로 수렴합니다.

5. **중복 제거도 결과 조회도 없는 외부망의 timeout**

    같은 ID를 다시 보내도 한 건으로 처리된다는 보장이 없고 기존 결과도 물을 수 없습니다. 자동 재전송을 멈추고 `UNKNOWN`과 수동 확인 대기열(queue)을 유지합니다. 기관 거래 내역이나 운영 대사로 최초 요청의 결과를 확인하기 전에는 새 출금을 만들지 않습니다.

6. **잔액 부족 또는 계좌 제한**

    고객 인증과 거래 허용은 성공했지만 기관이 거절합니다. 결제는 `DECLINED`와 기계가 읽을 수 있는 구체적인 사유 code를 보관합니다. 고객에게 다른 결제수단을 선택하게 할 수 있지만 같은 요청을 무한 재시도하지 않습니다.

7. **웹훅 중복·역순·버전 누락**

    `PROCESSING` 버전 6 이벤트가 `SUCCEEDED` 버전 7 뒤에 늦게 도착하면 상태를 되돌리지 않습니다. 현재 버전 5에서 갑자기 버전 7을 받으면 버전 6을 추측하지 않고 조회 API로 현재 resource를 다시 읽습니다. `occurredAt`은 순서 판정에 쓰지 않습니다. 서명이나 시간 창 검사가 실패해도 처리하지 않고 서버 조회로 확인합니다.

8. **성공 뒤 반환 또는 반대 거래**

    실행 상태가 `SUCCEEDED`인 뒤 자금이 반환되거나 반대 거래가 생깁니다. 원결제를 `DECLINED`로 되감지 않고 별도 조정 거래를 연결합니다. `fundsStatus=RETURNED` 또는 `REVERSED`와 원장 항목(entry)을 기록하고, 집금형이면 가맹점 정산 조정으로 이어 갑니다.

| `resourceVersion` | 결제 서버가 상태 변경마다 증가시키는 웹훅 순서 근거 |
| `occurredAt` | 상태가 관측된 시각. 감사용이며 순서 증명으로 쓰지 않음 |
| `settlementBatchId` | 집금형에서 가맹점 정산 묶음과 연결 |
| `reconciliationStatus`, `reconciledAt` | 기관 기록과 맞았는지, 언제 확인했는지 표시 |

관측 지표도 상태 의미를 따라야 합니다.

- `CUSTOMER_AUTHORIZED`인데 confirm 없이 만료되는 비율
- `PROCESSING`에 오래 머무는 건수와 최대 체류 시간
- 같은 멱등성 키의 fingerprint 충돌 건수
- 외부 timeout 뒤 조회로 성공·거절이 확정된 비율
- 웹훅 서명 실패, 중복, 역순 건수
- 대사 불일치 금액·건수·최장 미해결 시간
- 결제 성공과 가맹점 정산 완료 사이의 지연

비밀번호, 전체 계좌번호, 인증 token 원문은 로그에 남기지 않습니다. 문제를 재구성하는 데 필요한 식별자와 상태 전이만 구조화해 남깁니다.

## 14. 핵심 질문에 짧게 답하기

### “인증과 승인을 왜 나누나요?”

고객 인증은 “누구인가”를 확인하고, 고객 거래 허용은 “이 금액·수취인·수단을 허용했는가”를 증명하며, 금융기관의 거래 판단은 “잔액과 계좌 상태상 처리 가능한가”를 결정합니다. 커머스의 confirm은 주문과 재고가 아직 유효한지 다시 봅니다. 주체·입력·증거·실패가 다르기 때문에 분리해야 하며, 인증 성공을 결제 성공으로 보면 안 됩니다. 다만 논리적 분리가 반드시 네 번의 네트워크 호출을 뜻하지는 않습니다.

### “이미 등록된 계좌인데 왜 다시 확인하나요?”

등록은 사용할 계좌와 동의 관계를 준비한 것입니다. 일회성 결제라면 현재 금액·수취인·결제수단에 대한 거래 허용이 별도로 필요합니다. 반복 출금 위임이 있다면 매번 대화형 확인을 생략할 수 있지만, 현재 거래가 위임의 한도·기간·수취인 범위 안인지 검사해야 합니다.

### “API는 어떻게 설계하겠습니까?”

커머스 서버가 멱등성 키로 결제 의도를 만들고, 고객은 결제 서버가 통제하는 채널에서 직접 인증하고 거래를 허용합니다. 커머스는 주문 금액과 재고를 다시 확인한 뒤 `confirm`합니다. 결제 서버는 `CUSTOMER_AUTHORIZED -> PROCESSING`을 원자적으로 선점해 논리적 지급 지시와 안정된 외부 요청 ID를 하나만 만듭니다. 전달을 재시도할 때도 같은 ID를 쓰고, 외부 지급망의 중복 제거·결과 조회 계약으로 자금 효과를 한 건에 수렴시킵니다. 결과는 조회·서명 웹훅·대사로 확정하고, timeout은 실패가 아니라 미확정으로 둡니다.

### “돈은 어디로 흐르나요?”

인증과 고객 거래 허용 단계에서는 돈이 움직이지 않습니다. confirm 뒤 지급 지시가 나가고, 기관이 계좌에 debit/credit을 기록하면서 실제 예금채권이 변합니다. 기관 간 청산과 최종 결제, 집금형 계약의 가맹점 정산은 또 다른 단계입니다. 직접 수취형인지 집금 후 정산형인지는 계약을 확인해야 하며, 모든 서비스가 하나의 집금 계좌를 거친다고 단정하면 안 됩니다.

## 15. 문서를 덮고 다시 풀어 보기

다음 질문에 그림 없이 답할 수 있으면 핵심 구조를 다시 만들 수 있습니다.

1. 고객 인증, 고객 거래 허용, 기관 승인·접수, 주문 재확인의 주체와 실패를 각각 말해 보세요.
2. 등록 계좌와 42,800원 현재 거래 의도는 어떤 데이터가 다릅니까?
3. 고객이 42,800원을 허용한 뒤 금액이 바뀌면 왜 새 결제 의도가 필요합니까?
4. `authToken + used=true`보다 내부 grant와 원자적 상태 전이가 안전한 이유는 무엇입니까?
5. 외부 timeout을 `FAILED`로 바꾸고 재시도하면 어떤 중복 출금 경로가 생깁니까?
6. 직접 수취형과 집금 후 정산형에서 결제 성공 뒤 돈의 경로가 어떻게 다릅니까?
7. `SUCCEEDED`가 어느 수준의 최종성을 뜻하는지 왜 계약으로 정해야 합니까?
8. 웹훅, 조회, 대사가 각각 어떤 실패를 복구합니까?

작은 설계 실험도 해볼 수 있습니다.

1. 같은 `paymentId`에 confirm 요청 두 개를 동시에 보냅니다.
2. 논리적 지급 지시와 outbox 레코드가 하나이고 두 응답이 같은 `externalRequestId`를 가리키면 confirm 동시성 검사는 PASS입니다.
3. worker를 외부 전송 직후에 종료해 outbox를 다시 처리하게 합니다.
4. 외부 연동 모듈 호출이 두 번이어도 두 호출의 `externalRequestId`가 같고, 중복 제거를 흉내 낸 외부 기관의 자금 효과가 한 건이면 재전송 검사는 PASS입니다.
5. 논리적 지급 지시나 외부 요청 ID가 둘이거나, 외부 자금 효과가 두 건이면 FAIL입니다.

두 번째 실험에서는 외부 연동 모듈이 요청을 처리한 뒤 응답만 timeout 내게 합니다. 중복 제거·결과 조회를 지원하는 모형에서는 같은 외부 요청 ID를 조회하거나 재전송해 한 자금 효과와 `SUCCEEDED`로 수렴하면 PASS입니다. 둘 다 지원하지 않는 모형에서는 자동 재전송 없이 `UNKNOWN`과 수동 확인 대기열에 남으면 PASS입니다.

마지막으로 웹훅 버전 5 다음에 버전 7을 먼저 보냅니다. 소비자가 버전 6을 추측하지 않고 조회 API로 현재 결제 자원을 다시 읽어야 PASS입니다. 성공 뒤 반환 이벤트도 보내 보고, 원결제의 실행 성공을 지우지 않은 채 별도 조정 거래와 `fundsStatus=RETURNED`가 생기는지 확인합니다.
